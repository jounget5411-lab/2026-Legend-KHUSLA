# 08. 성능과 한계 — 실제로 몇 Hz 로 도는가

이 문서는 2026-07-31 에 차 PC 위에서 직접 측정한 인지 파이프라인 성능 기록이다. "몇 Hz 로 도는가", "예선보다 느려진 게 맞는가", "더 빠르게 할 수 있는가", "속도가 일정한 게 중요한가" 네 가지 질문에 숫자로 답한다. 모든 수치는 추정이 아니라 실행한 명령의 출력이며, 서로 다른 에이전트가 독립적으로 재측정해 교차검증했다. 재측정에서 뒤집힌 항목은 뒤집힌 대로 적었다.

---

## 0. 이 문서에 나오는 용어

| 용어 | 쉬운 뜻 | 어디서 나오나 |
|---|---|---|
| Hz (헤르츠) | 1초에 몇 번 하는가. 5Hz = 초당 5장 처리 | 문서 전체 |
| proc (처리시간) | 프레임 1장을 처리하는 데 걸린 시간(ms) | 1장, 3장 |
| gap (프레임 간격) | 앞 프레임과 뒤 프레임 처리 시작 시각의 차이 | 4장 |
| 지터(jitter) | 그 간격이 얼마나 들쭉날쭉한가. 작을수록 규칙적 | 4장 |
| sd (표준편차) | 흩어진 정도. 클수록 값들이 평균에서 멀리 퍼져 있다 | 문서 전체 |
| p95 | 100번 중 95번은 이 값보다 작다. "거의 최악" | 문서 전체 |
| 추론(inference) | 신경망에 사진을 넣어 답을 받는 계산 | 1장 |
| imgsz | YOLO 가 사진을 몇 픽셀로 줄여서 보는가 (416 = 416픽셀) | 3장 |
| 라운드로빈 | 여러 일을 매번 다 하지 않고 번갈아 하나씩 하는 것 | 3장 |
| 스레드(thread) | CPU 가 동시에 굴리는 작업 갈래. 많을수록 병렬 | 2장, 3장 |
| ZOH (영차 유지) | 새 값이 올 때까지 직전 값을 그대로 붙잡고 있는 것 | 5장 |
| 데드타임 | 실제로 일어난 일이 판단에 반영되기까지의 총 지연 | 6장 |
| 콜드스타트 | 프로그램이 막 켜졌을 때 유난히 느린 구간 | 1장 |
| 양자화(quantization) | 값이 연속이 아니라 계단처럼 띄엄띄엄 되는 것 | 4장 |

## 1. 현재 성능 — 5.0Hz (4.4Hz 가 아니다)

### 1.1 결론

```
                   Hz        프레임당 처리시간
  실측(정상상태)   5.0~5.3   약 194ms
  기동 첫 10초     4.4       219ms   ← 콜드스타트 오염
```

세션 초반에 `[perf] 45f/10.2s (4.4Hz) avg=219ms` 라는 로그를 근거로 "현재 4.4Hz" 라고 적었는데, **이 값은 틀렸다.** 검증 과정에서 원인이 밝혀졌다.

YOLO 의 첫 추론은 1,159~1,378ms 가 걸린다(실측). 2회차부터 101~167ms 로 정상 범위에 들어간다. 그런데 `[perf]` 로그는 기동 직후 10초 창의 45프레임 평균이라, 여기에 1.3초짜리 첫 프레임 1개가 섞이면 평균이 +25ms 오른다. 194 + 25 = 219ms — 관측값과 정확히 맞는다.

**정상상태는 약 194ms / 5.0~5.3Hz 다.** 이 문서의 모든 비교는 이 값을 기준으로 한다.

> 실무 교훈: 기동 직후 첫 `[perf]` 로그는 믿지 마라. 두 번째 이후 로그를 봐야 한다.

### 1.2 194ms 는 어디에 쓰이나

검출이 있는 프레임 기준 단계별 실측:

```
  이미지 준비 (bytes 복사 + 색변환)      3.8ms
  undistort remap (1920x1080)          17.8ms
  ├ lane.pt   78.7ms
  │   ├ RGB 반전 복사(1080p)     9.8ms
  │   ├ 추론                    47.8ms
  │   └ 마스크 후처리           21.1ms
  ├ best.pt   46.8ms
  │   ├ RGB 반전 복사(1080p)     9.9ms
  │   ├ 추론                    36.7ms
  │   └ 박스 처리                0.1ms
  └ light.pt  44.8ms
      └ 추론                    44.8ms
  ──────────────────────────────────────
  합계                          191.8ms
```

| 분류 | 시간 | 비중 |
|---|---|---|
| 순수 신경망 추론 | 129.3ms | 67% |
| 1920x1080 버퍼 복사·리샘플 | 62.5ms | 33% |

**3분의 1이 계산이 아니라 큰 사진을 복사하고 크기 바꾸는 데 쓰인다.** 이게 개선 여지의 핵심이다.

## 2. 예선은 몇 Hz 였나 — 10.4Hz, 하지만 의미가 다르다

### 2.1 실측 근거

노트북(WSL)에 남아 있던 예선 기간 ROS 로그를 전부 재집계했다. `yolo_lane_node` 가 20프레임마다 로그 1줄을 찍으므로(예선 `yolo_lane_node.py:131-135`) 로그 타임스탬프 간격으로 Hz 를 역산할 수 있다.

| 항목 | 값 |
|---|---|
| 세션 수 | 47 (2026-06-23 ~ 06-26) |
| 총 프레임 | 약 35만 |
| 평균 | 10.37 Hz |
| 중앙값 | 10.40 Hz |
| 범위 | 9.68 ~ 10.70 Hz |

이 값은 두 에이전트가 독립적으로 같은 로그를 집계해 동일하게 재현했다.

### 2.2 ★ 그런데 그 10.4Hz 는 GPU 성능이 아니다

예선을 그냥 "10.4Hz 였는데 지금 5Hz 로 반토막" 이라고 읽으면 틀린다. 결정적 증거 세 가지:

1. **같은 세션에서 lane 노드와 light 노드의 Hz 가 34쌍 전부 소수점까지 일치했다.** (예: 10.34 vs 10.34, 10.69 vs 10.72) 서로 다른 모델인데 속도가 같다는 건, 둘 다 "들어오는 프레임을 전부 처리하고 놀고 있었다"는 뜻이다.
2. **YOLO 모델 1개만 단독으로 돌린 세션도 10.53Hz** 였다. 3모델일 때와 차이가 없다.
3. 예선 시뮬 카메라는 640x480 이었고 GPU 는 RTX 4070 Laptop(CUDA)이었다.

즉 **예선의 병목은 Unity 시뮬레이터 카메라의 발행율(~10.4Hz)이었고, GPU 는 여유가 있었다.** 3모델 × 10.4Hz = 초당 31회 추론을 GPU 가 지연 없이 소화했다.

### 2.3 그래서 예선과 본선은 직접 비교가 안 된다

| | 예선 | 본선 |
|---|---|---|
| 하드웨어 | RTX 4070 Laptop (GPU) | Ryzen 7 5700U (CPU만) |
| 입력 | 640x480 시뮬 | 1920x1080 실카메라 |
| imgsz | 640 | 416 |
| 구조 | 3노드 병렬, 같은 프레임 3중 추론 | 1노드에서 3모델 순차 |
| 병목 | 시뮬 카메라 발행율 | CPU 추론 |
| 실측 | 10.4Hz | 5.0Hz |

**"느려진" 게 아니라 "환경이 완전히 다르다".** GPU 를 CPU 로 바꿨는데 5Hz 가 나오는 건 오히려 선방한 편이다.

### 2.4 ★ 다만 이게 진짜 문제를 하나 만든다

`config/tuning.yaml` 의 `[SIM]` 태그가 붙은 값들은 **전부 10.4Hz 인지 환경에서 튜닝된 값이다.** 지금 5.0Hz 는 그 절반이라, 같은 상수가 튜닝 시점보다 2배 늦은 정보로 평가되고 있다.

이게 속도 개선을 정당화하는 가장 강한 주행 관점 논거다. 8.8Hz 로 올리면 그 상수들이 원래 튜닝된 영역 근처로 돌아온다.

## 3. 더 빠르게 할 수 있나 — 8.8Hz 까지 실측

### 3.1 옵션별 실측 결과

| 항목 | 실측 Hz | 노력 | 판정 |
|---|---|---|---|
| `cv2.setNumThreads(8)` 복원 | 5.53 | 즉시 | **채택 권장** |
| obj/light 라운드로빈 | 6.78 | 즉시 | **채택 권장** |
| 마스크 후처리를 모델 해상도에서 | — | 수십분 | 조건부(아래 참조) |
| fused prep (전처리 융합) | — | 수시간 | 조건부 |
| imgsz 416 → 320 | 7.61 | 즉시 | 조건부 |
| imgsz 320 → 256 | 7.69 | 즉시 | **비권장** |
| torch 스레드 수 조정 | — | — | **무의미(아래 참조)** |
| undistort 생략 | 65.1 | 즉시 | **금지** |
| half=True (fp16) | 20.7 | 즉시 | 비권장 (더 느려짐) |
| INT8 동적 양자화 | 20.9 | 즉시 | 비권장 (더 느려짐) |

**조합 실측: 8.80Hz** (라이브 200프레임, proc 96.9ms). 이건 곱셈 추정이 아니라 실제로 돌린 값이고, 다른 에이전트가 8.63Hz 로 재현했다.

### 3.2 ★ 가장 어이없는 발견 — OpenCV 가 1스레드로 돌고 있다

`ultralytics` 를 import 하면 라이브러리가 내부에서 `cv2.setNumThreads(0)` 을 호출한다. 그 순간부터 **이 프로세스 안의 모든 OpenCV 연산이 1스레드로 떨어진다.** 8코어 16스레드 CPU 인데.

`undistort remap` 실측 (1920x1080):

```
   1스레드  17.36ms   ← 지금 이 상태
   2스레드   9.51ms
   4스레드   6.46ms
   8스레드   5.12ms
  16스레드   4.20ms
```

한 줄 고치면 13ms 가 그냥 돌아온다. 픽셀 결과는 완전히 동일하다 — 정확도 대가 0.

### 3.3 ★ 뒤집힌 결론 두 개

교차검증에서 처음 보고가 틀렸다고 밝혀진 항목이다. 그대로 적어둔다.

**(1) torch 스레드 실험 전체가 무효였다.**
`ultralytics` 의 `select_device()` 가 첫 추론 때 `torch.set_num_threads(8)` 을 무조건 강제한다. 그래서 스레드 수를 1/2/4/8/16 으로 바꿔가며 잰 6개 조건이 **실제로는 전부 8스레드였다.** 전부 비슷하게 나온 건 "스레드가 무의미해서"가 아니라 "조건이 실제로 하나뿐이어서"다.

이게 중요한 이유: 처음 보고는 "연산 효율이 하드웨어 이론치의 76% 라 한계에 가깝다"고 결론냈는데, 실제로는 8코어 피크의 **약 12%** 다. 즉 연산 여유가 6~8배 더 있고, ONNX/OpenVINO 같은 다른 추론 백엔드로 얻을 수 있는 이득이 처음 판단보다 크다.

**(2) imgsz 320 의 정확도 손실이 재현되지 않았다.**
처음 보고는 "마스크 화소 14,709 → 9,090 (−38%)" 을 근거로 320 을 강등했는데, 같은 프레임으로 재측정하니 화소가 오히려 **늘었다**(+10.5%, +26.2%). "MID 인스턴스 3→2" 는 재현되지만 화소가 늘었으니 이건 "차선을 놓쳤다"가 아니라 "두 덩어리가 하나로 합쳐졌다"로 읽어야 한다.

다만 표본이 사실상 1장이라 **"320 이 안전하다"고 말할 수도 없다.** `imgsz=256` 에서 물체 검출이 3개→0개로 붕괴하는 것만은 두 번 다 재현됐다 — 256 은 확실히 쓰면 안 된다.

### 3.4 절대 하면 안 되는 것

**`undistort` 생략은 65Hz 가 나오지만 절대 금지다.** `camera.yaml` 의 H 행렬은 "왜곡 보정된 픽셀 → 지면 미터" 로 정의돼 있다. 보정을 빼면 H 가 통째로 무효가 되고 `/detect/lane` 좌표가 전부 틀어진다. 시간은 아끼되 기능을 버리는 선택이다.

## 4. 지터 — "Hz 가 일정한 것도 중요하지 않나"

### 4.1 실측

| 측정 대상 | Hz | 간격 평균 | sd | p95 | max |
|---|---|---|---|---|---|
| 카메라만 (추론 없음) | 28.4 | 35.3ms | 9.3 | 56.1 | 98.8 |
| 현재 3모델 순차 | 5.02 | 200.6ms | 18.9 | 233.6 | 262.5 |
| 조합 적용 후 | 8.80 | 114.2ms | 14.5 | 141.5 | 162.6 |

카메라 자체의 sd 9.3ms 가 **지터의 하한**이다. 아무리 최적화해도 이보다 규칙적일 수는 없다.

### 4.2 지터의 원인 — 후보를 하나씩 배제했다

| 후보 | 판정 | 근거 |
|---|---|---|
| 가비지 컬렉션(GC) | ✗ 아님 | 4개 측정 모드 전부 콜백 중 gen2 수집 0회 |
| `_busy` 프레임 드랍 | ✗ 아님 | 모든 모드에서 drop=0 |
| 카메라 자체 지터 | △ 하한일 뿐 | sd 9.3ms 로 관측 sd 18.9ms 의 절반 이하 |
| **추론시간 산포** | **○ 원인** | gap sd 18.9ms ≈ proc sd 18.5ms 로 거의 완전 일치 |

검출이 0개인 장면에서도 sd 가 18.5ms 라, NMS 부하 변동이 아니라 **CPU 주파수 변동과 공존 프로세스 경합**(usb_cam 43%, 원격데스크톱 32%)이 원인이다.

### 4.3 ★ 부산물 — `_busy` 는 죽은 코드다

측정 중 확인된 사실이다. `yolo_node` 의 `_busy` 플래그는 "처리 중에 들어온 프레임을 버린다"는 의도인데, `rclpy.spin_once` 가 단일 스레드라 **콜백 재진입이 구조적으로 불가능하다.** 모든 모드에서 `busy_drop = 0` 이었다.

실제로 프레임을 버리는 건 QoS 의 `depth=1` 설정이다. `_busy` 는 해가 없지만 아무 일도 하지 않는다.

### 4.4 ★ 라운드로빈이 지터를 키우는가 — 아니다

이게 이 조사에서 가장 확인하고 싶었던 것이다. "lane 만 도는 프레임"과 "3개 다 도는 프레임"이 섞이면 그 자체가 지터가 될 거라고 예상했는데, **틀렸다.**

```
  obj 도는 프레임    138.8ms
  light 도는 프레임  139.4ms
  ────────────────────────
  차이                 0.6ms
```

`best.pt`(검출 16클래스)와 `light.pt`(세그 3클래스)의 추론 시간이 우연히 거의 같아서, 번갈아 돌려도 프레임마다 걸리는 시간이 사실상 같다. gap sd 도 순차와 동일했다.

### 4.5 ★ 또 뒤집힌 것 — "33ms 양자화 계단"은 없다

처음 보고는 "카메라 주기 33ms 의 배수로 Hz 가 계단처럼 뛴다"는 모델을 세우고, 그걸 근거로 "라운드로빈이 계단을 넘는 결정적 한 수"라는 서사를 만들었다. 검증에서 **이 메커니즘이 존재하지 않는 것으로 밝혀졌다.**

실측하면 `gap = proc + 상수` 인 단순 선형 관계다. 양자화 모델이 예측하는 잔차(15.7 / 24.0 / 2.4ms)와 실측 잔차(7.6 / 7.9 / 17.4ms)가 전부 어긋난다. 처음 보고가 기준선 1점에서 맞았던 건 우연이다.

**실무적 함의:** 라운드로빈은 "계단을 넘는 특별한 수"가 아니라 그냥 42ms 를 줄이는 평범한 옵션이다. 따라서 obj/light 갱신율이 반토막 나는 대가와 순수하게 저울질하면 되고, "계단 공포" 때문에 필수로 채택할 이유가 없다.

### 4.6 결론 — 지터는 문제가 아니다

네 직관("Hz 가 일정한 것도 중요하지 않나")은 일반론으로는 옳다. 하지만 **이 시스템에서는 아니다.** 이유:

1. **제어 경로에 dt 소비처가 없다.** `motion_node` 는 순수 기하 추종이라 미분항·적분항이 없다. 오차 적분 상태변수가 하나도 없다. 즉 주기가 흔들려도 계산이 틀어지지 않는다.
2. **신선도 가드가 전부 절대시간이다.** `objects_fresh_sec=0.5` 같은 값은 초 단위 절대 비교라, 주기가 아니라 최악 간격만 보면 된다.
3. **절대 sd 는 오히려 개선된다.** 18.9 → 14.5ms (23% 개선).

다만 **상대지터(변동계수 9.4% → 12.7% 상승)를 근거로 삼으면 안 된다.** 그건 이 시스템에서 의미 없는 지표다. 판단 기준은 절대 sd 뿐이다.

---

## 5. ★ 그런데 정말 중요한 건 Hz 가 아니다

### 5.1 653ms 지연

측정 중 아무도 예상하지 못한 값이 나왔다. `/image_raw` 의 `header.stamp`(사진이 찍힌 시각)와 실제 도착 시각의 차이:

```
  평균 653.2ms   sd 3.3ms   p50 652.9   p95 659.1   min 647.7   max 660.3
  (120프레임 직접 측정 + ros2 topic delay 469표본 교차확인)
```

sd 가 3.3ms 뿐이라 **매우 일정한 상수 오프셋**이다. 프레임 간격도 stamp 34.9ms vs 도착 35.0ms 로 일치해서, 프레임이 점점 밀리는 상황은 아니다.

### 5.2 이게 왜 중요한가

인지를 5.0 → 8.8Hz 로 올리면 프레임당 처리시간이 194 → 97ms 로 줄어든다. **약 97ms 이득이다.** 그런데 653ms 지연 앞에서 이건 전체의 13% 밖에 안 된다.

```
  센서 → 판단 전체 지연

  현재:   [카메라 653ms] + [처리 194ms] + [planner/motion 50ms] = 897ms
  개선후: [카메라 653ms] + [처리  97ms] + [planner/motion 50ms] = 800ms
                ↑
          여기가 73%
```

1.92m/s 로 달리면 653ms 동안 **125cm** 를 간다.

### 5.3 ★ 다만 두 가지 가능성이 있고, 아직 판별되지 않았다

| 가능성 | 실제 영향 |
|---|---|
| (a) usb_cam 이 타임스탬프를 653ms 과거로 찍는 버그 | **무해.** `path_planner_node.py:476` 이 `header.stamp` 가 아니라 수신 시각(`self._now()`)을 기록하므로 신선도 가드가 정상 동작한다 |
| (b) 진짜로 653ms 버퍼링이 있다 | **심각.** 125cm 지난 그림을 보고 판단하는 셈 |

배제된 것: ROS 시계와 시스템 시계는 일치한다(차이 0.000s). 부팅 경과 6시간 38분이라 monotonic-realtime 오프셋 가설도 아니다.

**판별법 (5초면 된다):** `bev_view.py` 를 켜고 카메라 앞에서 손을 흔들어라. 화면이 눈에 띄게(반 박자 넘게) 늦으면 (b) 다. 실시간으로 보이면 (a) 다.

(b) 로 밝혀지면 `usb_cam` 의 버퍼 설정과 MJPEG 디코드 경로를 먼저 봐야 하고, 그게 이 문서의 다른 모든 최적화보다 우선이다.

## 6. 우선순위 — 위험 대비 이득 순

대회가 2026-08-25 다. 현장에서 되돌릴 수 없는 변경은 피해야 한다.

| 순위 | 항목 | 이득 | 위험 | 되돌리기 |
|---|---|---|---|---|
| **0** | 653ms 지연이 진짜인지 판별 | 최대 | 없음 (측정만) | — |
| **0** | `stop_v_threshold=312` 실차 재보정 | 최대 | 없음 (측정만) | — |
| 1 | `cv2.setNumThreads(8)` 복원 | +0.5Hz | 없음 (픽셀 동일) | 1줄 |
| 2 | obj/light 라운드로빈 | +1.3Hz | 중간 (아래 조건) | 파라미터로 끄기 |
| 3 | 마스크 A행렬 warp | 정확도 | 중간 | 별도 커밋 |
| 4 | fused prep | +39ms | **높음** | 어려움 |
| 5 | imgsz 320 | +0.8Hz | 불명 (표본 1장) | 파라미터 |

### 6.1 ★ 사실 1순위는 Hz 가 아니다

`tuning.yaml` 의 `stop_v_threshold: 312.0`, `cross_v_threshold: 278.0`, `track_width: 4.4` 가 전부 `[SIM]` 시뮬 값이고 **실차 재튜닝 이력이 0회다.**

312 가 틀리면 인지가 5Hz 든 15Hz 든 정지선에서 잘못된 위치에 선다. 정차 상태에서 STOP 표지를 실제 정지 목표거리에 놓고 `/detect/objects` 의 v 를 읽어 312 를 재보정하는 작업(반나절)이, 이 문서의 성능 개선 패키지 전체보다 주행 개선 기여가 크다.

### 6.2 라운드로빈을 넣을 때 반드시 지킬 것

**거르는 프레임에는 발행 자체를 생략해야 한다.** 빈 `PoseArray` 를 발행하면 안 된다.

이유: `_on_objects`(`path_planner_node.py:445-476`)는 메시지가 비어 있어도 `_stop_max_v = None`, `_obj_cls = set()` 으로 지운 뒤 `_objects_time` 은 무조건 갱신한다. 그러면 "신선한데 내용이 빈" 상태가 매 프레임 교대로 들어가고, `_sc_left_hits`(`:787-791`)가 증감을 반복해 **LEFT 확정이 영구히 안 될 수 있다.**

### 6.3 fused prep 을 미루는 이유

단일 최대 기여(39ms)지만 위험이 크다.

- 픽셀이 완전히 같지 않다(완전일치 53.2%, 절대차 max 141). 실제로 한 프레임에서 검출 결과가 달라졌다.
- `/detect/objects` 의 u,v 좌표계를 바꿔 역변환을 새로 넣어야 한다.
- 그 u,v 가 비교되는 `stop_v_threshold=312` 가 미검증 시뮬 값이다.
- **미검증 임계값 위에 미검증 좌표변환을 얹는 구조**다. 부호 하나 틀리면 정지선을 통째로 놓치는데 현장에서 디버깅이 불가능하다.

### 6.4 마스크 A행렬 warp — 성능이 아니라 정확도 수정이다

이 항목은 성능 패키지에서 분리해야 한다. 라이브 Hz 측정이 전부 "검출 0" 프레임이라 이 항목의 8.8Hz 기여분은 사실상 0ms 다.

대신 **실재하는 기하 버그를 고친다.** 현재 마스크를 1920x1080 으로 키운 뒤 워프하는데, letterbox 비율(r = 416/1920 = 0.216667, top = 11)에서 대수적으로 유도되는 오차가 있다:

```
  v_추정 = 0.914 × v_실제 + 46.4     (고정점 v=540)
  v=545 에서  +0.4%
  v=951 에서 +11.0%   (-35.2px)
```

즉 **화면 아래쪽(가까운 곳)일수록 좌표가 틀어진다.** 다만 `camera.yaml` 의 H 가 2026-07-31 에 갱신된 것이고 주행 검증 이력이 0회라, 새 H 와 좌표계 변경을 동시에 얹으면 문제가 생겼을 때 원인 분리가 불가능하다. **정지 상태 + 고정 타겟으로 실측 거리를 먼저 검증한 뒤 단독 커밋할 것.**

## 7. 이 측정의 한계 — 믿으면 안 되는 것

정직하게 적는다. 아래 항목은 이 문서의 수치를 인용할 때 반드시 같이 봐야 한다.

1. **★ 가장 큰 한계: 검출 대상이 없는 장면에서 쟀다.** 차 카메라가 지금 보고 있는 곳에 차선도 표지도 신호등도 없다. `conf=0.10` 까지 낮춰도 3모델 전부 0검출이었다. 따라서 라이브 Hz(5.02 / 6.78 / 8.80)는 전부 "검출 0" 조건의 비용이고, **실제 주행에서는 마스크 후처리(17~21ms)가 얹혀 더 느리다.**

2. **오프라인 측정의 입력이 종횡비가 왜곡된 합성 영상이다.** 예선 시뮬 640x480(4:3)을 1920x1080(16:9)으로 늘렸는데, 가로 3.00배·세로 2.25배라 실차 카메라가 만들 수 없는 기하다. 차선처럼 기울기가 정보인 대상에서 이 결과는 실차로 이식할 수 없다.

3. **imgsz 정확도 비교는 표본 1장이다.** mAP 측정이 아니다. "손실이 있다/없다"를 이 데이터로 단정할 수 없다.

4. **벤치마크는 실제 노드가 아니라 재구현 스크립트다.** PoseArray 구성·4개 토픽 발행·rclpy executor 가 빠져 있다. "1.75배 빨라진다"는 스크립트끼리의 비교다.

5. **측정 내내 원격데스크톱(CPU 32%)이 돌고 있었다.** 실주행에는 없으므로 실제로는 여기 수치보다 조금 빠를 수 있다.

6. **ONNX / OpenVINO / ncnn 은 전부 미설치라 측정하지 못했다.** 설치하지 않았다. 이득 추정치는 여전히 추정이다. 다만 3.3절에서 밝혀졌듯 연산 여유가 8코어 피크의 88% 남아 있어, 이 백엔드들의 여지는 처음 판단보다 크다.

7. **CPU governor 를 `powersave` 로 둔 채 측정했다.** `performance` 로 바꿨을 때의 이득은 sudo 가 필요해 측정하지 않았다.

8. **카메라가 `framerate:=30.0` 인데 실측 발행율은 28.4Hz** 다(`ros2 topic hz` 로는 25.8~27.1Hz). 이미 설정값을 못 맞추고 있다.
