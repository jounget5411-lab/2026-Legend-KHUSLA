## 1. 전체 그림 — 인지 파이프라인 한 장

카메라 노드(`usb_cam`)가 찍은 원본 영상이 `/image_raw` 로 나오고, 그걸 **yolo_node 하나가** 받아서 세 개의 신경망을 차례로 돌린 뒤, 네 개의 토픽으로 결과를 뿌린다. 예선에서는 이 일을 세 개의 노드(`yolo_lane`, `yolo_detect`, `yolo_light`)가 각각 했고, 각각이 이미지를 따로 받아 따로 추론했다. 본선은 실차 CPU 뿐이라(GPU 없음) 그 낭비를 없애려고 한 노드로 합쳤다 (`yolo_node.py:11-12` 의 "예선 대비 변경점").

> 여기 나오는 ROS 낱말 세 개만 먼저 정리한다.
> **노드**는 따로 실행되는 프로그램 하나다(`yolo_node` 도 노드, `usb_cam` 도 노드).
> **토픽**은 노드 사이로 데이터가 흐르는 방송 채널이고, 이름이 `/image_raw` 처럼 슬래시로 시작한다.
> **추론**은 학습이 끝난 신경망에 사진 한 장을 넣어 결과를 뽑아내는 계산을 말한다.
> "세 개의 신경망을 차례로 돌린다" = "세 번 추론한다" 와 같은 말이다.

```
 [카메라 usb_cam]  1920x1080 MJPG 30fps
        |  /image_raw  (rgb8, sensor_data QoS depth=1)
        v
 +-------------------------------------------------------------+
 |  yolo_node  (yolo_node.py)                                   |
 |                                                              |
 |  1) Image msg -> BGR ndarray   lib/preprocess.py             |
 |  2) 렌즈 왜곡 보정 undistort   lib/bev.Undistorter           |
 |  3) 세 모델 "순차" 추론                                       |
 |       lane.pt  (segment) --+--> 마스크 -> BEV -> 지면 좌표    |
 |       best.pt  (detect)  --+--> bbox   -> (u,v)+클래스       |
 |       light.pt (segment) --+--> 초록/빨강 conf 비교 -> 디바운스|
 |  4) 발행                                                     |
 +-------------------------------------------------------------+
     |            |                  |                 |
     v            v                  v                 v
 /detect/lane  /detect/lane_quality  /detect/objects  /detect/traffic_light
 PoseArray     Float32 0~1           PoseArray        String
 (x,y[m],z=cls)                      (u,v[px],z=cls)  GREEN|RED|NONE
     |                                    |                 |
     +--------> path_planner_node (주행 판단) <--------------+
```

토픽 계약(어떤 필드에 무엇이 들어가는지)은 `yolo_node.py:7-10` 의 파일 헤더 주석에 그대로 적혀 있다. 이 계약이 곧 인지팀과 판단팀 사이의 인터페이스다.

그림 맨 위의 `sensor_data QoS depth=1` 은 "**영상은 최신 한 장만 받고, 놓친 프레임은 다시 달라고 하지 않는다**"는 수신 규칙이다. 왜 그렇게 정했는지는 §4.4 에서 푼다.

## 2. YOLO 가 뭔가 — "검출"과 "세그멘테이션"의 차이

**YOLO(You Only Look Once)** 는 사진 한 장을 신경망에 한 번만 통과시켜서 "무엇이 어디에 있는지"를 바로 뱉는 물체 인식 모델 계열이다. 사람이 사진을 슬쩍 보고 "왼쪽에 사람, 가운데 차"라고 말하는 것과 비슷해서 이런 이름이 붙었다. 우리가 쓰는 건 `ultralytics` 패키지의 YOLOv8 이고, 학습된 결과물이 `.pt` 파일이다(**파이토치 가중치**. 가중치는 학습을 거쳐 정해진 신경망 내부의 숫자 뭉치를 말하고, `.pt` 는 그 숫자 뭉치를 통째로 저장해 둔 파일이다. 즉 `.pt` 하나가 "학습이 끝난 모델 한 개"다).

같은 YOLO 라도 **출력의 모양**이 두 가지다. 이 프로젝트는 둘 다 쓴다.

```
 [detect : 물체검출]                  [segment : 세그멘테이션]
   네모(bbox) 하나 + 클래스              픽셀 하나하나에 "여기 그것"

   +------------------+                +------------------+
   |                  |                |     ....         |
   |   +--------+     |                |    ::::::        |
   |   | STOP   |     |                |   ::::::::       |  <- 차선 모양
   |   +--------+     |                |  ::::::::        |     그대로
   |                  |                | ::::::           |
   +------------------+                +------------------+
   "x1,y1,x2,y2 + cls"                 "cls별 0/1 마스크 이미지"
   물체가 '있다/없다', 대략 위치         물체의 '모양'이 필요할 때
```

- **detect** 는 물체를 감싸는 사각형(bounding box, 줄여서 bbox)과 클래스 번호, 확신도(confidence)를 준다. 정지선 표지, 사람, 다른 차처럼 "있냐 없냐 + 얼마나 가깝냐"만 알면 되는 대상에 적합하다.
- **segment(세그멘테이션)** 는 픽셀 단위 마스크를 준다. 차선처럼 **모양(휘어진 곡선)** 자체가 정보인 대상은 네모로는 표현이 안 되므로 세그멘테이션이 필요하다. 차선의 마스크가 있어야 뒤에서 BEV 로 펴서 곡선을 피팅할 수 있다.

> 여기서 나온 낱말 넷.
> **클래스**는 "이게 몇 번 물체인가"를 나타내는 번호다. 모델마다 0번부터 순서대로 이름표가 붙어 있고, 그 이름표 목록이 §3.2 의 표다.
> **확신도(confidence, 줄여서 conf)** 는 모델이 그 판정을 스스로 얼마나 믿는지를 0~1 로 적은 점수다. 0.9 면 꽤 확신, 0.3 이면 긴가민가다. 이 점수가 정해둔 문턱보다 낮은 결과는 아예 안 나온다(§9 의 `conf_lane`/`conf_obj`/`conf_light`).
> **마스크**는 "이 픽셀이 그것에 해당한다/아니다"를 흑백 그림으로 칠해 놓은 것이다. 사진과 같은 크기의 도장 찍힌 종이라고 보면 된다.
> **피팅(fitting)** 은 흩어진 점들에 가장 잘 맞는 수식을 찾아내는 일이다. 이 프로젝트에서 말하는 "2차 피팅"은 점들에 가장 잘 맞는 포물선(y = ax² + bx + c) 하나를 찾는 것을 뜻한다.

세그 모델도 bbox 는 같이 나온다(`r.boxes`). 그래서 `light.pt` 처럼 실제로는 세그 모델이지만 코드에서는 박스와 확신도만 쓰는 경우도 있다(§3.3 참고).

## 3. 모델 3개 — lane.pt / best.pt / light.pt

### 3.1 무엇을 하는 모델인가

| 파일 | 태스크 | 학습 베이스 | 이 코드에서 쓰는 출력 |
|---|---|---|---|
| `config/lane.pt` | segment | yolov8n-seg, imgsz 640, 100 epoch | 마스크(`r.masks`) → 차선 점 |
| `config/best.pt` | detect | yolov8n, imgsz 640, 100 epoch | 박스(`r.boxes.xyxy`) → (u,v) |
| `config/light.pt` | segment | yolov8n-seg, imgsz 640, 50 epoch | 박스의 클래스·확신도만 |

(태스크/베이스 값은 `.pt` 안에 저장된 `train_args` 를 직접 읽어 확인했다. 노드도 기동할 때 `model.task` 와 `model.names` 를 로그로 찍는다 — `yolo_node.py:230`.)

표의 학습 조건 두 개도 풀어 둔다. **imgsz** 는 신경망에 집어넣는 정사각형 입력 이미지의 한 변 픽셀 수다. `imgsz 640` 은 학습할 때 사진을 640x640 으로 줄여 넣었다는 뜻이고, 실차에서 추론할 때 쓰는 값은 이와 별개로 416 이다(§9). **epoch** 은 학습 데이터 전체를 처음부터 끝까지 몇 번 반복해서 보여줬는지를 세는 단위다. `100 epoch` 은 같은 사진 묶음을 100번 돌려 봤다는 말이다. 숫자가 클수록 잘 외우지만, 지나치면 학습 사진에만 맞고 실제 트랙에서는 오히려 못 맞히게 된다.

**왜 3개로 나눴나.** 세 모델은 학습 데이터와 목적이 다르다. 차선은 모양이 필요해서 seg 로 따로 학습했고, 표지·차량·사람은 detect 하나로 묶었고, 신호등은 예선 때 **주황불을 초록으로 오인하는 사고**가 있어서 "주황을 red 로 학습한" 별도 모델을 친구가 만들어 붙였다 (예선 `yolo_light_node.py` 헤더 주석). 한 모델로 전부 재학습하는 게 이상적이지만, 이미 검증된 모델을 대회 직전에 흔들 이유가 없다.

## 4. 한 프레임이 처리되는 순서

콜백 진입점은 `_on_image`(`yolo_node.py:242`), 실제 처리는 `_process`(`yolo_node.py:251`) 다. **콜백(callback)** 은 "메시지가 도착할 때마다 자동으로 불려서 실행되는 함수"를 말한다. 우리가 "지금 영상 한 장 줘"라고 부르는 게 아니라, 카메라가 한 장 보낼 때마다 ROS 가 알아서 이 함수를 불러 준다. 초당 30장이 오면 초당 30번 불린다.

```
 _on_image(msg)                         yolo_node.py:242
   |
   +-- self._busy 면 즉시 return  <-- 처리 중 도착 프레임은 "버린다"
   |
   v
 _process(msg)                          yolo_node.py:251
   |
   [1] preprocess.image_msg_to_bgr(msg)          :254   ROS msg -> BGR
   |      실패하면 사유를 5초 스로틀 경고 후 return  :256-259
   [2] 프레임 크기 == 캘리브 크기 확인            :266-276
   |      다르면 리맵 재생성 + 경고 (H 무효 가능)
   [3] frame = self._undist.apply(bgr)           :277   렌즈 왜곡 보정
   |
   [4] _run_lane(frame, header)   lane.pt        :282   -> /detect/lane(+quality)
   [5] _run_obj (frame, header)   best.pt        :286   -> /detect/objects
   [6] _run_light(frame)          light.pt       :290   -> /detect/traffic_light
   |
   [7] 10초마다 [perf] 로그 (Hz, 모델별 ms)      :299-313
```

### 4.1 [1] ROS Image → numpy BGR — `lib/preprocess.py` 는 왜 있나

ROS 의 `sensor_msgs/Image` 는 그냥 바이트 덩어리다. 여기엔 두 가지 함정이 있다.

첫째, **인코딩**이다. 인코딩은 "픽셀 하나를 바이트로 어떻게 적어 놨는가"를 정한 약속이다. `rgb8` 은 픽셀 하나를 빨강·초록·파랑 각 1바이트씩 이 순서로 적었다는 뜻이고, `bgr8` 은 같은 3바이트인데 순서가 파랑·초록·빨강으로 거꾸로다. `mono8` 은 흑백이라 픽셀당 1바이트다. 같은 바이트 덩어리라도 이 약속을 잘못 알면 색이 뒤바뀌거나 그림이 깨진다. 카메라 드라이버 설정에 따라 `rgb8`, `bgr8`, `yuyv`, `mono8` 등으로 나온다. 예선 코드는 `if msg.encoding != "rgb8": return` 처럼 **하드코딩**해 놓고, 다르면 아무 말 없이 버렸다(예선 `yolo_light_node.py` 의 `_on_image` 첫 줄). 그래서 인코딩이 바뀌면 노드가 살아 있는데 아무것도 안 나오는 상태가 됐고, 원인을 찾는 데 시간을 날렸다. 본선에서는 이걸 "재도입 금지 버그 8"로 못박고, 실패하면 **반드시 사유를 반환**하도록 바꿨다 (`preprocess.py:6-7`, 호출측 경고는 `yolo_node.py:256-259`). 지원 인코딩은 `_BYTES_PER_PIXEL`(`preprocess.py:18-30`)에 표로 있다.

이때 경고는 **5초 스로틀**로 찍는다. 스로틀(throttle)은 "같은 경고를 아무리 자주 만나도 몇 초에 한 번만 찍는다"는 뜻이다. 변환 실패는 초당 30번 일어날 수 있어서, 스로틀이 없으면 터미널이 같은 줄로 도배돼 정작 다른 로그를 못 보게 된다.

둘째, **step 패딩**이다. `msg.step` 은 한 행의 실제 바이트 수인데, 드라이버가 정렬을 위해 폭보다 크게 잡을 수 있다(예: 폭 640 픽셀 x 3바이트 = 1920 바이트면 충분한데 step 을 1920 보다 크게 잡고 뒤에 안 쓰는 자투리 바이트를 붙여 놓는 식이다. 메모리를 특정 배수 단위로 맞추면 CPU 가 빨리 읽기 때문에 드라이버들이 흔히 이렇게 한다). 그대로 `reshape`(바이트 한 줄을 "가로 x 세로" 격자로 다시 접는 일) 하면 행마다 자투리만큼 밀려서 영상이 사선으로 기운다. `preprocess.py:62-64` 가 `(h, step)` 으로 자른 뒤 앞의 유효 바이트만 잘라내서 이 문제를 없앤다.

기준 색순서는 **BGR** 로 통일했다. OpenCV 관례가 BGR 이기 때문이다 (`preprocess.py:8-9`).

### 4.2 [3] undistort — 렌즈 때문에 휜 직선을 펴는 일

렌즈는 유리를 곡면으로 깎은 물건이라, 실제로는 곧은 선이 사진에서는 배불뚝이처럼 휜다(배럴 왜곡). 이걸 수학적으로 되돌리는 게 **왜곡 보정(undistort)** 이다.

```
   [원본 raw]                         [undistort 결과]
  +--------------+                   +--------------+
  |  \        /  |                   |  |        |  |
  |   \      /   |   ---- 보정 --->  |  |        |  |
  |    \____/    |                   |  |________|  |
  +--------------+                   +--------------+
   직선이 바깥으로 휨                    직선이 직선으로
```

**왜 인지 단계에서 반드시 펴야 하나.** 뒤에서 바닥을 위에서 본 것처럼 펴는 변환(**호모그래피 H** — 비스듬히 찍은 평면 사진을 정면에서 본 것처럼 되돌리는 3x3 숫자표다. 자세한 건 §6.1)은 "직선은 직선으로 간다"는 가정 위에 서 있다. 렌즈 왜곡이 남아 있으면 그 가정이 깨져서, 화면 가장자리의 차선이 지면 좌표에서 엉뚱한 곳에 찍힌다. 그래서 `_process` 는 **세 모델 모두에게 보정된 프레임을 준다** (`yolo_node.py:264`). 결과적으로 `/detect/objects` 의 u,v 임계값도 전부 보정 프레임 기준으로 튜닝해야 한다는 뜻이다 (`yolo_node.py:265` 주석).

### 4.3 [4]~[6] 세 모델 순차 추론

세 모델은 **한 콜백 안에서 차례로** 돈다. 병렬로 돌리지 않는 이유는 실차 PC 에 GPU 가 없어 CPU 코어를 나눠 써봐야 전체 처리량이 나아지지 않기 때문이다. `device` 파라미터 기본값이 `"cpu"` 인 것도 같은 이유다 (`yolo_node.py:102`). 실측으로 `imgsz=416` 에서 3모델 순차 약 **11.5Hz** 가 나온다 (`yolo_node.py:5`, `yolo_node.py:93`). 카메라는 30fps 이므로 **약 3장 중 1장만 처리**되는 셈이다.

기동 시 `_warmup()`(`yolo_node.py:233`)이 검은 더미 이미지로 각 모델을 한 번씩 돌린다. CPU 추론은 첫 호출이 유난히 느리기 때문에, 그 지연이 실제 첫 프레임에 오지 않게 미리 털어내는 것이다.

### 4.4 `_busy` 플래그 — 밀린 프레임을 버리는 이유

```
 카메라 30fps  |----|----|----|----|----|----|----|----|   (33ms 간격)
 처리 11.5Hz   [======= 87ms =======][======= 87ms =======]
 도착 프레임      A    B    C    D    E    F    G    H
 처리되는 것      A(처리중 B,C 버림)   D(처리중 E,F 버림)   G ...
```

`_on_image` 는 `self._busy` 가 True 면 아무것도 안 하고 즉시 리턴한다 (`yolo_node.py:243-244`). 여기에 더해 구독 QoS 도 `depth=1` + `BEST_EFFORT` 로 잡아 큐 자체를 1칸만 둔다 (`yolo_node.py:145-150`).

**QoS 가 뭔가 — 우체국 배달 옵션 고르기.** QoS(Quality of Service, 서비스 품질)는 ROS 에서 **"이 토픽의 메시지를 어떤 방식으로 배달할지" 정해 놓은 규칙 묶음**이다. 택배를 보낼 때 "등기로 보낼까 일반으로 보낼까", "못 받으면 다시 보낼까", "쌓아둘까 버릴까"를 고르는 것과 같다. 우리 코드가 고른 값 네 개는 이렇다 (`yolo_node.py:145-150`).

| 설정 | 코드값 | 쉬운 뜻 |
|---|---|---|
| reliability(신뢰성) | `BEST_EFFORT` | "최선을 다해 한 번 보내고 끝". 중간에 유실돼도 재전송을 안 한다. 반대말이 `RELIABLE`(받았다는 확인이 올 때까지 다시 보냄) |
| depth(큐 깊이) | `1` | 아직 처리 못 한 메시지를 쌓아 두는 칸이 **1개**뿐. 새 게 오면 안에 있던 옛 것이 밀려 나간다 |
| history(보관 방식) | `KEEP_LAST` | 큐가 찼을 때 오래된 것부터 버리고 **최근 것만** 남긴다. 반대는 `KEEP_ALL`(다 쌓음) |
| durability(지속성) | `VOLATILE` | "휘발성". 발행자가 과거에 보낸 것을 저장해 두지 않아서, 나중에 켜진 구독자는 **켠 뒤에 온 것부터** 받는다. 반대는 `TRANSIENT_LOCAL`(늦게 온 구독자에게도 마지막 것을 다시 줌) |

**왜 "확실히 전달"이 아니라 "최신 것만 빨리"를 골랐나.** 두 옵션은 트레이드오프다.

- `RELIABLE` + 깊은 큐 = **하나도 안 놓치지만 늦는다.** 못 받은 프레임을 재전송받고, 처리 못 한 프레임을 큐에 쌓아 순서대로 다 처리한다. 로그 저장이나 지도 작성처럼 "빠짐없이"가 중요한 일에는 이게 맞다.
- `BEST_EFFORT` + `depth=1` = **놓치는 프레임이 생기지만 항상 지금 것이다.**

카메라 영상은 후자가 맞다. 이유는 **영상의 가치가 시간이 지나면 사라지기 때문**이다. 0.5초 전 프레임은 재전송으로 완벽하게 받아봐야, 그 사이 차가 이미 앞으로 한참 더 나갔으니 그 화면 속 차선 위치는 지금 차 위치와 안 맞는다. **정확하지만 과거인 정보**보다 **한 장 건너뛰었어도 지금인 정보**가 조향에는 훨씬 안전하다. 게다가 30fps 영상은 어차피 33ms 뒤에 다음 장이 또 온다 — 한 장 놓쳐도 곧 대체품이 온다는 뜻이라 재전송할 이유 자체가 약하다.

이런 성격의 토픽(카메라·라이다·IMU 같은 센서 스트림)에 쓰라고 ROS 가 미리 묶어 놓은 표준 조합이 있고, 그 이름이 **sensor_data QoS** 다. 위 표의 조합이 사실상 그것이고, 코드 주석도 "sensor_data 성격 + depth1(최신 프레임만 유지)"이라고 적어 놨다.

> ★ 주의: QoS 는 **발행자와 구독자의 설정이 서로 맞아야** 연결된다. 발행자가 `BEST_EFFORT` 인데 구독자가 `RELIABLE` 을 요구하면 **연결 자체가 안 돼서 토픽이 조용히 안 들어온다**. `ros2 topic list` 에는 토픽이 보이는데 콜백이 한 번도 안 불리면 이걸 먼저 의심해야 한다.

**왜 이렇게까지 하나.** 처리 속도(11.5Hz)가 입력 속도(30Hz)보다 느릴 때, 프레임을 큐에 쌓으면 큐가 무한정 길어지면서 **점점 과거의 영상을 보고 조향하게 된다**. 그래서 파일 헤더에 원칙이 못박혀 있다 — "CPU 전용(imgsz416 순차 ≈11.5Hz 실측)이라 백로그 금지 — 처리 중 프레임은 드랍" (`yolo_node.py:5`). **백로그(backlog)** 는 처리하지 못하고 밀려서 쌓인 일감을 말하고, **드랍(drop)** 은 그걸 쌓지 않고 그냥 버리는 것이다. 인지에서 조금 늦은 정보는 참을 수 있어도, **오래된 정보를 최신인 줄 알고 쓰는 것**은 못 참는다. 항상 최신 프레임만 처리하는 게 원칙이다.

### 4.5 [7] perf 로그 — 현장에서 성능을 눈으로 확인하는 법

`yolo_node.py:299-313` 이 10초마다 이런 줄을 찍는다.

```
[perf] 115f/10.0s (11.5Hz) avg=87ms (lane=41 obj=23 light=23) light_state=NONE
```

어느 모델이 시간을 먹는지 바로 보인다. 프레임률이 떨어지면 `imgsz` 를 낮추거나(416 → 320), 필요 없는 모델을 `enable_obj: false` 같은 스위치로 끄면 된다. 스위치가 꺼진 모델은 **로드 자체를 생략**해서 메모리도 아낀다 (`yolo_node.py:135-141`).

### 4.6 [4] 세그 마스크 후처리 — 신경망 출력이 차선 점이 되기까지

`_run_lane`(`yolo_node.py:317`)이 lane.pt 를 돌리면 결과가 바로 좌표로 나오는 게 아니다. **모델이 뱉은 흐릿한 마스크를 원본 크기로 키우고 → 0/1 로 딱 잘라 정하고 → 차체를 지우고 → BEV 로 펴는** 네 단계를 거친다. 이 절이 그 구간(`yolo_node.py:337-352` + `:355-358`)이다.

```
 lane.pt 추론 결과 r
   |
   |  r.boxes.cls   인스턴스별 클래스 번호 [8, 8, 6, ...]      :338
   |  r.masks.data  인스턴스별 마스크 (N, Hm, Wm)               :339
   |                 ^^^^^^^^^^^^^^^ "모델 해상도" — 원본보다 작다
   v
 [1] 원하는 클래스만 고른다 (MID=8, 켜져 있으면 dash=2)         :341-343
   |
 [2] cv2.resize 로 원본 프레임 크기(H_img x W_img)까지 확대     :349-351
   |     보간은 INTER_NEAREST
   v
 [3] m > 0.5 인 픽셀만 255 로 → 이진화 + 여러 인스턴스 합치기   :346,352
   |     binmask 한 장에 겹쳐 그리므로 차선이 두 조각으로
   |     검출돼도 자동으로 하나로 합쳐진다
   v
 [4] apply_car_mask — 가림선 아래(차체) 전부 0                  :355-356
   |
   v
 [5] bev.mask_to_bev_points(binmask, H) → xs, ys (미터)         :358
   |
   v
 Pose 하나씩 채워 z=8 로 /detect/lane 발행                      :359-368
 MID 점은 따로 보관해 lane_quality 산정에도 쓴다                :365-371
```

**[1] 왜 클래스별로 따로 모으나.** 세그 모델은 검출한 물체(인스턴스) 하나에 마스크 한 장씩을 준다. 화면에 중앙선 조각이 3개 잡히면 마스크도 3장이다. 그래서 `cls == 8` 인 것들의 번호(인덱스)를 먼저 골라내고(`sel`, `:342`), 그것들만 한 장에 겹쳐 그린다. 클래스가 다른 마스크(예: 흰 외곽선)가 섞여 들어가면 중앙선이 아닌 점이 z=8 로 발행돼 판단부가 속는다.

**[2] 왜 크기를 키워야 하나.** `r.masks.data` 는 **원본 프레임 크기가 아니라 모델이 내부에서 쓰는 해상도**로 나온다 (`yolo_node.py:339` 주석 "모델 해상도"). 우리가 가진 H(호모그래피)는 **보정된 원본 프레임 픽셀**을 입력으로 가정하고 만들어진 표이므로, 크기가 다른 마스크를 그대로 넣으면 좌표가 통째로 어긋난다. 그래서 `m.shape != (H_img, W_img)` 일 때 `cv2.resize` 로 원본 크기까지 늘린다 (`:349-351`). 보간은 여기서도 `INTER_NEAREST` 다 — 가장 가까운 픽셀 값을 그대로 복사하는 방식이라, 늘리는 과정에서 있지도 않은 중간 밝기가 생기지 않는다.

> 참고: `predict(..., retina_masks=False)` (`yolo_node.py:321`)로 두면 ultralytics 가 마스크를 원본 해상도로 되돌려 주지 않는다. 대신 우리가 **필요한 클래스만 골라서** 직접 키운다. 안 쓸 클래스까지 전부 원본 크기로 부풀리는 낭비를 피하는 선택이고, CPU 뿐인 실차에서는 이 차이가 프레임률로 돌아온다.

**[3] 이진화란.** 신경망이 뱉는 마스크 값은 0 또는 1 이 아니라 **0~1 사이의 실수**다. "이 픽셀이 차선일 것 같은 정도"라고 보면 된다. 0.92 인 픽셀도 있고 0.13 인 픽셀도 있다. 그런데 뒤에 오는 워프와 점 추출은 "차선이다/아니다"만 필요하다. 그래서 **0.5 를 문턱으로 삼아 넘으면 255, 못 넘으면 0** 으로 딱 잘라 정한다 (`binmask[m > 0.5] = 255`, `:352`). 이 "애매한 값을 두 값 중 하나로 잘라 정하는 일"이 **이진화(binarization)** 다. 문턱 0.5 는 코드에 상수로 박혀 있다.

```
   [모델이 준 마스크]              [이진화 후 binmask]
    .12 .40 .88 .95 .30            0   0  255 255  0
    .08 .55 .91 .97 .44    --->    0  255 255 255  0
    .03 .22 .61 .70 .19            0   0  255 255  0
    0~1 사이 실수                  0 또는 255 뿐
```

**[4] 왜 하필 이 순서인가.** 차체 지우기(`apply_car_mask`)는 **반드시 BEV 워프 전**에 해야 한다. 워프를 먼저 해버리면 차체 픽셀이 이미 "코앞 x≈0.1~0.2m 의 차선점"으로 둔갑한 뒤라, 그게 진짜 근거리 차선점인지 우리 범퍼인지 구분할 방법이 없어진다. 자세한 건 §6.8 이다.

**[5] 그 다음은 lib 담당.** 워프와 점 추출은 전부 `lib/bev.py` 의 검증된 함수 하나(`mask_to_bev_points`)로 넘긴다 (`:358`). 그 안에서 무슨 일이 일어나는지는 §6.6~§6.7 에 있다. 노드 쪽 코드에 좌표 계산이 흩어져 있지 않은 것은 의도된 구조다 — ROS 없이 유닛테스트할 수 있는 곳에 계산을 몰아 뒀다.

**마스크가 하나도 없으면.** `r.masks` 가 `None` 이거나 박스가 0개면 `if` 블록을 통째로 건너뛴다 (`:337`). 이때도 **빈 PoseArray 를 그대로 발행하고**, 품질은 빈 배열로 계산돼 0.0 이 나간다 (`:368-371`). "안 보이면 아무것도 안 보낸다"가 아니라 "안 보인다는 사실을 보낸다"는 쪽이다. 판단부는 이 0.0 을 보고 감속한다(§6.9).

## 5. BGR/RGB 색순서 문제 — `MODEL_WANTS_RGB`

`yolo_node.py:65` 에 이런 딕셔너리가 있다.

```python
MODEL_WANTS_RGB = {"lane": True, "obj": True, "light": False}
```

배경은 이렇다. `ultralytics` 는 numpy 배열을 입력으로 받으면 **그 배열이 BGR 순서라고 가정**한다. 그런데 예선에서 친구가 학습시킨 `lane.pt` / `best.pt` 는 학습·검증 내내 `rgb8` 배열을 **채널 스왑 없이 그대로** 넣은 채로 만들어졌다. 즉 이 모델들이 실제로 기대하는 배열은 RGB 순서다(비표준). 반면 `light.pt` 는 표준 색순서로 학습돼서 BGR 을 그대로 넣어야 맞다 (예선 `yolo_light_node.py` 의 `swap_rb=True` 주석에 근거가 남아 있다 — "legend_best.pt는 표준 색순서로 학습됨 … rgb8을 그대로 넣으면 R↔B가 뒤바뀌어 빨강↔파랑 오인").

**틀리면 어떻게 되나.** 빨강과 파랑이 통째로 뒤바뀐 영상을 모델이 보게 된다. 신호등에서는 그대로 빨강↔초록 오인으로 이어지고, 차선에서는 검출률이 눈에 띄게 떨어진다. 사람 눈에는 "좀 이상한 색" 정도지만 신경망에겐 완전히 다른 입력이다.

우리 파이프라인의 기준색은 BGR 이므로, **RGB 를 기대하는 모델만** 넣기 직전에 채널을 되뒤집는다.

```python
img = frame[:, :, ::-1] if MODEL_WANTS_RGB["lane"] else frame   # yolo_node.py:318
```

`::-1` 슬라이스는 뷰(view)라서 메모리가 연속이 아니다. **뷰**란 배열을 실제로 복사하지 않고 "읽을 때 거꾸로 읽어라"라는 지시만 붙여 놓은 상태를 말한다. 눈에 보이는 결과는 채널이 뒤집힌 배열이지만 메모리 안의 바이트 순서는 그대로라, "바이트가 한 줄로 끊김 없이 이어져 있을 것"을 요구하는 쪽에 그대로 넘기면 엉뚱하게 읽힌다. 그래서 진짜로 복사해서 한 줄로 펴 주는 `np.ascontiguousarray(img)` 로 감싸 넘긴다 (`yolo_node.py:320`). 같은 패턴이 `_run_obj`(376), `_run_light`(415)에도 있다.

`yolo_node.py:64` 에 남아 있는 TODO 는 정직한 부채 기록이다 — 재학습할 기회가 생기면 전 모델을 BGR 표준으로 통일하고 이 표를 지워야 한다.

## 6. `lib/bev.py` 완전 해설 — 카메라 캘리브레이션의 심장

이 파일은 rclpy(ROS)를 전혀 import 하지 않는 **순수 파이썬 라이브러리**다 (`bev.py:1`). 덕분에 ROS 없이 유닛테스트가 되고(`test/test_bev.py`, 테스트 함수 38개 — 파라미터화까지 세면 45케이스), `tools/bev_view.py` 같은 오프라인 도구도 같은 코드를 쓴다. **유닛테스트**는 함수 하나하나를 따로 불러서 "이 입력을 넣으면 이 답이 나와야 한다"를 자동으로 검사하는 코드다. **파라미터화**는 그 검사를 값만 바꿔가며 여러 번 돌리는 것이라, 테스트 함수는 38개인데 실제로 도는 검사는 45번이 된다. 차를 굴리지 않고도 좌표 계산이 맞는지 확인할 수 있다는 게 핵심이다. 인지의 좌표 정확도가 전부 여기 달려 있다.

### 6.1 K, D, new_K, H — 쉬운 말로

| 기호 | 정체 | 비유 |
|---|---|---|
| **K** | 카메라 내부 행렬 (fx, fy, cx, cy) | 카메라의 "시력 스펙". 초점거리와 화면 중심 |
| **D** | 왜곡 계수 | 렌즈가 "얼마나 휘게 보는지"를 적은 숫자들 |
| **new_K** | 보정 후 영상의 K | 보정된 사진의 "새 틀" |
| **H** | 호모그래피 | 비스듬히 찍은 바닥 사진을 위에서 본 것처럼 펴는 변환 |

- **K**: `fx, fy` 는 초점거리를 픽셀로 환산한 값, `cx, cy` 는 **광축**(렌즈 한가운데를 곧게 지나는 축)이 이미지에 닿는 점(대략 화면 중앙)이다. 현재 `config/camera.yaml` 값은 `fx=789.0, fy=874.6, cx=966.8, cy=540.3` (1920x1080 기준).
- **D**: `plumb_bob` 모델(일반 광각 렌즈용 표준 왜곡 수식 틀의 이름이다. §6.3 참고)에서 `[k1, k2, p1, p2, k3]` 5개. 현재 `k1=-0.374` 로 음수인데, 이건 전형적인 배럴(배불뚝이) 왜곡이다.
- **new_K**: 보정된 영상은 원본과 화각·중심이 조금 달라진다. 그 새 영상의 좌표계를 정의하는 게 new_K 다. 현재 값은 `fx=847.5, fy=939.4, cx=960, cy=540`.
- **H**: 3x3 행렬. **보정된 이미지 픽셀 (u,v) → 지면 좌표 (x 전방, y 좌측) 미터** 로 바꾼다. 기울어진 각도로 찍은 종이 사진을 반듯하게 펴는 것과 같다.

> **★ 가장 중요한 짝 관계**: H 는 "**new_K 로 보정된 픽셀**"을 입력으로 가정하고 만들어졌다.
> 그래서 **new_K 가 바뀌면 H 는 통째로 무효**다. 왜곡모델, alpha, 이미지 크기 중 하나만
> 달라져도 new_K 가 달라진다. 이 경고는 `bev.py:305-308`, `yolo_node.py:107-109` 에
> 두 번 적혀 있다.
>
> 여기 나오는 **alpha** 는 보정된 영상을 만들 때 "가장자리를 얼마나 살릴지" 정하는
> 0~1 사이 손잡이다. 왜곡을 펴면 사진 네 귀퉁이가 안쪽으로 말려 들어와 검은 여백이
> 생기는데, `alpha=0` 은 그 여백이 안 보이게 안쪽만 잘라 쓰고(화각 손해),
> `alpha=1` 은 원본 화소를 하나도 안 버리는 대신 검은 여백을 그대로 남긴다.
> 값이 달라지면 잘리는 범위가 달라지고 → new_K 가 달라지고 → H 가 무효가 된다.
> 우리 기본값은 `0.0` 이다 (§9).

### 6.2 `load_camera_config()` — 캘리브 로드와 두 개의 플래그

`bev.py:181` 의 함수다. `config/camera.yaml` 을 읽어 `K, D, H, model, new_K, image_size, car_mask_v, note` 를 담은 dict 를 돌려준다. 핵심은 **캘리브 완료 플래그가 두 개**라는 점이다 (`bev.py:11-14`, `185-195`). 여기서 **플래그(flag)** 는 참/거짓만 담는 깃발 같은 값이고, **폴백(fallback)** 은 진짜 값이 없거나 못 믿을 때 대신 쓰는 예비값을 말한다.

| 플래그 | 뜻 | False 일 때 동작 |
|---|---|---|
| `intrinsics_calibrated` | K/D 가 유효한가 | K=단위행렬, D=0 → undistort 가 패스스루 |
| `h_calibrated` | H 가 유효한가 | 예선 시뮬 폴백 H 사용 (`bev.py:49`) |

**왜 나눴나.** 실차 작업에서는 "K/D 는 임포트했는데 지면 H 는 아직 안 잡았다"가 **정상적인 중간 상태**로 자주 생긴다. 예전처럼 `calibrated` 하나로 묶으면 그 중간 상태에서 실측 K/D 까지 폴백으로 버려져 undistort 가 통째로 죽는다 (`bev.py:186-188`). 구버전 파일의 단일 키 `calibrated` 는 "둘 다"의 의미로 해석해 하위호환을 유지한다 (`resolve_calib_flags`, `bev.py:166`).

폴백이 일어난 사유는 버려지지 않고 `note` 문자열에 쌓여서(`bev.py:247-275`) 노드 기동 로그에 그대로 찍힌다 (`_log_camera_summary`, `yolo_node.py:174`). **현장에서 로그 한 줄만 보고 캘리브 상태를 판별할 수 있게** 만든 장치다. 특히 `h_calibrated=false` 인데 `intrinsics_calibrated=true` 인 조합은 "undistort 는 켜지는데 폴백 H 는 보정 이전 픽셀 기준이라 좌표계가 어긋난 상태"라고 명시적으로 경고한다 (`bev.py:269-271`).

참고로 현재 저장소의 `config/camera.yaml` 은 `intrinsics_calibrated: true`, `h_calibrated: true` 로 둘 다 완료 상태다.

### 6.3 `Undistorter` — plumb_bob 과 fisheye, 그리고 "170도 어안" 사건

`bev.py:288` 의 클래스다. 왜곡 모델이 두 가지 있다.

- `plumb_bob` (브라운-콘라디): 일반 광각 렌즈용. D 5개. **기본값** (`bev.py:71`).
- `fisheye` (등거리 어안): 진짜 어안 렌즈용. D 4개.

**왜 plumb_bob 인가 — 실측이 벤더 문서를 뒤집은 일화.** 벤더 PDF 에는 이 카메라가 "170도 어안"이라고 적혀 있었다. 그런데 실제로 재보니 **HFOV ≈ 87.2°, VFOV ≈ 64.1°** 의 평범한 광각 렌즈였다 (`bev.py:15-19`, `yolo_node.py:16`). HFOV/VFOV 는 카메라가 좌우로 / 위아래로 몇 도까지 담아내는가를 말한다(Horizontal/Vertical Field Of View). 사람 눈이 한 번에 또렷하게 보는 범위가 대략 이 정도라, 87° 는 "약간 넓은 보통 렌즈"이지 어안이 아니다. 87° 렌즈에 어안(등거리) 모델을 씌우면 파라미터가 과해져서(**과파라미터화** — 맞춰야 할 데이터에 비해 조절 손잡이가 너무 많아, 손잡이 값이 하나로 정해지지 않고 제멋대로 흔들리는 상태다) OpenCV 의 `CHECK_COND` 가 실패하거나, 보정을 해도 가장자리가 오히려 더 나빠진다. 그래서 기본 모델을 plumb_bob 으로 바꾸되, **fisheye 경로는 지우지 않고** `model` 필드로 고를 수 있게 남겼다. 카메라를 교체하거나 진짜 어안을 쓰게 될 경우를 대비한 것이다.

`model` 필드가 없거나 이상한 값이면 **D 배열의 길이로 추론**한다 — 5개면 plumb_bob, 4개면 fisheye (`resolve_distortion_model`, `bev.py:81`). 추론이 일어났다는 사실은 조용히 넘어가지 않고 `note` 에 한국어 문장으로 남는다.

**리맵 테이블을 한 번만 만들고 캐시하는 이유.** 왜곡 보정은 "결과 영상의 각 픽셀이 원본 영상의 어느 위치에서 오는가"를 미리 계산한 표(리맵 테이블, `map1/map2`)를 만들어 두고, 매 프레임은 그 표대로 값을 퍼오기만 하면 된다. 표를 만드는 `initUndistortRectifyMap` 은 1920x1080 기준 수십 ms 가 걸리는 무거운 연산이라, 프레임마다 다시 만들면 그것만으로 프레임률이 반토막 난다. 그래서 생성자에서 한 번 만들고(`bev.py:335-348`), `apply()` 는 `cv2.remap` 한 줄이다 (`bev.py:371-376`). 노드는 아예 **기동 시점에** 캘리브 해상도로 표를 만들어 둔다 (`yolo_node.py:127-129`) — 그래야 기동 로그만 보고 상태가 확정된다.

실패해도 예외를 던지지 않고 **패스스루(원본 그대로 통과)** 로 떨어진다 (`bev.py:353-355`). 대신 `enabled` 플래그를 노출해서, 호출측이 "K/D 는 유효한데 리맵 생성이 실패한" 모순 상황을 에러 로그로 남긴다 (`yolo_node.py:208-210`). 조용히 잘못 도는 것보다 시끄럽게 알리는 쪽을 택한 설계다.

### 6.5 BEV 격자 — `M_GRID` 와 상수 4개

BEV(Bird's Eye View, 조감도)는 지면을 위에서 내려다본 이미지다. 우리는 지면 좌표(미터)를 다시 **격자 이미지 픽셀**로 옮겨서 마스크를 워프한다. 그 격자를 정의하는 상수가 `bev.py:35-39` 다.

| 상수 | 값 | 뜻 |
|---|---|---|
| `BEV_RES` | 0.05 | 픽셀 하나 = 5cm |
| `BEV_X_MIN` / `BEV_X_MAX` | -2.0 / 12.0 | 전방 범위 (뒤 2m ~ 앞 12m) |
| `BEV_Y_HALF` | 5.0 | 좌우 각각 5m |
| `BEV_W` x `BEV_H` | 200 x 280 | 계산 결과 이미지 크기 |

```
        BEV 격자 (200 x 280 px, 1px = 5cm)
        y=+5m                 y=0                 y=-5m
   u=0    |---------------------|---------------------|  u=200
   v=0    +---------------------+---------------------+   x = +12.0 m (먼 곳)
          |                     |                     |
          |                     |                     |
          |          ::         |                     |
          |          ::  <- 차선 마스크가 여기 찍힌다  |
   v=200  |          ::         |                     |   x = +2.0 m
          |         [차]        |                     |
   v=280  +---------------------+---------------------+   x = -2.0 m (뒤)
                            원점(0,0) = 라이다 중심 아래 지면
        화면 위 = 멀리(+x),  화면 왼쪽 = 좌측(+y)   ← ROS REP-103
```

`M_GRID`(`bev.py:42-46`)는 이 그림을 그대로 행렬로 쓴 것이다. `u = (BEV_Y_HALF - y)/BEV_RES`, `v = (BEV_X_MAX - x)/BEV_RES` 이며, y 와 x 앞에 붙은 마이너스가 "왼쪽이 +y", "위쪽이 +x" 를 만든다.

그림 아래에 적힌 **REP-103** 은 ROS 진영이 정해 놓은 좌표계 표준 문서의 번호다. "차 기준으로 **x 는 앞, y 는 왼쪽, z 는 위**, 각도는 반시계가 +" 를 못박아 둔 것이라, 이걸 따르면 남이 만든 노드와 좌표 뜻을 맞추느라 싸울 일이 없다. 우리 `/detect/lane` 의 x, y 도 이 규칙을 따른다.

### 6.6 `mask_to_bev_points()` — 마스크에서 차선 점까지

`bev.py:494`. 딱 3줄짜리 함수인데 하는 일이 크다.

```python
H_pix2bev = M_GRID @ H          # 이미지픽셀 -> 미터 -> BEV픽셀 을 한 행렬로 합침
bev_mask  = cv2.warpPerspective(mask, H_pix2bev, (BEV_W, BEV_H), INTER_NEAREST)
return _mask_to_centerline_xy(bev_mask)
```

**워프(warp)** 는 그림 전체를 정해진 변환표대로 비틀어 다시 그리는 연산이다. `cv2.warpPerspective` 는 그중에서도 "비스듬히 본 평면을 정면에서 본 것처럼" 비트는 종류이고, 그 비트는 방법을 적어 놓은 게 H 다.

`M_GRID @ H` 로 두 변환을 **하나의 3x3 행렬로 미리 곱해두는** 게 요령이다. 이미지→미터(H)와 미터→BEV픽셀(M_GRID)을 따로 돌리면 워프를 두 번 해야 하지만, 행렬을 먼저 곱하면 `warpPerspective` 한 번으로 끝난다. 보간은 `INTER_NEAREST` 인데, 이진 마스크에 선형 보간을 쓰면 0과 255 사이의 애매한 값이 생겨서 그렇다.

여기서 **보간(interpolation)** 은 그림을 늘리거나 비틀 때 "원본에 딱 맞는 픽셀이 없는 자리"의 값을 주변에서 지어내는 일이다. 두 가지만 알면 된다. `INTER_LINEAR`(선형 보간)는 주변 픽셀들을 섞어 중간값을 만든다 — 사진에는 부드럽고 자연스럽다. `INTER_NEAREST`(최근접)는 가장 가까운 픽셀 값을 그대로 복사한다 — 계단처럼 각지지만 **원본에 없던 값이 절대 생기지 않는다**. 우리 입력은 0 아니면 255 뿐인 이진 마스크라 후자를 쓴다. 선형 보간을 쓰면 127 같은 중간값이 생겨 "차선인가 아닌가"가 다시 애매해진다.

```
 [보정된 카메라 영상]      H (호모그래피)      [BEV 격자]        중심점 추출
  +--------------+                            +-----+          x=3.2, y=+0.3
  |    \    /    |    ---- M_GRID @ H ---->   |  |  |   --->   x=3.0, y=+0.3
  |     \  /     |                            |  |  |          x=2.8, y=+0.2
  |      \/      |     원근감 제거             |  |  |          ...
  +--------------+                            +-----+       (lidar_frame, m)
   차선이 소실점으로                          차선이 평행하게
```

### 6.7 `_mask_to_centerline_xy()` — x 구간마다 점 하나만

`bev.py:425`. BEV 마스크 픽셀을 전부 좌표로 바꿔서 그대로 넘기면 안 된다. **차선은 두께가 있기 때문**이다.

```
  [그대로 넘기면]                    [bin 별 중앙값만 뽑으면]
   x=3.0 : y = 0.28 0.30 0.32          x=3.0 : y = 0.30
   x=2.9 : y = 0.27 0.29 0.31   --->   x=2.9 : y = 0.29
   x=2.8 : y = 0.26 0.28 0.30          x=2.8 : y = 0.28
   같은 x 에 점 여러 개 → 2차식 피팅이   x 하나에 점 하나 → 깔끔한 곡선
   두께 노이즈에 흔들려 "와리가리"
```

동작은 이렇다. 전방 x 를 `LANE_CENTERLINE_BIN_M = 0.18` m 구간으로 자르고(`bev.py:442`), 각 구간에서 점이 2개 이상일 때만 **x 와 y 의 중앙값(median)** 하나를 뽑는다 (`bev.py:445-450`). 중앙값은 값들을 크기순으로 줄 세웠을 때 딱 한가운데 오는 값이다. 평균이 아니라 중앙값인 이유는 튄 점(**outlier**, 다른 것들과 혼자 동떨어진 값) 하나에 끌려가지 않기 위해서다. 예를 들어 y 가 `0.28, 0.30, 0.32, 5.00` 이면 평균은 1.47 로 엉뚱한 곳을 가리키지만 중앙값은 0.31 로 멀쩡하다. 마지막에 x 오름차순 정렬해서 돌려준다 (`bev.py:456`).

앞단에는 `LANE_PIX_SUBSAMPLE = 3`(`bev.py:55`)도 있다. 마스크 픽셀을 3개 중 1개만 쓴다는 뜻으로(**서브샘플링** — 촘촘한 데이터에서 일정 간격으로 골라서만 쓰는 것이다), 정확도 손해는 거의 없고 계산량은 1/3 이 된다. 차선 마스크는 어차피 수천 픽셀이 뭉쳐 있어서 3개 중 1개만 써도 중앙값은 거의 안 바뀐다.

이 로직은 새로 만든 게 아니라 예선 `lane_detect_node._mask_to_centerline_xy` **원문을 그대로 이식**한 것이다 (`bev.py:430`). 이미 시뮬에서 검증된 코드를 손대지 않는다는 원칙이다.

### 6.8 `car_mask_row` / `apply_car_mask` — 차체를 잘라내기 (2026-07-31 추가)

카메라가 아래를 보고 있으니 화면 맨 아래에는 **우리 차의 라이다 원통과 범퍼**가 찍힌다. 이건 지면이 아니다. 그런데 H 는 "화면에 보이는 건 전부 지면"이라고 가정하고 계산하므로, 차체 픽셀이 차선 마스크에 들어가면 **x ≈ 0.1~0.2 m 위치의 가짜 차선점**으로 변환된다 (`bev.py:146-150`, `yolo_node.py:130-131`). 코앞에 차선이 있다고 착각한 차는 그쪽으로 조향을 꺾는다.

```
        [보정된 카메라 영상 1080 높이]
   v=0   +--------------------------------+
         |         하늘 / 배경             |
         |                                |
         |   ///  차선  ///               |   <- 진짜 지면
         |                                |
 v=951 --+================================+--  car_mask_v (가림선)
         |  [라이다 원통]   [범퍼]         |   <- 이 아래는 전부 0 으로 지움
   v=1080+--------------------------------+
```

- 값은 `config/camera.yaml` 의 `car_mask_v` 에 저장된다. 현재 값은 **951.43** (1080 높이 기준).
- 정하는 방법은 `tools/bev_view.py` 를 띄우고 **`m` 키를 누른 뒤 카메라 화면에서 가림선 위치를 클릭, `s` 키로 저장**이다 (도구 헤더 주석에 사용법이 있다).
- `car_mask_row()`(`bev.py:460`)는 이 값을 **현재 프레임 높이에 맞춰 비율 환산**한다. 환산하지 않으면 640x480 프레임에서 v=951 이 화면 밖이라 마스킹이 통째로 무효가 된다 (`bev.py:464-465`).
- `apply_car_mask()`(`bev.py:480`)는 `mask[row:, :] = 0` 으로 잘라낸다. 호출은 **BEV 워프 전에** 이뤄진다 (`yolo_node.py:355-356`) — 워프 후에는 이미 가짜 점이 되어 구분이 안 되기 때문이다.
- 값이 없으면 노드가 기동 시 경고를 띄운다 (`yolo_node.py:201-205`). 조용히 넘어가지 않는다.

물체 검출(`_run_obj`)에서도 같은 가림선을 쓴다. 다만 처리가 다르다 (`yolo_node.py:397-403`).

- 박스 **전체**가 가림선 아래면 → 차체를 물체로 오인한 것이므로 **버린다**.
- 박스의 **아랫변만** 가림선에 걸치면 → 버리지 않고 `y2` 를 가림선까지 **당긴다**. 범퍼 코앞의 진짜 장애물을 지워버리면 안 되므로, "가장 가까운 거리"로 읽히도록 보수적으로 클램프하는 것이다. **클램프(clamp)** 는 값이 정해진 한계를 넘지 못하게 그 한계에 눌러 붙이는 것을 말한다. 여기서는 `y2` 가 가림선보다 아래로 내려가려 하면 가림선 값으로 잡아 둔다.

### 6.9 `lane_quality()` — 차선 인식이 얼마나 믿을 만한가

`bev.py:514`. 0~1 점수를 만든다. 공식은 단순하다.

```
 점수 = clip(점 개수 / 20, 0, 1)  x  clip(x스팬(m) / 3.0, 0, 1)
```

공식에 나오는 `clip(값, 0, 1)` 은 앞의 클램프와 같은 뜻이다 — 0보다 작으면 0으로, 1보다 크면 1로 잘라 버린다. 그래서 점이 20개든 200개든 그 항은 1.0 을 넘지 않는다.

- 점 개수(`LANE_QUALITY_GOOD_POINTS = 20`): 차선 점이 몇 개나 잡혔나.
- x 스팬(`LANE_QUALITY_GOOD_SPAN_M = 3.0`): 가장 먼 점과 가까운 점의 전방 거리 차이. **얼마나 멀리까지 이어져 보이나.** **스팬(span)** 은 뻗어 있는 길이를 뜻하는 말이다.

둘을 **곱하는** 게 핵심이다. 점이 30개라도 전부 코앞 50cm 안에 몰려 있으면 곡선을 못 그리므로 점수가 낮아야 한다. 반대로 멀리까지 이어져도 점이 3개뿐이면 역시 못 믿는다. 어느 한쪽이 0 이면 전체가 0 이다.

품질은 **주행 기준선인 MID(z=8) 점만으로** 산정한다 (`yolo_node.py:369-371`). 이 값을 `path_planner_node` 가 받아 `lane_quality_min: 0.3` 미만이면 `low_quality_speed_cap: 7.0` 으로 감속한다 (`config/tuning.yaml:32-33`). **안 보이면 천천히 간다**는 아주 상식적인 안전장치다.

## 7. 발행 토픽 계약 (판단부와의 인터페이스)

| 토픽 | 타입 | frame_id | 내용 |
|---|---|---|---|
| `/detect/lane` | PoseArray | `lidar_frame` | x,y = 지면 미터, z = 클래스(8=MID, 16=DASH) |
| `/detect/lane_quality` | Float32 | — | 0~1 |
| `/detect/objects` | PoseArray | `usb_cam_front` | x = bbox 중심 u(px), y = bbox 하단 v(px), z = best.pt 클래스 |
| `/detect/traffic_light` | String | — | `GREEN` / `RED` / `NONE` |

표의 낱말 둘. **타입**은 그 토픽에 흐르는 메시지의 정해진 모양이다. `PoseArray` 는 (x, y, z) 자세 여러 개를 한 묶음으로 보내는 그릇이고, `Float32` 는 실수 하나, `String` 은 글자 하나다. **frame_id** 는 "이 좌표가 어느 기준점에서 잰 것인가"를 메시지에 같이 적어두는 칸이다. `lidar_frame` 이면 라이다 회전중심 기준, `usb_cam_front` 면 앞 카메라 기준이라는 뜻이고, 이게 없으면 받는 쪽이 숫자만 보고 어디를 가리키는지 알 수가 없다.

`/detect/objects` 가 **미터가 아니라 픽셀**인 점을 꼭 기억해야 한다. 카메라만으로는 거리를 못 재므로, "박스 아랫변 v 가 클수록 가깝다"는 대리 지표를 주고 **거리 판단은 planner 몫**으로 넘긴 설계다 (`yolo_node.py:20`). 예선의 `events_raw` 방식(x,y=0으로 비워 보내던 것)은 폐기했다.

**신호등 디바운스.** **디바운스(debounce)** 는 원래 전기 스위치 용어다. 스위치를 한 번 눌러도 접점이 아주 짧은 순간 여러 번 잘게 튀어서(bounce) "눌렸다 떼졌다"가 수십 번 감지되는데, 그걸 걸러내고 "한 번 눌린 것"으로 만드는 처리를 디바운스라고 한다. 여기서는 **같은 판정이 N번 연속 나올 때만 진짜로 인정한다**는 뜻으로 쓴다.

`_run_light`(`yolo_node.py:414`)는 초록/빨강 중 확신도가 높은 쪽을 고르고(동률이면 GREEN 우선, `yolo_node.py:430`), 그 판정이 `light_debounce_n = 3` 프레임 연속 같을 때만 확정 상태를 갱신한다 (`yolo_node.py:436-442`). 한 프레임 튄 오검출로 급정거하는 걸 막기 위해서다.

```
 프레임별 raw 판정   G  G  R  G  G  G  G  R  R  R  R
 연속 카운트         1  2  1  1  2  3  4  1  2  3  4
 확정 상태(발행)     N  N  N  N  N  G  G  G  G  R  R
                                    ^^ 3번 연속돼야 바뀐다
```

그리고 **확정 상태는 매 프레임 발행**한다 — 상태가 바뀔 때만 한 번 발행하는 "래치" 방식은 구독자가 그 한 번을 놓치면 영영 모르게 되므로 금지다 ("재도입 금지 버그 4", `yolo_node.py:444`). **래치(latch)** 는 한 번 걸리면 그대로 걸려 있는 걸쇠를 말한다. 메시지에 쓰면 "상태가 바뀌는 순간에만 한 번 알리고, 그 뒤로는 조용히 있는" 방식이 된다. 발행보다 늦게 켜진 노드나 그 한 프레임을 놓친 노드는 신호등이 초록인 걸 영원히 모르게 되므로, 초당 11번이 낭비처럼 보여도 매번 다시 알려주는 쪽을 택했다.

## 8. 디버그 뷰어 — `yolo_lane_viewer_node.py`

인지 결과를 눈으로 확인하는 창이다. 실행은 주행 launch 와 **분리**돼 있다. 규정상 `drive.launch.py` 에 뷰어를 넣을 수 없기 때문이다 (`launch/viewer.launch.py` 헤더).

```
ros2 launch track_drive viewer.launch.py      # 또는
ros2 run track_drive yolo_lane_viewer
```

600x840 픽셀 창에 **전방 0~12m, 좌우 ±5m** 를 그린다 (`yolo_lane_viewer_node.py:26-31`).

```
  +-------------------------------------------+
  | MID(8): 23    <- 클래스별 검출 개수 범례   |
  | DASH(16): 0                               |
  | LANE(6): 0                                |
  | CHILD(2): 0                               |
  | TARGET path (magenta)                     |
  | offset: +0.35m (L)   <- 명령 오프셋        |
  |                                           |
  |        .  .   :   .  .                    |  <- 회색 = 라이다 raw 점
  |          :::  |  :::                      |  <- 노랑 = MID 차선점
  |          ::: (|) :::                      |  <- 마젠타 굵은선 = center_path
  |   ------ 2m 그리드 ------                 |
  |              (o)  <- 빨강 = 차 (원점)      |
  +-------------------------------------------+
```

보이는 것과 소스 위치는 이렇다.

- 클래스별 색 구분 점: `CLS_STYLE`(`:34-39`) — 8=노랑, 16=주황, 6=흰색, 2=회색.
- 라이다 `/scan` 원본 점(회색): `:164-167`. **차선과 라이다가 같은 좌표계에서 겹쳐 보이는지**를 확인하는 용도로, 캘리브 검증에 제일 유용하다.
- `/center_path` 최종 목표 경로(굵은 마젠타): `:187`.
- 점구름에서 중앙선/좌우 흰선을 각각 2차 피팅하고 ±1.5m 오프셋까지 그리는 `_draw_base_fits`(`:123`).
- `_commanded_offset`(`:107`): 목표 경로와 검출 중앙선의 x=2.0m 지점 가로 차이 = 실제로 적용 중인 오프셋. 좌(+)/우(-)로 표시된다.

카메라 원본·BEV·좌표 측정이 필요하면 뷰어가 아니라 `tools/bev_view.py` 를 쓴다. 마우스를 올리면 그 지점의 (x, y) 가 실시간으로 뜨고, 두 점을 클릭하면 실제 거리(mm)가 나온다. 45cm 자를 바닥에 놓고 재면 축척 검증이 된다 (도구 헤더 주석).

## 9. 실행과 튜닝 파라미터

주행은 `ros2 launch track_drive drive.launch.py` 하나로 뜨고, 그 안에서 `yolo` 실행파일이 이 노드다 (`launch/drive.launch.py`, `setup.py:32`). 파라미터는 `config/tuning.yaml` 의 `yolo_node:` 블록에서 온다.

| 파라미터 | 기본값 | 의미 |
|---|---|---|
| `imgsz` | 416 | 추론 입력 해상도. 낮추면 빨라지고 작은 물체를 놓친다 |
| `conf_lane` / `conf_obj` | 0.25 | 검출 확신도 문턱 |
| `conf_light` | 0.4 | 신호등만 높게 — 오인 비용이 크다 |
| `light_debounce_n` | 3 | 연속 동일 판정 프레임 수 |
| `enable_lane/obj/light` | true | 끄면 모델 로드 자체를 생략 |
| `enable_child_dash` | false | z=16 발행 루프는 준비만 됨 |
| `device` | "cpu" | 실차는 CUDA 없음 |
| `undistort_alpha` | 0.0 | 0=검은 여백 없이 크롭, 1=원본 화소 전부 보존 |

주의: 위 표에서 **`undistort_alpha` 와 모델 경로(`lane_model_path` 등), `camera_yaml` 은 현재 `tuning.yaml` 에 적혀 있지 않다.** 코드의 `declare_parameter` 기본값(`yolo_node.py:103-110`, alpha 는 `bev.UNDISTORT_ALPHA_DEFAULT = 0.0`)이 그대로 쓰인다. 바꾸려면 `tuning.yaml` 의 `yolo_node:` 블록에 키를 새로 추가하면 된다.

센서 쪽은 `sensors.launch.py` 가 띄운다. 카메라 해상도는 `1920x1080`, `pixel_format: mjpeg2rgb`(→ `/image_raw` 인코딩 `rgb8`), 30fps 다. MJPG 를 쓰는 이유는 이 카메라가 **YUYV 1920x1080 에서는 6fps 밖에 안 나오기 때문**이다(`v4l2-ctl --list-formats-ext` 실측, `sensors.launch.py` 주석). **YUYV** 는 압축을 전혀 안 한 생 화소를 그대로 USB 로 흘려보내는 방식이라 데이터량이 크고, USB 대역폭이 먼저 막혀서 초당 장수가 안 나온다. **MJPG**(Motion JPEG)는 프레임 한 장 한 장을 JPEG 사진으로 압축해서 보내는 방식이라 같은 선으로 훨씬 많은 장을 보낼 수 있다. 대신 받는 쪽에서 압축을 푸는 CPU 비용이 든다(`mjpeg2rgb` 가 그 일이다). 그리고 이 해상도는 `config/camera.yaml` 의 `image_width/height` 와 **반드시 같아야 한다** — 다르면 new_K 가 달라져 H 가 무효다.

현재 `config/camera.yaml` 의 캘리브 근거도 파일 안에 기록돼 있다.

- `h_source`: `tools/ground_fit.py` 물리값 수동 튜닝.
- `h_phys`: 카메라 높이 `0.2 m`, 내림각(pitch) `7.24°`, roll `-1.6°`, yaw `-0.2°`, 격자 간격 `0.4533 m`.
  (**pitch / roll / yaw** 는 카메라가 어느 쪽으로 얼마나 돌아가 있는지를 세 방향으로 나눠 적은 것이다. pitch 는 고개를 위아래로 끄덕이는 각도라 여기선 "얼마나 아래를 보나"이고, roll 은 고개를 옆으로 갸웃하는 각도, yaw 는 좌우로 고개를 돌린 각도다. roll 이 -1.6° 라는 건 카메라가 아주 살짝 기울어 붙어 있다는 뜻이다.)
- `intrinsics_source`: 640x480 캘리브를 1920x1080 으로 환산(배율 1.9999, 잘림 원점 (319.6, 52.8) ORB 정합). D 는 정규화 좌표 기준이라 해상도가 바뀌어도 불변이다.
  (**ORB 정합**은 두 사진에서 눈에 띄는 모서리 점들을 자동으로 찾아 서로 짝지어 "이 사진과 저 사진이 얼마나 어긋나 있는가"를 계산하는 방법이다. ORB 는 그 점을 찾는 알고리즘 이름이다. 여기서는 640x480 으로 찍힌 화면이 1920x1080 화면의 어느 위치에 해당하는지를 이 방법으로 알아냈다는 뜻이다.
  **정규화 좌표**는 픽셀 단위가 아니라 초점거리로 나눠 0 근처의 비율로 환산해 둔 좌표다. 비율이라 해상도가 두 배가 되든 반이 되든 값이 그대로여서, D(왜곡 계수)는 해상도를 바꿔도 다시 잴 필요가 없다. 반대로 K 는 픽셀 단위라 해상도가 바뀌면 같이 환산해야 한다.)
- `h_lidar_offset_x: 0.1` — 좌표 원점이 라이다 회전중심 기준임을 반영한 값.

## 10. 읽는 사람이 알아둬야 할 주의사항 (코드에서 확인된 것)

1. **`/detect/lane` 은 현재 MID(z=8)만 나온다.** `_run_lane` 의 발행 대상은 `targets = [(SEG_MID, Z_MID)]` 이고, dash(z=16)는 `enable_child_dash` 가 켜져야 추가된다 (`yolo_node.py:329-331`). 그런데 소비측인 `lane_planner.py:43` 은 흰선(`WHITE_CLS_IDS = {6, 2}`)도 받을 준비가 돼 있고 뷰어도 흰선을 그린다. **즉 흰 외곽선 경로는 코드만 있고 데이터가 안 흐른다.** 흰선을 쓰려면 `targets` 에 lane.pt cls 6 을 추가해야 한다.
2. **dash 클래스 번호는 미확인 상태다.** `SEG_CHILD_DASH = 2` 옆에 "클래스 id 는 lane.pt 재확인 필요"라는 주석이 있는데(`yolo_node.py:69`), 실제 lane.pt 의 cls 2 는 `CHILD_LANE` 이다. 이걸 z=16(노란 점선)으로 발행하면 판단부는 점선으로 해석한다. `enable_child_dash` 를 켜기 전에 반드시 확인해야 한다.
3. **`light.pt` 는 사실 segment 모델이다.** 코드는 박스와 확신도만 쓰므로 동작에는 문제가 없지만, 세그 마스크 계산 비용을 그냥 버리고 있는 셈이다. 프레임률을 더 짜내야 하면 검토 대상이다.
4. **`yolo_node.py:6` 의 헤더 주석이 낡았다.** "640x480 ~29.8Hz, yuyv2rgb"로 적혀 있지만 실제 `sensors.launch.py` 와 `camera.yaml` 은 1920x1080 / mjpeg2rgb 다. 코드 동작은 yaml 을 따르므로 문제없지만, 주석만 보고 판단하면 안 된다.
5. **`check_new_K_match` 는 만능이 아니다.** 현재 `camera.yaml` 에 `new_K` 가 명시돼 있어서 런타임이 그 값을 그대로 쓰므로(`bev.py:345-346`), 이 대조는 항상 통과한다. 실제로 H 를 무효로 만들 수 있는 건 **프레임 해상도가 달라지는 경우**이며, 그건 `yolo_node.py:267-276` 의 별도 경고가 잡는다. `alpha` 파라미터를 바꿔도 new_K 가 yaml 값으로 고정이라 조용히 넘어간다는 점을 알고 있어야 한다.
