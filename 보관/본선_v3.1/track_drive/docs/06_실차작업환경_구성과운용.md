# 06. 실차 작업환경 구성과 운용 — "차에 붙어서 일하는 법"

이 문서는 **본선 실차(Xycar) 앞에 앉아서 실제로 손을 움직일 때 필요한 것 전부**를 다룬다.
차에 뭐가 달려 있고, 어떻게 접속하고, 코드를 어디서 고쳐서 어떻게 차에 올리고,
어떤 순서로 켜고, 무엇이 보이면 정상이고, 뭘 하면 차가 망가지는지를 순서대로 적었다.
알고리즘 설명은 다른 문서(01~05)에 있다. 여기는 **손과 발**에 대한 문서다.

읽는 순서는 위에서 아래가 맞다. 다만 급할 때는 이렇게 쓰면 된다.

- 지금 차를 켜고 주행까지 가야 한다 → **7장 점검 체크리스트**
- 뭔가 안 된다 → **9장 자주 나는 문제와 해결**
- 절대 하면 안 되는 것 → **8장 안전 수칙** (이건 한 번은 통독할 것)

## 0. 이 문서에 나오는 용어

이 문서에는 ROS·카메라·모터 쪽 전문용어가 섞여 나온다. 아래 표는 **이 문서에서 실제로
쓰인 것만** 모은 것이다. 본문에서 처음 나오는 자리에도 한 번씩 풀어 놨으니, 여기서는
대충 감만 잡고 넘어가도 된다. 막히면 이 표로 돌아오면 된다.

(표가 끝난 다음의 "0. 전체 그림 한 장" 부터가 원래 본문이다. 기존 절 번호는 그대로 뒀다.)

## 1. 하드웨어 구성 — 차에 뭐가 달려 있나

### 1.1 한 문단 요약

차는 1/10 크기 RC 카 형태의 Xycar 다. 위쪽에 **USB 카메라**, 그 앞아래에 **2D 라이다**,
본체 안에 **IMU**(자세 센서)와 **초음파 센서 8개**, 바퀴 쪽에 **VESC 모터 컨트롤러**
(모터와 서보에 전류를 실제로 넣어 주는 제어보드. 자세히는 1.3절)가 있다.
계산은 차에 얹힌 리눅스 PC 가 하고, 우리 코드는 전부 여기서 돈다.
모터만 예외적으로 옛날 ROS1 **도커 컨테이너**(docker container, 다른 버전의 리눅스 환경을
통째로 상자 하나에 담아 격리해서 돌리는 방식. 여기서는 ROS1 시절에 만들어진 모터
소프트웨어를 고치지 않고 그대로 쓰려고 상자째 얹어 뒀다)를 거쳐 나간다(8.3절).

### 1.2 물리 배치

```
       옆에서 본 모습 (차 앞쪽 = 오른쪽)

                            ┌──────────┐
                            │  카메라   │  지면에서 0.20 m
                            └────┬─────┘  아래로 7.24° 기울임
                       ┌─────────┴────────┐
                       │     2D 라이다     │  카메라보다 0.10 m 앞
                       └─────────┬────────┘
        ┌────────────────────────┴───────────────┐
        │       본체 PC · 배터리 · VESC · IMU      │
        └───┬────────────────────────────────┬───┘
            ●                                ●
   ═════════╧════════════════════════════════╧═══════════════ 지면
          뒷바퀴                            앞바퀴
                                              ▲
                                    좌표 원점 (x=0, y=0)
                                    = 라이다 회전중심에서 지면으로
                                      수직으로 내린 점
```

숫자의 출처는 전부 `config/camera.yaml` 이다. 추측이 아니라 캘리브 결과다.

| 항목 | 값 | 출처 |
|---|---|---|
| 카메라 높이 | 0.20 m | camera.yaml:49 (`h_phys.height`) |
| 카메라 내림각(pitch) | 7.24° | camera.yaml:51 |
| 카메라 좌우틀어짐(yaw) | −0.20° | camera.yaml:54 |
| 카메라 기울어짐(roll) | −1.60° | camera.yaml:52 |
| 라이다가 카메라보다 앞선 거리 | 0.10 m | camera.yaml:39 (`h_lidar_offset_x`) |

용어를 풀면 이렇다.

- **pitch(내림각)** = 카메라가 얼마나 고개를 숙였나. 7.24° 는 거의 수평에 가깝게
  살짝 숙인 상태다.
- **yaw(좌우틀어짐)** = 카메라가 정면에서 좌우로 얼마나 돌아갔나.
- **roll(기울어짐)** = 카메라가 시계/반시계로 얼마나 갸우뚱한가. 사진이 삐뚤어져 보이는 그것.

**좌표계는 ROS 표준(REP-103)** 을 따른다. REP-103 은 ROS 쪽에서 "좌표축 방향과 단위를
이렇게 쓰자"고 정해 둔 표준 문서의 번호다. 이걸 지키면 남의 코드·도구와 축이 안 엇갈린다.
원점에서 **x 는 앞쪽이 +, y 는 왼쪽이 +**,
단위는 미터다. 코드 전체가 이 규약 하나로 통일돼 있다(`tools/bev_view.py:5-8` 에 명문화).

### 1.3 센서와 토픽

"토픽(topic)"은 ROS 에서 데이터가 흘러다니는 **이름 붙은 배관**이다.
센서 노드가 배관에 데이터를 흘리면(publish, 발행), 우리 노드가 그 배관을 열어
받는다(subscribe, 구독). 여기서 **노드(node)** 는 "ROS 위에서 도는 프로그램 한 개"를
말한다 — 카메라 노드, 주행 노드처럼 하나가 한 가지 일을 맡는다.
아래 표의 "형식" 칸에 있는 `Image`, `LaserScan`, `Float32MultiArray` 같은 이름은
ROS 가 미리 정해 둔 **메시지 상자 규격**이다. 보내는 쪽과 받는 쪽이 같은 규격을 써야 통한다.

| 센서 | 토픽 | 형식 / 주기 |
|---|---|---|
| USB 카메라 | `/image_raw` | Image, rgb8, 1920×1080, 30 fps |
| 2D 라이다 | `/scan` | LaserScan, 500빔, 약 9.7 Hz |
| IMU | `/imu` | Imu(쿼터니언+각속도+가속도), 35 Hz |
| 초음파 | `/xycar_ultrasonic` | Int32MultiArray 8개 값, 24 Hz |
| 모터 명령 | `/xycar_motor` | Float32MultiArray `[angle, speed]` |
| VESC 텔레메트리 | `/vesc/state` | Float32MultiArray 6개 값 |

보충 설명:

- **IMU 의 `쿼터니언`** 은 차가 지금 어느 쪽을 보고 얼마나 기울었는지(3차원 회전)를
  **숫자 4개로** 나타내는 방식이다. 각도 3개로 쓰는 방식보다 계산이 안정적이라
  로봇 쪽에서는 이게 표준이다. 우리는 이걸 다시 각도(yaw)로 풀어서 쓴다.
- **`/image_raw` 는 `rgb8`** 이다. `rgb8` 은 화소 하나를 빨강·초록·파랑 1바이트씩으로
  적어 둔 형식이라는 뜻이다. `pixel_format:=mjpeg2rgb` 로 띄우기 때문이다
  (`launch/sensors.launch.py:50`). 우리 코드는 내부적으로 BGR(같은 색 정보를
  파랑·초록·빨강 순서로 늘어놓은 것. OpenCV 의 기본 순서다)로 통일해 쓰므로
  `lib/preprocess.image_msg_to_bgr` 가 변환을 맡는다. 순서를 안 맞추면 빨간 신호등이
  파랗게 보이는 식으로 색이 뒤집힌다.
- **`/scan` 은 BEST_EFFORT QoS** 다. **QoS(Quality of Service)** 는 그 배관의 **배달 규칙**
  이라고 보면 된다. 등기우편처럼 "반드시 도착할 때까지 다시 보낸다"(RELIABLE)로 할지,
  일반우편처럼 "빠르게 보내되 놓친 건 다시 안 보낸다"(BEST_EFFORT)로 할지를 고르는 설정이다.
  센서 데이터는 어차피 다음 것이 곧 오므로 후자를 쓴다.
  쉽게 말해 "놓쳐도 재전송 안 하는" 배관이라,
  구독할 때 반드시 `qos_profile_sensor_data` 를 써야 데이터가 들어온다.
  ★ 여기서 중요한 건 **보내는 쪽과 받는 쪽의 규칙이 맞아야 연결이 성립한다**는 점이다.
  안 그러면 토픽은 보이는데 콜백이 한 번도 안 불린다. 우리 코드는 전부 맞춰져 있다
  (예: `path_planner_node.py:337`).
- **초음파는 현재 코드에서 쓰지 않는다.** 센서는 정상 동작하지만 v3.1 파이프라인
  어디에서도 구독하지 않는다(저장소 전체 grep 결과 참조 0건). 나중에 후방/근접
  안전용으로 붙일 여지로 남아 있다.
- **VESC** 는 모터를 실제로 돌리는 컨트롤러다. 전압·전류·회전수(eRPM)·주행거리를
  되돌려 주는데, 그게 `/vesc/state` 다. 이 값은 도커 안의 **릴레이**(relay, 받은 메시지를
  형식만 바꿔 다시 내보내는 중계 프로그램)가 변환해서 내보낸다
  (`ros1_docker/vesc_relay.py:8-10`).
  여기서 **eRPM(electrical RPM)** 은 바퀴의 회전수가 아니라 **모터 내부의 전기적 회전수**다.
  모터 안에 자석 극이 여러 쌍 있어서 실제 회전 한 바퀴에 전기적으로는 여러 바퀴를 도는 셈이라
  숫자가 크게 나온다. 이 차는 실측으로 **eRPM = 4614 × (m/s)** 관계라, 이 값을 나눠서
  속도를 역산한다(`config/car.yaml:49` `erpm_per_ms: 4614.0`).

### 1.4 ★ 경고 — 카메라 마운트는 한 번 맞췄으면 절대 건드리지 마라

카메라는 마운트 위에서 **좌우로 돌아간다**. 이게 이 프로젝트에서 가장 조용하고
가장 치명적인 사고 원인이다.

왜 치명적인가를 풀어서 쓰면 이렇다.
우리는 카메라 사진의 픽셀을 "지면 위 몇 미터 앞, 몇 미터 왼쪽"으로 바꾸는
**호모그래피(Homography, H)** 라는 3×3 행렬을 쓴다. 호모그래피는 비스듬히 찍은
바닥 사진을 **위에서 내려다본 것처럼 펴주는 변환**이다. 기울여 찍은 종이 사진을
반듯하게 펴는 것과 같다. "3×3 행렬"이라고 하면 어렵게 들리지만, **숫자 9개짜리 변환표**
하나라고 보면 된다. 픽셀 좌표를 이 표에 넣으면 지면 좌표(m)가 나온다.

그렇게 펴 놓은 그림을 **BEV(Bird's Eye View, 새가 위에서 내려다본 시점의 그림)** 라고
부른다. 이 문서에서 "BEV" 라고 하면 전부 이걸 말한다 — 카메라 사진을 H 로 펴서
**바닥을 지도처럼 위에서 본 그림**. 차선이 실제로 곧고 나란하면 BEV 에서도 곧고 나란하게
보여야 하고, 그렇지 않으면 H 가 안 맞는 것이다. 그래서 BEV 는 캘리브가 맞았는지를
눈으로 확인하는 가장 빠른 방법이기도 하다(7장 6단계).

그런데 이 행렬은 **"카메라가 지금 이 위치에서 이 각도로 보고 있다"는 전제** 위에
계산돼 있다(camera.yaml:41-54 의 `h_phys` 가 바로 그 전제다). 마운트를 조금만 돌리면
그 전제가 깨지고, **차선 위치·장애물 거리·정지선 판정이 전부 어긋난다.**
게다가 화면은 멀쩡해 보인다. 사진은 여전히 잘 나오니까. 그래서 알아채기가 어렵다.

지켜야 할 것:

1. 캘리브가 끝난 뒤에는 **카메라 마운트 나사를 풀지 않는다.**
2. 차를 옮기거나 부딪혔으면 **BEV 로 한 번 확인한다** (7장 6단계).
3. 부득이 돌렸다면 **캘리브를 다시 해야 한다.** `tools/cam_modes.py` 의 조준 도우미가
   도움이 된다 — 화면 아래 라이다 원통을 찾아 "중심에서 몇 % 벗어났는지"를 실시간으로
   띄워준다. 이 값이 0 에 가까워지도록 카메라를 돌리면 좌우 정렬이 끝난다
   (`tools/cam_modes.py:205-219`). 다만 이건 **좌우 정렬만** 잡아주는 것이고,
   높이·내림각까지 맞추려면 `tools/ground_fit.py` 로 H 를 다시 잡아야 한다.

## 2. 접속 — 차에 들어가는 법

### 2.1 SSH

**SSH(Secure Shell)** 는 다른 컴퓨터의 명령줄에 원격으로 들어가는 통로다. 아래 명령을
치면 그 다음부터 내 터미널에 찍는 명령이 **차 PC 에서** 실행된다.

```bash
ssh xytron@10.42.0.1
# 비밀번호: xytron
```

> **비밀번호 주의** — `xytron` 은 Xycar 출고 기본 비밀번호다. 이 저장소가 공개될 수
> 있으므로 여기 적어 두되, **대회가 끝나면 반드시 변경**할 것. 대회 기간에는 키 인증이
> 설정돼 있어 비밀번호 없이도 들어간다(`~/_deploy_car.sh` 가 `ssh -o BatchMode=yes`,
> 즉 "비밀번호 물어보면 그냥 실패해라" 모드로 도는데 정상 동작한다 = 키 인증이 살아 있다는 뜻).

### 2.2 네트워크 구조

`10.42.0.1` 이라는 주소가 힌트다. 리눅스 NetworkManager 가 **"이 컴퓨터의 인터넷을
다른 컴퓨터와 공유"** 모드로 동작할 때 기본으로 쓰는 대역이 `10.42.0.0/24` 이고,
공유하는 쪽(=여기서는 차)이 `10.42.0.1` 을 가져간다. 즉 **차가 네트워크의 주인**이고
노트북이 그 밑으로 들어가는 구조다.

실제 구성이 궁금하면 차에서 확인할 수 있다(노트북 홈에 점검 스크립트가 있다):

```bash
ssh xytron@10.42.0.1 'bash -s' < ~/_car_net.sh
```

이 스크립트는 인터페이스/IP, 게이트웨이, 인터넷 도달 여부, WiFi 가 핫스팟인지
클라이언트인지, 그리고 전원이 배터리인지 어댑터인지까지 한 번에 찍어 준다.

**대회장에서는 이 점을 기억할 것** — 차가 자기 네트워크를 만들고 있다면 인터넷은
안 될 수 있다. `pip install` 같은 건 미리 다 끝내 놓고 가야 한다.

### 2.3 GUI 도구를 원격에서 쓰기

캘리브 도구와 뷰어는 전부 **OpenCV 창**을 띄운다. 원격에서 창을 보려면 세 가지 방법이 있다.

**(a) X11 포워딩** — SSH 가 화면을 노트북으로 실어 나른다.

> **X11 이 뭔가** — 리눅스에서 창을 그리는 방식의 이름이다. 프로그램이 직접 화면에
> 그리는 게 아니라, "여기에 이런 창을 그려 달라"고 **화면 담당(X 서버)에게 부탁**하는
> 구조다. 부탁하는 쪽과 그리는 쪽이 분리돼 있으니, 그 부탁을 네트워크 너머로 보낼 수도
> 있다. 그게 **포워딩**이다. 즉 계산은 차에서 하고 창은 내 노트북에 뜬다.
> 창을 어디에 그릴지는 `DISPLAY` 라는 환경변수에 적혀 있다.

```bash
ssh -X xytron@10.42.0.1        # 또는 신뢰 모드: ssh -Y
# 접속 후
echo $DISPLAY                  # localhost:10.0 같은 값이 나와야 정상
```

`DISPLAY` 가 비어 있으면 창이 안 뜬다. 우리 도구는 그걸 미리 검사해서 친절히 죽는다
(`tools/bev_check.py:697-698` — "표시할 X11 디스플레이가 없다"). 여기에는 배경이 있다:
OpenCV 파이썬 패키지의 화면 표시(HighGUI = OpenCV 안에 들어 있는 간단한 창 띄우기 기능)에는
Qt(창을 그리는 라이브러리) 의 **xcb 플러그인만** 들어 있어서
X11 이 필요하다. Wayland 는 X11 을 대체하려고 나온 **새 창 관리 방식**이고,
WSLg 처럼 Wayland 만 살아 있는 환경에서 `imshow` 를 부르면 Qt 가
플러그인을 못 찾고 죽는다. 그래서 `WAYLAND_DISPLAY` 는 인정하지 않고 `DISPLAY` 만 본다
(`tools/bev_check.py:691-696` 주석).

**(b) 차 화면 직접 / 원격 데스크톱** — 차에 모니터를 붙이거나 VNC·RDP 로 붙는다.
`h_tuner.py` 처럼 슬라이더를 계속 만지는 도구는 이쪽이 편하다
(`tools/h_tuner.py` 파일 헤더의 실행 예시가 "차 화면 터미널에서"를 전제로 적혀 있다).

**(c) 아예 화면을 안 보내는 방법** — `tools/bev_stream.py`.
노트북 WSL2 는 NAT 뒤에 있어서 ROS2 의 통신(DDS)이 차까지 안 닿는다.

> **DDS** 는 ROS2 가 속으로 쓰는 통신 규격이다. 같은 네트워크에 있는 노드끼리
> "나 여기 있다" 하고 서로를 **자동으로 찾아** 연결한다(4.2절의 `ROS_DOMAIN_ID` 가 바로
> 이 자동탐색의 채널 번호다).
> **NAT(Network Address Translation)** 는 안쪽 주소를 바깥 주소로 바꿔 주는 중계다.
> 안에서 밖으로 거는 건 되지만, 밖에서 안으로 직접 들어오는 건 막힌다. WSL2 는 윈도우
> 안쪽에 NAT 로 숨어 있어서, 차가 WSL 을 먼저 찾아갈 수가 없다. 그래서 자동탐색이 실패한다.

네트워크를
뜯어고치는 대신, **SSH 파이프 하나로 JPEG 프레임만 흘려보내는** 도구를 만들어 뒀다.
(파이프 = 한 프로그램의 출력을 다른 프로그램의 입력에 그대로 연결하는 리눅스의 기본 배관.
표준출력 = 프로그램이 화면에 찍는 그 출구.)
차 쪽에서 캡처→왜곡보정→BEV 까지 다 하고 결과 JPEG 만 표준출력으로 뱉으면,
노트북이 그걸 읽어 창에 그린다. 설정이 필요 없고 대역폭도 ~1 MB/s 다
(`tools/bev_stream.py:4-19`, 클라이언트 구현 `:100-107`).

```bash
# 노트북 WSL 대화형 터미널에서
cd ~/xycar_ws/본선/track_drive/tools
python3 bev_stream.py
```

### 2.4 ★ 왜 도구들이 "입력이 있을 때만 다시 그리는가"

원격으로 화면을 보내면 **화면 전송 자체가 병목**이 된다. 1920×1080 짜리 창을 초당
30번 보내면 조작이 끊긴다. 그래서 캘리브 도구들은 아래 원칙으로 만들어졌다.

- **기본이 '정지 화면'이다.** 카메라도 장면도 안 움직이는데 실시간일 이유가 없다.
  스페이스를 눌러야 새 프레임을 한 장 받아온다(`tools/ground_fit.py:335-337` 주석).
- **키나 클릭이 없으면 화면을 다시 그리지 않는다.** 키 입력을 기다리는 루프를 돌다가
  입력이 들어왔을 때만 다시 그린다(`tools/ground_fit.py:597-605`).
- **화면 갱신 상한을 인자로 줄 수 있다.** `--fps` 를 낮추면 더 가벼워진다
  (`tools/ground_fit.py:187` — "원격 데스크톱 부하 줄이기").
- **무거운 계산은 캐시한다**(캐시 = 한 번 계산한 결과를 저장해 두고 다음엔 다시 안 만드는 것).
  BEV 역매핑 격자(= 펴진 그림의 각 칸이 원본 사진의 어느 픽셀에서 오는지 미리 적어 둔 표)는
  파라미터가 바뀔 때만 다시 만든다
  (`tools/ground_fit.py` 파일 헤더 "성능" 항목).

그러니 **"툴이 멈춘 것 같다"는 착각을 하지 마라.** 정상이다. 키를 누르면 반응한다.
`calib_ground_h.py` 는 아예 그 상황에 주석까지 달아 뒀다 —
"콘솔 입력 동안 창 갱신 멈춤 — 정상"(`tools/calib_ground_h.py:476`).

## 3. 작업 원칙 — 어디서 고치고 어떻게 옮기나

### 3.1 ★ 모든 작업은 차 PC 의 `~/xycar_ws/src/track_drive/` 에서 한다

이 원칙을 어기면 **"고쳤는데 왜 안 바뀌지?"** 로 몇 시간을 날린다.

```
[노트북]  ~/xycar_ws/본선/track_drive     = git 저장소. 버전관리·문서·백업용.
[차 PC]   ~/xycar_ws/src/track_drive      = 실제로 빌드되고 실행되는 코드.
```

차 PC 쪽 경로가 `src/track_drive` 인 것에 주의. 노트북 저장소는 `예선/` `본선/` 으로
나뉜 상태지만, 차에는 **본선 코드만** `src/track_drive` 로 평평하게 들어간다.
차 위의 스크립트들이 전부 이 경로를 하드코딩하고 있다
(예: `tools/bev_stream.py:35`, `dev/scripts/_shot.py:18` 의 `PKG = "/home/xytron/xycar_ws/src/track_drive"`).

### 3.2 노트북 → 차 (코드 배포)

가장 안전한 방법은 노트북 홈에 있는 배포 스크립트를 쓰는 것이다.

```bash
bash ~/_deploy_car.sh
```

이 스크립트가 하는 일은 6단계다.

1. 차의 기존 `track_drive` 를 `~/xycar_ws/src/_backup_track_drive_MMDD_HHMM` 로 백업
   (이미 본선 코드면 스킵)
2. `rsync`(파일 동기화 도구. 전체를 다시 보내지 않고 **바뀐 부분만 골라 보내서** 빠르다) 로 전송
3. 차에서 `colcon build`
4. 차에서 `pytest`(파이썬 테스트 자동 실행 도구. `test/` 밑에 미리 적어 둔 검사들을
   한꺼번에 돌려서 코드가 깨졌는지 확인한다)
5. `ros2 pkg executables track_drive` 로 실행이름 확인
6. 배포된 파일 목록 출력

직접 손으로 하려면 이렇게 한다.

```bash
rsync -az --delete \
  --exclude '__pycache__' --exclude '*.pyc' --exclude '.pytest_cache' \
  -e "ssh" \
  /home/xytron/xycar_ws/본선/track_drive/ \
  xytron@10.42.0.1:/home/xytron/xycar_ws/src/track_drive/
```

> **`--delete` 주의** — 이 옵션은 "로컬에 없는 파일은 차에서도 지운다"는 뜻이다.
> 차에서만 만든 사진·로그가 있으면 **날아간다.** 차에서 뭔가 만들었으면 먼저
> 노트북으로 가져오고(3.3절) 배포할 것. 확신이 없으면 `--delete` 를 빼고 돌려라.
> 지워질 목록만 미리 보려면 `--dry-run`(실제로는 아무것도 안 하고 "이렇게 할 것이다"
> 목록만 찍는 연습 모드) 을 붙인다.

## 4. 빌드와 실행

### 4.1 매번 하는 3줄

```bash
source /opt/ros/humble/setup.bash
cd /home/xytron/xycar_ws
colcon build --packages-select track_drive --symlink-install
source install/setup.bash
```

용어 풀이:

- **`source ... setup.bash`** = "이 셸에게 ROS 를 쓰는 법을 알려준다". 새 터미널을 열
  때마다 해야 한다. 안 하면 `ros2: command not found` 가 난다.
- **`colcon build`** = ROS2 의 빌드 명령. 파이썬 코드지만 패키지 등록·launch 파일 설치가
  필요해서 빌드를 거친다.
- **`--packages-select track_drive`** = 우리 패키지만 빌드. 다른 것까지 건드리지 않는다.
- **`--symlink-install`** = 파일을 **복사하지 않고 링크만**(symlink = 심볼릭 링크,
  실제 파일을 가리키기만 하는 바로가기) 걸어둔다. 그래서 `.py` 를
  고치면 **다시 빌드하지 않아도** 반영된다. 단, `setup.py`·`launch/`·`config/` 를
  건드렸으면 다시 빌드해야 한다.
- **`source install/setup.bash`** = 방금 빌드한 결과를 이 셸에 등록.

빌드+테스트를 한 번에 하려면 `~/build_track_drive.sh` 를 쓴다. 이 파일은 **노트북 홈**에
있고(3.5절), 내용은 차 경로(`/home/xytron/xycar_ws`)를 그대로 쓰므로 차에 파이프해서 돌린다.

```bash
ssh xytron@10.42.0.1 'bash -s' < ~/build_track_drive.sh
```

`src` 밑 `track_drive` 패키지 중복까지 검사해 준다(`build_track_drive.sh:6-7`) — 같은 이름
패키지가 두 개 있으면 엉뚱한 쪽이 빌드돼서 "고쳤는데 안 바뀐다"가 발생한다.

### 4.2 ★ `export ROS_DOMAIN_ID=7`

```bash
export ROS_DOMAIN_ID=7
```

ROS2 는 같은 네트워크의 노드들을 **자동으로** 찾아서 연결한다. 편하지만 대회장처럼
여러 팀이 한 네트워크에 있으면 **남의 차 토픽이 우리 차에 섞여 들어온다.**
`ROS_DOMAIN_ID` 는 그 자동탐색의 **채널 번호**다. 번호가 다르면 서로 안 보인다.

우리는 **7번**을 쓴다. 이건 취향이 아니라 **강제**다 — 모터로 나가는 길목의
ros1_bridge 가 `ROS_DOMAIN_ID=7` 로 떠 있기 때문에(`~/_motor_up.sh` 브릿지 기동부),
7번이 아니면 **`/xycar_motor` 를 발행해도 차가 움직이지 않는다.**
저장소 안에서도 7번으로 통일돼 있다(`dev/scripts/start_cam.sh:21`,
`tools/bev_shot.py:20`, `tools/undist_check.py:22`, `tools/bev_viewer.py:17`).

> **알려진 불일치** — `tools/calib_shot.sh:20` 만 기본값이 `0` 이다
> (`export ROS_DOMAIN_ID=${ROS_DOMAIN_ID:-0}`). 도메인 7 로 띄운 센서를 이 스크립트가
> 못 볼 수 있다. 쓸 때는 `ROS_DOMAIN_ID=7 bash tools/calib_shot.sh ...` 처럼
> 앞에 붙여서 실행할 것.

### 4.3 실행 — launch 와 run

**launch 파일**은 "여러 노드를 한 번에 켜는 스위치"다. 세 개가 있다.

| 명령 | 뭘 켜나 | 파일 |
|---|---|---|
| `ros2 launch track_drive sensors.launch.py` | 카메라 + 라이다 + IMU | launch/sensors.launch.py |
| `ros2 launch track_drive drive.launch.py` | 주행 4노드 | launch/drive.launch.py |
| `ros2 launch track_drive viewer.launch.py` | 디버그 뷰어 1개 | launch/viewer.launch.py |

`drive.launch.py` 가 켜는 4개는 이렇다(`launch/drive.launch.py:31-36`).

```
  yolo          3모델 순차 추론 → /detect/lane, /detect/objects, /detect/traffic_light
  path_planner  상태머신       → /drive_cmd, /center_path
  motion        경로추종+중재   → /xycar_motor (20 Hz 연속)
  car_state     IMU+VESC 집계   → /car_state
```

위 네 줄에 나온 말을 풀면 이렇다.

- **상태머신(state machine)** = 차의 상황을 "차선주행 중", "정지선 대기 중" 같은 몇 개의
  **상태**로 나눠 두고, 정해진 조건이 맞을 때만 다음 상태로 넘어가게 만든 구조.
  지금 어느 상태인지가 항상 하나로 정해져 있어서 "왜 이렇게 움직였나"를 추적할 수 있다.
- **경로추종** = 앞에서 그려 준 경로를 그대로 따라가도록 **조향각을 계산하는 일**.
- **중재** = 여러 군데(자율주행 판단, 텔레옵 등)에서 명령이 올 때 **무엇을 실제로 모터에
  내보낼지 고르는 일**. 그래서 주행 중에는 모터로 나가는 출구가 `motion` 하나로 모인다
  (예외는 7장 8단계의 `teleop --direct` 뿐이다).

뷰어가 `drive.launch.py` 에 없는 것은 **일부러**다. 대회 규정상 주행 launch 에
뷰어를 넣으면 안 되기 때문에 따로 뺐다(`launch/viewer.launch.py:1-7`).

### 4.4 ★ 실행 이름이 파일 이름과 다르다

이게 처음 만지는 사람이 제일 많이 헤매는 지점이다.
`ros2 run` 에 넣는 이름은 **파일 이름이 아니라 `setup.py` 에 등록한 별명**이다
(`setup.py:31-39`).

| `ros2 run` 에 쓰는 이름 | 실제 파일 |
|---|---|
| `yolo` | `track_drive/yolo_node.py` |
| `path_planner` | `track_drive/path_planner_node.py` |
| `motion` | `track_drive/motion_node.py` |
| `car_state` | `track_drive/car_state_node.py` |
| `teleop` | `track_drive/teleop_node.py` |
| `yolo_lane_viewer` | `track_drive/yolo_lane_viewer_node.py` |

즉 `ros2 run track_drive yolo_node` 는 **없는 이름**이라 실패한다. `yolo` 가 맞다.

```bash
ros2 run track_drive yolo
ros2 run track_drive path_planner
ros2 run track_drive teleop --direct   # 키보드 수동 조종 (단독 실행이면 --direct)
ros2 pkg executables track_drive       # 헷갈리면 이걸로 목록 확인
```

### 4.5 정상이면 이런 로그가 나온다

**(a) 카메라 캘리브가 제대로 물렸을 때** — `yolo` 노드 기동 직후
(`yolo_node.py:191-198` 이 찍는 한 줄):

```
[camera] model=plumb_bob intrinsics_calibrated=true h_calibrated=true
         undistort=enabled(alpha=0.00, new_K fx=847.52 fy=939.42 cx=960.00 cy=540.00)
         H=yaml size=1920x1080 car_mask_v=951 yaml=.../config/camera.yaml note=-
[camera] new_K 일치 — H 좌표계가 런타임 undistort 와 같다
```

**로그에 나오는 말부터 풀고 가자.** 여기 나오는 `model` · `alpha` · `new_K` · `H` 는
전부 "카메라 사진을 지면 좌표로 바꾸는 한 줄짜리 흐름"의 부품 이름이다. 흐름은 이렇다.

```
  카메라 원본 사진        휜 사진 (렌즈 때문에 직선이 휨)
        │
        │  왜곡보정(undistort) — K 와 D 를 써서 편다.  alpha 로 여백 처리 방식을 고른다
        ↓
  보정된 사진            직선이 직선으로 나오는 사진
        │                └── 이 사진의 픽셀 좌표계를 정의하는 것이 new_K
        │  호모그래피 H — "보정된 픽셀 → 지면 몇 m"
        ↓
  BEV / 지면좌표 (x 앞, y 왼쪽, 단위 m)
```

- **K (카메라 행렬)** — 렌즈의 초점거리(`fx`, `fy`)와 화면 중심(`cx`, `cy`)을 담은
  숫자 9개짜리 표. "3차원의 점이 사진의 몇 번째 픽셀에 찍히는가"를 정하는 값이다.
- **D (왜곡계수)** — 렌즈 때문에 직선이 휘어 보이는 정도를 나타내는 숫자 묶음.
- **model=plumb_bob** — 그 휘어짐을 어떤 수식으로 표현할지 정한 **표준 모델의 이름**이다.
  일반 광각 렌즈에 쓰는 방식이고, 어안(fisheye) 렌즈용 모델과는 계산이 다르다.
  이 카메라는 실측 화각이 약 87° 인 일반 광각이라 `plumb_bob` 이 맞다
  (`lib/bev.py:65-72`).
- **왜곡보정(undistort)** — K 와 D 를 써서 휜 사진을 **직선이 직선으로 나오게 펴는 것**.
- **alpha** — 사진을 펴면 가장자리가 휘어 들어가면서 **검은 여백**이 생긴다. 그 여백을
  어떻게 할지 정하는 0~1 사이의 손잡이다. **0 이면 여백이 안 보이게 잘라내고, 1 이면
  원본 화소를 전부 남긴다**(대신 가장자리에 검은 부분이 남는다). 우리는 0.00 을 쓴다
  (`lib/bev.py:73-75`, `camera.yaml:32` `h_alpha: 0.0`).
- **new_K** — 그렇게 **편 사진의 카메라 행렬**이다. 말을 바꾸면 "보정된 사진의 픽셀
  좌표계가 어떻게 생겼는지"를 정의하는 값이다. alpha 를 바꾸거나 이미지 크기를 바꾸면
  이 값이 같이 달라진다(`lib/bev.py:339-346`).

★ 그래서 **new_K 가 가장 중요한 판정 기준**인 이유는 이렇다.
H 는 "**보정된 픽셀** → 지면 m" 를 옮기는 표다. 즉 H 는 **어떤 좌표계의 픽셀을 받는지를
전제로** 만들어져 있고, 그 전제가 바로 캘리브 당시의 new_K 다.
지금 런타임이 다른 new_K 로 사진을 펴 놓고 그 위에 옛날 H 를 적용하면, **자로 잰 눈금이
다른 자를 쓰는 것**과 같아서 나온 거리·위치가 통째로 틀린다. 그런데 **화면은 멀쩡해 보인다**
— 사진은 여전히 잘 나오니까. 1.4절의 마운트 사고와 똑같은 성질의 조용한 사고다.
그래서 캘리브 때 쓴 new_K 를 `camera.yaml` 에 숫자로 적어 두고(`config/camera.yaml:62` 아래),
기동할 때마다 런타임이 계산한 값과 한 자리씩 대조한다
(`lib/bev.py:379-407` `check_new_K_match`, 허용 오차 0.001 픽셀).
`camera.yaml` 에 new_K 가 적혀 있으면 런타임은 alpha 로 다시 계산하지 않고 **그 값을
그대로 쓴다** — 캘리브 당시 값이 정답이기 때문이다(`lib/bev.py:339-346`).

여기서 봐야 할 것 네 가지:

1. `h_calibrated=true` — 지면 변환이 실측 캘리브 값이라는 뜻. `false` 면 시뮬 폴백이다.
   (**폴백(fallback)** = 제대로 된 값이 없을 때 대신 쓰는 예비값. 여기서는 실차 캘리브가
   없을 때 예선 시뮬에서 쓰던 H 로 일단 굴러가게 해 두는 것이다. 굴러는 가지만
   거리 값은 못 믿는다.)
2. `undistort=enabled` — 렌즈 왜곡 보정이 실제로 돌고 있다.
   (`disabled(passthrough)` 로 나오면 보정을 못 해서 **원본 사진을 그대로 흘려보내는**
   상태다. 이때 H 는 무효다.)
3. `size=1920x1080` — 카메라 해상도와 일치해야 한다.
4. **`new_K 일치`** — ★ 이게 제일 중요하다. H 는 "왜곡보정을 이 방식으로 했을 때"를
   전제로 만들어졌는데, 지금 런타임의 보정 방식과 같다는 확인이다. 여기가
   `new_K 불일치...` 경고로 바뀌면 **지면 좌표가 통째로 틀린 상태**다.

같은 줄의 `car_mask_v=951` 도 알아 두면 좋다. **car_mask_v** 는 "사진에서 이 가로줄보다
아래쪽은 지면이 아니라 **우리 차 몸통**(라이다 원통·범퍼)이니 차선 찾기에서 빼라"는
기준선이다(숫자는 픽셀 세로좌표). 이걸 안 정해 두면 차체 화소가 H 를 통과해
**바로 코앞(x≈0.15~0.25 m)에 있지도 않은 가짜 차선점**으로 들어온다. `-` 로 나오면
경고가 함께 뜨고, `tools/bev_view.py` 에서 `m` 키로 선을 정하고 `s` 로 저장하면 된다.

**(b) 나머지 노드**

```
PLANNER(실차) 시작                      ← path_planner_node.py:352
motion_node up (realcar)               ← motion_node.py:188
yaw 기준각 캡처: 12.3 deg               ← car_state_node.py:89 (IMU 첫 수신 시)
[objects] v 환산: 실제 1080p → 기준 480p (x0.4444)  ← path_planner_node.py:440
WAIT — 센서 확인, 출발 신호 대기          ← path_planner_node.py:588
```

`[objects] v 환산` 이 왜 중요한지: 정지선·교차로 판정에 쓰는 픽셀 임계값은 전부
**예선 시뮬 480p 에서 튜닝된 숫자**다. 1080p 를 그대로 넣으면 STOP 이 2.25배 멀리서
오발동한다. 그래서 실제 해상도를 읽어 환산한다(커밋 `d1be718` 설명).
이 줄 대신 `camera.yaml 에서 image_height 를 못 읽었다` 경고가 뜨면 위험하다.

**(c) 카메라 기동 로그** — `start_cam.sh` 마지막에 이런 게 나오면 정상
(`dev/scripts/start_cam.sh:52-59`):

```
=== 프로세스 ===
12345 /opt/ros/humble/lib/usb_cam/usb_cam_node_exe --ros-args ...
=== 실제 발행 ===
average rate: 29.870
```

## 5. 카메라 기동 — `dev/scripts/start_cam.sh`

### 5.1 기본 사용법

```bash
bash ~/xycar_ws/src/track_drive/dev/scripts/start_cam.sh
```

인자를 안 주면 **1920×1080 MJPG 30 fps** 로 뜬다. 인자는 순서대로
`가로 세로 포맷 fps` 다(`dev/scripts/start_cam.sh:23-26`).

> **MJPG 와 YUYV** — 카메라가 USB 선으로 그림을 보내는 두 가지 방식이다.
> **MJPG**(Motion JPEG)는 매 프레임을 JPEG 으로 **압축해서** 보낸다. 선으로 가는 데이터가
> 적어 고해상도에서도 fps 가 잘 나오는 대신, PC 가 매 프레임 압축을 푸는 일을 해야 한다.
> **YUYV** 는 압축 없이 화소를 **그대로** 보낸다. 푸는 일이 없어 편하지만 데이터가 커서
> 고해상도에서 fps 가 확 떨어진다(5.3절 표 참고).

```bash
bash start_cam.sh 640 480 yuyv2rgb 30      # 640x480 YUYV 30fps
```

스크립트가 알아서 해 주는 것:

1. 이미 `usb_cam_node_exe` 가 떠 있으면 내리고 다시 띄운다 (`:28-32`)
2. `/dev/video0` 를 다른 프로그램이 잡고 있으면 **에러 내고 멈춘다** (`:33-37`)
3. `setsid nohup` 으로 띄워 SSH 세션이 끊겨도 살아 있게 한다 (`:40-43`)
   — `setsid`/`nohup` 은 프로그램을 **터미널과 끊어서 독립적으로** 띄우는 방법이다.
   보통은 터미널이 닫히면 거기서 띄운 프로그램도 같이 죽는데, 이렇게 띄우면 안 죽는다.
4. 10초 기다렸다가 프로세스 생존·실제 발행 Hz·토픽 정보·로그 꼬리를 찍는다 (`:44-59`)

로그는 `/tmp/cam.log` 에 쌓인다.

### 5.2 ★ 해상도마다 화각이 다르다 (중요)

**화각(FOV, Field of View)** 은 카메라가 한 번에 담는 시야의 넓이(각도)다. 넓을수록
좌우로·위아래로 더 많이 보인다.

보통 카메라는 저해상도가 "줄인 것"이지만, 이 카메라는 **센서를 잘라낸 것**이다.
그래서 해상도를 바꾸면 **보이는 범위 자체가 달라진다.** 실측값
(`dev/scripts/start_cam.sh:5-11`):

| 해상도 | 가로 화각 | 세로 화각 |
|---|---|---|
| 1920×1080 | 100 % | 100 % |
| 1024×768 | 75 % | 99 % |
| 640×480 | 67 % | 89 % |
| 1280×720 | 67 % | 67 % |

그래서 **기본을 1920×1080 으로 잡았다.** 위쪽이 더 보여 신호등 인식에 유리하고
(`tools/cam_modes.py:6-8`), YOLO 는 어차피 `imgsz`(YOLO 가 추론 직전에 이미지를 줄여서
넣는 목표 크기. 원본이 1080p 든 480p 든 이 크기로 맞춰 넣는다) 로 줄여 넣으므로 추론 속도는
해상도와 무관하다(실측). 늘어나는 부담은 MJPG 디코딩(압축을 푸는 일)뿐이다.

### 5.3 ★ 지원하지 않는 fps 를 요청하면 노드가 죽는다

카메라가 실제로 지원하는 조합만 먹는다. 안 맞으면 `usb_cam` 이 그냥 종료된다
(`dev/scripts/start_cam.sh:13-16`):

```
MJPG  1920x1080 = 30 fps   /  1280x720 = 60  /  1024x768 = 30  /  640x480 = 120
YUYV   640x480  = 30 fps   /  1920x1080 = 6
```

**왜 MJPG 인가**: 이 카메라는 YUYV 1080p 가 **6 fps** 밖에 안 나온다. 30 fps 를
얻으려면 MJPG 가 강제된다(`launch/sensors.launch.py:48-49`).

확인하는 법:

```bash
v4l2-ctl --list-formats-ext -d /dev/video0
```

이 명령이 카메라가 지원하는 **모든 포맷 × 해상도 × fps** 조합을 다 찍어 준다.
없는 조합을 요청하지 마라.

### 5.4 ★ `/dev/video0` 를 다른 프로세스가 잡고 있으면 죽는다

리눅스에서 카메라 장치는 **한 번에 하나의 프로그램만** 열 수 있다.
`tools/cam_modes.py` 나 `bev_stream.py --server` 처럼 ROS 없이 카메라를 직접 여는
도구를 켜 둔 채 `usb_cam` 을 띄우면 실패한다.

`fuser` 는 **어떤 파일·장치를 지금 누가 쓰고 있는지** 알려주는 명령이다. 결과에 나오는
`PID` 는 리눅스가 돌고 있는 프로그램마다 붙여 주는 번호다. 이 번호를 알면 그 프로그램만
정확히 지목해서 끌 수 있다.

```bash
# 누가 잡고 있나
fuser -v /dev/video0

# 예시 출력
#                      USER   PID  ACCESS COMMAND
# /dev/video0:         xytron 4821 F....m python3
```

`start_cam.sh` 는 이걸 자동으로 검사해서 경고하고 멈춘다(`:33-37`).
해결은 **그 PID 를 정확히 지목해서 끄는 것**이다.

```bash
kill 4821            # PID 로 정확히
sleep 1
fuser -v /dev/video0 # 아무것도 안 나오면 해제됨
```

`pkill -f python3` 같은 광범위한 명령은 **쓰지 마라** (8장 참고).

### 5.5 해상도를 바꾸면 캘리브가 무효다

**해상도는 `config/camera.yaml` 의 `image_width`/`image_height` 와 반드시 일치해야 한다.**
다르면 왜곡보정 결과 좌표계(new_K)가 달라져 **H 가 통째로 무효**가 된다
(`launch/sensors.launch.py:45-47`).

다행히 코드가 조용히 넘어가지 않는다. 프레임 크기가 캘리브 기준과 다르면
`yolo` 노드가 경고를 찍고 **리맵**(remap, 보정된 사진의 각 픽셀이 원본 사진의 어디서
왔는지 미리 계산해 둔 대응표. 매 프레임 수식을 다시 푸는 대신 이 표를 보고 옮긴다)을
다시 만든다(`yolo_node.py:266-276`):

```
[camera] 프레임 크기 640x480 가 캘리브 기준 1920x1080 와 다르다 — 리맵 재생성.
         new_K 가 달라져 H 는 무효일 수 있다.
```

이 경고를 보면 **주행하지 마라.** 카메라를 1080p 로 다시 띄우든지, 그 해상도로
캘리브를 다시 하든지 해야 한다.

## 7. 점검 체크리스트 — 전원부터 주행까지

- ✅ 프롬프트가 뜬다 → 다음
- ❌ 안 되면: 차 전원(메인 배터리 Li-ion 12~19 V)이 켜졌나, 노트북이 차 네트워크에
  붙었나(`ip addr` 로 `10.42.0.x` 를 받았는지), 부팅 대기(1~2분)

### 2단계 — 환경 준비

```bash
source /opt/ros/humble/setup.bash
source ~/xycar_ws/install/setup.bash
export ROS_DOMAIN_ID=7
```

- ✅ `ros2 --version` 이 답한다
- ❌ `command not found` → 첫 줄 source 를 안 했다

### 3단계 — 센서 기동

```bash
ros2 launch track_drive sensors.launch.py
# 또는 카메라만: bash ~/xycar_ws/src/track_drive/dev/scripts/start_cam.sh
```

- ✅ 에러 없이 로그가 흐른다
- ❌ 카메라만 안 뜨면 5.4절(`/dev/video0` 점유) 확인. 첫 실행은 원래 잘 죽는다 —
  `sensors.launch.py` 는 `respawn=True`(노드가 죽으면 launch 가 **자동으로 다시 띄우는**
  설정)로 자동 재기동한다
  (`launch/sensors.launch.py:41`).

### 4단계 — 토픽이 나오는지

```bash
ros2 topic list
```

- ✅ `/image_raw`, `/scan`, `/imu` 가 보인다
- ❌ 하나라도 없으면 그 센서 노드가 죽은 것. 로그(`/tmp/cam.log`) 확인

### 5단계 — 실제로 데이터가 흐르는지 (토픽 이름만 보이는 건 의미 없다)

```bash
ros2 topic hz /image_raw     # 기대: average rate: 29.x
```

- ✅ 위 숫자 근처가 나온다
- ❌ `no new messages` → 노드는 살았지만 데이터가 안 나온다.

내용까지 보려면:

```bash
ros2 topic echo /image_raw --field encoding --once   # rgb8
ros2 topic echo /image_raw --field width --once      # 1920
ros2 topic echo /image_raw --field height --once     # 1080
```

### 6단계 — 캘리브 확인 (★ 이 단계를 건너뛰지 마라)

```bash
cd ~/xycar_ws/src/track_drive
python3 tools/bev_view.py --topic /image_raw          # 실시간 BEV
# 또는 저장된 사진으로
```

- ✅ BEV 에서 **차선이 직선이고 서로 평행**하다. 바닥 격자가 정사각형이다.
  노란 점선이 실제 줄눈 위에 겹친다.
- ❌ 휘거나 벌어지면 → 카메라 마운트가 틀어졌거나 H 가 안 맞다. 1.4절 참고.

> BEV 격자선을 실선이 아니라 **점선**으로 그리는 데는 이유가 있다. 실선은 판정
> 대상인 줄눈을 덮어버려서 "겹쳤는지"를 눈으로 확인할 수가 없다

> (`teleop_node.py:5-8`, `:78-81`). 이 단계에서는 주행 노드가 아직 안 떠 있으므로
> `--direct`(CarInterface 거쳐 `/xycar_motor` 직발행)로 써야 한다.
> 9단계에서 `drive.launch.py` 를 띄운 뒤라면 `--direct` 없이도 motion 을 거쳐 나간다.

- ✅ 바퀴가 돌고 조향이 움직인다
- ❌ 안 움직이면: `--direct` 를 줬는지 → `ROS_DOMAIN_ID=7` 확인 → 브릿지 확인 →
  배터리 전압 확인
- 참고: **speed 명령 4 미만은 안 구른다**(데드존, `config/car.yaml:18`).
  2 를 넣고 "안 움직인다"고 하지 마라.
  **데드존(dead zone)** 은 명령을 줘도 실제로는 아무 일도 안 일어나는 구간을 말한다.
  마찰과 모터 특성 때문에 아주 작은 명령으로는 바퀴가 못 움직인다. 그래서 주행 최저
  명령은 데드존보다 큰 5 로 잡아 뒀다(`config/car.yaml:22`).

- ✅ 4.5절의 로그들이 나오고, `WAIT — 센서 확인, 출발 신호 대기` 에서 멈춘다
- ❌ `new_K 불일치` 나 `h_calibrated=false` 경고가 뜨면 **주행하지 말 것**

## 8. ★ 안전 수칙

여기 적힌 것은 **전부 실제로 사고가 났거나, 날 뻔해서 코드에 방지책이 들어간 항목**이다.
읽고 지켜라.

### 8.1 캘리브·테스트 중에는 `/xycar_motor` 를 발행하지 마라

캘리브는 사람이 차 앞에 쪼그려 앉아 바닥을 보면서 한다. 그 상태에서 모터 명령이
나가면 사람을 친다. `tools/calib_shot.sh:8` 이 아예 주석으로 못을 박아 뒀다 —
"모터/주행 토픽은 건드리지 않는다".

- 캘리브 중에는 `drive.launch.py` 를 **켜지 마라.**
- `teleop` 도 끄고, `ros2 topic hz /xycar_motor` 로 발행이 없는지 확인하고 시작하라.

### 8.2 바퀴를 띄우고 시험하라

코드 수정 후 첫 실행은 **반드시 차를 받침대에 올려 바퀴를 공중에 띄운 상태**에서 한다.
조향 부호가 뒤집혔거나 속도 부호가 틀렸을 때 차가 튀어나가면 못 잡는다.

특히 조심할 조합:
- **조향 트림이 −20 이다.** **트림(trim)** 은 기계가 치우쳐 장착된 것을 상쇄하려고
  명령에 **항상 더해 두는 보정값**이다. 자동차 핸들이 삐뚤게 끼워졌을 때 "똑바로 가려면
  핸들을 항상 조금 왼쪽으로 잡아야 하는" 그 보정량이라고 보면 된다.
  즉 `/xycar_motor` 로 나가는 조향값 **0 은 직진이 아니라
  우측으로 20 만큼 꺾인 상태**이고, 직진은 **−20** 이다 (`config/car.yaml:12`).
  서보가 기계적으로 우측으로 치우쳐 장착돼 있어서 그렇다.
  (우리 코드 안에서 쓰는 *논리* 조향 0 은 `CarInterface` 가 트림을 더해 주므로 직진이
  맞다 — `angle_out = steer_trim + rel`, `lib/car_interface.py:113-115`.)
- **`+angle` 이 우회전**이다.
- **좌우 기계 한계가 비대칭**이다: 좌 −32 / 우 +62 (`config/car.yaml:14-15`).
  이 값을 넘겨 밀면 서보가 스톱에 부딪혀 계속 힘을 쓴다(**스톨(stall)** = 더는 못
  움직이는데 명령은 계속 밀고 있어서 힘만 쓰는 상태. 서보가 뜨거워지고 오래 두면 탄다).

### 8.3 모터 도커를 건드리지 마라

모터 명령이 실제 바퀴까지 가는 길은 이렇다.

```
  우리 코드(ROS2)  --/xycar_motor-->  ros1_bridge (호스트 프로세스)
        --> docker "ros1_container" (osrf/ros:noetic-xycar, ROS1 VESC 스택)
        --> VESC --> 모터/서보
```

왜 이렇게 복잡한가 하면, 모터 쪽 소프트웨어가 **ROS1** 시절 것이고 우리 코드는 **ROS2**
이기 때문이다. 둘은 서로 말이 안 통한다. 그래서 사이에 **ros1_bridge**(두 세계 사이에서
메시지를 **통역해 옮겨 주는** 프로그램)를 세워 뒀다. ROS1 쪽 프로그램들은 옛날 리눅스
환경이 필요해서 도커 컨테이너(1.1절) 안에 통째로 들어가 있고, 그 안에서
**ROS1 마스터**(ROS1 에서 누가 어떤 토픽을 갖고 있는지 관리하는 중앙 안내소. ROS2 에는
없는 개념이다)가 돈다.

- **`docker stop` / `docker rm` 을 함부로 하지 마라.** 컨테이너를 내리면 모터가
  완전히 죽고, 되살리는 데 시간이 걸린다.
- **`motor` 명령을 SSH 에서 직접 실행하지 마라.** TTY(= 사람이 앉아서 키를 두드리는
  대화형 단말. `ssh 주소 '명령'` 처럼 명령만 던져 넣으면 TTY 가 없다) 가 없어서
  스크립트가 "사용자가 끝냈다"고 보고 정리
  단계까지 실행돼 컨테이너가 오히려 내려간다. 대신 `~/_motor_up.sh` 를 쓴다.
  이 스크립트는 `motor` 의 대화형 부분을 뺀 버전이라 SSH 에서 안전하다.
- 브릿지만 죽었으면 `~/_car_bridge_restart.sh` 로 브릿지만 되살린다
  (컨테이너 = ROS1 마스터는 그대로 두는 게 빠르고 안전하다).
- 모터 관련 파라미터(`vesc.yaml` 등)는 **노드 시작 시 1회만 읽는다.**
  고쳤으면 반드시 모터 스택을 재시작해야 반영된다.

### 8.4 ★ `pkill -f` 로 광범위하게 죽이지 마라 — SSH 세션 자살 사례

이건 실제로 당한 사고다. `pgrep` 은 **이름으로 프로그램의 PID 를 찾는** 명령이고,
`pkill` 은 **찾아서 바로 죽이는** 명령이다. `-f` 를 붙이면 프로그램 이름만이 아니라
**실행할 때 쓴 명령줄 전체**를 검색 대상으로 삼는다. 문제는 여기서 생긴다.
`pkill -f <패턴>` 은 **명령줄 전체**에서 패턴을 찾는데,
SSH 로 원격 명령을 실행하면 **그 원격 명령줄 자체에 패턴이 들어 있다.**
그래서 `pkill` 이 자기를 실행한 SSH 세션까지 죽여버린다.

방지책이 `~/cleanup_sensors.sh` 파일 머리에 주석으로 남아 있다.

> ※ pkill -f 패턴이 ssh 원격 명령줄 자체를 잡아 세션이 끊기는 사고를 막으려고
> 파일로 파이프해서 실행한다 (원격 명령줄은 "bash -s" 뿐).

그 스크립트가 쓰는 안전한 방법 두 가지:

**(a) 스크립트를 파일로 파이프한다** — 원격 명령줄에는 `bash -s` 만 남는다.

```bash
ssh xytron@10.42.0.1 'bash -s' < ~/cleanup_sensors.sh
```

**(b) PID 를 뽑아서 하나씩 죽인다.**

```bash
for PID in $(pgrep -f usb_cam_node_exe); do
  echo "kill $PID"; kill "$PID"
done
```

**(c) 패턴 문자열을 쪼개서 자기 자신 매칭을 피한다** — 실제로 쓰는 기법이다.

```bash
pgrep -f "ros2 launch track_drive sen""sors.launch.py"
```

`"sen""sors"` 로 나눠 놓으면 셸에서는 합쳐져 `sensors` 가 되지만, 이 명령 자체의
명령줄에는 `sen""sors` 로 남아 패턴에 안 걸린다.

그리고 `cleanup_sensors.sh` 는 마지막에 **모터 관련 프로세스를 안 건드렸음을
확인해서 출력**한다. 정리 스크립트가 지켜야 할 태도가 이거다.

### 8.5 배터리

- 모터 배터리는 NiMH, 정격 8.4 V / 완충 10~11 V. **8.6 V 미만이면 경고**가 뜬다
  (`config/car.yaml:50`, `car_state_node.py:109-112`).
- 전압이 낮으면 고속·고부하에서 **VESC 저전압 컷오프**(전압이 정해진 선 아래로 떨어지면
  컨트롤러가 배터리를 보호하려고 **스스로 출력을 끊어 버리는** 동작)가 걸려 차가 갑자기 선다.
  "왜 갑자기 멈추지?" 의 상당수가 이거다. 주행 전 완충할 것.
- 메인 PC 배터리(Li-ion 12~19 V)와는 다른 물건이다. 헷갈리지 마라.

### 8.6 코드가 넣어 둔 자동 안전장치 (믿어도 되지만 의존하진 마라)

먼저 **워치독(watchdog)** 이라는 말부터. 정해진 시간 안에 소식(메시지)이 안 오면
"저쪽이 죽었다"고 보고 **미리 정해 둔 안전 동작을 하는 감시 타이머**다. 개가 집을 지키다가
인기척이 끊기면 짖는 것과 같다. 여기서는 "짖는다" 대신 "차를 세운다".

- **`/drive_cmd` 0.3초 워치독** — planner 가 죽으면 motion 이 0.3초 안에
  MISSION_STOP 으로 간주해 차를 세운다 (`lib/drive_cmd.py:19`, `motion_node.py:234-235`).
- **`/teleop_cmd` 0.3초 워치독** — 텔레옵 끊기면 텔레옵 비활성 (`lib/drive_cmd.py:20`).
- **경로 신선도 0.5초** — 경로가 낡으면 추종하지 않는다 (`motion_node.py:123`).
- **속도 슬루 제한** — 20 Hz 틱당 속도 변화 1.5 (`config/car.yaml:17`).
  **슬루(slew) 제한**은 "한 번에 이만큼보다 더 크게는 못 바꾼다"는 **변화량 상한**이다.
  20 Hz 니까 1초에 20번 갱신되고, 한 번에 1.5 씩만 움직이므로 0 → 30 까지 가는 데
  약 1초가 걸린다. 목표값으로 계단을 밟아 올라가는 셈이고, 이 완만한 오르막을 **램프**라 부른다.
  왜 필요한가 하면, **센서리스 ESC** 때문이다. ESC 는 모터 속도 제어기인데,
  "센서리스"는 **회전자 위치를 재는 센서 없이 전류 파형만 보고 지금 모터가 어느 각도에
  있는지 짐작한다**는 뜻이다. 그런데 멈춰 있으면 전류 파형에서 읽을 게 없어서 짐작이 안 된다.
  그래서 정지에서 고속으로 직행하면 안 물린다(모터가 부르르 떨기만 하고 안 돈다).
  그래서 램프가 필수다.
- **후진 금지** — 자율주행 경로는 `allow_reverse: false` (`config/car.yaml:19`).
  텔레옵만 후진 허용.
- **데드맨 가드(옵션)** — **데드맨(dead man's switch)** 은 원래 기관사가 쓰러지면 열차가
  스스로 서는 장치를 말한다. "조종하는 쪽이 살아 있다는 신호"가 끊기면 자동으로 멈추는
  구조다. 여기서도 같다 — ROS2 쪽이 죽어 `/xycar_motor` 가 끊겨도 차가 굴러가는 것을
  막는 장치가 도커측 릴레이에 준비돼 있다(0.4초 침묵하면 정지 명령을 대신 넣는다).
  기본은 꺼져 있다
  (`ros1_docker/vesc_relay.py:6, :20`).

## 9. 자주 나는 문제와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| `usb_cam` 첫 기동 실패 (`Select timeout`) | 이 카메라의 알려진 flaky 동작(flaky = 같은 조건인데도 가끔 이유 없이 실패하는 성질) | 그냥 다시 띄운다. `sensors.launch.py` 는 `respawn=True` 로 자동 재기동 (launch/sensors.launch.py:41) |
| 카메라가 안 뜨고 "다른 프로그램이 잡고 있다" | `/dev/video0` 점유 | `fuser -v /dev/video0` → PID 확인 → `kill <PID>` (start_cam.sh:33-37) |
| 카메라가 조용히 죽는다 | 지원 안 되는 해상도/포맷/fps 조합 | `v4l2-ctl --list-formats-ext -d /dev/video0` 로 확인. MJPG 1080p 는 30 fps 뿐 |
| 로그에 `프레임 크기 ... 캘리브 기준과 다르다` | 카메라 해상도 ≠ camera.yaml | 1080p 로 다시 띄우거나 캘리브 재수행 (yolo_node.py:266-276) |
| 로그에 `new_K 불일치` | 런타임 왜곡보정이 H 캘리브 때와 다른 좌표계 | camera.yaml 에 `new_K` 가 있는지 확인(있으면 런타임이 그대로 쓴다 — `lib/bev.py:346, 367-369`). 없으면 `undistort_alpha` 를 캘리브 때 값으로. 그래도 나면 `Undistorter 초기화 실패` 로 패스스루가 된 것(K/D 확인). `~/cam_push.sh` 로 재검증 |
| 로그에 `H 미보정(h_calibrated=false)` | 시뮬 폴백 H 로 도는 중 | `tools/ground_fit.py` 로 H 재캘리브 (yolo_node.py:219-222) |
| 로그에 `car_mask_v 없음` 경고 | 차체 가림선 미설정 | `tools/bev_view.py` 에서 `m` 으로 지정, `s` 로 저장 (yolo_node.py:201-205) |
| BEV 근거리(x≈0.15~0.25 m)에 가짜 차선점 | 차체(라이다 원통·범퍼) 화소가 지면으로 변환됨 | 위와 같음. `car_mask_v` 설정 |
| STOP/교차로가 너무 멀리서 발동 | v 임계값이 480p 기준인데 1080p 를 넣음 | `[objects] v 환산` 로그 확인. 안 뜨면 camera.yaml 의 `image_height` 확인 (path_planner_node.py:432-443) |
| `/xycar_motor` 는 나오는데 차가 안 움직임 | ros1_bridge 죽음 (자주 죽는다) | `~/_car_bridge_chk.sh` → `~/_car_bridge_restart.sh` |
| 명령을 보내도 반응 없음 | `ROS_DOMAIN_ID` 가 7 이 아님 | `export ROS_DOMAIN_ID=7` (브릿지가 7로 떠 있다) |
| speed 를 넣었는데 안 구름 | 데드존 미만 | 명령 4 이상. 주행 최저는 5 (`car.yaml:18, :22`) |
| 고속에서 갑자기 멈춤 | 배터리 저전압 컷오프 | 모터 배터리 완충(10~11 V). `/car_state` 전압 확인 |
| 차가 계속 한쪽으로 감 | 조향 트림 −20 미적용 | `car.yaml` 이 로드됐는지 확인. `drive.launch.py` 는 자동 전달 |
| 도구가 멈춘 것처럼 보임 | 입력 있을 때만 다시 그리는 설계 | 정상. 키를 눌러라 (2.4절) |
| `imshow` 에서 죽음 / 창이 안 뜸 | `DISPLAY` 없음 | `ssh -X` 로 접속. `echo $DISPLAY` 확인 (bev_check.py:697) |
| 노트북에서 차 토픽이 안 보임 | WSL2 가 NAT 뒤라 DDS 미도달 | `tools/bev_stream.py` (SSH 파이프) 사용 |
| SSH 세션이 갑자기 끊김 | `pkill -f` 가 자기 명령줄을 잡음 | PID 로 죽이거나 `ssh ... 'bash -s' < script.sh` (8.4절) |
| 고쳤는데 반영이 안 됨 | 노트북에서만 고침 / `src` 에 패키지 중복 | 차의 `~/xycar_ws/src/track_drive` 에서 작업. `~/build_track_drive.sh` 가 중복 검사 |
| `ros2 run track_drive yolo_node` 실패 | 실행이름은 `yolo` | `ros2 pkg executables track_drive` (4.4절) |
| YOLO 가 느림 (1080p 4.4 Hz) | CPU 3모델 순차 추론 | 알려진 미해결. `imgsz` 조정 또는 라운드로빈(round-robin, 차례를 돌아가며 하나씩 처리하는 방식) 개선 필요 (커밋 d1be718 "알려진 미해결") |
