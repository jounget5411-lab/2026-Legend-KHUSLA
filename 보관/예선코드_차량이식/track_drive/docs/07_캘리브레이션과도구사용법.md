# 07. 캘리브레이션과 도구 사용법

이 문서는 "카메라가 본 화면 픽셀"을 "바닥 위의 실제 미터"로 바꾸는 작업 — 캘리브레이션 —
이 무엇이고, 이 프로젝트에서 그것을 어떤 파일의 어떤 함수가 어떻게 하는지, 그리고
`tools/` 폴더에 있는 19개 도구를 각각 언제 어떻게 쓰는지를 다룬다. 캘리브를 처음부터
다시 해야 할 때 따라 할 수 있는 단계별 절차와, 지금 값이 맞는지 확인하는 법, 그리고
아직 검증이 안 된 부분(알려진 한계)까지 적었다. 대상 파일은 `tools/` 전체와
`config/camera.yaml`, 그리고 그 결과를 실제로 소비하는 `track_drive/lib/bev.py` 다.

---

## 0. 이 문서에 나오는 용어

이 문서에만 나오는 낯선 단어를 먼저 모아 둔다. 본문을 읽다 막히면 여기로 돌아오면 된다.
각 용어는 본문에서 처음 나오는 자리에도 한 번씩 풀어 놓았다.

### 0.1 좌표와 행렬

| 용어 | 쉬운 뜻 | 이 문서 어디서 쓰나 |
|---|---|---|
| 캘리브레이션 | 카메라가 본 "화면 픽셀"을 "바닥 위 실제 미터"로 바꾸는 규칙을 실측으로 확정하는 작업 | 문서 전체 |

| D (왜곡 계수) | 렌즈가 사진을 얼마나 휘게 만드는지를 적은 숫자 묶음. 5개 `[k1,k2,p1,p2,k3]` | 1.3, 5단계 |
| k1 | D 중 첫 번째이자 제일 굵은 손잡이. 음수면 볼록하게 부푼 것(배럴)을 펴는 방향이다 | 1.3, 8.3 |
| H (호모그래피) | 비스듬히 본 바닥 사진을 위에서 내려다본 것처럼 펴 주는 3x3 숫자판. 우리 H 는 "편 사진 픽셀 → 지면 미터"다 | 1.4, 2장 전체 |

| alpha | 편 사진을 네모 화면에 담을 때 "검은 여백 없이 잘라 담을지(0)" "원본 화소를 다 살리고 여백을 둘지(1)"를 정하는 0~1 숫자 | 1.5 (그림 있음), 6.2 |
| BEV | Bird's Eye View. 새가 바로 위에서 내려다본 것처럼 편 그림 | 1.4 이후 전체 |
| ppm | pixels per meter. **BEV 그림에서 1미터를 몇 픽셀로 그릴지.** 크면 그림이 커지고 세밀해진다. 좌표값 자체와는 무관한 "표시 배율"이다 | 3.2, 6.2 |
| 축척 | 지도의 축척과 같은 뜻. 화면에서 1픽셀 움직였을 때 지면에서 몇 미터인가의 비율 | 2.2, 2.4, 3.7 |
| 역행렬 | 변환을 거꾸로 돌리는 짝 행렬. A 로 갔던 것을 `inv(A)` 로 되돌린다 | 2.3, 6.2 |
| REP-103 | ROS 가 정한 좌표축 표준 — x 는 앞, y 는 왼쪽, z 는 위, 단위는 미터 | 1.4 |
| 정규화 좌표 | 픽셀 개수가 아니라 "초점거리로 나눈 비율"로 위치를 세는 방식. 그래서 해상도가 바뀌어도 값이 안 변한다 | 5단계, 8.3 |

## 1. 캘리브레이션이 무엇이고 왜 필요한가

### 1.1 한 문단 요약

차선을 따라가려면 "차선이 화면의 왼쪽 아래에 있다"가 아니라 "차선이 내 왼쪽 30cm,
앞으로 1.2m 지점에 있다"를 알아야 한다. 조향각을 계산하려면 미터 단위 좌표가
필요하기 때문이다. 캘리브레이션은 픽셀을 미터로 바꾸는 변환을 실측으로 확정하는
작업이고, 이 프로젝트에서는 **두 단계**로 나뉜다. ① 렌즈 때문에 휘어 보이는 것을
펴는 **왜곡 보정**(행렬 K, 계수 D), ② 비스듬히 본 바닥을 위에서 본 것처럼 펴는
**지면 호모그래피**(행렬 H). 결과는 전부 `config/camera.yaml` 한 파일에 들어가고,
주행 노드는 `track_drive/lib/bev.py` 를 통해 그것을 읽는다.

### 1.2 전체 그림

```
 [카메라 원본]        ① 왜곡 보정        ② 지면 호모그래피      [주행 코드]
 1920x1080 픽셀   ──────────────────>  ────────────────────>  x,y 미터 좌표
                    K, D 사용            H 사용
 직선이 휘어 보임    직선이 곧아짐        위에서 본 그림(BEV)    조향/거리 판단

 ┌───────────────────────────────────────────────────────────────────┐
 │  config/camera.yaml  ← 이 두 단계의 숫자가 전부 여기 들어 있다      │
 │    K, D, model      : 왜곡 보정용                                  │
 │    new_K            : 편 사진의 픽셀 좌표계를 정의                 │
 │    H                : 편 픽셀 → 지면 미터                          │
 │    h_phys           : H 를 만든 물리값 4+3개 (사람이 만지는 값)     │
 │    car_mask_v       : 화면 아래 차체를 잘라내는 경계선             │
 └───────────────────────────────────────────────────────────────────┘
```

이 문서에서 제일 자주 나오는 네 이름(K, D, H, new_K)을 한 번에 정리해 둔다. 생김새가
비슷해서 헷갈리기 쉬운데, **역할과 "언제 다시 만들어야 하는지"가 서로 다르다.**

| 이름 | 무엇인가 | 언제 다시 만들어야 하나 |
|---|---|---|
| **K** | 렌즈의 신분증. 픽셀 하나가 어느 방향인지를 정하는 3x3 (`fx, fy, cx, cy`) | 렌즈를 바꾸거나 해상도를 바꿨을 때 |
| **D** | 렌즈가 사진을 얼마나 휘게 만드는지를 적은 숫자 5개 `[k1,k2,p1,p2,k3]` | 렌즈를 바꿨을 때 (해상도가 바뀌어도 그대로) |
| **new_K** | 왜곡을 편 결과를 담을 "화면 틀". 편 사진의 픽셀 번호를 정한다 | K/D/해상도/`alpha` 중 하나라도 바뀌면 |
| **H** | 편 사진 픽셀 → 지면 미터로 바꾸는 3x3 | 위 셋 중 하나라도 바뀌면 (= 제일 잘 무효가 된다) |

읽는 순서는 **K,D → new_K → H** 다. 위쪽이 바뀌면 아래쪽은 전부 다시 해야 하고,
반대로 아래쪽만 따로 바뀌는 일은 없다. 이 의존 관계 하나만 기억하면 이 문서에 나오는
경고문의 절반이 저절로 이해된다.

### 1.3 ① 렌즈 왜곡 보정 (K, D)

렌즈는 유리를 깎아 만든 물건이라 완벽하지 않다. 특히 화각(카메라가 한 번에 담는
시야의 각도. 넓을수록 많이 보이지만 가장자리가 더 휜다)이 넓은 렌즈일수록 사진의
가장자리가 볼록하게 부풀어 보인다(배럴 왜곡 — 술통(barrel)처럼 가운데가 부풀어
직선이 활처럼 휘는 현상). 실제로는 자로 그은 직선인 바닥 테이프가
사진에서는 활처럼 휘어 나온다.

```
   실제 바닥              원본 사진 (배럴 왜곡)        왜곡 보정 후
  ┌───────────┐          ┌───────────┐              ┌───────────┐
  │ ───────── │          │  ╭─────╮  │              │ ───────── │
  │ ───────── │   찍으면 │ ╭───────╮ │   K,D 적용   │ ───────── │
  │ ───────── │  ──────> │╭─────────╮│  ─────────>  │ ───────── │
  │ ───────── │          │╰─────────╯│              │ ───────── │
  └───────────┘          └───────────┘              └───────────┘
   직선                   바깥쪽이 휨                 다시 직선
```

이 휨을 펴는 데 필요한 숫자가 두 덩어리다.

- **K (내부 행렬, 3x3)**: 초점거리 `fx`, `fy` 와 화면 중심 `cx`, `cy`. "픽셀 하나가
  몇 도의 각도에 해당하는가"를 정하는 값이다. 우리 값은 `camera.yaml:18-27` 에
  `fx=789.0`, `fy=874.6`, `cx=966.8`, `cy=540.3` 로 들어 있다.
  말하자면 **렌즈의 신분증**이다. `fx`/`fy` 는 "픽셀 몇 개가 얼마만큼의 각도인가"
  (크면 확대돼 보이는 렌즈), `cx`/`cy` 는 "렌즈의 정중앙이 화면의 몇 번째 픽셀에
  찍히는가"다. 우리 값 `cx=966.8`, `cy=540.3` 은 1920x1080 화면의 한가운데
  (960, 540) 바로 옆이다 — 렌즈가 거의 정중앙에 달려 있다는 뜻이다.
- **D (왜곡 계수)**: 왜곡 모델이 `plumb_bob` (브라운-콘라디, 일반 광각용)이면 5개
  `[k1, k2, p1, p2, k3]`. `camera.yaml:2-7` 에 `k1=-0.374` 등으로 들어 있다.
  `k1` 이 음수면 배럴 왜곡을 펴는 방향이다.
  `k1, k2, k3` 는 **중심에서 멀어질수록 얼마나 휘는가**(방사 왜곡)를 1차·2차·3차로
  나눠 적은 것이고, `p1, p2` 는 **렌즈와 센서가 아주 조금 안 나란해서 생기는
  치우침**(접선 왜곡)이다. 이 중 굵은 손잡이가 `k1` 이라 손으로 만질 일이 생기면
  `k1` 부터 건드린다(`tuner.py:66`).

렌즈 모델을 `fisheye`(등거리 어안)가 아니라 `plumb_bob` 으로 확정한 근거는
`dev/README.md:24` 와 `lib/bev.py:15` 에 남아 있다 — **벤더 PDF 의 "170도 어안" 표기는
오기였고, 실측 화각은 가로 87.2도 / 세로 64.1도의 일반 광각**이었다. 87도짜리 렌즈에
어안 모델을 쓰면 파라미터가 남아돌아(**과파라미터화** — 펴야 할 휨보다 손잡이가 더
많은 상태. 남는 손잡이가 진짜 휨이 아니라 촬영 잡음까지 따라 그려 버려서, 사진 몇 장에는
잘 맞는 대신 다른 사진에서는 오히려 더 나빠진다) 가장자리가 오히려 더 나빠진다
(`tools/calib_camera.py:11-13`, 같은 취지가 `calib_camera.py:220-221` 의 실패 안내문에도 있다).

실제로 펴는 코드는 `lib/bev.py` 의 `Undistorter` 클래스(288~376줄)다. 리맵 테이블을
한 번만 만들어 캐시하고(`__init__` 안 `cv2.initUndistortRectifyMap`, 347~348줄), 매 프레임은
`apply()` 에서 `cv2.remap` 만 부른다(371~376줄).

> **리맵 테이블**이란 "결과 사진의 (0,0) 픽셀은 원본 사진의 (3.2, 1.7) 에서 퍼오고,
> (0,1) 은 (4.1, 1.7) 에서 퍼오고 …" 를 화면 전체에 대해 미리 다 적어 둔 표다.
> 휘는 정도를 계산하는 일(삼각함수, 거듭제곱)은 표를 만들 때 딱 한 번만 하고,
> 이후 매 프레임은 표를 보고 픽셀을 퍼 오기만 하면 된다. K/D/해상도가 안 바뀌면
> 표도 안 바뀌므로 이 캐시가 성립한다.

### 1.4 ② 지면 호모그래피 (H)

호모그래피(Homography)는 **카메라가 비스듬히 본 바닥 사진을 "위에서 내려다본 것처럼"
펴주는 3x3 변환 행렬**이다. 기울어진 각도로 찍은 종이 사진을 스캐너로 반듯하게 펴는
것과 같다. 결과 그림을 BEV(Bird's Eye View, 새가 위에서 본 시야)라고 부른다.

```
   [옆에서 본 그림]

              카메라 (높이 0.20 m, 내림각 7.24도)
               ▗▄▖
               ▐█▌ ＼
               ▐█▌   ＼  ← 시선
        ┌──────┴─┴─────＼────────────────────────────────
        │ 원점            ＼
        │ (라이다 회전중심의        ＼
        │  지면 수선의 발)              ＼
        └──────────────────────────────────＼──── 바닥
        x=0            x=0.45m         x=0.9m   x=1.35m ...
                       (타일 줄눈 = 0.4533 m 간격)

   화면에서는 이 등간격 줄눈이 위로 갈수록 촘촘해 보인다.
   H 는 그 "촘촘해짐"을 정확히 되돌려 다시 등간격으로 만든다.
```

H 는 `camera.yaml:8-17` 에 9개 숫자로 저장된다. 이 H 는 **"편 사진의 픽셀 (u,v)" 를
넣으면 "지면 좌표 (x,y) 미터" 가 나오는** 행렬이다. 좌표 규약은 ROS REP-103
(ROS 가 정해 둔 좌표축 표준 문서. x 는 앞, y 는 왼쪽, z 는 위, 단위는 미터. 이걸
따라야 라이다·IMU 등 다른 센서와 좌표가 저절로 맞는다) 을 따른다
(`bev_view.py:5-8`):

- 원점 = **라이다 회전중심을 지면에 수직으로 내린 점** (`camera.yaml:34` `h_frame: lidar_frame`)
- x = 전방(+), y = 좌측(+), 단위 m
- 카메라 렌즈는 라이다보다 10cm 뒤에 있다 (`camera.yaml:39` `h_lidar_offset_x: 0.1`)

### 1.5 두 단계의 순서가 왜 중요한가

**왜곡 보정을 먼저 확정하고, 그다음 H 를 맞춰야 한다.** 이유는 하나다 — H 는 "편
사진의 픽셀"을 입력으로 받기로 약속했는데, 왜곡 계수를 하나라도 건드리면 편 사진의
모든 픽셀이 통째로 움직여 버린다. 그러면 앞서 맞춘 H 는 전부 무효다.

`dev/TUNING.md:78-81` 에 이 규칙이 명시돼 있다: "`k1` 을 바꾸면 보정영상의 픽셀 위치가
통째로 움직이므로 H 를 먼저 맞춰도 무효가 된다."

더 미묘한 함정이 하나 더 있다. 왜곡을 펼 때 "편 사진을 어떤 화면 틀에 담을지"를
정하는 또 하나의 행렬이 있는데 그것이 **`new_K`** 다. `plumb_bob` 모델은 `alpha`
값과 이미지 크기에 따라 `new_K` 가 자동으로 달라진다(`lib/bev.py:339-344` 의
`cv2.getOptimalNewCameraMatrix(K, D, (w,h), alpha)`). 즉
**해상도만 640x480 → 1920x1080 으로 바꿔도 `new_K` 가 달라져 H 가 무효가 된다.**
그래서 캘리브 당시의 `new_K` 를 yaml 에 그대로 적어 두고(`camera.yaml:62-71`),
런타임에 `check_new_K_match()` (`lib/bev.py:379-409`)로 대조해 어긋나면 경고를 띄운다.

#### `alpha` 가 무엇인가 — 그림으로

왜곡을 펴면 사진의 가장자리가 안쪽으로 오목하게 들어간다(원래 바깥으로 부풀어 있던
것을 폈으니 당연하다). 그런데 화면은 네모다. **오목한 그림을 네모 화면에 담는 방식**
두 가지 중 어느 쪽으로 갈지를 정하는 0~1 사이 숫자가 `alpha` 다.

```
  alpha = 0.0  (우리가 쓰는 값)             alpha = 1.0
  ┌─────────────────────┐                  ┌─────────────────────┐
  │█████████████████████│                  │▒▒▒░░░░░░░░░░░░░░░▒▒▒│ ← 검은 여백
  │█████████████████████│                  │░░███████████████░░░░│
  │███  사진으로 꽉  ████│                  │░░██  사진 전부  ██░░░│
  │█████████████████████│                  │░░███████████████░░░░│
  │█████████████████████│                  │▒▒▒░░░░░░░░░░░░░░░▒▒▒│
  └─────────────────────┘                  └─────────────────────┘
   검은 여백이 0. 대신 오목하게            원본 화소를 하나도 안 버린다.
   들어간 바깥쪽 화소는 잘려 나간다        대신 네 귀퉁이에 검은 여백이 생긴다
```

- `alpha = 0` : **검은 여백 없이 크롭.** 여백을 없애려고 안쪽만 오려 담으므로,
  원본의 바깥쪽 화소 일부를 버린다. 화면이 깔끔하고 "모든 픽셀이 진짜 영상"이다.
- `alpha = 1` : **원본 화소 전부 보존.** 하나도 안 버리는 대신 귀퉁이에 검은 여백이
  남고, 그 여백까지 차선으로 잘못 잡힐 여지가 생긴다.
- 중간값(0.5 등)은 이 둘을 섞은 절충이다.

기본값은 `lib/bev.py:73-75` 의 `UNDISTORT_ALPHA_DEFAULT = 0.0` 이고, `camera.yaml:32`
에도 `h_alpha: 0.0` 이 기록돼 있다.

★ 여기서 핵심은 **`alpha` 를 바꾸면 `new_K` 가 바뀌고, `new_K` 가 바뀌면 편 사진의
픽셀 번호가 통째로 밀린다**는 것이다. H 는 그 픽셀 번호를 입력으로 받기로 약속한
행렬이므로 그대로 무효가 된다. `alpha`, 왜곡 모델, 이미지 크기 — 이 셋 중 하나라도
캘리브 때와 다르면 H 를 다시 맞춰야 한다(`lib/bev.py:405-407` 의 경고문이 이 셋을
그대로 열거한다).

> 지금 우리 설정에서의 실제 동작 한 가지를 덧붙인다. `camera.yaml` 에 `new_K` 가
> **직접 적혀 있으면** 런타임은 그 값을 그대로 쓰고 `getOptimalNewCameraMatrix` 를
> 아예 부르지 않는다(`lib/bev.py:339-346` — `if new_K is None:` 일 때만 부른다).
> 그리고 그 `new_K` 는 `ground_fit.py` 가 캘리브 당시 `출력화각` 값으로 직접 만들어
> 저장한 것이다(`ground_fit.py:383-386`). 그래서 `camera.yaml:62-71` 의 `new_K` 는
> 중심이 정확히 (960.0, 540.0) — 화면 한가운데 — 로 딱 떨어져 있다.
> 즉 `alpha` 는 지금 "yaml 에 `new_K` 가 없을 때를 대비한 값"이다.

> 실제로 1080p 로 올릴 때 이 문제를 겪었다. 커밋 `d1be718` 메시지에 "camera.yaml 의
> image_width/height 와 반드시 일치해야 한다 (다르면 new_K 가 달라져 H 가 통째로
> 무효)" 라고 기록돼 있다.

## 2. ★ 물리 파라미터 방식 — 9개 대신 4개를 만진다

### 2.1 한 문단 요약

H 는 숫자 9개짜리 행렬이지만, 이 프로젝트는 그 9개를 직접 만지지 않는다. 대신
**카메라의 물리적 자세 4개**(높이·내림각·좌우틀어짐·기울기)를 조절하고, 그로부터
H 를 계산해 낸다. 그 계산을 하는 함수가 `tools/ground_fit.py:83` 의 `build_H()` 다.
그리고 조절한 물리값은 `camera.yaml` 의 `h_phys` 항목(41~54줄)에 그대로 저장돼,
다음에 도구를 열면 그 값부터 다시 시작할 수 있다.

### 2.2 왜 9개가 아니라 4개인가

H 의 9개 원소는 서로 얽혀 있다. `h00` 하나를 키우면 축척(지도의 축척과 같은 뜻 —
화면에서 1픽셀 움직였을 때 지면에서 몇 미터인가의 비율)도 변하고 기울기도 변하고
원점도 밀린다. 사람이 "지금 화면이 이렇게 안 맞으니 어떤 숫자를 어느 쪽으로 돌려야
하는가"를 감으로 잡을 수가 없다. `tools/tuner.py:86-88` 에 그 어려움이 실측으로
기록돼 있다 — "어떤 원소도 거리와 무관한 평행이동이 아니다. 전부 1/W 를 공통인자로
가져서 먼 곳에서 효과가 커진다(2m/1m 배율: h21 3.4배, h22·h20 3.8배)."

반면 물리값 4개는 **실물과 1:1 로 대응된다**. "카메라를 자로 재보니 지면에서 20cm
높이에 있다", "고개를 약 7도 숙이고 있다" 처럼 눈으로 확인하고 검증할 수 있는 값이다.
값이 이상하면(예: 높이가 0.6m 로 나오면) 그 자체로 "뭔가 틀렸다"를 알 수 있다.
`ground_fit.py:5-7` 의 주석이 이 판단을 그대로 적어 놓았다.

### 2.3 `build_H()` 가 하는 일 (수식 없이)

`tools/ground_fit.py:83-98`.

1. 초점거리 `fx, fy` 와 화면 중심 `cx, cy` 로 카메라 내부 행렬 K 를 만든다(90줄).
   이것이 "화면의 이 픽셀은 카메라에서 어느 방향인가"를 정한다.
2. 카메라가 세상을 어느 방향으로 보고 있는지를 회전 행렬로 만든다(91~96줄).
   기본 자세 `R0`(수평 정면)에 내림각 `Rp`, 좌우틀어짐 `Ry`, 기울기 `Rr` 을 차례로 곱한다.
3. 카메라가 지면 원점에서 어디에 있는지(높이 `height`, 앞뒤 `cam_x`, 좌우 `cam_y`)를
   평행이동 `t` 로 넣는다(97줄). 라이다가 카메라보다 10cm 앞이므로 `cam_x = -0.10` 이
   들어간다(`ground_fit.py:409`).
4. "지면의 점 → 화면 픽셀" 변환을 만든 뒤 **역행렬**(어떤 변환을 정확히 거꾸로
   돌리는 짝 행렬. A 로 갔던 것을 `inv(A)` 로 되돌리면 원래 자리로 돌아온다)**을
   취해** "화면 픽셀 → 지면의 점" 으로 뒤집는다(98줄 `np.linalg.inv`). 물리적으로
   상상하기 쉬운 방향은 "바닥의 이 점이 화면 어디에 찍히나"인데, 주행 코드가 필요한
   건 그 반대 방향("화면의 이 점이 바닥 어디인가")이라 한 번 뒤집는 것이다.

즉 build_H 는 "카메라를 이 높이, 이 각도로 세워 놓았다고 치면 화면과 바닥이 어떻게
대응되겠는가"를 계산해 주는 함수다. 사람은 물리적으로 상상 가능한 값만 넣으면 되고,
9개 숫자의 정합성은 함수가 알아서 보장한다.

### 2.4 파라미터를 올리면 화면에서 무엇이 움직이는가

`ground_fit.py:101-114` 의 `PARAMS` 목록이 화면 하단에 그대로 뜬다.

먼저 각도 세 개의 이름부터. 카메라가 어느 방향을 보고 있는지는 **축 세 개로 나눠**
부르는 것이 관례이고, 사람 머리로 비유하면 이렇다.

```
   내림각 (pitch)          좌우틀어짐 (yaw)         기울기 (roll)
   고개를 끄덕 ↕            고개를 도리 ↔            고개를 갸우뚱 ↻

      ○                        ○                       ○
     /|\  ↓ 아래를 봄        ←/|\→  옆을 봄           /|\  ↺ 옆으로 기울임
```

우리 카메라는 앞을 보되 바닥이 보이게 조금 숙여 달았으므로 **내림각이 7.24도**,
좌우로는 거의 안 틀어졌으니 **좌우틀어짐 -0.20도**, 살짝 갸우뚱하게 달렸으니
**기울기 -1.60도** 다. 이 세 값은 자로 재거나 눈으로 확인할 수 있는 물리량이다.

| 파라미터 | 뜻 | 값을 올리면 |
|---|---|---|
| 내림각 (pitch, deg) | 카메라가 아래를 보는 각 ★ | 먼 곳이 화면 위로 올라감 (BEV 세로 압축) |
| 높이 (height, m) | 카메라 지면높이 ★ | BEV 가 통째로 커짐 (전체 균일 확대) |
| 좌우틀어짐 (yaw, deg) | 좌우 회전 | 격자가 좌우로 회전 (테이프가 비스듬할 때) |
| 기울기 (roll, deg) | 화면이 갸우뚱한 정도 | 한쪽 변이 들리는 변형 |

여기에 "차를 어디 세웠나"를 맞추는 격자 위치 2개와 축척 손잡이가 붙는다.

★ 격자 위치 2개는 격자의 **간격**이 아니라 **시작 위치**를 정하는 값이다(전문 용어로는
격자의 "위상"이라고 한다). 간격은 바닥 타일이 정한 것이라 이미 0.4533m 로 고정돼
있고(`--pitch-m`), 그 자를 앞뒤·좌우로 통째로 밀어 실제 줄눈에 겹쳐 놓는 것이
`격자_앞`/`격자_옆` 이다. 차를 세운 위치가 조금 달라지면 이 두 값만 다시 맞추면 된다.

| 파라미터 | 뜻 | 값을 올리면 |
|---|---|---|
| 격자_앞 (grid_x0, m) | 라이다 중심 → 첫 가로줄 거리 | 초록 가로선이 통째로 앞으로 밀림 |
| 격자_옆 (grid_y0, m) | 중앙 세로줄의 좌우 위치 | 초록 세로선이 통째로 왼쪽으로 밀림 |
| fx | ★가로 축척 | 작게 하면 지면 좌우가 넓게 계산됨 |
| 출력화각 (out_fx) | 보정영상을 얼마나 넓게 담을지 | 작게 하면 더 넓게 보임 (BEV 좌표엔 영향 0) |

**★ 여기서 가장 헷갈리기 쉬운 것이 `fx` 와 `출력화각` 의 구분이다.** 왜곡 보정을 켠
상태에서 조절한 `fx/fy` 는 **왜곡 모델의 K** 로 들어간다(`ground_fit.py:374-376`).
그것이 픽셀→각도 변환을 정하고, 곧 지면 축척이 된다. 반면 `출력화각`은 결과 영상의
화면 틀(`new_K`)만 정하며, 뒤에서 `inv(new_K)` 로 상쇄되므로 **지면 좌표에는 영향이
전혀 없다**(`ground_fit.py:381-386` 주석). 커밋 `d1be718` 에 실측 검증이 남아 있다 —
"출력 fx 를 789~560 으로 흔들어도 지면좌표 변화 0.000000m".

### 2.5 현재 채택된 값 (2026-07-31 기준)

`config/camera.yaml:41-54` 의 `h_phys`:

| 항목 | 값 | 비고 |
|---|---|---|
| height | 0.20 m | 카메라 지면높이 |
| pitch_deg | 7.24 | 내림각 |
| yaw_deg | -0.20 | 거의 정면 |
| roll_deg | -1.60 | 살짝 갸우뚱 |
| fx / fy | 789.01 / 874.56 | 왜곡모델 K 기준 |
| out_fx | 847.52 | 출력 화면 틀 (좌표 무관) |
| grid_x0 / grid_y0 | 0.45 / 0.00 | 촬영 당시 차 위치 |
| undistort | **true** | 왜곡보정 켜고 저장했다 |

> ★ 읽을 때 주의: `ground_fit.py` 의 파일 맨 위 설명(3~11줄)은 "왜곡보정을 아예 쓰지
> 않고 원본 픽셀에 H 를 건다"고 적혀 있다. 그것은 도구를 처음 만들 때의 설계 의도이고,
> **최종 채택된 값은 왜곡보정을 켠 상태**다(`h_phys.undistort: true`,
> `camera.yaml:58 intrinsics_calibrated: true`, `camera.yaml:55 h_source` 에
> "왜곡보정 사용, new_K=K 기준 보정픽셀" 로 기록). 실행 중 `[u]` 키로 켠 뒤 저장한
> 결과다. 문서와 실제 값이 다르니 이 문단을 기억할 것.

## 3. `tools/ground_fit.py` — 주력 캘리브 도구

### 3.1 한 문단 요약

지면 H 를 물리값으로 맞추는 도구. 왼쪽에 카메라 영상 + 예측 격자, 오른쪽에 BEV 를
나란히 띄우고, 방향키로 물리값을 돌리면 두 화면이 즉시 다시 그려진다.
**초록선이 바닥 테이프 위에 얹히면 맞은 것**이고, 그 상태에서 `s` 를 누르면
`camera.yaml` 이 갱신된다. 737줄짜리 파일이지만 실제로 알아야 할 것은 키 12개다.

### 3.2 실행

```bash
# 차에서 실시간으로
python3 tools/ground_fit.py --topic /image_raw
# 저장된 사진으로 (노트북 WSL 에서 작업할 때)
python3 tools/ground_fit.py --image dev/shots/tape4_raw.jpg
# 화면이 커서 창이 안 들어가면
python3 tools/ground_fit.py --view-h 320 --ppm 110
```

★ **`--ppm` 은 "pixels per meter", 곧 BEV 그림에서 1미터를 몇 픽셀로 그릴지다.**
`--ppm 110` 이면 지면 1m 가 화면에서 110픽셀이 된다. 전방 2.75m 를 보면 세로 약
302픽셀짜리 그림이 나오는 식이다. 순전히 **그림을 얼마나 크게 그릴지**를 정하는
표시 배율이라, 이 값을 바꿔도 마우스로 찍어 읽는 좌표값이나 저장되는 H 는 전혀
안 변한다. 창이 화면에 안 들어갈 때 줄이고, 격자를 자세히 보고 싶을 때 키운다.

```
   같은 지면 1.0m 구간을 BEV 로 그린 결과

   --ppm 110        [■■■■■■]              110 px  ← 창이 작다, 대신 거칠다
   --ppm 300        [■■■■■■■■■■■■■■■■]    300 px  ← 세밀하다, 대신 창이 크다

   어느 쪽이든 "이 구간은 1.000 m" 라는 좌표값은 똑같다
```

기본값은 `0` 인데, 이것은 "안 쓴다"가 아니라 **`--view-h`(화면 패널 높이)와 전방
범위로부터 자동으로 역산하라**는 뜻이다(`ground_fit.py:260`
— `ppm = view_h / (전방범위 폭)`). 그래서 보통은 `--view-h` 만 주면 된다.
BEV 를 작게 만들어 놓고 나중에 확대하면 영상이 번지고 격자선이 뭉개지므로, 처음부터
표시할 크기 그대로 렌더하려고 이렇게 짜 놓은 것이다(`ground_fit.py:258-260` 주석).

주요 옵션 (`ground_fit.py:168-188`):

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `--pitch-m` | 0.453333 | 바닥 타일 한 칸 실측 피치 (m) |
| `--nx` / `--ny` | 6 / 5 | 그릴 가로줄 / 세로줄 개수 |
| `--lidar-offset` | 0.10 | 라이다가 카메라보다 앞선 거리 (m) |
| `--range-x` | -0.35 ~ 2.4 | BEV 전방 범위. 음수까지 넣어야 원점 뒤도 보인다 |
| `--ppm` | 0 (자동) | BEV 표시 배율, 픽셀/미터. 0 이면 `--view-h` 에서 역산 |
| `--view-h` | 380 | 화면 패널 높이 px |
| `--fps` | 6.0 | 화면 갱신 상한 (원격 데스크톱 부하 절감) |

### 3.3 화면 구성

```
┌──────────────────────────────┬──────────────────────────────┐
│ 왼쪽: 카메라 영상             │ 오른쪽: BEV (위에서 본 그림)   │
│                              │                              │
│  초록 가로선 = H 로 예측한    │  노랑 가로선 = 예측 격자      │
│    타일 줄눈 위치            │  하늘색 세로선 = y=0 (정면)   │
│  하늘색 세로선 = 중앙 세로줄  │  빨강 가로선 = x=0 (원점)     │
│  파란 원 = 원점(라이다 지면점)│  자홍 가로선 = 카메라 렌즈    │
│                              │  주황 점선 = "여기부터 실제   │
│  ★ 초록선이 실제 테이프 위에  │    지면" (아래는 차체)        │
│    얹히면 맞다               │  ★ 두 점 클릭 → 실제 거리 mm  │
├──────────────────────────────┴──────────────────────────────┤
│ 파라미터 12줄 (선택된 줄은 노랑 + ▶ 표시)                     │
│   내림각  7.24   ±0.2   카메라가 아래를 보는 각 deg ★ ...     │
│ 잰 거리 452 mm   (45cm 자=450, 타일 한 칸=453)               │
│ ↑↓ 선택  ←→ 값  [ ] 스텝  0 되돌리기  ... s 저장  q 종료      │
└─────────────────────────────────────────────────────────────┘
```

왼쪽 초록선을 그리는 코드는 `line_img()` (`ground_fit.py:429-441`)이고,
BEV 는 `ground_fit.py:477-500` 에서 역매핑으로 만든다. **역매핑**은 "원본 픽셀을
하나씩 결과 쪽으로 던지는" 게 아니라 반대로 **"결과 그림의 빈칸마다 원본 어디서
가져올지를 되짚어 가는"** 방식이다. 앞의 방식은 던진 픽셀이 겹치거나 빈 구멍이
생기지만, 되짚는 방식은 결과 그림의 모든 칸이 정확히 한 번씩 채워진다.
1.3절의 리맵 테이블도 같은 발상이다. **BEV 격자와 리맵 테이블은
파라미터가 바뀔 때만 다시 만든다**(`cache["key"]` 비교, 482줄). 매 프레임 다시 만들면
1920x1080 에서 창이 버벅이기 때문이다(23~24줄 주석).

또 하나 성능 대책 — **기본이 '정지 화면'이다**(`ground_fit.py:335-337`). 카메라도 장면도
안 움직이므로 실시간일 이유가 없고, 원격 데스크톱으로 매 프레임을 전송하는 것이 진짜
병목이었다. 새 프레임이 필요하면 `[스페이스]` 를 누른다.

### 3.4 키 목록 전체

`ground_fit.py:606-730` 의 키 처리부에서 그대로 추출한 것이다.

| 키 | 동작 |
|---|---|
| `↑` `↓` (또는 `w` `x`) | 파라미터 선택 (12개 순환) |
| `←` `→` (또는 `a` `d`) | 선택한 값 감소 / 증가 |
| `[` `]` | 스텝 배율 ÷10 / ×10 (0.001 ~ 1000배) |
| `0` | 선택한 항목만 초기값으로 |
| `R` (대문자) | 전부 초기값으로 |
| `b` | ★ 대략맞추기 (부트스트랩 — 맨바닥에서 출발값을 자동으로 잡아 주는 것) — 아래 3.5 참고 |
| `u` | 왜곡보정 켜기/끄기 |
| `스페이스` | 새 프레임 한 장 받아오기 |
| `c` | BEV 에서 찍은 거리 측정 점 지우기 |
| `s` | `camera.yaml` 저장 (백업 자동 생성) |
| `q` / `ESC` | 종료 |

화살표 키가 안 먹는 환경(원격 데스크톱 등)이 있어서 `w x a d` 를 대체 키로 넣어 뒀다
(`ground_fit.py:609-612`).

### 3.5 ★ 초기 부트스트랩 — `b` 키 (가로 테이프 3줄 클릭)

값이 아무것도 없는 상태에서 방향키만으로 4개 파라미터를 찾는 건 고통스럽다. 그래서
**클릭 3번으로 대략의 답을 자동으로 풀어 주는** 기능이 있다.

1. `b` 를 누른다. 화면에 "가로 테이프 3줄을 가까운 것부터 차례로 클릭"이라고 뜬다.
2. 왼쪽(카메라) 화면에서 바닥의 **가로 테이프/줄눈 3개**를 가까운 것부터 클릭한다.
3. 3번째 클릭 뒤 아무 키나 누르면 계산이 돌고, **내림각·높이·격자_앞** 3개가 자동으로
   채워진다. 잔차(mm)도 함께 표시된다.
   (**잔차** = 계산이 내놓은 답으로 다시 그려 본 줄 위치와, 내가 실제로 클릭한 위치의
   차이. 이 값이 몇 mm 수준이면 잘 풀린 것이고, 몇 cm 씩 나오면 클릭을 잘못했거나
   엉뚱한 줄을 찍은 것이다.)

원리는 `rough_fit()` (`ground_fit.py:292-332`). 연속한 가로줄이므로 지면 x 좌표는
반드시 `gx0`, `gx0+P`, `gx0+2P` 여야 한다(P = 타일 피치 0.4533m). 미지수 3개에 식 3개라
풀린다. 좌우틀어짐과 기울기는 0 으로 두고 푼다(295~296줄). 초기 추정값 5세트로
각각 최소제곱을 돌려 제일 잘 맞은 것을 고른다(320~329줄).

> **최소제곱**은 "잔차들을 각각 제곱해서 다 더한 값이 가장 작아지는 답"을 찾는
> 방법이다. 제곱을 하는 이유는 부호(+/-)를 없애고, 크게 어긋난 점에 더 큰 벌점을
> 주기 위해서다. 클릭이 픽셀 단위로 조금씩 부정확해도 세 점을 "가장 덜 어긋나게"
> 만족시키는 답을 자동으로 골라 준다.
> **초기 추정값 5세트**를 쓰는 이유는, 이런 계산은 출발점이 나쁘면 엉뚱한 답에
> 주저앉을 수 있어서다. 서로 다른 출발점에서 5번 풀어 보고 제일 잘 맞은 것을 채택한다.

> 주의: `scipy` 가 필요하다(`from scipy.optimize import least_squares`, 299줄).
> 없으면 "scipy 없음" 메시지만 뜨고 아무 일도 안 일어난다.

### 3.6 `s` 를 누르면 `camera.yaml` 의 무엇이 바뀌는가

`ground_fit.py:669-730`. 저장 전에 백업을 두 개 만든다 — 최초 1회만 `.orig`,
그리고 매번 `.bak.MMDD-HHMMSS` (680~683줄). 그래서 `config/` 에 `camera.yaml.bak.*`
파일이 여러 개 쌓여 있는 것이다.

바뀌는 항목:

| 키 | 내용 |
|---|---|
| `H` | 현재 물리값으로 만든 3x3 행렬 (685줄) |
| `h_calibrated` | 항상 `true` (686줄) |
| `intrinsics_calibrated`, `calibrated` | `[u]` 로 켠 왜곡보정 상태 그대로 (687-688줄) |
| `K`, `D`, `new_K` | 왜곡보정 켰을 때만. 끄면 `new_K` 를 지운다 (689-697줄) |
| `image_width/height` | 지금 프레임 크기 (698줄) |
| `h_frame` | `"lidar_frame"` 고정 (699줄) |

저장 직후 터미널에 H 행렬이 그대로 찍힌다(730줄). 이 값을 복사해 두면 나중에 비교가
쉽다.

### 3.7 ★ 캘리브를 처음부터 다시 한다면 — 단계별 절차

카메라를 새로 달았거나, 위치가 틀어졌거나, 해상도를 바꿨을 때 따라 할 순서다.

**0단계 — 바닥 준비.** 등간격 격자가 있는 바닥을 찾는다. 우리는 복도 테라조 타일
줄눈을 썼다. 피치는 **여러 칸을 한 번에 재서 나눈다** — 6칸을 2.72m 로 재서
`2.72/6 = 0.453333 m` (`calib_ground_h.py:38-39`, 상수는 `calib_ground_h.py:128`).
한 칸만 재면 오차가 6배로 남는다.
줄눈이 없으면 바닥에 마스킹 테이프로 격자를 붙인다. **화면 중앙뿐 아니라 좌우
가장자리까지 격자가 걸치게 붙일 것** (지금 캘리브의 알려진 한계가 이것이다 — 8.3 참고).

**1단계 — 해상도 모드 결정.** `python3 tools/cam_modes.py` 로 모드를 고른다(5장 참고).
지금은 **1920x1080 MJPG 30fps** 로 확정돼 있으므로 카메라를 바꾸지 않았다면 건너뛴다.

**2단계 — 카메라 좌우 정렬.** 같은 `cam_modes.py` 화면에서 화면 아래 라이다 원통을
자동으로 찾아 "중심에서 몇 % 벗어났는지"를 실시간으로 보여 준다(`cam_modes.py:206-219`).
카메라를 손으로 돌려 이 값이 ±1% 안으로 들어오게 맞춘다. 여기서 맞춰 두면 나중에
`좌우틀어짐(yaw)` 을 거의 안 건드려도 된다.

**3단계 — 카메라 기동.**
```bash
bash ~/xycar_ws/src/track_drive/dev/scripts/start_cam.sh      # 1920x1080 MJPG 30fps
```
스크립트가 기동 후 `ros2 topic hz /image_raw` 로 실제 발행 fps 까지 확인해 준다
(`start_cam.sh:55-58`).

**4단계 — 사진 촬영.** 차를 격자 위에 세우고 조명을 켠 다음:
```bash
python3 ~/xycar_ws/src/track_drive/dev/scripts/_shot.py tape5 20
```
**20장을 받아 중앙값을 취한다**(`_shot.py:50` `np.median`. 두 번째 인자를 빼면 기본
15장이다 — `_shot.py:24`). JPEG 압축 잡음과 센서 노이즈가 줄어
줄눈이 훨씬 또렷해진다.

> **중앙값**은 20장의 **같은 자리 픽셀 20개**를 밝기순으로 늘어놓고 딱 가운데 것을
> 고르는 것이다. 평균이 아니라 중앙값을 쓰는 이유는, 어느 한 장에 튄 잡음이 섞여도
> 그 값은 줄 맨 끝으로 밀려나 결과에 아예 반영되지 않기 때문이다. 카메라도 장면도
> 안 움직이는 캘리브 촬영이라 이 방법이 그대로 통한다. `dev/shots/tape5_raw.jpg` 와 현재 K/D 로 보정한
`tape5_und.jpg` 두 장이 나온다.

**5단계 — K/D 확보.** 체스보드(흑백 격자를 인쇄한 판. 격자 간격이 얼마인지 이미
알고 있으니, 사진 속 격자가 얼마나 휘어 찍혔는지를 보면 렌즈 왜곡을 역산할 수 있다.
카메라 캘리브의 교과서적 방법이다) 재촬영은 하지 않는다(7장 참고). 차에 이미 있는
벤더 캘리브를 가져온다:
```bash
# 패키지 루트(~/xycar_ws/src/track_drive)에서 실행할 때
python3 tools/import_camera_info.py --file ~/.ros/camera_info/default_cam.yaml \
    --save config/camera.yaml
```
`--save` 는 그냥 현재 폴더 기준 경로다(`import_camera_info.py:343-344`). 파일 헤더의
예제(`--save ../config/camera.yaml`)는 `tools/` 안에서 실행할 때의 경로이니 섞어 쓰지 말 것.

해상도가 캘리브 당시와 다르면 K 를 배율+크롭 오프셋으로 환산해야 한다. 우리는
640x480 캘리브를 1080p 로 환산했고, 그 근거가 `camera.yaml:59-61` 의
`intrinsics_source` 에 적혀 있다 (실측 배율 1.9999, 잘림원점 (319.6, 52.8) — ORB 정합).
D 는 정규화 좌표 기준이라 해상도가 바뀌어도 그대로다.

두 낯선 말을 풀면 이렇다.

- **ORB 정합**: ORB 는 사진에서 모서리처럼 눈에 띄는 지점(특징점)을 자동으로 찾아
  주는 알고리즘이고, 정합은 두 사진에서 찾은 특징점끼리 짝을 지어 주는 일이다.
  640x480 사진과 1080p 사진에서 같은 지점들을 짝지어 보면 "두 사진이 몇 배 차이나고
  (배율 1.9999), 저해상도 쪽이 원본의 어디서부터 잘린 것인지(잘림원점 319.6, 52.8)"가
  숫자로 나온다. 눈대중이 아니라 사진 자체에서 실측했다는 뜻이다.
- **정규화 좌표**: 위치를 "몇 번째 픽셀"이 아니라 "초점거리로 나눈 비율"로 세는
  방식이다. 화면 크기가 두 배가 되면 픽셀 번호도 초점거리도 함께 두 배가 되므로,
  그 비율은 변하지 않는다. 왜곡 계수 D 가 이 비율 좌표 위에서 정의돼 있기 때문에
  **해상도를 바꿔도 D 는 손댈 필요가 없고, K 만 환산하면 된다.**

   건드린다. `[` `]` 로 스텝을 줄여 가며 미세조정한다.

## 4. `tools/bev_view.py` — 실시간 BEV 뷰어

### 4.1 한 문단 요약

`camera.yaml` 이 이미 완성된 상태에서 **"지금 좌표가 맞는가"를 확인하는** 도구다.
마우스를 BEV 위에 올리기만 해도 그 지점의 `(x, y)` 미터가 실시간으로 뜨고, 두 점을
클릭하면 그 사이 실제 거리가 mm 로 나온다. 여기에 **차체 가림선(`car_mask_v`) 을
정하는 기능**이 붙어 있다.

### 4.2 실행

```bash
python3 tools/bev_view.py --topic /image_raw
python3 tools/bev_view.py --view-h 320                 # 화면이 클 때
python3 tools/bev_view.py --range-y -1.5 1.5           # 좌우를 더 넓게 보기
python3 tools/bev_view.py --image dev/shots/tape4_raw.jpg   # 저장된 사진으로
```

옵션(`bev_view.py:120-129`): `--range-x` 기본 `-0.2 ~ 2.4` m, `--range-y` 기본
`-1.2 ~ 1.2` m, `--pitch-m` 0.453333, `--view-h` 420, `--fps` 8.0.

`--range-y` 는 좌우로 얼마나 넓게 펼쳐 볼지다. 차선이 화면 밖으로 나간다 싶으면
이 값을 키운다. 단 넓힐수록 창이 커지고 가장자리는 화질이 뭉개진다(원래 사진에서
그 부분이 몇 픽셀 안 되기 때문이다).

### 4.3 화면 보는 법

```
┌───────────────────────────┬───────────────────────────────┐
│ 왼쪽: 보정된 카메라 영상    │ 오른쪽: BEV                    │
│                           │                               │
│  붉은 반투명 영역          │  청록 점선 = 타일 피치 격자     │
│   = 차체 (무시할 부분)     │  초록 실선 = 0.5 m 눈금 + 라벨  │
│  주황 실선 = 가림선 v      │  빨강 십자 = 원점 축 (x=0, y=0) │
│                           │  파란 원 = 원점(라이다)         │
│                           │  흰 화살표 = +x 전방 / +y 좌    │
├───────────────────────────┴───────────────────────────────┤
│ 좌표: 원점=라이다 지면투영점,  x=전방(+),  y=좌측(+)  [ROS]  │
│ 마우스 위치: x=+1.203 m   y=-0.315 m         ← 실시간       │
│ 잰 거리 452 mm   (Δx +450, Δy +42)                        │
│ [m] 차체경계 지정  [s] 저장  [c] 점 지움  [g] 격자 ...      │
└───────────────────────────────────────────────────────────┘
```

격자를 **실선이 아니라 점선**으로 그리는 이유가 있다 — 실선은 판정 대상인 줄눈을
덮어 버려서 "겹쳤는지"를 눈으로 확인할 수가 없다(`bev_check.py:13-14` 에 명시).

### 4.4 조작

| 키 / 마우스 | 동작 |
|---|---|
| 마우스 올리기 (BEV 위) | 그 지점의 `(x, y)` 미터를 실시간 표시 (`bev_view.py:189-193`) |
| 좌클릭 2번 (BEV 위) | 두 점 사이 실제 거리 mm + Δx, Δy (`bev_view.py:289-294`) |
| `m` | 차체 가림선 지정 모드 → 왼쪽 화면에서 경계 높이를 클릭 |
| `s` | `car_mask_v` 를 `camera.yaml` 에 저장 (백업 자동) |
| `c` | 찍은 점 지우기 |
| `g` | 격자 on/off |
| `f` | 현재 화면을 `~/bev_view/bev_MMDD_HHMMSS.jpg` 로 저장 |
| `q` / `ESC` | 종료 |

### 4.5 `m` — 차체 가림선이 왜 필요한가

화면 아래쪽에는 바닥이 아니라 **우리 차 자신**(범퍼, 라이다 원통, 바퀴)이 찍혀 있다.
그런데 H 는 "화면의 모든 픽셀은 바닥"이라고 가정하고 계산하므로, 차체 픽셀이 차선으로
잘못 잡히면 **BEV 에서 x=0.15~0.25m 지점의 가짜 차선점**으로 변환된다. 코앞에 차선이
있다고 착각한 주행 코드는 조향을 크게 꺾는다.

`[m]` 을 누르고 왼쪽 화면에서 차체 윗변을 클릭하면 그 아래 전부를 무시하도록 표시되고
(`bev_view.py:198-200`), `[s]` 로 `camera.yaml` 의 `car_mask_v` 에 저장된다
(`bev_view.py:363-386`). 현재 값은 `car_mask_v: 951.43` (1080p 기준, `camera.yaml:31`).

런타임에서는 `lib/bev.py` 의 `car_mask_row()` (460~477줄)와 `apply_car_mask()`
(480~491줄)가 이걸 적용한다. **캘리브 기준 높이 대비 비율로 환산**하므로 프레임
해상도가 달라져도 같은 지점을 자른다 — 환산을 안 하면 640x480 프레임에서 v=951 이
화면 밖이라 마스킹이 통째로 무효가 된다(463~465줄 주석, 실제 환산은 470~471줄).

## 5. `tools/cam_modes.py` — 해상도 모드 고르기

### 5.1 ★ UVC 카메라의 저해상도 모드는 "축소"가 아니라 "잘라내기"다

이것이 이 도구가 존재하는 이유이자, 이 프로젝트에서 가장 반직관적인 사실이다.

(**UVC** = USB Video Class. 드라이버를 따로 안 깔아도 USB 에 꽂으면 인식되게 만든
웹캠 표준 규격이다. 우리 카메라도 이 규격이라 `/dev/video0` 으로 바로 열린다.)

보통 "640x480 은 1920x1080 을 작게 줄인 것"이라고 생각한다. **그런데 이 카메라는
아니다.** 저해상도 모드에서는 센서의 일부만 읽어 오거나(**크롭** — 사진의 일부만
오려내는 것) 화소를 묶어서 읽는다(**비닝** — 이웃한 화소 2x2 를 하나로 합쳐 읽는 것.
크기는 절반이 되지만 보이는 범위는 그대로다). 그 결과 **해상도마다 화각(보이는 범위)
자체가 다르다.**

```
        1920x1080 (센서 전체)                    640x480 모드
   ┌───────────────────────────┐          ┌───────────────────────────┐
   │  신호등이 여기 보인다  ↓   │          │░░░░░░░░░░░░░░░░░░░░░░░░░░░│ ← 안 보임
   │      ┌─────────────┐      │          │░░░░┌─────────────┐░░░░░░░│
   │      │             │      │          │░░░░│  이 부분만   │░░░░░░░│
   │      │             │      │   대비    │░░░░│  나온다      │░░░░░░░│
   │      └─────────────┘      │          │░░░░└─────────────┘░░░░░░░│
   │                           │          │░░░░░░░░░░░░░░░░░░░░░░░░░░░│
   └───────────────────────────┘          └───────────────────────────┘
        가로 100% / 세로 100%              가로 67% / 세로 89% (실측)
```

`dev/scripts/start_cam.sh:5-12` 와 `cam_modes.py:68-77` 에 실측표가 있다.

| 해상도 | 화각 가로 | 화각 세로 |
|---|---|---|
| 1920x1080 | 100% | 100% (센서 전체) |
| 1024x768 | 74.6% | 99.4% |
| 640x480 | 66.7% | 88.9% (예전 설정) |
| 1280x720 | 66.7% | 66.7% |

1280x720 이 특히 함정이다 — 정합 배율이 1.000 이었다(`ground_fit.py:119-120` 의
`SCALE` 표). 즉 **1080p 픽셀을 1:1 로 가운데만 오려낸 것**이고, 해상도만 낮아졌지
디테일이 좋아진 것도 아니고 화각만 66.7% 로 좁아졌다.

### 5.2 그래서 1920x1080 을 고른 근거

`start_cam.sh:1-13` 에 그대로 적혀 있다.

1. **상하좌우 모두 제일 넓다.** 특히 위쪽이 더 보여 **신호등에 유리하다**.
2. **YOLO 추론 속도는 입력 해상도와 무관하다(실측).** YOLO 는 어차피 `imgsz`
   (추론 직전에 입력 사진을 정해진 크기로 줄여 넣는 설정값)로
   줄여서 넣기 때문이다. 1080p 로 받든 480p 로 받든 모델에 들어가는 그림 크기는
   같으니 추론 시간도 같다. 늘어나는 비용은 MJPG 디코딩(카메라가 JPEG 로 압축해 보낸
   것을 다시 그림으로 푸는 일)뿐이다.
3. 화각은 **캡처 모드가 정하고**, 크기는 나중에 얼마든지 줄일 수 있다. 그러니
   넓게 받아 두는 쪽이 손해가 없다.

포맷을 MJPG 로 강제한 이유도 실측이다 — **이 카메라는 YUYV 1080p 가 6fps 밖에
안 나온다**(`start_cam.sh:14-17`). MJPG 는 1920x1080 에서 30fps 가 나온다.

(**MJPG** = 카메라가 매 장을 JPEG 으로 압축해서 USB 로 보내는 방식. 데이터가 작아
USB 대역폭에 여유가 생기는 대신 받는 쪽에서 푸는 일이 생긴다. **YUYV** = 압축 없이
그대로 보내는 방식. 푸는 일은 없지만 데이터가 훨씬 커서 USB 가 못 버티고 fps 가
떨어진다. 1080p 에서는 압축해 보내는 쪽이 압도적으로 유리하다.)

### 5.3 실행과 조작

```bash
python3 tools/cam_modes.py          # 차 PC 에서, ROS 카메라 노드를 먼저 내리고
```

`/dev/video0` 을 직접 여는 도구라 **ROS 카메라 노드가 떠 있으면 안 된다**
(`cam_modes.py:18`). 먼저 `pkill -f usb_cam_node_exe` 로 내린다.

| 키 | 동작 |
|---|---|
| `1` ~ `7` | 해상도 즉시 전환 (`cam_modes.py:71-77` 의 MODES 순서) |
| `m` | MJPG / YUYV 포맷 전환 |
| `b` | 지금 모드 안에서 640x480 모드의 화각이 어디까지인지 상자로 표시 |
| `g` | 세로 10% 간격 눈금 격자 (상하 각도를 재현 가능하게 잡을 때) |
| `스페이스` | 정지 / 실시간 |
| `f` | `~/cam_modes/cam_1920x1080_MMDD_HHMMSS.jpg` 로 저장 |
| `q` | 종료 |
| 마우스 드래그 | ROI(Region Of Interest, 관심영역 = 전체 화면 중 실제로 쓸 네모 구역) — 잘라 쓸 영역의 크기/비율을 알려 준다 |

**조준 도우미**가 항상 켜져 있다(`find_lidar()`, `cam_modes.py:91-109`). 화면 아래쪽
중앙에서 가장 큰 어두운 덩어리(= 라이다 원통)를 찾아 화면 중심에서 몇 % 벗어났는지
실시간으로 띄운다. `±1%` 안이면 "정렬 좋음"으로 초록색이 된다(`cam_modes.py:215-219`).
카메라를 손으로 돌려 이 값이 0 이 되게 하면 좌우 정렬이 끝난다.

종료하면 그 모드로 ROS 카메라를 띄우는 명령줄을 그대로 출력해 준다(`cam_modes.py:289-295`).

### 6.2 보조 도구 설명

**`import_camera_info.py`** — 체스보드 재촬영 없이, 차에 이미 있는 유효한 캘리브를
그대로 채택하는 도구다. ROS 표준 `camera_info` yaml 을 읽어 우리 형식(`model`/`K`/`D`)
으로 변환한다. 실차 `usb_cam` 은 `/home/xytron/.ros/camera_info/default_cam.yaml` 에
`plumb_bob` 캘리브를 이미 갖고 있고, 그 값으로 보정하면 실제 직선이 곧게 펴지는 것을
확인했다(`import_camera_info.py:10-12`).
```bash
# 패키지 루트에서 실행 (tools/ 안에서 실행한다면 --save ../config/camera.yaml)
python3 tools/import_camera_info.py --file ~/.ros/camera_info/default_cam.yaml \
    --save config/camera.yaml
```
★ 중요 — **`new_K` 항목은 자동으로 지운다.** `new_K` 는 K/D/model/alpha 에서 파생되는
값이라 K/D 를 갈아끼우면 낡은 값이 되고, 낡은 채로 두면 런타임이 잘못된 좌표계를
"일치"로 오판한다(`import_camera_info.py:31-33` 설명, 실제 삭제는 `404-407`줄).
K/D 를 바꿨으면 **H 는 반드시 다시 맞춰야 한다.**

**`bev_shot.py`** — `[스페이스]` 로 한 프레임 고정 → 현재 K/D/H 로 BEV 를 만들어
나란히 표시 → BEV 위에서 두 점 클릭으로 실제 거리 측정. `bev_view.py` 와 기능이
겹치지만 이쪽은 "한 장 딱 잡아서 본다"에 특화돼 있고 `+`/`-` 로 확대, `w`/`s` 로
전방 범위, `a`/`d` 로 좌우 범위를 넓히고 줄인다(`bev_shot.py:348-362`).
★ 저장은 **`[f]`** 다 — raw/보정/BEV 3장이 한 번에 나온다(`bev_shot.py:363-368`).
파일 맨 위 설명(`bev_shot.py:10`)에는 아직 "[s] 로 저장"이라고 적혀 있지만 이건
낡은 문구이고, 실제 `s` 키는 BEV 전방 범위를 줄인다(`bev_shot.py:355-357`).

**`bev_check.py`** — 창을 못 띄우는 환경(SSH 헤드리스)에서 저장된 사진으로 BEV 격자를
검증하고 결과를 파일로 떨어뜨리는 CLI(창 없이 명령줄로만 쓰는 프로그램). 콘솔 수치에
대한 중요한 경고가 docstring(파일 맨 위에 적어 둔 설명글)에
있다(`bev_check.py:16-20`) — **BEV 상의 타일 크기는 구성상 항상 `pitch × ppm` 이라,
그 픽셀 오차는 "타일이 정사각형이냐"를 재는 게 아니다.** 판정은 어디까지나 육안
(노란 점선 vs 실제 줄눈)이다. 수치가 0 이어도 H 가 엉터리일 수 있다.

> 왜 그런지 한 번 더 풀면 이렇다. BEV 그림은 "지면 미터에 `ppm`(1미터당 픽셀 수)을
> 곱해 그린 축소판"으로 **정의**돼 있다(`bev_check.py:237-256`). 그러니 타일 한 칸을
> 0.4533m 로 치고 그린 격자는, H 가 맞든 틀리든 화면에서 언제나 `0.4533 × ppm` 픽셀로
> 나온다. 자기가 그린 걸 자기가 다시 재는 셈이라 항상 0 이 나오는 것이다.
> 진짜 판정은 **그 격자선이 사진 속 실제 줄눈 위에 얹혔는가**를 눈으로 보는 것뿐이다.
```bash
python3 tools/bev_check.py --image dev/shots/tape4_raw.jpg \
    --camera config/camera.yaml --enhance --save /tmp/bev_after.jpg
```

**`bev_stream.py`** — WSL2 는 NAT 뒤에 있어 ROS2 DDS 가 차까지 닿지 않는다. 네트워크
설정을 바꾸는 대신 **SSH 파이프 하나로 JPEG 프레임을 흘려보내는** 우회로다
(`bev_stream.py:5-8`). 차에서 캡처→보정→H→BEV→JPEG 를 만들어 stdout 으로 뱉고,
노트북이 그걸 읽어 창에 띄운다. 설정 불필요, 대역폭 약 1MB/s.

> 용어 셋만 풀면 이렇다. **DDS** 는 ROS2 노드들이 서로를 자동으로 찾아 토픽을
> 주고받는 통신 방식인데, 서로가 서로를 먼저 불러 봐야(양방향) 성립한다.
> **NAT** 는 안쪽 컴퓨터들을 하나의 바깥 주소 뒤에 숨기는 방식이라, 안에서 밖으로는
> 나가지지만 밖에서 안으로는 먼저 못 들어온다. WSL2 가 이 NAT 안에 있어서 차가
> 노트북을 불러 줄 수가 없고, 그래서 DDS 가 성립하지 않는다.
> **stdout** 은 프로그램이 화면에 글자를 뿌릴 때 쓰는 그 출구인데, 여기서는 글자
> 대신 JPEG 덩어리를 뱉게 하고 SSH 가 그 출구를 노트북까지 그대로 이어 준다.
> SSH 접속 한 줄만 되면 되므로 네트워크 설정을 건드릴 일이 없다.

**`verify_lidar_cam.py`** — 라이다 스캔 점을 H 의 역행렬로 영상 위에 투영한다
(투영 = 3차원 공간의 점이 사진의 몇 번째 픽셀에 찍히는지를 계산해 그 자리에 표시하는 것).
벽이나 콘의 라이다 점이 영상 속 실물 발치와 겹치면 카메라와 라이다의 좌표계가 서로
맞다는 뜻이다(이렇게 두 센서가 같은 곳을 같은 좌표로 가리키는지 맞춰 보는 것을
**정합**이라고 한다). 스캔 파일(`scan.npz`)은 `calib_shot.sh` 가 사진과 함께 만들어 준다.
```bash
# 패키지 루트에서 실행 (tools/ 안에서라면 --camera ../config/camera.yaml)
python3 tools/verify_lidar_cam.py --image ground.jpg --scan scan.npz \
    --camera config/camera.yaml --save overlay.jpg
```

**`make_enhanced.py`** — 테라조 바닥은 줄눈 대비가 약해 클릭하기 어렵다. CLAHE + 언샤프로
또렷하게 만든다. **CLAHE** 는 사진을 8x8 구역으로 나눠 구역마다 따로 대비를 올리는
방법이다(`make_enhanced.py:29-30`) — 사진 전체를 한꺼번에 밝히면 밝은 데는 하얗게
타 버리는데, 구역별로 하면 어두운 구석의 줄눈도 살아난다. **언샤프**는 원본에서
흐릿하게 뭉갠 판을 빼서 윤곽선만 도드라지게 만드는 방법이다(`make_enhanced.py:31-32`). ★ **기하는 절대 안 건드린다** — 밝기/대비만 바꾸므로 강화 전/후에
같은 줄눈이 같은 (u,v) 에 있다(`make_enhanced.py:11-13`). 그래서 강화한 그림 위에서
클릭한 좌표를 원본 좌표로 그대로 써도 된다. 리사이즈나 크롭을 여기에 추가하면 그
전제가 깨지므로 넣지 말 것.

**`calib_shot.sh`** — 차에서 센서가 안 떠 있으면 `sensors.launch.py` 로 띄우고 12초
기다린 뒤, 사진 N장(`shot_NNNN.jpg`)과 스캔 1개(`scan.npz`)를 저장한다. 모터/주행
토픽은 건드리지 않는다.

**`calib_ground_h.py` (56KB)** — 예전 H 캘리브 방식. 바닥 기준점을 클릭하고 각 점의

좌표 대신 격자 번호 "i j" 만 넣으면 되고, 확대 클릭 보조(휠 줌 1x→2x→4x, 매그니파이어
= 마우스 주변만 확대해 보여 주는 돋보기 창, 우클릭 패닝 = 확대된 그림을 끌어서
이동)까지 붙어 있다(`calib_ground_h.py:52-58`). 이 방식으로 만든 결과가
`dev/calib/h_pts_auto.csv` (RMS 6.1mm)이고 `dev/README.md:6` 에 기록돼 있다.

> **RMS** 는 Root Mean Square, 우리말로 제곱평균제곱근이다. 점마다 "예측 위치와
> 실측 위치의 차이(잔차)"가 나오는데, 그것들을 제곱해 평균 내고 다시 제곱근을 씌운
> 값이다. 부호를 없애고 크게 틀린 점에 벌점을 더 주는 방식의 평균이라, 한마디로
> **"평균적으로 이만큼 틀린다"를 한 숫자로 요약한 것**이다. 여기서 RMS 6.1mm 는
> 클릭한 14개 점이 평균 6mm 정도 어긋났다는 뜻이다. 이 계산은
> `calib_ground_h.py:901-902` 에 있고, 5cm 를 넘으면 경고를 띄운다(`121`, `903-905`줄).
> 렌즈 캘리브 쪽(`calib_camera.py:313`)에서 말하는 RMS 는 단위가 미터가 아니라
> **픽셀**이며, 이쪽은 "재투영 오차" 라고 부른다 — 체스보드 격자점을 다시 사진 위로
> 되쏘았을 때 원래 찍힌 자리에서 몇 픽셀 벗어나는가다. 둘 다 작을수록 좋다.
**지금은 안 쓴다** — 대응점 14개를 정확히 클릭하는 것보다 물리값 4개를 돌리는 쪽이
빠르고 결과 해석도 쉬웠기 때문이다.

**`calib_fisheye.py` — 폐기.** 파일 맨 위(3~11줄)에 `deprecated`(더는 쓰지 말라고
공식적으로 표시해 둔 상태. 지우지는 않고 기록으로만 남겨 둔다는 뜻이다)라고 명시돼 있다.

**`bev_viewer.py` — 폐기.** `bev_view.py` (이름이 한 글자 다르다!)의 옛 버전.

## 7. 체스보드 캘리브를 왜 포기했나

### 7.1 무슨 일이 있었나

`tools/chess_capture.py`(23KB), `tools/calib_camera.py`(20KB), `tools/capture_frames.py`
셋은 **체스보드(체커보드)로 K/D 를 직접 구하기 위해** 잘 만들어 둔 도구들이다.
특히 `chess_capture.py` 는 촬영 커버리지를 실시간으로 채점하며 조건이 맞는 순간
자동으로 저장까지 해 준다(`chess_capture.py:11-19`). 그런데 **실제 캘리브에는 쓰지
않았다.**

이유는 **체스보드 판이 평평하지 않았기 때문**이다. 캘리브 이론은 판이 완벽한 평면
(z=0)이라고 가정하고 계산한다(`calib_camera.py:384` — "체커보드 3D 좌표 (z=0 평면)").
판이 조금이라도 휘어 있으면 그 휨이 렌즈 왜곡으로 오인돼 D 에 섞여 들어간다. 그 결과
**직접 찍어 구한 K/D 가 차에 이미 들어 있던 벤더 기본값보다 오히려 나빴다.**

그래서 방향을 틀어, 재촬영 없이 벤더 캘리브를 그대로 가져다 쓰기로 했다. 그것이
`tools/import_camera_info.py` 이고, 그 결정의 흔적이 `camera.yaml:59-61` 에 남아 있다:

```
intrinsics_source: 640x480 캘리브(default_cam.yaml)를 1920x1080 으로 환산 —
  배율 1.9999, 잘림원점 (319.6,52.8) 실측(ORB 정합). D 는 정규화좌표 기준이라 불변.
```

즉 **지금 차에 올라가 있는 K/D 는 체스보드로 새로 찍은 값이 아니라, 벤더가 640x480 에서
잡아 둔 값을 1080p 로 환산한 것**이다. 그리고 그 결과가 `undist_check.py` 의 직선 자
검증을 통과했다.

### 7.2 나중에 다시 시도하려는 사람에게

- **판이 평평한지 먼저 확인하라.** 유리판이나 알루미늄 판에 인쇄물을 붙여야 한다.
  A4 를 클립보드에 끼운 정도로는 안 된다.
- 새로 찍은 K/D 가 벤더값보다 **정말 나은지** `undist_check.py` 로 같은 테이프에 대고
  비교하라. 좋아졌다는 확증 없이 갈아끼우지 말 것.
- K/D 를 바꾸면 **H 는 전부 무효다.** `ground_fit.py` 로 H 를 다시 맞춰야 한다
  (1.5절 참고). `import_camera_info.py` 도 이 사고를 막으려고 `calibrated` 가 true 로
  남아 있으면 경고를 띄운다(`import_camera_info.py:517-519`).
- 어안 모델(`--model fisheye`)은 쓰지 마라. 87도 렌즈에 쓰면 과파라미터화로 가장자리가
  나빠진다.

## 8. 캘리브 결과 검증법과 알려진 한계

### 8.1 잘 맞았는지 어떻게 아는가 — 다섯 가지 방법

**① 격자 위에서 눈으로 확인 (가장 중요).**
`ground_fit.py` 나 `bev_check.py` 에서 **예측 격자선이 실제 바닥 줄눈/테이프 위에
얹히는지** 본다. 가까운 줄과 먼 줄이 동시에 맞아야 한다. 한쪽만 맞으면 내림각과
높이의 조합이 틀린 것이다. 격자를 점선으로 그리는 이유가 이 판정을 위해서다.
현재 값의 기록은 `dev/README.md:28` — **"예측↔실제 줄눈 일치 1.7px 이내"**,
커밋 `d1be718` — **"격자 실측 오차 1~3cm"**.

**② 자로 실측 비교.**
`bev_view.py` 나 `ground_fit.py` 의 BEV 에서 두 점을 클릭하면 mm 가 나온다.
바닥에 45cm 자를 놓고 양 끝을 클릭해 **450 이 나오는지** 본다. 타일 한 칸이면 453 이다
(`ground_fit.py:579`, `bev_view.py:329`).

**③ 좌우 대칭 확인.**
차를 격자 중앙에 정확히 세웠다면 왼쪽 3번째 줄까지의 거리와 오른쪽 3번째 줄까지의
거리가 같아야 한다. 어긋나면 `좌우틀어짐(yaw)` 이나 `왜곡중심X` 를 의심한다.

**④ (자동) 런타임 정합 검사.**
`bev_view.py:222-224` 가 시작할 때 `check_new_K_match()` 를 돌려 `camera.yaml` 의
`new_K` 와 지금 계산된 `new_K` 를 대조한다. 어긋나면 콘솔에 "▲ new_K 불일치 — H 는
캘리브 당시 new_K 기준이라 지금 좌표계에서는 무효다" 라는 경고가 뜬다
(`lib/bev.py:404-407`). **이 경고가 뜨면 주행하지 말 것.**

**⑤ 물리값 ↔ H 재구성 일치.**
`h_phys` 의 물리값으로 `build_H()` 를 다시 돌리면 저장된 `H` 와 정확히 같아야 한다.
커밋 `d1be718` 에 검증 기록이 있다 — **"최대차 0.000e+00"**. 즉 `h_phys` 와 `H` 는
서로 모순되지 않는다. 누가 `H` 만 손으로 고쳤다면 이 검사에서 걸린다.

### 8.2 검증 명령 모음

```bash
# 왜곡 보정만 판정 (직선 자)
python3 tools/undist_check.py --topic /image_raw

# 지면 좌표 판정 (실시간, 좌표+거리)
python3 tools/bev_view.py --topic /image_raw

# 저장된 사진으로 격자 겹침 판정 (헤드리스 가능)
python3 tools/bev_check.py --image dev/shots/tape4_raw.jpg \
    --camera config/camera.yaml --enhance --save /tmp/bev_after.jpg

# 라이다와 카메라가 같은 곳을 가리키는지
python3 tools/verify_lidar_cam.py --image ground.jpg --scan scan.npz \
    --camera config/camera.yaml --save overlay.jpg
```

### 8.3 ★ 알려진 한계 (본선 전에 반드시 읽을 것)

커밋 `d1be718` 의 "알려진 미해결" 항목 그대로다.

**① 절대 축척이 타일 피치 가정에 의존한다.**
지금 모든 거리는 "복도 테라조 타일 한 칸 = 0.453333 m" 라는 가정 위에 서 있다. 이 값은
6칸을 2.72m 로 실측해 나눈 것이지만, **자로 재는 독립 검증이 아직 안 됐다.** 만약 타일
피치가 실제로 0.46m 였다면 모든 거리가 1.5% 씩 틀어진다. 1.5m 앞의 물체가 1.52m 로
잡히는 정도라 주행에는 큰 영향이 없겠지만, **본선 전에 45cm 자를 BEV 위에 놓고 한 번은
재봐야 한다.** `bev_view.py` 로 두 점 클릭 → 450 이 나오는지만 보면 된다. 5분이면 끝난다.

**② 화면 가장자리 좌표가 미검증이다.**
테이프 격자를 화면 중앙에만 붙여 놓고 맞췄기 때문에, **화면 좌우 끝의 좌표가 맞는지
확인된 적이 없다.** 왜곡 보정의 오차는 가장자리에서 가장 크게 나타나므로(코너의 정규화
반지름이 r=1.08~1.20 으로 1보다 커서 고차 왜곡항이 바깥에서 더 크게 작동한다 —
`tuner.py:63-64` 참고) 여기가 실제로 위험한 부분이다. 차선이 화면
가장자리에 걸치는 급커브에서 좌표가 틀어질 수 있다.

> 괄호 안을 풀면 이렇다. **정규화 반지름 r** 은 화면 중심에서 그 점까지의 거리를
> 초점거리로 나눈 값이다. 우리 화면의 네 귀퉁이는 r 이 1.08~1.20 으로 **1보다 크다.**
> 그런데 왜곡 계수 `k2`, `k3` 는 이 r 을 각각 4제곱·6제곱해서 곱한다(그래서 "고차"
> 항이다). r 이 1보다 크면 제곱할수록 값이 더 커지므로, 같은 계수라도 중앙에서는
> 거의 티가 안 나다가 귀퉁이에서 확 커진다. `tuner.py:63-64` 가 적어 둔
> "코너 영향 서열이 k3 > k2 > k1 로 직관과 반대" 라는 실측이 정확히 이 이유다.
> 화면 중앙만 보고 맞춘 캘리브가 가장자리에서 어긋날 수 있다는 것이 이 항목의 요지다.
→ 대책: 격자 테이프를 **화면 좌우 끝까지 걸치게** 다시 붙이고 `ground_fit.py` 로
가장자리 초록선이 맞는지 확인. 안 맞으면 `왜곡중심X` 와 `왜곡k1` 을 조금씩 조절한다
(`ground_fit.py:111-113` 의 마지막 3개 파라미터가 이 용도다).

**③ 처리 속도 (캘리브 자체의 문제는 아니지만 1080p 전환의 대가).**
CPU 에서 3개 모델을 순차로 돌리므로 1080p 에서 4.4Hz (평균 219ms) 다. 차선만 매
프레임 돌리고 나머지를 라운드로빈(여러 개를 한꺼번에 돌리지 않고 한 프레임에 하나씩
돌아가며 처리하는 방식. 1번 프레임엔 A, 2번엔 B, 3번엔 C, 다시 A … 식이다)으로
돌리는 개선이 필요하다.

```
 무엇을 하고 싶은가              →  어떤 도구
 ────────────────────────────────────────────────────────────────
 카메라 해상도/화각 고르기        →  cam_modes.py  (1~7 키)
 카메라 좌우 정렬                →  cam_modes.py  (라이다 % 를 0 으로)
 카메라 기동                     →  dev/scripts/start_cam.sh
 캘리브용 사진 찍기              →  dev/scripts/_shot.py <이름> 20
 벤더 K/D 가져오기               →  import_camera_info.py
 왜곡 보정이 맞나 확인           →  undist_check.py  (두 점 클릭 = 직선 자)
 ★ 지면 H 맞추기                 →  ground_fit.py   (b 로 시작, s 로 저장)
 ★ 좌표/거리 확인                →  bev_view.py     (마우스 올리기 / 두 점 클릭)
 차체 가림선 정하기              →  bev_view.py     (m → 클릭 → s)
 헤드리스에서 격자 검증          →  bev_check.py --save
 라이다-카메라 정합 확인         →  verify_lidar_cam.py
 노트북에서 차 BEV 원격 보기     →  bev_stream.py
 ────────────────────────────────────────────────────────────────
 절대 하지 말 것
   · K/D 를 바꾸고 H 를 그대로 두기      → H 가 통째로 무효
   · 해상도를 바꾸고 camera.yaml 방치    → new_K 가 달라져 H 무효
   · calib_fisheye.py 사용               → 우리 렌즈는 어안이 아니다
   · tuner.py 삭제                       → 다른 도구들의 한글 렌더러가 여기 있다
```

**최종 판정 한 줄**: `bev_view.py` 를 띄웠을 때 콘솔에 경고가 없고, BEV 격자가 바닥
줄눈에 겹치고, 45cm 자가 450mm 로 나오면 캘리브는 정상이다.
