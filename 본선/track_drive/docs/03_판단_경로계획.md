# 03. 판단 · 경로계획 — "차가 어디로 갈지 정하는 법"

이 문서는 카메라·라이다가 만들어낸 인지 결과(차선점, 물체 박스, 라이다 점군)를 받아서
**"지금 어느 상황이고, 그래서 어디로 갈 것인가"** 를 결정하는 부분을 다룬다.
대상 파일은 `track_drive/path_planner_node.py`(1259줄, 이 프로젝트에서 가장 큰 파일),
`track_drive/lane_planner.py`(1282줄, 예선에서 넘어온 차선 피팅 코어),
그리고 보조 모듈 3개 `lib/cluster.py`, `lib/path_gen.py`, `lib/arbitration.py` 다.
읽고 나면 "라바콘 구간에서 차가 왜 저렇게 도는지", "정지선 앞에서 왜 멈췄는지",
"그걸 고치려면 어느 파일 어느 줄 / `tuning.yaml` 의 어느 값을 만져야 하는지"를
전부 짚을 수 있어야 한다.

## 0. 이 문서에 나오는 용어

이 문서에는 제어·영상 쪽 전문용어가 섞여 나온다. 본문에서도 **처음 나오는 자리마다
한 번씩** 풀어 썼지만, 읽다가 막히면 여기로 돌아오면 된다.
아래 표에는 **이 문서에 실제로 나오는 말만** 적었다.

## 1. 이 노드는 무슨 일을 하는가

한 문단으로 요약하면 이렇다. **`path_planner_node` 는 "판단하는 뇌"다.**
직접 모터를 돌리지 않는다. 대신 초당 20번(20Hz), 두 종류의 결과물을 뱉는다.

1. **`/center_path` (가야 할 길)** — 차 앞쪽 바닥에 그린 "이 선을 따라와라"는 점들의 줄.
   그리고 그 중 한 점을 콕 집은 `/target`.
2. **`/drive_cmd` (지금의 주행 정책)** — "지금은 정지다", "속도는 16 이하로 묶어라",
   "조향은 라바콘 프로파일로 해라" 같은 **이번 20분의 1초 동안의 명령 스냅샷**.

여기서 **스냅샷**은 "그 순간의 상태를 통째로 찍은 사진"이라는 뜻이다. 다음 20분의 1초에는
사진을 버리고 새로 찍는다. 지난번 사진이 남아 있지 않다는 게 중요한데, 이유는 2장에 있다.

실제로 조향각을 계산하고 모터 토픽을 쏘는 건 `motion_node` 다(문서 04 참고).
즉 planner 는 **어디로 갈지(경로) + 어떤 태도로 갈지(정책)** 만 정하고,
**어떻게 핸들을 꺾을지(제어)** 는 motion 이 맡는 분업 구조다.

```
   [인지]                 [판단 = 이 문서]              [제어 / 그 외]

 yolo_node ─ /detect/lane ──────┐         ┌─ /center_path ─┐
           ─ /detect/objects ───┤         │  /drive_cmd  ──┴─→ motion_node
           ─ /detect/traffic_light ┤      │                        ↓
           ─ /detect/lane_quality ─┤      │                   /xycar_motor
 라이다 ──── /scan ──────────────┼─→ path_planner_node
 car_state ─ /car_state ────────┤    (20 Hz)   ├─ /target      ┐
 외부팀 ──── /corridor_path ─────┤             │  /lane_left   ├─→ rviz · 디버그
 조작자 ──── /manual_go ─────────┘             │  /lane_right  ┘
                                              └─ /capture_yaw ─→ car_state_node
```

주의: motion_node 가 실제로 구독하는 planner 출력은 **`/center_path` 와 `/drive_cmd`
두 개뿐**이다 (`motion_node.py:179~182`). `/target`, `/lane_left`, `/lane_right` 는
사람이 보라고 내는 시각화·디버그용이고, `/capture_yaw` 는 motion 이 아니라
`car_state_node` 가 받는다.

구독/발행 목록은 `path_planner_node.py:333~349` 에 한 덩어리로 모여 있다.
주기 타이머는 `path_planner_node.py:351` 의 `create_timer(1.0 / PLAN_HZ, self._tick)` 이고
`PLAN_HZ = 20` 은 `lane_planner.py:45` 에서 가져온다.

### 입력 토픽이 각각 무엇인가

| 토픽 | 내용 | 받는 콜백 |
|---|---|---|
| `/detect/lane` | 차선 점 (x, y, z=클래스ID) | `_on_lane` (:388) |
| `/detect/objects` | 물체 (x=u, y=v, z=클래스ID) | `_on_objects` (:445) |
| `/detect/traffic_light` | "GREEN"/"RED"/"NONE" 문자열 | `_on_light` (:478) |
| `/scan` | 라이다 500빔 거리값 | `_on_scan` (:510) |
| `/car_state` | yaw_rel, 속도, 배터리 등 | `_on_car_state` (:484) |
| `/detect/lane_quality` | 차선 검출 품질 0~1 | `_on_quality` (:481) |
| `/corridor_path` | 외부팀이 만든 콘 통로 경로 | `_on_corridor` (:487) |
| `/manual_go` | 수동 출발/진행 신호 (Bool) | `_on_manual_go` (:493) |

여기서 헷갈리기 쉬운 게 `/detect/objects` 다. 이건 **미터 좌표가 아니라 화면 픽셀 좌표**다.
`position.x` 에 bbox 중심의 u(가로 픽셀), `position.y` 에 bbox **아래쪽 변의 v(세로 픽셀)** 가
들어온다. 이 v 가 왜 중요한지는 6장에서 자세히 다룬다.

**bbox**(bounding box)는 YOLO 가 "여기 물체가 있다"고 감싸 그린 네모 상자다.
**u** 는 화면 가로 픽셀, **v** 는 화면 세로 픽셀이고 **v=0 이 화면 맨 위**다.
그러니 v 가 클수록 화면 아래쪽이라는 뜻이 된다.

## 2. 매 틱(1/20초)마다 벌어지는 일

`_tick()` (`path_planner_node.py:574`) 이 심장이다. 순서가 정해져 있고, 그 순서 자체가 설계다.

**틱(tick)** 은 프로그램이 주기적으로 깨어나 한 번 일하고 다시 자는 것을 말한다.
시계 초침 소리에서 온 말이다. 여기서는 1초에 20번이니 한 틱이 0.05초다.
"한 틱에 6cm", "3틱 연속" 같은 말이 아래에 계속 나오는데 전부 이 0.05초가 단위다.

```
  _tick()  ── 20Hz ────────────────────────────────────────────────
    │
    ├─ (1) self._cmd = _fresh_cmd()      ← 정책 스냅샷을 매번 백지로 리셋 (:580)
    │        "라치 금지" — 지난 틱의 감속 명령이 저절로 이월되지 않는다
    │
    ├─ (2) _update_stop_block(now)       ← 정지선 차단 타이머 갱신 (:584)
    │
    ├─ (3) phase 분기 (:586~604)
    │        IDLE / WAIT / LANE / CONE / SHORTCUT / PEDESTRIAN
    │        └─ 여기서 경로(/center_path, /target)를 발행하고
    │           self._cmd 에 owner·cap·profile 을 채워 넣는다
    │
    ├─ (4) _update_s_zone(now)           ← phase 와 무관하게 매 틱 (:607)
    ├─ (5) _update_corner_boost(now)     ← 마찬가지 (:608)
    ├─ (6) 차선 품질 낮으면 감속 cap 추가 (:610~612)
    │
    ├─ (7) _publish_drive_cmd()          ← 스냅샷 확정 발행 (:614)
    └─ (8) _log_phase()                  ← 1초에 한 번 현재 상태 로그 (:615)
```

그림에 나온 세 낱말만 먼저 짚고 가자. **owner** 는 "이번 틱에 조향을 누가 쥐는가"를
적어 둔 이름표, **cap** 은 "이 속도를 넘지 마라"는 상한, **profile** 은 "이 구간에서는
이런 성격으로 꺾어라"라고 묶어 둔 조향 설정 한 벌이다. 셋 다 7장에서 자세히 다룬다.

**(1)의 "라치 금지"가 이 파일의 핵심 설계 원칙이다.**
여기서 **래치(latch, 위 그림의 "라치")** 는 *한 번 켜지면 켠 조건이 사라져도 계속 켜져
있는 걸쇠*를 말한다. 현관문을 걸쇠로 열어 두면 손을 떼도 계속 열려 있는 그것이다.
정책에 래치가 걸려 있으면 "감속하라"는 상태가 스스로는 절대 안 풀린다.
예선 코드는 `/child_zone`,
`/cone_mode`, `/shortcut_slow` 같은 Bool 토픽을 켜고 끄는 방식이었는데,
"켜는 메시지는 갔는데 끄는 메시지가 유실되면 차가 영원히 느려진 채로 달린다"는
고질적 버그가 있었다(파일 헤더 주석 `path_planner_node.py:13~14`).
본선에서는 그 Bool 들을 전부 없애고, **매 틱 처음부터 다시 계산한 `/drive_cmd` 한 개**로
합쳤다. 이번 틱에 아무도 감속을 요구하지 않으면 감속은 그냥 사라진다.

**(4)(5)(7)이 phase 분기 바깥에 있는 것도 의도적이다.** 어떤 phase 가 중간에
`return` 해서 빠져나가도 `/drive_cmd` 는 반드시 발행된다. motion 쪽에는
"0.3초 동안 `/drive_cmd` 가 안 오면 정지"라는 **워치독**(watchdog, 감시견 — 정해진 시간
안에 소식이 없으면 상대가 죽은 것으로 보고 안전동작을 하는 타이머)이 있으므로
(`lib/drive_cmd.py:19`, `motion_node.py:235`), planner 가 조용해지는 것 자체가
비상정지 트리거다.

## 3. 상태기계(phase) 완전 해설

### 3-1. 어떤 상태들이 있나

**상태기계(state machine)** 는 "지금 어떤 상황인가"를 이름표 하나로 들고 다니면서,
정해진 조건이 맞을 때만 다른 이름표로 갈아타는 방식이다. 이름표가 곧 상태(phase)고,
어떤 조건에서 어디로 갈아탈 수 있는지가 **전이(transition)** 다.
장점은 "지금 무슨 상태냐"고 물으면 답이 언제나 딱 하나라는 것이다.
그래서 로그만 봐도 그 순간 차가 무슨 생각을 했는지 재구성할 수 있다.

상태 변수는 문자열 하나 `self.phase` 다 (`path_planner_node.py:233`, 초기값 `"IDLE"`).
분기는 `_tick()` 의 `path_planner_node.py:586~604` 에 전부 있다.

| phase | 쉬운 말로 | 담당 함수 |
|---|---|---|
| `IDLE` | 센서가 아직 안 켜졌다. 아무것도 안 함 | `_tick` 안에 인라인 (:586) |
| `WAIT` | 출발선. 정지한 채 초록불/수동 신호 대기 | `_tick_wait` (:636) |
| `LANE` | 기본 주행. 노란 중앙선 따라감 | `_tick_lane_phase` (:667) |
| `CONE` | 라바콘 슬라럼. 콘 줄을 보고 안쪽으로 감 | `_tick_cone` (:912) |
| `SHORTCUT` | 지름길. 정지 → 좌회전 → 추종 → 좌회전 | `_tick_shortcut` (:778) |
| `PEDESTRIAN` | 사람 보고 잠깐 멈춤 (기본 비활성) | `_tick_pedestrian` (:1047) |

`SHORTCUT` 만 내부에 서브상태 `self._sc_sub` 를 하나 더 가진다
(`None | WAITING | TURNING_1 | FOLLOW | TURNING_2`, `path_planner_node.py:292`).
**서브상태**는 말 그대로 상태 안의 상태다. "지름길"이라는 큰 상태 안에서 다시
"지금은 서서 기다리는 중 / 도는 중 / 따라가는 중"을 구분한다.
`SHORTCUT` 는 절차가 4단계로 정해져 있어 phase 하나로는 표현이 안 되기 때문이다.

그리고 phase 는 아니지만 **동시에 켜질 수 있는 오버레이 3종**이 따로 있다.
이들은 phase 를 바꾸지 않고 정책(`self._cmd`)만 건드린다.
**오버레이(overlay)** 는 밑그림 위에 겹쳐 올리는 투명 필름 같은 것이다.
밑그림(phase)은 그대로 두고 그 위에 "여기는 어린이보호구역"이라는 조건만 덧씌운다.
그래서 phase 하나에 오버레이 여러 개가 동시에 붙을 수 있다.

- `_red_stopping` — 정지선 정지 중 (LANE phase 를 유지한 채 owner 만 MISSION_STOP)
- `_child_zone` — 어린이보호구역 (속도 cap 만 추가)
- `_s_zone_active` — S자 구간 (조향 프로파일만 교체)

`_log_phase()` (`path_planner_node.py:617`) 가 1초에 한 번 찍는 로그가
`LANE +STOP +CHILD +S` 처럼 보이는 이유가 이것이다. 앞이 phase, 뒤 `+` 가 오버레이다.

### 3-3. 전이 조건을 코드에서 하나씩 확인

**IDLE → WAIT** (`:587`)
```python
if self._has_lane or self._scan_seq > 0:
```
차선 메시지를 한 번이라도 받았거나 라이다 스캔을 한 번이라도 받았으면 넘어간다.
"센서가 살아 있는가"만 본다.

**WAIT → LANE** (`:647`, `:641~645`)
초록불(`self._light == "GREEN"`)이거나 `/manual_go` 가 신선하게 들어오면
`_wait_confirm` 에 6을 넣고(`start_confirm_ticks`), 매 틱 1씩 깎아서 0이 되면
`_start_drive()` 를 부른다. 6틱 = 0.3초. 신호등 한 프레임 오검출로 튀어나가지 않게 하는
확인 시간이다.

`_start_drive()` (`:652`)에서 두 가지 중요한 일이 일어난다.
- `self._grace_until = now + start_grace_sec(20초)` — grace 는 "봐주는 시간"이라는 뜻이다.
  **출발 후 20초 동안은 정지선/지름길
  판정을 아예 안 한다.** 출발선 바로 앞의 정지선을 자기가 방금 출발한 그 정지선으로
  다시 인식해서 멈춰버리는 사고를 막는 장치다.
- `/capture_yaw` 를 발행한다 (`:658`). 이게 **"지금 이 순간 차가 향한 방향을 0도로 삼아라"**
  라는 신호다. **yaw(요)** 는 차가 어느 쪽을 향해 돌아 있는지를 나타내는 각도다.
  **heading** 도 같은 뜻으로 쓴다. 회전을 재는 자이로가 들어 있는 **IMU** 센서가 재 준다.
  이후 모든 heading 판정은 절대 방위각이 아니라 이 기준 대비 상대각
  `yaw_rel` 로 한다. 예선에서는 IMU 절대각(예: "270도일 때")으로 판정했는데,
  그러면 차를 출발선에 놓는 방향이 조금만 달라져도 전부 어긋난다. 본선은
  "출발 방향에서 몇 도 돌았나"로 바꿨다 (헤더 주석 `path_planner_node.py:17`).

**LANE → CONE** (`:699~704`)
```python
if (self._cone_enter_streak >= int(P("cone_enter_scans"))     # 3스캔 연속
        and not self._red_stopping                             # 정지선 정지 중 아님
```

안 되고 3스캔을 내리 만족해야 1로 친다.

세 조건 전부 필요하다. 뒤 두 개는 각각 "정지선에서 멈춘 채로 콘 모드에 빠지는 것"과
"CONE↔LANE 을 초당 몇 번씩 왔다갔다 하는 핑퐁"을 막는다.

**CONE → LANE** (`:951`)
```python

```
콘 줄 피팅에 20스캔 연속 실패하면 나간다. 단 외부팀이 주는 `/corridor_path` 가
신선하게 들어오고 있으면 유지한다. 나갈 때 `cone_reenter_block_sec`(5초) 재진입 차단과
`s_zone_block_sec`(8초) S존 오인 차단 타이머를 같이 건다 (`:955~956`).

이렇게 **"한 번 일어난 뒤 정해진 시간 동안 같은 일이 또 일어나지 못하게 막는 타이머"** 를
**쿨다운(cooldown)** 이라고 부른다. 게임에서 스킬 한 번 쓰면 몇 초간 다시 못 쓰는 그것이다.
이 문서에서 "차단 타이머", "재진입 차단", "쿨다운"은 전부 같은 장치를 가리킨다.

**LANE → SHORTCUT** (`_check_shortcut`, `:758`)
- `self._shortcut_done` 이 이미 True 면 안 간다 → **평생 1회 원샷**

- `_stop_gate_ok(now)` 통과 — **게이트(gate)** 는 조건을 만족해야만 통과시키는 문이다.
  통과 못 하면 그 아래 판정을 아예 하지 않는다 (heading 창 + 차단 타이머, 아래 6장)

진입하는 그 줄(`:769`)에서 `_shortcut_done = True` 로 먼저 래치를 걸어버린다.
중간에 어떤 이유로 튕겨 나와도 다시 안 들어온다. 단 하나의 예외가 WAITING 타임아웃인데,
8초 동안 LEFT 표지판도 `/manual_go` 도 없으면 "지름길이 아니었나 보다" 하고
래치를 풀고 LANE 으로 돌아간다 (`:793~801`).

**SHORTCUT 내부 전이** — TURNING_1/2 는 시간이 아니라 **실제로 몇 도 돌았는지**로 끝낸다

`_circ_diff_deg` (`:79`)는 359도와 1도의 차이를 358도가 아니라 2도로 계산해주는

IMU 가 죽어서 yaw 가 갱신 안 될 때 영원히 도는 걸 막는 안전망이다.

## 4. LANE 모드 — 기본 주행

### 4-1. 한 문단 요약

노란 중앙선 점들에 2차식(포물선) 하나를 맞춘다. **그 2차식 자체를 갈 길로 쓴다.**
x=3.0m 앞에서 그 선의 y 값이 목표점이다. 그 다음 라이다로 확인된 장애물을 피하려고
경로 전체를 좌우로 조금 평행이동시킨다. 끝.

여기서 **2차식**이란 `y = a·x² + b·x + c` 를 말한다. x 는 차 앞쪽 거리(m),
y 는 좌우 위치(m, 왼쪽이 +)다. 계수 세 개가 각각 뜻하는 게 있다.

| 계수 | 뜻 | 크면 |
|---|---|---|
| `a` | 휘어짐 = **곡률** | 선이 많이 굽었다 (코너) |
| `b` | **기울기** — 차 바로 앞에서 선이 얼마나 비스듬한가 | 선이 옆으로 크게 벌어져 나간다 |
| `c` | 차 바로 앞(x=0)에서의 좌우 위치 | 선이 차에서 멀리 떨어져 있다 |

아래에서 "곡률 |a| ≤ 1.30", "기울기 |b| ≤ 2.80" 같은 말이 나오면 전부 이 셋 이야기다.
"이 선은 사람이 낼 수 없을 만큼 심하게 굽었으니 피팅이 잘못됐다"고 걸러 내는 기준이다.

### 4-4. 클래스 ID 를 어떻게 나눠 쓰나

**클래스 ID** 는 YOLO 가 "이건 몇 번 물체다"라고 붙여 주는 번호다. 학습시킬 때 사람이
정해 준 순서대로 0, 1, 2 … 가 매겨지고, **검출 결과에는 이름 대신 이 번호만 실려 온다.**
그러니 번호표를 잘못 읽으면 노란 중앙선을 흰 선으로 알아듣는다. 아래 함정이 그 이야기다.

`lane_planner.py:41~43` 에 정의돼 있다.

| 상수 | 값 | 무엇 |
|---|---|---|
| `YELLOW_CLS_IDS` | `{8}` | MID = 노랑 중앙선 |
| `YELLOW_DASH_CLS_IDS` | `{16}` | 어린이보호구역용 노란 점선 조각 |
| `WHITE_CLS_IDS` | `{6, 2}` | LANE = 흰 외곽선, CHILD_LANE = 학교구역 마킹 |

`_on_lane` (`path_planner_node.py:406~411`)이 `np.isin` 으로 한 번에 갈라 캐시에 넣는다.

**★ 여기서 반드시 짚고 갈 함정이 있다. 번호 체계가 두 벌이다.**
위 표의 8/16/6/2 는 **차선 모델(`lane.pt`)** 의 클래스 번호로, `/detect/lane` 의
`position.z` 로 들어온다. 반면 표지판·신호·차량을 보는 **물체 모델(`best.pt`)** 은
완전히 다른 번호를 쓴다 (`path_planner_node.py:52~62`).

| 모델 | 토픽 | 번호 예 |
|---|---|---|
| `lane.pt` | `/detect/lane` | 8=MID(노랑), 16=노랑 점선, 6·2=흰선류 |
| `best.pt` | `/detect/objects` | 0=BLACK_CAR, 1=CHILD_END, 3=CHILD_START, 4=CROSSROAD_OUT, 7=GREEN_CAR, 10=LEFT, 14=STOP |

같은 숫자 6이 차선 모델에서는 "흰 외곽선", 물체 모델에서는 "GREEN(초록불)"이다.
**두 토픽의 z 를 같은 표로 해석하면 안 된다.** 코드에서도 차선 쪽 상수는
`lane_planner.py:41~43`, 물체 쪽 상수는 `path_planner_node.py:56~62`
(`LEFT_SIGN_CLS_ID` 등)로 완전히 분리해 뒀다.

두 벌을 번호 순으로 나란히 놓으면 이렇다. 왼쪽 열 번호가 같아도 두 칸의 뜻은
서로 아무 상관이 없다는 것이 이 표의 요점이다.

| 1 | (코드가 안 씀) | CHILD_END |

명시돼 있다: "흰선 점은 안 쓴다 (signature는 호환 위해 유지)".

띄운 **순수 시각화용 선**이다 (`lane_planner.py:1252~1254`).
즉 "차선 폭 안에서 중앙을 잡는다"가 아니라 **"노란 선을 그대로 밟고 간다"** 가
현재 동작이다. 파일 안에 흰선 기반 차선 선택 로직(`_choose_lane_plan_from_white` 등)이
남아 있지만 `plan()` 에서 호출되지 않는 죽은 경로다.

### 4-5. TARGET_X / TARGET_Y_LIMIT 의 의미

```python
TARGET_X = 3.0        # lane_planner.py:53
TARGET_Y_LIMIT = 4.0  # lane_planner.py:54
```

- **TARGET_X = 3.0m** — 목표점을 차 앞 몇 미터에서 찍을 것인가.
  자전거 탈 때 바로 앞 바퀴를 보지 않고 몇 미터 앞을 보는 것과 같다.
  올리면 시선이 멀어져 부드럽지만 둔해지고(코너를 크게 돎), 내리면
  민감해지지만 흔들린다. 실제 조향에 쓰이는 **lookahead**(전방주시거리 — 차가 지금
  어디를 보고 핸들을 꺾을지, 그 "보는 거리") 는 motion 쪽에서
  속도 비례로 다시 잡으므로(`steer_focus_*`), 여기 값은 "planner 가 보고하는
  대표 목표점"의 성격이 강하다.
- **TARGET_Y_LIMIT = 4.0m** — 좌우 클리핑 한계. 피팅이 터져서 y=50m 같은
  말도 안 되는 값이 나와도 ±4m 로 잘라낸다. 안전 클램프다.
  **클리핑·클램프**란 값이 정해 준 범위를 벗어나면 범위 끝값으로 잘라 붙이는 것을 말한다.
  여기서는 +50m 든 +4.1m 든 전부 +4m 가 된다.
  `_publish_lane_result` (`:1213`, `:1214`, `:1225~1228`)와 CONE 경로(`:981`)에서
  모두 이 값으로 자른다.

샘플 점은 x = 1.0 ~ 11.0m 를 13개로 나눈 것이다
(`SAMPLE_X_MIN/MAX/COUNT`, `lane_planner.py:104~106`, `_sample_xs()` `:425`).

### 4-6. 노란선 피팅이 실제로 하는 일

`_fit_yellow_sliding()` (`lane_planner.py:648`)이 전부다. 이름에 sliding 이 붙어 있지만
실제로는 단순 `np.polyfit(2차)` + 여러 겹의 가드다. 주석(`:650`)에 이유가 있다 —
"YOLO seg가 직접 클래스를 골라주므로 RANSAC 같은 outlier 제거가 불필요".

용어부터 정리하고 가자. 이 절에만 낯선 말이 몰려 있다.

- **폴리핏(polyfit, 다항식 맞춤)** — 흩어진 점들 사이를 가장 잘 지나가는 곡선식 하나를
  찾아내는 계산이다. 엑셀 산점도에서 "추세선 추가"를 누르는 것과 같은 일이고,
  여기서는 그 추세선을 2차식(포물선)으로 잡는다.
- **outlier(이상치)** — 나머지 점들과 동떨어져 있어서 곡선을 엉뚱한 쪽으로 끌고 가는 점.
  점 하나가 크게 튀면 곡선 전체가 딸려 간다.
- **RANSAC** — 이상치가 잔뜩 섞인 점 무더기에서 "다수파"만 골라내 곡선을 맞추는
  유명한 방법이다. **여기서는 안 쓴다.** YOLO 가 이미 "이 픽셀은 노란 중앙선"이라고
  골라 준 점들만 오기 때문에 다수파를 다시 찾을 필요가 없다는 게 위 주석의 뜻이다.
- **seg(세그멘테이션)** — 물체를 네모 상자로 알려주는 게 아니라 **픽셀 하나하나를
  "여기는 차선"이라고 칠해서** 알려주는 검출 방식. 자세한 건 문서 02.
- **가드(guard)** — 이상한 값이 통과하지 못하게 덧대 놓은 검사 장치.
  아래 순서의 2·3·4·6번이 전부 가드다.

순서:
1. **ROI 자르기** (`:661`) — x는 0.5~12.0m, |y| < 4.5m 안만 쓴다.
   **ROI**(Region Of Interest, 관심영역)는 "이 범위 안의 것만 본다"고 미리 잘라 둔 구역이다.
   범위 밖의 점은 아예 계산에 넣지 않는다.
2. **직전 피팅 기준 이상치 제거** (`_filter_yellow_direction_outliers`, `:611`) —
   직전 곡선에서 법선 방향으로 0.70m 넘게 떨어진 점은 버린다.
   **법선 방향**은 곡선에 수직인 방향이다. 곡선이 비스듬히 누워 있어도
   "선에서 옆으로 얼마나 벗어났나"를 제대로 재려면 이 방향으로 재야 한다.
3. **x 구간마다 가장 가까운 점 하나만 선택** (`_select_yellow_closest_to_previous_fit`, `:623`) —
   0.45m 간격 bin 마다 1점. 선이 두껍게 검출돼도 한 줄로 얇아진다.
   **bin** 은 x 를 일정 간격으로 잘라 만든 "칸"이다. 칸마다 대표 1점만 남긴다.
4. **피팅 최소 조건** (`:666~667`) — 남은 점이 12개(`FIT_MIN_POINTS`) 이상이고
   x 스팬이 0.75m(`FIT_MIN_X_SPAN`) 이상일 때만 폴리핏을 돌린다.
   **스팬(span)** 은 점들이 x 방향으로 퍼져 있는 폭이다 — 가장 먼 점의 x 에서
   가장 가까운 점의 x 를 뺀 값. 점이 12개 있어도 전부 한 자리에 뭉쳐 있으면
   스팬이 0.75m 를 못 넘어 피팅을 안 한다. 한 뼘에 뭉친 점들로는 선이 어느 쪽으로
   뻗는지(기울기)를 정할 수 없기 때문이다.
   못 넘기면 그대로 실패 처리(아래 6번 hold)로 간다. 노란선이 점점이 조금만
   보이는 상황에서 엉뚱한 곡선을 만들지 않으려는 장치다.
   **이 두 문턱이 "왜 피팅이 실패하나"의 1순위 답이다** — 아래 4-6 끝의 정리 참고.
5. **가중 polyfit** (`:670~672`)
   ```python
   w = 1.0 / (1.0 + xs * xs)
   coef = np.polyfit(xs, ys, 2, w=w)
   ```
   **가중치** `w` 는 점마다 "이 점을 얼마나 믿을지" 매겨 둔 무게다. 무거운 점 쪽으로
   곡선이 더 끌려간다. 식이 `1/(1+x²)` 이니 가까운 점일수록 무겁고 먼 점은 가볍다
   (x=1m 이면 0.5, x=10m 이면 0.0099 — 100배 차이가 난다).
   주석이 이유를 정확히 적어놨다: "호모그래피 비선형성으로 멀리 픽셀 한 점 =
   가까운 안정점 한 점이 동일 가중되면 곡률(a)이 튄다."
   비스듬히 본 화면을 위에서 본 것처럼 펴면(**호모그래피** homography — 기울어진 카메라
   화면을 바닥 평면 좌표로 펴 주는 변환. 자세한 건 문서 02), 화면 위쪽 한 픽셀이
   바닥에서는 수십 cm 에 해당한다. 먼 점은 부정확하니 가중치를 낮춘다.
6. **계수 sanity + 점프 가드** (`:675~679`) — **sanity 체크**는 "이 값이 상식적으로
   말이 되나"를 보는 검사다. 곡률 |a| ≤ 1.30, 기울기 |b| ≤ 2.80,
   그리고 직전 곡선 대비 x=1.8/3.0/7.5m 세 곳에서 0.55m 넘게 튀면 거부.
   앞의 두 개는 "이 선 자체가 말이 되나", 뒤의 하나는 "직전 프레임과 견줘 말이 되나"다.
   0.05초 만에 차선이 55cm 옆으로 순간이동할 리는 없으니 그건 오검출로 본다.
7. **실패 시 hold** (`:682~689`) — 6프레임(`YELLOW_MAX_MISS`)까지는 직전 곡선을 그대로 쓴다.
   그 이상이면 `None` 반환 → `plan()` 도 `None` → planner 가 직전 결과 재발행
   (`_publish_last_lane`, `path_planner_node.py:1181`).
8. **EMA 스무딩** (`:691~697`) — 새 계수를 35%만 반영. 떨림 억제.

**EMA 스무딩**(지수이동평균, Exponential Moving Average)은 새로 측정한 값을 그대로 쓰지
않고, **직전 값을 새 값 쪽으로 조금씩 끌어당기는** 방식이다. 식은 이렇다.

```
   새값 = 이전값 + α × (측정값 - 이전값)
```

여기서 **α(알파)** 가 "새 측정값을 얼마나 반영할지" 정하는 0~1 사이 비율이고,
노란선 계수에는 0.35 가 쓰인다(`YELLOW_FIT_SMOOTH_ALPHA`). α 가 작을수록 부드럽지만
반응이 느리고, 1에 가까울수록 측정값을 곧이곧대로 따라가 떨림까지 따라간다.
0.35 면 한 프레임에 35%씩 따라가니, 값이 갑자기 바뀌어도 서너 프레임(0.2초쯤)에 걸쳐
옮겨 간다는 뜻이다.

목표점도 따로 스무딩된다 (`_smooth_target_y`, `:437`): 2cm 데드밴드,
알파 0.27 저역통과, 한 틱 최대 17.5cm 이동 제한.
세 가지가 각각 다른 일을 한다.
- **데드밴드(dead band, 무시 구간)** — 변화가 2cm 보다 작으면 아예 안 움직인다.
  차가 가만히 있어도 ±1cm 씩 꿈틀대는 잡음에 핸들이 반응하지 않게 만드는 장치다.
- **저역통과(low-pass)** — 천천히 변하는 성분만 통과시키고 빠른 떨림은 걸러낸다.
  바로 위 EMA 와 같은 식(α=0.27)이고 부르는 이름만 다르다.
- **한 틱 최대 이동 제한** — 앞의 둘을 통과했어도 한 틱(0.05초)에 17.5cm 넘게는
  못 움직인다. 값이 갑자기 튀어도 목표점은 계단처럼 조금씩만 옮겨 간다.

**정리 — 노란선 피팅은 이럴 때 실패한다.**
현장에서 "화면에는 노란선이 보이는데 차가 못 따라간다"는 상황을 만나면 이 목록을 짚으면 된다.
위에서 아래로 순서대로 걸린다.

| 걸리는 곳 | 실패 조건 | 기준값 |
|---|---|---|
| 1번 ROI | 노란 점이 x 0.5~12.0m, \|y\| < 4.5m 밖에만 있음 | `FIT_X_MIN/MAX`, `FIT_Y_ABS_MAX` |
| 2·3번 필터 뒤 | 남은 점이 12개 미만 | `FIT_MIN_POINTS = 12` |
| 4번 | 남은 점의 x 스팬이 0.75m 미만 (한 자리에 뭉침) | `FIT_MIN_X_SPAN = 0.75` |
| 6번 | 곡률 \|a\| > 1.30 또는 기울기 \|b\| > 2.80 | `FIT_CURVE_MAX`, `FIT_SLOPE_MAX` |
| 6번 | 직전 곡선 대비 세 지점 중 하나라도 0.55m 넘게 튐 | `YELLOW_MAX_JUMP_M = 0.55` |

주의할 점이 두 가지 있다.
- **2·3번 필터는 직전 곡선이 있을 때만 돈다** (`lane_planner.py:612`, `:624`).
  첫 프레임이나 오래 놓친 직후에는 필터 없이 바로 폴리핏으로 간다.
- **필터가 점을 걷어내기 때문에 "보이는 점 수"와 "피팅에 쓰이는 점 수"가 다르다.**
  화면에 노란 점이 40개 찍혀도 0.45m 칸마다 1점만 남기니 실제로는 10점 남짓이 될 수 있고,
  그러면 12개 문턱에 걸려 피팅이 안 돈다. 짧게 끊긴 노란선 조각에서 자주 생기는 일이다.

실패해도 곧장 경로가 끊기지는 않는다. 6프레임까지는 직전 곡선을 그대로 쓰고(hold),
그 이상이면 `None` 을 돌려주며 planner 가 직전 결과를 다시 내보낸다
(`_publish_last_lane`). 위 7번 항목이 그 이야기다.

### 4-7. 회피는 plan() 이 아니라 path_gen 이 한다 (이중 회피 방지)

`plan()` 안에도 장애물 회피 코드가 있다 (`lane_planner.py:1240~1250`).
전방 0.3~3.5m(`AVOID_X_MIN/MAX`)에 있고 목표점에서 좌우 0.7m(`AVOID_LATERAL`) 안에
들어온 장애물 하나라도 걸리면, 목표점을 통째로 0.8m(`AVOID_SHIFT`) 옆으로
밀어버리는 방식이다. 단계도 없고 램프도 없다. 거칠다.
**램프(ramp)** 는 경사로라는 뜻으로, 목표가 갑자기 바뀌어도 실제 값은 한 번에 조금씩만
따라가게 만드는 장치다. 램프가 없으면 0.8m 를 한 틱 만에 그대로 옮겨 버린다.

본선은 이걸 **끄고** 썼다. `_tick_lane_publish` (`path_planner_node.py:1155~1160`):
```python
result = lane_plan(self._yellow_xs, self._yellow_ys,
                   self._white_xs, self._white_ys,
                   [],   # 빈 장애물 — plan() 내부 0.8m 시프트 비활성
                   ...)
```
빈 리스트를 넘겨서 내부 회피 루프가 한 번도 안 돌게 만든다.
대신 회피는 전부 `PathGen` 이 맡는다 (5-3장). 파일 헤더(`:20`)에 그대로 적혀 있다 —
"plan()엔 빈 장애물(내부 0.8m 시프트 비활성) → path_gen 오프셋 최적화가 회피 전담."
회피가 두 군데서 동시에 일어나면 서로 싸워서 경로가 진동한다.

## 5. CONE 모드 — 라바콘 슬라럼

### 5-1. 한 문단 요약

**슬라럼(slalom)** 은 스키에서 온 말로, 세워 둔 표지 사이를 지그재그로 빠져나가는 주행이다.

라이다 점들을 "붙어 있는 것끼리" 묶어 덩어리(클러스터)로 만든다(`cluster_scan`).
이렇게 흩어진 점을 덩어리로 묶는 작업을 **클러스터링(clustering)** 이라 하고,
묶여 나온 덩어리 하나하나가 **클러스터** = 물체 하나 후보다.
그 덩어리들을 프레임 간에 추적해서 "진짜 있는 것"만 확정한다(`ClusterTracker`).
확정된 것 중 **왼쪽 콘 줄**에 2차식을 맞추고, 거기서 트랙 폭의 절반만큼
오른쪽으로 평행이동한 선을 갈 길로 삼는다.

### 5-2. cluster.py — 라이다 점을 덩어리로 묶기

**`cluster_scan()` (`lib/cluster.py:25`)** — 스캔 1회분을 클러스터 목록으로 바꾼다.

라이다는 500개 방향으로 "저기까지 몇 미터"를 알려준다. 이걸 x,y 점으로 바꾸면
(`:49`) 바닥에 뿌려진 점들이 된다. 콘 하나에는 여러 점이 찍힌다.
**이웃한 두 점 사이 거리가 임계값보다 크면 "다른 물체"로 자른다**는 게 핵심이다 (`:54~57`).

```
  라이다 점들 (위에서 본 그림)

    ●●●        ●●        ●●●●          ●
    └┬┘  gap   └┬┘  gap  └─┬─┘   gap   │
   콘1 ────크다── 콘2 ──크다── 벽 ──크다── 노이즈(1점, 버림)
```

임계값이 고정이 아니라 **거리에 비례**한다 (`:55`):
```python
allow = gap_m + gap_per_m * np.minimum(r[:-1], r[1:])
```
멀리 있는 물체일수록 빔과 빔 사이 간격(호 길이)이 벌어지기 때문이다.
5m 앞 콘은 점이 듬성듬성 찍히는데 고정 임계값을 쓰면 콘 하나가 3조각으로 쪼개진다.

그 외 두 가지 처리:
- **랩 병합** (`:61~66`) — 라이다 각도는 -π 에서 시작해 +π 에서 끝난다.
  차 바로 뒤에 있는 물체는 스캔의 맨 앞과 맨 뒤에 걸쳐 두 조각으로 나온다.
  양 끝점이 가까우면 하나로 합친다.
- **최소 점수 = 2** (`:70`) — 점 하나짜리는 노이즈로 보고 버린다.
  예선은 1이었다(주석에 명시).

결과는 `{"x","y","r","n"}` 목록이다. `r` 은 중심에서 가장 먼 점까지 거리에
padding(5cm)을 더한 **덩어리 반경**이다 (`:74`). 이 r 값이 나중에
"콘이냐 벽이냐"를 가르는 잣대가 된다.

**`ClusterTracker` (`lib/cluster.py:89`)** — 왜 추적이 필요한가?

한 스캔만 보면 노이즈와 진짜 물체를 구분할 수 없다. 반사가 튀어서 허깨비 덩어리가
한 프레임에 생겼다 사라지는 일이 흔하다. **그걸 믿고 핸들을 꺾으면 차가 헛돈다.**

그래서 프레임 사이를 이어붙인다. 이렇게 프레임을 넘어가며 "이건 아까 그놈"이라고
이어 붙인 대상 하나를 **트랙(track)** 이라고 부른다.
(9-6 에 나오는 `track_width` 의 track 은 "코스 폭"이라는 전혀 다른 뜻이다. 헷갈리지 마라.)

- **최근접 그리디 매칭** (`:122~137`) — **그리디(greedy, 탐욕적)** 는 전체를 놓고 최적을
  따지지 않고 "지금 눈앞에서 제일 가까운 짝"부터 차례로 확정해 버리는 단순한 방법이다.
  이전 트랙과 새 클러스터의 모든 거리쌍을 정렬해
  가까운 것부터 짝짓는다. `match_dist`(0.5m)를 넘으면 다른 물체로 본다.
- **k-of-n 확정** (`:173`) — 이름 그대로 "최근 n 번 중 k 번 이상 보였으면 진짜"로
  인정하는 규칙이다. 최근 3프레임(`n`) 중 2프레임(`k`) 이상 보이면
  `confirmed = True`. planner 는 `confirmed` 인 트랙만 쓴다
  (`path_planner_node.py:526`, `:875`, `:1018`, `:1205`).
- **coasting(코스팅)** (`:146~147`) — 자동차에서 액셀을 떼고 관성으로 굴러가는 것을
  coasting 이라고 한다. 여기서는 안 보인다고 바로 지우지 않고 잠깐 관성으로 끌고 간다는 뜻이다.
  이번 프레임에 안 보여도 트랙은 살려두고
  `seen = False` 로 표시. 3프레임 연속 안 보이면 제거 (`:167`).
- **vel_xy** (`:150`) — 프레임 간 이동량. 정적(라바콘) / 동적(다른 차) 판별 재료다.
  지금은 계산만 하고 아무도 안 쓴다. OVERTAKE 를 구현할 때 쓸 자리다
  (`path_planner_node.py:95` TODO 주석).

주의: 이 파일 헤더(`:13~14`)에 "외부팀(콘 통로 모듈)도 이 파일 하나만 import 한다 —
패키지 내 다른 모듈/rclpy 에 의존하지 말 것"이라고 적혀 있다. 이 파일에는
ROS 의존성을 넣으면 안 된다.

### 5-3. path_gen.py — 오프셋 후보에 점수 매기기

**중요한 사실 먼저**: `PathGen` 은 CONE 모드에서 호출되지 않는다.
`generate()` 를 부르는 유일한 곳은 `_publish_lane_result` (`path_planner_node.py:1211`),
즉 **LANE 경로의 장애물 회피**다. CONE 진입 시엔 `reset()` 만 불린다 (`:869`).
라바콘 사이를 지나는 경로는 5-4의 왼쪽 콘 피팅이 만든다.

`PathGen` 의 아이디어는 단순하다. **경로를 통째로 좌우로 몇 cm 밀지만 정한다.**
모양은 그대로 두고 평행이동만 한다.

```
   후보 오프셋: -1.2 -0.9 -0.6 -0.3  0.0 +0.3 +0.6 +0.9   (0.3m 간격, path_gen.py:51)
                                              └── +0.9 초과는 잘라냄 (left_offset_max)
                     ↑좌(+y)가 위쪽

   각 후보마다 경로를 그만큼 민 뒤 비용 계산 (_candidate_costs, :72)

      비용 = w_obs(3.0)      × Σ(0.45m 여유 침해량)
           + w_collision(100) × (경로가 장애물 원판을 관통한 개수)
           + w_lane(0.4)      × |오프셋|            ← 중앙으로 돌아오려는 힘
           + w_cont(1.5)      × |오프셋 - 현재값|   ← 갑자기 안 튀게

   ┌──────────────────────────────────────────────────┐
   │  d=-0.6 │ d=-0.3 │ d=0.0 │ d=+0.3 │ d=+0.6      │
   │  102.4  │  3.81  │ 1.24  │  0.52  │  0.94       │ ← 비용
   │         │        │       │   ★    │             │ ← 최소
   └──────────────────────────────────────────────────┘
                              ▼
        히스테리시스 (:117): 직전 선택보다 0.15 이상 좋아야 갈아탄다
                              ▼
        램프 (_ramp_toward, :67): 한 번에 0.06m 까지만 이동
                              ▼
              실제 적용 오프셋 → ys = ref_ys + offset
```

그림에 나온 말들을 먼저 풀면 이렇다.

- **오프셋(offset)** — 경로 모양은 그대로 두고 좌우로 통째로 밀어낸 거리. +가 왼쪽이다.
  이 노드가 정하는 건 오직 이 숫자 하나다.
- **비용(cost)** — 후보마다 매기는 **벌점 총합**이다. 점수가 아니라 벌점이라
  **낮을수록 좋다.** 여러 기준(장애물에 가까움, 중앙에서 멀어짐, 갑자기 움직임)을
  각각 벌점으로 환산해 더한 뒤, 합이 가장 작은 후보를 고른다.
  `w_obs`, `w_lane` 같은 `w_` 는 그 기준을 얼마나 무겁게 볼지 정하는 가중치다.
- **여유(clearance)** — 경로와 장애물 **표면** 사이에 남는 거리. 0 이하면 뚫고
  지나간다는 뜻이라 `w_collision`(100)이라는 큰 벌점을 맞는다.
- **장애물 원판** — 라이다 덩어리를 중심 + 반경 r 짜리 동그란 판 하나로 단순화해
  다룬다는 뜻이다. 실제 모양은 보지 않는다.
- **히스테리시스(hysteresis)** — 갈아타는 문턱을 "유지" 쪽으로 조금 높여 두는 것.
  새 후보가 지금 것보다 **0.15 이상 더 좋아야만** 갈아탄다. 두 후보 비용이
  엎치락뒤치락할 때 매 틱 좌우로 왔다갔다 하는 걸 막는다. 방 온도조절기가 목표 온도
  근처에서 껐다 켰다를 반복하지 않도록 위아래로 여유를 두는 것과 같은 장치다.

세 겹의 안정화 장치가 다 다른 일을 한다는 게 포인트다.
- **`w_cont`** — 비용 단계에서 "지금 위치와 먼 후보"에 벌점. 부드러운 선호.
- **히스테리시스** — 두 후보 비용이 비슷할 때 딱 붙어 진동하는 것 방지. 결정 단계.
- **`ramp_step`** — 결정이 갑자기 바뀌어도 실제 경로는 틱당 6cm 씩만 움직임. 출력 단계.

**좌우 비대칭**이 있다. `left_offset_max = 0.9` 로 왼쪽 후보를 잘라낸다 (`:54`).
파일 주석(`:12~13`)에 이유가 있다 — "좌측(+y)은 조향 스톱 여유 부족(-32)으로".
이 차는 좌우 조향 기계 스톱이 비대칭이라 왼쪽으로 크게 꺾지 못한다.
따라갈 수 없는 회피 경로를 만들어봐야 소용없으므로 아예 후보에서 뺐다.

또 하나. 참조 경로가 비어도 `return` 하지 않고 램프는 계속 진행시킨다 (`:106~109`).
주석에 "early-return 상태 동결(예선 버그 6) 금지"라고 적혀 있다.
중간에 빠져나가면 오프셋이 0.6m 인 채로 얼어붙어버린다.

### 5-4. CONE 모드가 실제로 도는 방식

`_cone_fit_attempt()` (`path_planner_node.py:871`) + `_tick_cone()` (`:912`).

```
  1) 확정 트랙을 ROI 로 자름 (x 0.3~10.0m, y -6~+6m)          (:880~882)
  2) 왼쪽 콘 고르기                                            (:886~890)
       - 직전 피팅이 있으면: 그 곡선에서 1.5m 이내 점들
       - 없으면(첫 프레임): y > 0 인 점들 = 왼쪽 절반
  3) 조건 확인: 점 2개 이상 + x 스팬 0.8m 이상                 (:894~898)
  4) 폴리핏: x스팬 ≥2.0m & 3점 이상이면 2차, 아니면 1차        (:900)
       가중치 1/(1+x²) — 가까운 콘 우선 (:901)
  5) sanity: |곡률| ≤ 1.5, |기울기| ≤ 3.0                      (:906)
  6) EMA 스무딩 alpha=0.20                                     (:941~946)

     실패했을 때 (:930~939)
       miss += 1
       직전 피팅 곡률항을 miss 당 20%씩 죽여가며 재사용 ("coast")
       → 콘이 잠깐 안 보여도 갑자기 직진으로 튀지 않고 서서히 펴진다
       miss 20 도달 → CONE 종료

  왼쪽 콘 줄 (left_fit)                       중심선 (center_coef)
       ●    ●    ●    ●                            :
       │                                           :
       └──── track_width/2 = 2.2m ────────────────→ 여기를 따라간다  (:974~976)
```

두 개의 특수 처리가 있다.

**콘 1개 이하일 때 바이어스** (`:977~978`)
```python
if self._cone_left_count <= 1:
    center_coef[1] -= float(P("cone_single_bias"))   # 0.268 = tan(15°)
```
왼쪽 콘이 거의 안 보이면 기울기 항에서 tan(15°)를 빼서 **시계방향으로 15도 틀어준다.**
**바이어스(bias)** 는 판단에 일부러 넣어 두는 한쪽 방향 치우침을 말한다.
근거가 부족할 때 아무 쪽도 안 고르는 대신, 미리 정해 둔 쪽으로 기울여 두는 것이다.
콘 코스가 시계방향 루프라는 사전 지식을 넣은 것이다. 예선 시뮬 기준값이므로
본선 코스 방향이 다르면 부호를 뒤집어야 한다.

**`/corridor_path` 우선** (`:918~919`, `:961~963`)
외부팀이 만든 콘 통로 경로가 0.5초 이내로 신선하게 들어오면, 자체 피팅 결과를 버리고
그걸 그대로 기준선으로 쓴다 (`_publish_corridor`, `:992`). 협업 인터페이스다.
빈 메시지를 받으면 신선도를 갱신하지 않아 자연 만료된다 (`:491`).

**CONE 정책** (`:915~916`): 조향 프로파일을 `SteerProfile.CONE` 으로 바꾸고
속도 cap 16을 건다. 프로파일이 실제로 뭘 바꾸는지는 `motion_node.py:400~401` 이다 —
평소대로 계산한 조향각에 `cone_steer_gain`(1.12, `tuning.yaml:174`)을 **곱한다**
(**게인** gain = 곱해 주는 배수).
즉 같은 경로라도 12% 더 크게 꺾는다. lookahead 를 건드리는 프로파일은 CONE 이 아니라
`S_ZONE` 이다 (`s_steer_focus_x` 3.7m 고정, `motion_node.py:531~532`).

## 6. 정지선 · 지름길 · 어린이보호구역 — 그리고 v 임계값 환산

### 6-1. v 픽셀이 왜 거리인가

`/detect/objects` 의 `position.y` 에는 **bbox 아래쪽 변의 세로 픽셀 좌표 v** 가 들어온다.
카메라를 앞으로 향하게 달았을 때, **바닥에 붙은 물체는 가까울수록 화면 아래쪽에 찍힌다.**

```
   화면 (v=0 이 맨 위)
   ┌──────────────────────────┐ v=0
   │                          │
   │      ┌──────┐            │ ← 멀리 있는 정지선 표지: v_bottom ≈ 180
   │      │ STOP │            │
   │      └──────┘  v=180     │
   │                          │
   │   ┌────────────┐         │
   │   │            │         │
   │   │    STOP    │         │ ← 가까운 정지선 표지: v_bottom ≈ 330
   │   └────────────┘ v=330   │
   └──────────────────────────┘ v=480
```

정확한 거리를 재려면 호모그래피를 써야 하지만, **"충분히 가까워졌나"만 알면 되는
판정에는 v 하나로 충분하다.** 그래서 v 를 거리 대용치(proxy)로 쓴다.
`_on_objects` (`:452~469`)가 클래스별로 **v 의 최댓값**을 뽑는다. 최댓값 = 가장 가까운 것.

### 6-2. ★ obj_v_ref_height 환산 (2026-07-31 추가)

**여기가 이 장에서 가장 중요한 부분이다.**

문제: `stop_v_threshold = 312.0` 같은 임계값들은 전부 **예선 시뮬레이터의
480p(가로x세로 640x480) 영상에서 튜닝된 픽셀값**이다. 그런데 본선 실차 카메라는
1920x1080 으로 올라갔다.

같은 거리에 있는 같은 표지판이라도 화면 세로가 480 → 1080 으로 2.25배 커지면
v 값도 2.25배가 된다. 480p 에서 v=312 였던 위치가 1080p 에서는 v=702 다.
반대로 말하면, **1080p 영상에서 v=312 가 나오는 시점은 아직 한참 먼 곳**이다.

그대로 두면 어떻게 되나?

```
   480p 기준 튜닝:  |———— 접근 ————|  v=312 도달 → 정지  (정지선 앞 0.5m)
                                    ▲ 여기서 멈춰야 함

   1080p 그대로:    |—— v=312 ——|—————— 남은 거리 ——————|
                    ▲ 여기서 멈춤 (훨씬 먼 곳)
```

한 가지 주의. **2.25배는 "픽셀값의 배율"이지 "거리의 배율"이 아니다.**
바닥에 붙은 물체의 v 는 거리에 반비례하듯 움직이므로(대략 `v ≈ 지평선 v + k/거리`),
환산을 빼먹었을 때 실제로 몇 미터 앞에서 오발동하는지는 호모그래피로 따로 계산해야
나온다. 확실한 건 "훨씬 멀리서 반응한다"는 방향뿐이다.

정지선을 한참 앞에서 오인식해 멈추고, 지름길 좌회전도 엉뚱한 데서 시작한다.
CROSSROAD_OUT 임계값도 마찬가지다.

해결: **들어오는 v 를 480p 기준으로 되돌려서 비교한다.**
`_resolve_obj_v_scale()` (`path_planner_node.py:413`)가 기동 시 딱 한 번 배율을 계산한다.

```python
ref = obj_v_ref_height          # 480.0 — 임계값이 튜닝된 기준 높이
h   = camera.yaml 의 image_height   # 실차 1080
scale = ref / h                 # 480/1080 = 0.4444
```

그리고 `_on_objects` (`:452`)에서 매 물체마다 곱한다.
```python
v_bot = float(p.position.y) * self._obj_v_scale
```

이 설계의 장점은 **해상도를 바꿔도 `tuning.yaml` 의 임계값들을 안 건드려도 된다**는 것이다.
`tuning.yaml:80~82` 에도 그렇게 적어놨다: "실차 카메라가 1080p 여도 planner 가
480p 로 환산해서 비교하므로 해상도를 바꿔도 이 값들은 그대로 두면 된다."

세 가지 주의점.
1. **높이의 단일 출처는 `config/camera.yaml` 의 `image_height` 다** (`:416~417`).
   `sensors.launch.py` 의 카메라 해상도 설정과 이 값이 어긋나면 환산이 틀어진다.
   해상도를 바꿀 땐 두 곳을 같이 봐야 한다.
2. **읽기 실패하면 배율 1.0 + 경고 로그** (`:432~437`). 조용히 틀리지 않는다.
   기동 로그에 `[objects] camera.yaml 에서 image_height 를 못 읽었다` 가 뜨면
   그날 주행은 정지선이 오발동한다고 봐야 한다.
3. **성공하면 이런 로그가 뜬다** (`:440~442`):
   `[objects] v 환산: 실제 1080p → 기준 480p (x0.4444)`.
   **주행 전에 이 줄이 있는지 확인하는 게 현장 체크리스트 1번이다.**
4. 이 환산은 `obj_v_ref_height` 기준 임계값 **전부**에 적용된다 —
   `stop_v_threshold`, `cross_v_threshold`, `child_start_v_thr`, `child_end_v_thr`,
   그리고 OVERTAKE 스텁용 `_car_max_v`.

### 6-3. 정지선(STOP) 로직

```
  _tick_lane_phase (:684)  ── now >= _grace_until (출발 20초 지남) ──┐
                                                                     ▼
                                         gate_ok = _stop_gate_ok(now)   (:730)
                                           ├ yaw_ref_set 인가?          (:733)
                                           ├ 지금 stop_block 중인가?    (:735)
                                           └ |yaw_rel - 0도| ≤ 10도인가? (:737)
                                                     │
                            ┌────────────────────────┴────────────────┐
                            ▼ (_shortcut_done 아직 False)             ▼
                  _check_shortcut (:758)                    _check_red_stop (:740)
                    STOP v ≥ 312 → SHORTCUT.WAITING          STOP v ≥ 312
                    + 평생 1회 래치                           + 신호등이 GREEN 아님
                                                             → _red_stopping = True
                                                               (GREEN 이 와야만 해제)
```

**heading 게이트가 왜 필요한가?** 정지선 표지판은 코스 여러 군데서 보인다.
옆 구간을 지나가다가 멀리 보이는 정지선에 반응하면 안 된다.
"차가 정지선 구간과 같은 방향(`stop_heading_rel` ± `stop_heading_tol`)을 보고 있을 때만"
반응하게 잠근다. 기준은 절대 방위각이 아니라 출발 기준 상대각 `yaw_rel` 이다(3-3 참고).

**`_update_stop_block` (`:720`)** 은 그 반대다. yaw_rel 이 `stop_block_heading_rel`(-90도)
부근이면 3초 동안 정지선 트리거를 **막는다**. 이미 정지선을 통과해 좌회전을 마친
직후이므로 같은 정지선에 다시 걸리면 안 된다는 뜻이다.
이 함수는 `_tick` 맨 앞(`:584`)에서 phase 와 무관하게 매 틱 돈다.
주석(`:583`)에 "red_stop과 shortcut '양쪽'에 공통 적용 — 기존 비대칭 버그 수정"이라고
적혀 있다. 예선에는 한쪽에만 걸려 있었다.

**red stop 은 GREEN 으로만 풀린다** (`:745~748`). 시간이 지나도 안 풀린다.
초록불을 못 보면 계속 서 있는다 — 의도된 동작이고, 그래서 `/manual_go` 라는
수동 탈출구가 따로 있다.

### 6-4. 지름길(SHORTCUT)

정지선에서 좌회전으로 질러가는 미션이다. 실행 자체는 planner 가 하지 않는다 —
**`owner = BLOCK` 과 목표 각도만 던지고, 실제 조향은 motion 이 한다**
(`motion_node.py:284~289`: `angle_cmd = BLOCK_STEER_ANGLE`, 값은 `tuning.yaml:204` 의 -100.0).
planner 는 "다 돌았나"만 판정한다.

```
  WAITING     정지 (owner=MISSION_STOP). LEFT 표지판 2회 검출 또는 /manual_go 대기
              8초 넘으면 포기 → 래치 풀고 LANE 복귀
     ↓
  TURNING_1   owner=BLOCK, block_param=90도, block_id +1 (새 블록 = 원샷)
              |yaw_rel - 진입시 yaw_rel| ≥ 90도가 되면 종료
     ↓
  FOLLOW      owner 는 LANE 으로 자동 복귀(스냅샷을 안 채우니까). 차선 추종.
              CROSSROAD_OUT v ≥ 278 이거나 15초 지나면 종료
     ↓
  TURNING_2   두 번째 좌회전. 같은 방식.
     ↓
  LANE 복귀 (다시는 안 옴)
```

`block_id` 는 `_sc_enter_turn` (`:840`)에서 +1 된다. **여기서 오해하기 쉬운 게 있다.**
motion 은 `owner == BLOCK` 인 동안 매 틱 `BLOCK_STEER_ANGLE` 을 그대로 출력한다
(`motion_node.py:284~289`). 즉 좌회전은 "한 번 실행하고 끝"이 아니라
**planner 가 owner=BLOCK 을 계속 보내는 동안 계속 실행되는 상태**다.
그러면 `block_id` 는 왜 있나? motion 에서 `block_id` 의 실제 쓰임은 딱 하나,
`detect_transition()` 이다 (`motion_node.py:248~252`) — owner 나 block_id 가 바뀐
그 틱에 `_transition_reset()` 을 한 번 불러 조향 스무딩 상태를 리셋한다.
그래서 TURNING_1 과 TURNING_2 는 서로 다른 id 를 받아 각각 깨끗한 상태로 시작한다.

"원샷"을 보장하는 주체는 motion 이 아니라 **planner 자신**이다 — `_shortcut_done`
래치(`:769`)와 서브상태 머신이 좌회전을 한 번씩만 걸어준다.
`lib/arbitration.py:86` 의 `should_run_block()` 은 id 기반 원샷 게이트로 만들어져
있고 단위 테스트(`test/test_arbitration.py:119~143`)도 있지만, **현재 motion_node 는
이 함수를 import 조차 하지 않는다** (`motion_node.py:27` 은 `arbitrate_speed`,
`detect_transition` 둘만 가져온다). 나중에 BLOCK 을 "한 번만 실행하는 동작"으로
바꾸고 싶을 때 쓰라고 준비만 해둔 부품이다.

`LEFT` 표지판 디바운스(`:786~789`)는 올림 1 / 내림 1 방식이다. 검출되면 +1,
안 되면 -1(0 이하로는 안 내려감). 2회 누적되면 확정.
한 프레임 오검출로 좌회전이 시작되지 않게 하는 장치다.

**디바운스(debounce)** 는 원래 전기 스위치 용어다. 스위치를 한 번 눌러도 접점이 미세하게
여러 번 붙었다 떨어지는데(bounce), 그걸 "한 번"으로 정리하는 처리를 디바운스라고 한다.
여기서는 그 정신만 빌려 **"한 번 튄 검출은 안 믿고 여러 번 쌓여야 인정"** 하는 데 쓴다.
3-3 의 `start_confirm_ticks`(6틱), CONE 진입의 `cone_enter_scans`(3스캔)도 같은 계열이다.

### 6-5. 어린이보호구역(CHILD_ZONE) — 기본 비활성

`enable_child_zone: false` 다 (`tuning.yaml:113`). 지금은 안 돈다.

동작 자체는 `_tick_child_zone` (`:1058`)에 있다.
CHILD_START 표지 v ≥ 200 이면 켜고, CHILD_END v ≥ 400 이면 3초 뒤 끈다.
켜져 있는 동안 하는 일은 두 가지뿐이다.
1. 속도 cap 22 추가 (`:674~675`)
2. `plan()` 에 `child_zone=True` 전달 → 노란 **점선**(z=16) 기반 피팅으로 전환
   (`lane_planner.py:1214~1222`)

안전망이 여러 겹이다: 하드 타임아웃 17초(`:1073`), 진입 쿨다운 3초, 종료 쿨다운 10초.
"들어갔는데 END 표지를 영영 못 보는" 상황에서 계속 기어가는 걸 막는다.

START v 임계(200)가 END(400)보다 훨씬 낮다는 데 주의. START 는 **멀리서부터**
반응해서 미리 감속해야 하고, END 는 **완전히 지나친 뒤**에 풀어야 하기 때문이다.

### 6-6. 보행자(PEDESTRIAN) — 기본 비활성

`enable_pedestrian: false`. `_check_pedestrian` (`:1007`)의 판정 방식만 짚어둔다.
전방 1.5~8m, 반경 0.1~0.4m(사람 크기) 클러스터가 **노란 중앙선 곡선 기준 ±1.2m 안**에
있으면 후보다 (`:1025~1027`). 여기서 `self._lane_center_coef` 를 쓰는데,
이건 `_publish_lane_result` (`:1193`)에서 매번 갱신된다.

재밌는 예외 처리가 하나 있다 (`:1034~1040`): 후보가 3개 이상이고 서로 1.5m 안에
밀집해 있으면 **사람이 아니라 차량**으로 보고 무시한다. 차 한 대의 옆면이
여러 클러스터로 쪼개져 나오는 걸 사람 여럿으로 오인하지 않으려는 것이다.

## 7. lib/arbitration.py — 누가 이기는가

### 7-1. 왜 중재가 필요한가

**중재(arbitration)** 는 여러 요구가 동시에 들어왔을 때 미리 정해 둔 우선순위 규칙으로
하나를 정하는 일이다. 그때그때 사람이 판단하는 게 아니라 **규칙표가 정해져 있다**는 게 요점이다.

여러 요구가 동시에 들어온다.

```
   "어린이보호구역이니까 22 이하"          ─┐
   "차선 품질이 나쁘니까 7 이하"            ─┼→ ??? → 최종 속도 하나
   "코너 안쪽이니까 최소 7.2는 내야 함"     ─┤
   "지금은 정지선이니까 0"                  ─┘
```

이걸 임의로 처리하면 "감속 명령이 가속 명령에 덮여서 어린이보호구역을 전속으로 통과"
같은 사고가 난다. 예선 코드가 실제로 그랬다 (`arbitration.py:7` 주석의 "버그 2 무조건 대입").

### 7-2. 규칙

`arbitrate_speed()` (`lib/arbitration.py:31`). 우선순위가 docstring 에 명시돼 있다.
요구는 세 종류로 들어온다 — **cap(상한)** 은 "이 속도를 넘지 마라",
**floor(하한)** 은 "이 속도는 내라", **fixed(고정)** 는 "이 속도로 해라"다.

```
   1. stop 이면 → 무조건 0.0          (제일 셈)
   2. v = max(v_base, 모든 floor)     (최소 속도 보장)
   3. fixed > 0 이면 → v = fixed      (floor 결과를 덮음)
   4. v = min(v, 모든 cap)            (cap 이 최종 승자)
```

**"cap 이 floor 를 이긴다"** 가 핵심 결정이다. 주석(`:8~9`)에 근거가 있다 —
"예선 실효 의미론: slow cap 5.0 > 코너 floor 7.2". **안전 방향(느리게)이 항상 이긴다.**

`<= 0` 이거나 NaN/inf 인 cap/floor 는 "없음"으로 무시된다 (`_valid_entries`, `:16`).
(NaN 은 "숫자가 아님", inf 는 "무한대"라는 뜻의 특수값이다. 나눗셈이 어긋나면 나온다.)
그래서 `Float32MultiArray`(ROS 메시지 종류 이름 — 실수 여러 개를 한 줄로 싣는 통)에서
"값 없음"을 표현하려고 별도 플래그를 둘 필요가 없다.
0을 넣으면 그게 없음이다.

planner 쪽에서는 `_publish_drive_cmd` (`:1117`)가 **cap 후보들의 최솟값**만 골라
한 개로 압축해서 보낸다 (`:1120~1121`). 여러 곳에서 `self._cmd["caps"].append(...)` 로
쌓아둔 것들이 여기서 하나로 합쳐진다.
`fixed` 도 cap 을 넘으면 cap 으로 잘린다 (`:1123~1124`, 주석: "예선 '무조건 대입' 버그
재발 방지").

### 7-3. Owner 개념

**owner(오너, 소유자)** 는 이번 틱에 **조향을 누가 쥐는가**를 적어 둔 이름표다.
`lib/drive_cmd.py:28~33`.

| Owner | 뜻 | motion 의 반응 |
|---|---|---|
| `LANE` (0) | 평상시. 경로 추종해라 | 경로로 조향각 계산 |
| `BLOCK` (1) | 정해진 동작 실행해라 (좌회전 등) | 하드코딩 조향각 -100도 |
| `MISSION_STOP` (2) | 미션상 정지 | 속도 0, 조향은 마지막 각 유지 |
| `SAFETY_STOP` (3) | 안전 정지 | 동일 |

**한 틱에 owner 는 정확히 하나다.** 여러 모드가 동시에 "내가 조향한다"고 나설 수 없다.
이게 owner 의 존재 이유다. 예선처럼 여러 Bool 토픽이 각자 조향에 개입하면
누가 이겼는지 로그를 봐도 알 수 없다.

**owner 는 조향의 소유권만 정하고, 속도 cap 은 owner 와 무관하게 누구나 얹을 수 있다.**
예를 들어 SHORTCUT 의 TURNING_1 은 owner=BLOCK 이면서 동시에 `shortcut_speed_cap` 15가
얹혀 있고, motion 은 하드코딩 속도 10을 그 cap 에 종속시켜 계산한다
(`motion_node.py:288`). 조향은 BLOCK 이 독점, 속도는 협의 — 이런 분리다.

`owner_from_value()` (`drive_cmd.py:43`)는 **알 수 없는 값이 오면 `SAFETY_STOP`** 을
돌려준다. 잘린 메시지나 깨진 값 = 정지다. fail-safe 방향이 일관되게 잡혀 있다.
**fail-safe** 란 고장이 났을 때 위험한 쪽이 아니라 **안전한 쪽(정지·감속)으로 넘어지게**
만들어 둔 설계를 말한다. "모르겠으면 선다"가 이 시스템 전체의 기본 태도다.

`detect_transition()` (`arbitration.py:76`)은 owner 나 block_id 가 바뀌었는지 본다.
motion 은 True 일 때 조향 스무딩 등 내부 상태를 리셋한다 (`motion_node.py:248~250`).
BLOCK 좌회전 직후 이전 LANE 주행의 스무딩 상태가 남아 있으면 복귀가 이상해진다.

## 8. 신선도 가드 — 센서가 죽었을 때

이 시스템에는 "값이 왔다"와 "값이 **최근에** 왔다"를 구분하는 가드가 세 개 있다.
전부 `path_planner_node.py:375~384` 에 모여 있다.

값이 너무 오래돼서 못 믿는 상태를 **스테일(stale, 상했다)** 이라 하고, 반대로 방금 온
믿을 만한 값을 **신선(fresh)** 하다고 한다. 우유에 붙은 유통기한과 같은 개념이고,
이 문서에서 "신선도"는 전부 이 뜻이다.

```python
def _objects_fresh(self, now):   # objects_fresh_sec = 0.5
    return (now - self._objects_time) <= float(self._prm("objects_fresh_sec"))
def _lane_fresh(self, now):      # lane_stale_sec = 0.6
    return (now - self._lane_rx_time) <= float(self._prm("lane_stale_sec"))
def _scan_fresh(self, now):      # scan_stale_sec = 1.0
    return (now - self._scan_rx_time) <= float(self._prm("scan_stale_sec"))
```

**왜 필요한가?** 노드가 죽어도 마지막에 받은 값은 변수에 그대로 남아 있다.
YOLO 가 3초 전에 죽었는데 planner 는 3초 전의 "정지선 v=350" 을 아직 들고 있다.
그걸 믿고 판단하면 유령 정지선에 반응한다. **"오래된 값은 값이 아니다"** 가 원칙이다.

| 가드 | 스테일이면 벌어지는 일 | 코드 위치 |
|---|---|---|
| `objects_fresh_sec` (0.5s) | STOP/CROSSROAD/CHILD/LEFT 판정 전부 스킵 | `:669`, `:749`, `:765`, `:786`, `:827`, `:1064` |
| `lane_stale_sec` (0.6s) | **`/center_path` 발행을 멈춘다** | `_tick_lane_publish` `:1146~1151` |
| `scan_stale_sec` (1.0s) | 회피 장애물 목록을 비움, CONE miss 매 틱 계수 | `:1201~1210`, `:927~932` |

**`lane_stale` 의 처리가 특히 영리하다.** 경로 발행을 그냥 **중단**한다.
`/drive_cmd` 는 계속 나간다 (`_publish_drive_cmd` 는 `_tick` 에서 무조건 호출).
그러면 motion 쪽의 경로 워치독(`path_stale_sec` 0.5s, `motion_node.py:123`, `:259`)이
걸려서 `_lane_lost_cmd()` 로 감속 정지한다. **폴백 책임을 명확히 한 쪽에 몰아준 설계다.**
planner 가 억지로 옛날 경로를 계속 뿜어내면 차는 존재하지 않는 차선을 따라 달린다.

**`scan_stale` 의 CONE 처리** (`:927~932`)도 짚어둘 만하다.
```python
if not scan_fresh:
    self._cone_miss += 1     # 스테일 — new_scan/grace 무관 매 틱 계수
```
평소 miss 는 "새 스캔이 왔는데 피팅 실패"일 때만 센다. 그런데 라이다가 아예 멈추면
새 스캔이 안 오니 miss 가 영원히 안 늘고 CONE 에서 탈출할 수 없다.
주석(`:926`)에 그 이유가 적혀 있다.

차선 품질도 신선도를 적용한다 (`:610`):
```python
lane_q = self._lane_quality if self._lane_fresh(now) else 0.0
```
스테일이면 0.0 = 최악 취급 → 감속 cap. 안전 방향으로 틀린다.
