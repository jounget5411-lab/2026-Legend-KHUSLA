# 04. 제어 — 판단을 실제 움직임으로 (모터와 차량 인터페이스)

이 문서는 "어디로 갈지 정해진 다음"부터를 다룬다. path_planner 가 만들어 준 경로점
(`/center_path`)과 주행 명령(`/drive_cmd`)을 받아, 실제 조향각과 속도를 계산하고,
그 값을 실차 서보/모터가 알아듣는 숫자로 바꿔 `/xycar_motor` 로 20Hz 로 계속 쏘는 부분이다.
담당 파일은 `motion_node.py`(계산), `lib/car_interface.py`(실차 변환),
`lib/drive_cmd.py`(명령 형식 계약), `car_state_node.py`(차 상태 집계),
`teleop_node.py`(수동 조종), `ros1_docker/vesc_relay.py`(ROS1 다리), `config/car.yaml`(실측값)이다.
인지(YOLO/BEV)와 판단(상태머신)은 다른 문서에서 다룬다.
(여기서 "서보"는 각도를 지정하면 그 각도로 돌아가 그 자세를 버티는 모터로, 이 차에서는
앞바퀴를 꺾는 부품이다. 그냥 "모터"라고 하면 뒤에서 차를 미는 구동 모터를 말한다.
BEV 는 Bird's Eye View — 카메라 영상을 위에서 내려다본 것처럼 펴 놓은 그림이고 02 문서 소관이다.)

### 0.1 코드에서 확인된 안전장치 (전부 실제로 있는 것)

표를 읽기 전에 네 단어만 풀어 둔다. **틱(tick)** = 제어 주기 한 번, 이 문서에서는 항상
0.05초(20Hz) 한 사이클이다. **워치독** = "정해진 시간 안에 소식이 없으면 고장으로 간주"하는
타이머다. **클램프/클립** = 정해진 최대·최소를 벗어나면 그 경계값으로 잘라 붙이는 것.
**mux(멀티플렉서)** = 여러 입력 중 하나만 골라 내보내는 선택기, TV 입력 전환 스위치와 같다.

| 안전장치 | 위치 | 동작 |
|---|---|---|
| `/drive_cmd` 워치독 0.3초 | motion_node.py:234-236 | 명령이 0.3초 끊기면 owner 를 MISSION_STOP 으로 간주 → 속도 0 |
| 경로 워치독 0.5초 | motion_node.py:259-260, 441-452 | owner=LANE 중 `/center_path` 가 0.5초 끊기면 조향은 직전각 유지, 속도는 1초에 걸쳐 0 으로 |

| 텔레옵 우선 mux | motion_node.py:306-311 | `/teleop_cmd` 가 신선하면(0.3초 이내) 자율 출력을 무시하고 사람 명령을 쓴다 |
| 텔레옵 estop | teleop_node.py:164-167 | 스페이스바 → 속도 0 + estop(emergency stop, 비상정지) 플래그 |

### 0.2 ★ 코드에서 확인된 "구멍" — 알고 있어야 할 것

1. **motion_node 는 종료할 때 정지 명령을 보내지 않는다.**
   `main()` 은 `destroy_node()` → `rclpy.shutdown()` 만 한다 (motion_node.py:741-750).
   Ctrl+C 로 죽이면 `/xycar_motor` 발행이 그냥 끊긴다. 마지막 명령을 ROS1 쪽 VESC 스택이
   계속 유지하는지 여부는 **저장소 안에서 확인할 수 없다**(차에서 실험해야 할 항목).
   → 그래서 아래 3번의 데드맨 가드가 중요하다.

2. **vesc_relay 데드맨 가드는 기본값이 꺼져 있다.** `deadman_enable` 기본 False
   (vesc_relay.py:34). 켜려면 실행할 때 `_deadman_enable:=true` 를 붙여야 한다
   (vesc_relay.py:20). 실차 주행 전에 반드시 결정할 것.

3. **텔레옵 estop(스페이스)은 "즉시 정지"가 아니다 — mux 모드에서는 램프로 내려간다.**
   스페이스를 누르면 motion 이 speed_cmd=0 을 만들지만(motion_node.py:308-309),
   출력은 CarInterface 의 slew 를 거치므로 틱당 1.5 씩만 줄어든다(car_interface.py:127-129).
   주행속도 24(≈1.9 m/s)에서 0 까지 16틱 = **약 0.8초**. 그동안 대략 0.5~0.8 m 는 더 간다.
   (`--direct` 모드 텔레옵은 스페이스에서 `car.reset()` 을 호출해 즉시 0 이 된다 —
   teleop_node.py:167. 즉 **직발행 모드가 더 급하게 선다**.)

4. **텔레옵을 끄면 0.3초 뒤 자율주행이 다시 살아난다.** teleop mux 는 신선도(마지막으로
   받은 지 얼마나 됐나 — 정해진 시간 안에 온 것만 "신선하다"고 보고 쓴다) 기반이라
   `/teleop_cmd` 가 0.3초 안 오면 자동 해제된다(motion_node.py:242, drive_cmd.py:20).
   즉 "텔레옵으로 세워 놓고 q 로 껐다" = 차를 놓아준 것이다. planner 가 LANE 상태면
   차는 다시 출발한다. **완전히 세우려면 텔레옵이 아니라 launch(=motion_node)를 죽여야 한다.**

5. **속도 명령 2~3 은 "정지"가 아니라 "출발"이다.** 데드존(명령을 줘도 모터가 아예 안 구르는
   구간. 이 차는 속도명령 4 미만이 그렇다) 스냅(car_interface.py:135-147)이
   명령 크기가 데드존의 절반(2.0) 이상이면 구르는 최소값 4 로 **올려 준다**.
   반쯤 죽은 명령이 정지 상태로 낑낑대는 것(기어 손상·소음)을 막으려는 의도지만,
   "작은 값이니 안 움직이겠지"는 틀린 생각이다.

### 0.3 비상 정지 절차 (권장 순서)

```
  1순위  차를 들어올린다 / 배터리(모터배터리) 커넥터를 뽑는다   ← 확실
  2순위  motion_node 가 떠 있는 터미널에서 Ctrl+C                ← 발행 중단
         (단 0.2절 1번: ROS1 쪽 마지막 명령 유지 여부 미확인)
  3순위  텔레옵 스페이스바(estop)                                ← 0.8초 램프 정지
         ※ 텔레옵을 종료하면 안 된다. 종료하면 0.3초 뒤 자율 복귀.
```

`ros2 topic pub` 으로 `/xycar_motor` 에 정지를 쏘는 것은 **효과가 없다**.
motion_node 가 20Hz 로 계속 자기 값을 덮어쓰기 때문이다.

## 1. 전체 그림 — 명령이 바퀴까지 가는 길

한 문단 요약: planner 는 "어디로 갈지(경로)"와 "어떻게 갈지(주행권/제한속도)"를 따로 보낸다.
motion 은 경로에서 조향각과 기본속도를 만들고, 주행권/제한으로 최종 속도를 중재(여러 곳에서
들어온 요구를 정해진 우선순위로 하나로 정리하는 것)한 뒤, CarInterface 로 실차 숫자(트림·기계
스톱·데드존·램프 반영)로 바꿔 `/xycar_motor` 에 발행한다. 여기서 **트림**은 기계가 치우쳐
조립된 것을 보정하려고 항상 더해 주는 값이다 — 이 차는 명령 -20 이 직진이다.
그 토픽은 ROS1 브리지(ROS1 과 ROS2 사이에서 토픽을 서로 옮겨 주는 프로그램)를 건너 도커 안의
VESC 스택으로 들어가 서보와 모터를 돌린다.
반대 방향으로는 VESC 텔레메트리(기기가 스스로 보고해 주는 계측값 — 전압·전류·회전수 등)가
`/vesc/state` 로 돌아와 car_state 가 속도·거리·전압으로 가공해 `/car_state` 로 뿌린다.

```
 [ROS2 / 우리 코드]
 ┌───────────────┐  /center_path (경로점 PoseArray)   ┌──────────────┐
 │ path_planner  │───────────────────────────────────>│              │
 │  (판단)       │  /drive_cmd  (owner/cap/floor …)   │ motion_node  │
 │               │───────────────────────────────────>│  (제어)      │
 └───────────────┘                                    │              │
        ^                                             │  CarInterface│
        │ /car_state ── planner + motion 둘 다 구독   └──────┬───────┘
 ┌──────┴────────┐                                           │
 │ car_state_node│<── /imu (35Hz)                            │
 │  (상태집계)   │<── /vesc/state                            │ /xycar_motor
 └───────────────┘         ^                                 │ [angle, speed]
                           │                                 │ 20Hz 연속
 [키보드]  teleop_node ─────┼─── /teleop_cmd ────────────────>│(mux)
                           │                                 v
 ─────────────────────────┼──────────────────────── ros1_bridge (호스트) ──
 [ROS1 / 도커 컨테이너]    │                                 │
                           │                                 v
                    vesc_relay.py                    xycar_motor.py (벤더)
                     ^                                       │
                     │ /sensors/core                         v
                     └──────────────────────────────── VESC ─┴─> 서보 + 모터
```

| 파일 | 한 줄 역할 |
|---|---|
| `track_drive/motion_node.py` | 경로 → 조향각/속도 계산, 주행권 게이트(누가 운전하느냐에 따라 출력을 통째로 고르는 관문), 20Hz 발행 |
| `track_drive/lib/drive_cmd.py` | 토픽 배열의 "몇 번째 칸이 무엇인가" 계약 + enum(숫자에 이름을 붙여 둔 목록) |
| `track_drive/lib/arbitration.py` | 속도 중재(cap=상한/floor=하한/fixed=고정/stop=정지) 순수 함수(입력이 같으면 항상 같은 값을 내고 바깥 상태를 안 건드리는 함수 — 그래서 시험하기 쉽다) |
| `track_drive/lib/car_interface.py` | 논리 명령 → 실차 서보/모터 숫자 변환 |
| `track_drive/car_state_node.py` | IMU + VESC → `/car_state` 한 줄로 집계 |
| `track_drive/teleop_node.py` | 키보드 수동 조종 |
| `ros1_docker/vesc_relay.py` | ROS1 쪽에서 VESC 텔레메트리 변환 + 데드맨 가드 |
| `config/car.yaml` | 이 차 고유의 **실측값** (시뮬 값 없음) |

그림에서 놓치기 쉬운 선이 하나 있다. `/car_state` 는 planner 뿐 아니라 **motion 도 구독한다**
(motion_node.py:182). motion 은 이걸 두 군데에 쓴다 — 자율주행 중이 아닐 때 "직전 속도"를
VESC 실측값으로 되돌리는 데(motion_node.py:325)와, 주인이 바뀌었을 때 상태를 재시드하는
데(motion_node.py:435)다.

이 선만 따로 그리면 이렇다.

```
  car_state_node ──/car_state (20Hz, 8칸)──> motion_node
                                              · 구독 배선            182행
                                              · 콜백은 스냅샷 저장만  220행
                                              · 8칸 중 motion 이 실제로 꺼내 쓰는 건 speed_ms 하나

    쓰는 곳 ①  매 틱 (325행)
               "owner=LANE + 경로 신선 + 텔레옵 안 끼어듦" 이 전부 참일 때만
               직전 속도 = 방금 낸 속도 명령.  그 외 모든 경우(정지·BLOCK·텔레옵·경로 소실)는
               직전 속도 = VESC 실측 속도(speed_ms)를 명령 단위로 되돌린 값

    쓰는 곳 ②  주인이 바뀐 직후 (435행, _transition_reset)
               같은 방식으로 직전 속도를 실측값에서 다시 심는다(재시드)

    그 "직전 속도"가 쓰이는 곳
               focus_x = clip(3.8 + 0.055 × 직전속도, 4.2, 5.0)  [m]
               = 지금 몇 m 앞을 보고 핸들을 꺾을지(lookahead) — 3.4절
```

왜 이렇게 해 놨냐면, 서 있다가 다시 출발할 때 "직전 속도"가 옛날 주행 속도(24)에 얼어붙어
있으면 차는 기어가는 중인데 5 m 앞을 보고 꺾어 코너를 놓치기 때문이다. 자율로 굴러가는
동안에는 명령값이 곧 속도이니 명령값을 쓰고, 그 외에는 **실제로 바퀴가 도는 속도**를 믿는다.

(그림에 나온 `PoseArray` 와 뒤에 나올 `Float32MultiArray` 는 ROS 가 기본으로 주는 메시지
형식 이름이다. 각각 "위치·자세 목록"과 "실수 배열"이라는 뜻이고, 그 이상의 의미는 없다.)

### 1.1 이 문서에서 계속 나오는 용어 7개

0절 용어표 중에서도 이 일곱 개는 3·4·6·7장에 계속 되풀이해 나온다. 여기서 한 번 더 짚는다.

| 용어 | 뜻 (일상 비유) |
|---|---|
| mux (멀티플렉서) | 여러 입력 중 하나만 골라 내보내는 선택기. TV 입력 전환 스위치 |
| 워치독 | "일정 시간 소식이 없으면 문제로 간주"하는 타이머. 알람 안 끄면 신고 |
| slew / 램프 | 값이 한 번에 못 튀게 "틱당 최대 변화량"을 거는 것. 볼륨 서서히 올리기 |
| IIR 저역통과 | 새 값을 조금만 반영해 떨림을 깎는 평활. `새 = 이전 + α×(목표−이전)` |
| 데드존 | 명령을 줘도 아무 일도 안 일어나는 구간. 페달 유격 |
| 센서리스 ESC | 모터 위치센서 없이 도는 모터 구동기. 정지→급가속에 약하다 |
| eRPM | 모터의 전기적 회전수. 실제 바퀴 회전수 × 극쌍수. 여기선 4614 eRPM = 1 m/s |

## 2. 명령의 형식 — `lib/drive_cmd.py`

### 2.1 왜 이런 파일이 생겼나

예선에서는 판단 노드가 `/limit_speed`(Bool), `/target`, 그 밖에 12개쯤 되는 플래그 토픽을
따로따로 쐈다. 문제는 이 방식이 **라치(latch, 걸쇠)** 라는 점이다. "속도 제한 켜"를 한 번 보내면
"꺼"를 받을 때까지 계속 켜져 있다. 그 "꺼"가 유실되거나 노드가 재시작되면 제한이 영원히 걸린
채로 주행한다. 파일 머리말(drive_cmd.py:6-8)에 "재도입 금지 버그 3·4·5 대응"이라고 적혀 있는 게
이 얘기다.

본선에서는 **스냅샷(snapshot) 방식**으로 바꿨다. 매 틱(20Hz) 지금 이 순간의 상태 전부를
숫자 8칸짜리 배열 하나에 담아 보낸다. 받는 쪽은 기억하지 않고 "지금 온 것"만 본다.
메시지 하나를 놓쳐도 50ms 뒤에 완전한 상태가 다시 온다.

### 2.2 `/drive_cmd` 레이아웃 (planner → motion, 8칸)

| 인덱스 | 이름 | 뜻 |
|---|---|---|
| 0 | `owner` | 지금 조향·속도의 주인 (아래 2.3) |
| 1 | `steer_profile` | 조향 특성 프로파일 — 미리 정해 둔 설정 묶음 (아래 2.4) |
| 2 | `speed_cap` | 속도 상한. 0 이하 = 제한 없음 |
| 3 | `speed_floor` | 속도 하한. 0 이하 = 없음 |
| 4 | `speed_fixed` | 속도 고정값. cap 에 종속 |
| 5 | `block_id` | 원샷(한 번만 실행되고 끝나는) 동작 일련번호. 같은 번호 재수신은 무시 |
| 6 | `block_param` | 블록 파라미터 (좌회전 목표 회전각 deg 등) |
| 7 | `lane_offset` | planner 가 적용 중인 횡방향(진행방향 기준 좌우) 오프셋(m). 디버그용 |

정의는 drive_cmd.py:63-71, 기본값은 74-83, 인코딩/디코딩은 106-128 에 있다.

### 2.3 Owner — 왜 "주인"이 명령에 실려 다니나

```python
class Owner(IntEnum):     # drive_cmd.py:28-33
    LANE = 0              # 차선 추종이 운전한다
    BLOCK = 1             # 정해진 동작(좌회전 등)을 실행한다
    MISSION_STOP = 2      # 미션상 정지 (신호/정지선/보행자/대기)
    SAFETY_STOP = 3       # 안전상 정지
```

자율주행에서 가장 흔한 사고는 "두 로직이 동시에 핸들을 잡는 것"이다. 예를 들어 차선추종은
"오른쪽으로 붙어"라 하고 회피 로직은 "왼쪽으로 꺾어"라 하면, 두 값을 더하거나 번갈아 쓰는
순간 차는 갈지자로 간다. Owner 는 이 문제를 "**핸들은 한 번에 한 명만 잡는다**"는 규칙으로
푼다. 매 틱 명령에 "지금 주인이 누구인지"가 같이 실려 오고, motion 은 그 주인에 따라 출력을
통째로 고른다(motion_node.py:284-304). 주인이 바뀌면 스무딩(값이 급하게 튀지 않게 부드럽게
깎는 처리) 상태를 리셋한다
(motion_node.py:247-252, arbitration.py:76-83) — 이전 주인의 관성이 새 주인 명령에
섞여 들어가는 것을 막기 위해서다.

Owner 값이 안전 설계에 쓰이는 방식이 두 가지 더 있다.

* **모르는 값 = 정지.** `owner_from_value()` 는 정의되지 않은 숫자나 NaN 을 받으면
  SAFETY_STOP 을 돌려준다 (drive_cmd.py:43-48).
* **짧은 메시지 = 정지.** 배열이 잘려 owner 칸이 아예 없으면 기본값이 SAFETY_STOP 이다
  (drive_cmd.py:74-75).

참고로 현재 planner 는 SAFETY_STOP 을 **한 번도 발행하지 않는다**(저장소 전체 grep 확인:
정의·기본값·motion 의 수신 처리에만 등장). 즉 SAFETY_STOP 은 "통신이 깨졌을 때를 위한
비상 기본값"으로만 존재한다. 실제 정지는 전부 MISSION_STOP 으로 나간다
(path_planner_node.py:590, 638, 679, 690, 695, 783, 1049).

### 2.4 SteerProfile — 조향 "성격"을 바꾸는 스위치

```python
class SteerProfile(IntEnum):   # drive_cmd.py:36-40
    NORMAL = 0
    CONE   = 1     # 라바콘 슬라럼(지그재그로 빠져나가기) 구간
    S_ZONE = 2     # S자 구간
```

owner 를 바꾸지 않고(= 여전히 차선추종이 운전하면서) 조향의 성격만 바꾸고 싶을 때 쓴다.
motion 에서 실제로 하는 일은 두 가지뿐이다.

* `CONE` → 계산된 조향각에 1.12 배(`cone_steer_gain`)를 곱한다 (motion_node.py:400-401).
  콘 사이를 빠져나갈 때 조금 더 날카롭게 꺾으라는 뜻이다.
* `S_ZONE` → 앞을 보는 거리(lookahead, 전방주시거리 — "얼마나 앞을 보고 핸들을 꺾을지"의
  거리다. 3.4절에서 자세히 다룬다)를 고정 3.7 m 로 바꾼다 (motion_node.py:531-532).
  평소에는 속도에 비례해 4.2~5.0 m 를 보는데, S자에서는 멀리 보면 두 커브가 상쇄돼
  직진처럼 보이기 때문에 일부러 가까이 본다.

### 2.5 나머지 세 토픽

  (**yaw** 는 위에서 내려다봤을 때 차가 좌우로 얼마나 돌아 있나, 즉 "방향"이다.

  시간 비율 0~1, 액셀을 얼마나 밟았나에 해당한다. **tacho** = 모터가 몇 바퀴 돌았는지
  세는 누적 카운터, 즉 주행거리계다.)
* **`/teleop_cmd`** (텔레옵 → motion, 3칸): `angle`, `speed`, `estop` (drive_cmd.py:227-230).

  (drive_cmd.py:232-237), **인코드**할 때는 0.0 이다(drive_cmd.py:242-246).
  "잘린 메시지를 받으면 정지로 해석하되, 보내는 쪽이 estop 을 빼먹은 건 정상 주행 의도"라는
  뜻이다. 받는 쪽은 비관적으로, 보내는 쪽은 명시적으로.

### 3.2 "섀도우 계산"이 무엇이고 왜 하나

4번 단계가 이 노드 설계의 핵심이다. 정지 중이든 좌회전 블록 실행 중이든, **경로만 신선하면
차선추종 계산을 매 틱 그대로 돌린다**(motion_node.py:254-266). 결과를 출력에 쓰지 않아도
돌린다. 그래서 "그림자(shadow)" 계산이다.

바로 아래 문단에 나오는 **히스테리시스**는 켜지는 문턱과 꺼지는 문턱을 일부러 다르게 둬서, 경계에서
판정이 깜빡거리는 걸 막는 방식이다. 에어컨이 26도에서 켜지고 24도에서 꺼지는 것과 같다
(실제 숫자는 3.5절). **스무딩**은 값이 급하게 튀지 않게 부드럽게 깎는 처리다.

이유는 이 계산이 **상태를 가진(stateful)** 계산이기 때문이다. 코너 판정 히스테리시스
(`_corner_frames`), 직진 확정 카운터(`_straight_ticks`), 부스트 레벨
(`_straight_boost_level`), 조향 스무딩 기준각(`_prev_angle`) 같은 내부 상태가 매 틱 갱신돼야
연속적인 값이 나온다. 정지 중에 계산을 멈춰 두면, 다시 출발하는 순간 이 상태들이
몇 초 전 값에 얼어붙어 있어 엉뚱한 조향이 튀어나온다. "이전 상태가 동결된 채 이월되는 것"이
재도입 금지 **버그 6** 이고(arbitration.py:78-80 주석), 섀도우 계산이 그 대책이다.
파일 머리말이 이 노드의 역할을 "경로가 있으면 owner와 무관하게 매 틱 섀도우 계산(내부 상태
갱신 유지)"이라고 못 박아 둔 것도 같은 얘기다(motion_node.py:4-5).
(머리말 13-14행에 나오는 "버그 6 대응"은 이것과 짝을 이루는 **다른** 장치를 가리킨다 —
주인이 바뀌었을 때 스무딩 기준각을 CarInterface 의 마지막 발행각에서 되살리는 것,
즉 `_transition_reset()`(motion_node.py:419-435)이다.)

### 3.3 볼 구간 자르기 — `_reanchored_segment()` (463-492)

받은 경로점 전부를 쓰지 않는다. 유효하지 않은 점(NaN, x<0)을 걸러내고, x 순으로 정렬하고,
겹치는 점을 지운 뒤, "지금 차에서 가장 가까운 점"을 찾아(482행) 거기서부터의 **경로를 따라 잰
거리** `rel_s` 를 계산한다.

여기서 재미있는 판단이 하나 있다(487-489행).

* 가장 가까운 경로점까지의 거리가 `reanchor_far_m`(0.65 m)보다 **멀면** → 차가 경로에서
  이탈한 상태다. 이때는 `min_s = 0` 으로 두고 **가장 가까운 점부터** 본다 = 경로로 되돌아간다.
* 그보다 **가까우면** → 이미 경로 위에 있다. 이때는 `min_s = 1.0 m` 부터 본다 = 발밑은 무시하고
  **앞쪽만** 본다.

발밑을 계속 보면 이미 지나간 오차에 반응해 핸들을 떨게 된다. 반대로 이탈했는데 앞만 보면
영원히 돌아오지 못한다. 두 상황을 거리 하나로 가른 것이다. 보는 최대 거리는
`lookahead_x_max`(10 m)까지다.

### 3.4 ★ 조향 알고리즘 — "가우시안 가중 다점 순수추종"

#### 쉬운 설명

순수추종(Pure Pursuit)은 자율주행에서 가장 널리 쓰이는 조향 방법이다. 원리는
**"앞쪽 한 점을 정해 놓고 그 점을 향해 핸들을 꺾는다"** 가 전부다. 자전거를 탈 때 바로 앞
바닥을 보면 비틀거리고, 저 앞을 보면 안정적으로 가는 것과 같다. 그 "보는 거리"를
lookahead(전방주시거리)라고 한다.

```
        멀리 볼 때 (lookahead 큼)          가까이 볼 때 (lookahead 작음)
                     ● 목표점                          ● 목표점
                   ╱                                  ╱
                 ╱                               ╱
        ┌──┐  ╱  작은 각도 → 부드러움     ┌──┐╱   큰 각도 → 민첩·불안
        │차│╱                             │차│
        └──┘                              └──┘
```

이 코드는 여기서 두 가지를 더 얹었다.

**(1) 한 점이 아니라 여러 점을 쓴다.** 경로점 하나를 골라 쓰면 그 점이 튀었을 때 조향도 튄다.
그래서 구간 안 **모든 점**에 대해 각각 "이 점을 향하려면 얼마나 꺾어야 하나"를 계산해 놓고
(motion_node.py:501), **가중평균**을 낸다(538-539). 가중치는 목표 거리(`focus_x`)를 중심으로 한
종 모양 곡선(가우시안)이다. 즉 "4.5 m 앞 점을 제일 중요하게, 4 m 와 5 m 도 꽤, 2 m 와 8 m 는
조금만" 반영한다. `steer_focus_sigma`(1.8 m)가 그 종의 폭이다.

```
   가중치
    1.0 ┤          ╭──╮            focus_x = 4.5m 예시
        │        ╭─╯  ╰─╮          sigma  = 1.8m
    0.5 ┤     ╭──╯      ╰──╮
        │  ╭──╯            ╰──╮
    0.0 ┼──┴────┬────┬────┬──┴────  경로 진행거리 rel_s
        0      2.5  4.5  6.5   9  (m)
```

**(2) "그 점을 향하는 각"과 "그 점에서의 길 방향"을 섞는다.** 앞의 것만 쓰면 코너 안쪽을
파고들고, 뒤의 것만 쓰면 옆으로 밀린 것을 못 고친다.

```
   ┌ pursuit(그 점을 향하는 각) ┐        ┌ heading(그 점에서 길이 향한 각) ┐
   │  "저기로 가라"             │        │  "가서는 저 방향으로 서라"       │
   └────────────────────────────┘        └──────────────────────────────────┘

        경로 ·  ·  ·  ●  ·  ·  ·             경로 ·  ·  ·  ●─→ (길의 방향)
                    ╱                                     ╱
                  ╱  ← 이 각이 pursuit                  ╱   ← 이 각이 heading
        ┌──┐    ╱                             ┌──┐    ╱      (차 방향과 길 방향의 차이)
        │차│  ╱                               │차│  ╱
        └──┘                                  └──┘

   pursuit 만 쓰면  : 목표점만 보고 질러가서 코너 안쪽을 깎는다
   heading 만 쓰면  : 방향은 맞추는데 옆으로 1 m 밀려 있어도 그대로 나란히 간다
   그래서 둘을 각각 게인을 곱해 더한다
```

* `pursuit_angles` = 그 점을 향하는 각도 = `atan2(-y, x)` (motion_node.py:501)
* `heading_angles` = 그 점에서 경로가 향한 각도 = `atan(-dy/dx)` (motion_node.py:504-507)
* 최종 = `pursuit_gain × pursuit + heading_gain × heading` (motion_node.py:524-527)

(부호에 `-` 가 붙는 이유: 좌표계는 y 가 왼쪽이 +(REP-103 — ROS 가 정한 표준 좌표 규약이다.
x 는 차 앞쪽, y 는 왼쪽, z 는 위쪽)인데, 조향 명령은 **+가 우회전**이라
부호를 뒤집어야 한다.)

#### 게인이 상황에 따라 바뀐다 (motion_node.py:509-522)

**게인(gain)** 은 "재 놓은 오차를 얼마나 세게 반영할까"를 정하는 곱셈 계수다. 게인이 크면
조금만 틀어져도 핸들을 확 꺾는다 — 민첩하지만 불안하다. 작으면 둔하지만 안정적이다.
아래 표의 숫자가 그 계수이고, 이 코드는 그 값을 상황에 따라 바꾼다.

| 상황 | pursuit 게인 | heading 게인 |
|---|---|---|
| 직진 (steer_ratio < 0.50) | 0.08 | 0.08 |
| 직진 + 부스트 최대 | 0.656 까지 블렌드 | 0.656 까지 블렌드 |
| 커브 (steer_ratio ≥ 0.50) | 1.62 | 2.22 |

직진 게인이 0.08 로 극단적으로 작은 게 눈에 띈다. 직진에서는 거의 핸들을 안 건드린다는 뜻이고,
그래야 고속 직선에서 좌우로 흔들리는 위빙(weaving, 뱀이 기어가듯 좌우로 계속 흔들리는 현상)이
안 생긴다. 대신 진짜로 방향이 틀어졌을 때
느리게 복귀하는 문제가 생기므로, **직진 부스트**(motion_node.py:366-384)가 "경로와 내 방향의
각도 오차(`line_angle_error`)"에 따라 게인을 끌어올린다. 단계는 이렇다.

| 각도 오차 | 부스트 레벨 | 직진 pursuit/heading 게인 |
|---|---|---|
| 0° | 0.0 | 0.08 |
| 5° (`straight_boost_on_deg`) | 1.0 | 0.40 |
| 10° 이상 (`straight_boost_full_deg`) | 1.8 (최대) | 0.656 |

두 가지를 헷갈리지 말 것. ① **부스트가 5°에서 "시작"하는 게 아니다.**
`straight_boost_off_deg` 가 0.0 이라 0°부터 이미 올라가기 시작한다(제곱 곡선이라 초반에는
아주 천천히 — motion_node.py:367-371). 5° 는 레벨이 1.0 에 "도달"하는 지점이고, 5° 를 넘어야
시작되는 것은 레벨 1.0 → 1.8 의 **추가** 부스트다(372-378).
② **레벨 1.8 은 "게인 1.8배"가 아니다.** 게인은 레벨을 섞음비로 써서 0.08 ↔ 0.40 사이를 선형
보간(두 값 사이를 비율대로 섞는 것. 레벨 0.5 면 0.08 과 0.40 의 딱 절반인 0.24)
하는데(motion_node.py:515-522), 레벨이 1.0 을 넘으면 0.40 을 지나쳐 최대 0.656 까지 간다.
기준 0.08 대비 약 8 배다.
`straight_boost_blend_alpha`(0.45)로 매 틱 부드럽게 섞기 때문에 계단식으로 튀지는 않는다.
여기서 **α(alpha)** 는 "새로 계산된 값을 얼마나 반영할까"의 비율이다. 0.45 면 매 틱
새 값 쪽으로 45%만 따라간다 — 남은 55%는 직전 값이 붙잡고 있으니 값이 계단처럼 튀지 않는다.

#### 직진이냐 커브냐는 어떻게 아나 — `_steer_gain_ratio()` (565-621)

경로점들의 **곡률**(κ, 얼마나 휘었나)과 **방향 변화량**(bend, 시작 대비 몇 도나 돌았나)을
계산해 각각 0~1 로 정규화(단위가 다른 값을 0~1 이라는 공통 눈금으로 옮기는 것. 0 이면
"전혀 안 휘었다", 1 이면 "완전히 급커브")한 뒤 큰 쪽을 쓴다.
곡률은 길이 얼마나 휘었는지를 재는 값으로, 반지름 큰 원(완만)일수록 작고 반지름 작은
원(급커브)일수록 크다.

* 곡률: `κ = |y''| / (1+y'²)^1.5` (602행) — 미분기하 표준식. 0.018 부터 0.080 까지를 0→1 로 맵.
* 방향변화: 4° 부터 20° 까지를 0→1 로 맵.
* 둘 다 85 퍼센타일(백분위 — 값을 작은 것부터 줄 세웠을 때 아래에서 85% 지점에 있는 값.
  100개면 85번째)을 쓴다(604, 606행). 평균이 아니라 상위값을 쓰는 이유는,
  경로 일부만 급하게 휘어도 그것을 커브로 봐야 하기 때문이다. 그렇다고 최대값을 쓰면
  점 하나 튄 것에 속는다. 85 퍼센타일은 그 절충이다.

가까운 구간(2.4 m)과 먼 구간(5.5 m)에 대해 각각 계산해 **큰 쪽**을 최종 `steer_ratio` 로 쓴다
(motion_node.py:352-356). 지금 휘었거나 앞이 휘었으면 커브로 본다는 뜻이다.

#### 속도에 따라 보는 거리가 변한다 (motion_node.py:534-537)

```
focus_x = clip(3.8 + 0.055 × 직전속도명령, 4.2, 5.0)   [m]
```

명령 24(≈1.9 m/s)면 3.8+1.32 = 5.12 → 상한 5.0 m. 명령 8이면 4.24 m.
빠를수록 멀리 본다 = 부드럽게, 느릴수록 가까이 본다 = 민첩하게. 자전거 비유 그대로다.
`_last_speed` 는 자율주행 중에는 명령값, 그 외에는 VESC 실측 속도로 갱신된다
(motion_node.py:321-325).

#### 코너 탈출 되감기 (corner-exit unwind, 542-551)

코너를 빠져나올 때 사람은 핸들을 미리 풀기 시작한다. 코드도 같은 일을 한다.
직전 곡률비(바로 위에서 만든 0~1 값 `steer_ratio` 다. 1 에 가까울수록 급커브)가 0.45
이상이었는데 지금 0.22 이하로 떨어졌으면(=코너가 끝나는 중),
5프레임 동안 조향 크기를 0.80배로 줄인다(motion_node.py:386-395, 542-551).
단, 부호가 바뀐 경우(반대로 꺾으려는 경우)에는 건드리지 않는다(547-548).

전환 직후에는 이 트리거가 금지된다(`unwind_block_ticks`=5, motion_node.py:387-388).
정지에서 막 출발한 직후 "곡률이 뚝 떨어진 것처럼" 보여 잘못 발동하는 것을 막는 신규 게이트다.

#### 조향 스무딩 3단 — `_smooth_angle()` (553-563)

```
   새 목표각 ──> ① 데드밴드 ──> ② IIR 저역통과 ──> ③ 스텝 제한 ──> 논리 조향각
                |Δ|<0.6°면      prev + 0.55×Δ       한 틱 최대 12
                무시(그대로)     (55%만 따라감)
```

① 미세한 떨림 무시, ② 지수평활(새 값을 55%만 반영 — 관성), ③ 한 틱에 12 이상 못 움직임.
여기까지가 **논리 조향각**(±100 스케일)이고, 실제 서보 값으로 가는 길에 CarInterface 의
레이트 리밋(틱당 8)이 **한 번 더** 걸린다(4장). 즉 조향은 총 4중으로 부드럽게 눌러져 있다.

세 단계의 이름을 풀면 이렇다.

* **데드밴드(deadband)** — 변화가 아주 작으면 아예 없던 일로 치는 구간. 여기서는 새 목표각이
  직전 각과 0.6° 밖에 차이 안 나면 그냥 직전 각을 그대로 쓴다. 손이 미세하게 떨려도 핸들이
  안 움직이게 하는 것과 같다.
* **IIR 저역통과(=지수평활, exponential smoothing)** — 새 값으로 확 갈아타지 않고 직전 값을
  새 값 쪽으로 조금씩 끌어당기는 방식이다. 식은 `새 = 이전 + α×(목표 − 이전)` 하나뿐이고,
  여기서 α = 0.55 다. α 가 작을수록 부드럽지만 반응이 느리고, 1 이면 스무딩이 없는 것과 같다.
  "저역통과"란 천천히 변하는 성분(진짜 코너)은 통과시키고 빠르게 튀는 성분(잡음)은 깎는다는
  뜻이고, "IIR"은 옛날 값의 영향이 아주 조금씩이나마 계속 남는 방식이라는 뜻이다.
* **스텝 제한(레이트 리밋)** — 한 틱에 움직일 수 있는 최대량을 못박는 것. 위 두 단계를
  통과했어도 한 번에 12 이상은 못 움직인다.

세 개를 한 문장으로 하면 "작은 건 무시하고, 큰 건 절반만 따라가고, 그래도 크면 잘라낸다"다.

### 3.5 속도는 어떻게 정해지나

속도 결정은 두 단계다. **① `_speed_from_angle()` 이 기본속도(v_base)를 만들고,
② `arbitrate_speed()` 가 제한들을 적용해 최종값을 만든다.**

#### ① 기본속도 (motion_node.py:667-702)

두 개의 후보 속도를 계산해 **작은 쪽**을 쓴다(699행).

* **각도 기반**(671-686): 조향각을 그대로 쓰지 않고, 먼저 `angle_scale` 을 곱한다(671-679).
  이 스케일은 **앞이 곧을수록 작아진다** — 앞이 안 휘었으면 0.60(`corner_exit_angle_scale`),
  앞이 휘어 있으면 1.0, 코너 안에 있으면 거기에 ×0.82(`corner_inside_angle_scale`).
  "지금은 꺾고 있어도 앞이 곧게 뻗어 있으면 굳이 속도를 죽이지 말라"는 뜻이다.
  그렇게 나온 값 `a` 가 12°(`speed_slow_start_deg`) 이하면 기본 24, 40°(`speed_slow_full_deg`)
  까지 선형으로 3(`speed_min`)까지 줄인다. "많이 꺾으면 느리게".
  ※ 스케일 때문에 **조향각 40° 가 곧 속도 3 은 아니다.** 직선 구간(스케일 0.60)에서
  조향각 40° 면 a = 24 → 속도는 약 15 다. 속도가 3 까지 떨어지려면 조향각이 약 67 은 돼야 한다.
* **예측(preview) 기반**(690-698): 앞 5 m 구간의 곡률과 횡방향 변화량으로 `preview_ratio`
  (0~1)를 만들고(623-665), 그 비율만큼 미리 감속한다. "앞이 휘었으면 도착하기 전에 느리게".

여기에 코너 히스테리시스가 붙는다(motion_node.py:359-363).

```
  preview_ratio ≥ 0.55(enter) 가 4프레임 연속  →  in_corner = True
  preview_ratio ≤ 0.35(exit)                  →  즉시 카운터 0
```

들어갈 땐 4프레임 확인하고 나올 땐 즉시 — 코너 판정이 깜빡이며 속도가 출렁이는 것을 막는
전형적인 히스테리시스다. `in_corner` 이면 속도에 **하한**(`corner_inside_speed`=7.2)을 건다
(700-701행). 코너 안에서 너무 느려져 멈춰버리는 것을 막는다. 주석에 "예선 보존 — 반드시 유지"
라고 못 박혀 있다(688행).

#### ② 중재 (arbitration.py:31-66) — cap 이 floor 를 이긴다

**중재(arbitration)** 란 여기저기서 들어온 속도 요구를 정해진 우선순위에 따라 하나로 정리하는
일이다. **cap** = 상한("이보다 빠르면 안 됨"), **floor** = 하한("이보다 느리면 안 됨"),
**fixed** = 고정값("무조건 이 속도")이다.

```python
def arbitrate_speed(v_base, caps, floors, fixed, stop):
    1. stop 이면 무조건 0.0
    2. v = max(v_base, 유효한 floor 들)      # 하한 적용
    3. fixed > 0 이면 v = fixed              # 고정값이 덮어씀
    4. v = min(v, 유효한 cap 들)             # 상한이 최종 승자
```

우선순위가 **정지 > 상한 > 고정 > 하한** 이라는 점이 중요하다. 예를 들어 어린이보호구역
제한속도 cap 5.0 과 코너 하한 floor 7.2 가 동시에 걸리면 최종은 **5.0** 이다.
"안전 제한은 무슨 일이 있어도 뚫리지 않는다"가 규칙이다(arbitration.py:8-9 주석).
0 이하이거나 NaN 인 cap/floor 는 "없음"으로 무시된다(16-28행).

motion 이 매 틱 넣는 cap/floor 목록은 다음과 같다(motion_node.py:271-282).

| 종류 | 값 | 출처 |
|---|---|---|
| cap | `cmd["speed_cap"]` | planner (신호·구역·지름길 등) |
| cap | 20.0 (`speed_curve_base`) | **직진 미확정**이면 걸린다 |
| floor | 7.2 (`corner_inside_speed`) | 코너 안일 때만 |
| floor | 5.0 (`speed_min_drive`) | 항상 — 데드존(4) 위 보장 |
| floor | `cmd["speed_floor"]` | planner |

**직진 미확정 cap** 이 중요한 설계다. `_straight_ticks` 는 코너가 아니고, preview_ratio 가 낮고,
조향각이 12° 이하일 때만 올라가고 아니면 0 으로 초기화된다(motion_node.py:409-413).
이게 20틱(=1초) 쌓여야 "직진 확정"이고, 그 전까지는 속도가 20 으로 묶인다. **"직선인 것 같다"가
아니라 "1초 내내 직선이었다"여야 풀가속(24)을 허용**한다는 뜻이다.

계산 예: 직진 확정 상태, planner cap 없음, 코너 아님 →
`v_base=24` → floor 5 적용해도 24 → cap 없음 → **최종 24** (≈1.92 m/s).
직진 미확정이면 마지막 단계에서 cap 20 이 걸려 **20** (=1.6 m/s).

`speed_min_drive: 5.0` 이 car.yaml 에 있는 이유는 실측 데드존이 4 이기 때문이다
(car.yaml:22). 예선 코드의 `SPEED_MIN=3.0` 을 그대로 쓰면 실차에서 **차가 안 구른다**.
주석의 "재도입 금지 버그 7"이 그것이다.

### 3.6 경로가 사라지면 — lane-lost (441-452)

```
   경로 소실 감지 (0.5초 미수신)
        │
        ├─ 조향: 마지막 명령각을 그대로 유지        ← 꺾인 채로 있으면 꺾인 채로
        └─ 속도: 소실 시점 속도부터 1초에 걸쳐 선형으로 0
```

예선 코드는 차선을 잃으면 `±100` 풀조향으로 "찾으러 가는" 복구 동작을 했는데, 실차에서는
그것이 벽으로 돌진하는 동작이 될 수 있어 **삭제됐다**(motion_node.py:122, 442-446 주석).
직전각 유지 + 1초 감속은 "모르겠으면 하던 대로 하면서 조용히 선다"는 보수적 정책이다.

주의: 이건 **감속**이지 급정지가 아니다. 1초 동안 평균 절반 속도로 가면 1.9 m/s 기준
약 1 m 를 더 간다.

### 3.7 BLOCK — 정해진 동작 실행 (284-290)

지름길 좌회전 같은 "정해진 동작"은 owner=BLOCK 으로 온다. motion 이 하는 일은 단순하다.
조향을 `-100`(풀 좌), 속도를 `10` 으로 놓는 것뿐이다(motion_node.py:127-128, 285-289).
**언제 끝나는지는 motion 이 판단하지 않는다.** planner 가 `/car_state` 의 yaw 진행을 보고
목표 각도만큼 돌았다 싶으면 owner 를 LANE 으로 되돌린다
(path_planner_node.py:806-812 부근). 역할 분리가 명확하다 — planner 는 판단, motion 은 실행.

BLOCK 속도도 planner 의 cap 에 종속된다(motion_node.py:288-289). 하드코딩 값이 제한을
뚫지 못하게 하는 방어다.

### 3.8 디버그 문자열 읽는 법 (715-736)

`/debug/arbitration` 이 1Hz 로 이런 줄을 뱉는다.

```
owner=LANE prof=NORMAL | cap: cmd=- straight=20.0 | floor: corner=- min=5.0 cmd=- |
fixed=- | v_base=24.0 -> cmd(a=-3.2, v=20.0) out(a=-21.3, v=20.0) |
teleop=off shadow=ok lost=0 off=0.00
```

읽는 순서: 주인이 누구고(owner) → 어떤 제한이 걸렸고(cap/floor) → 기본속도가 얼마였고(v_base)
→ 논리 명령이 얼마가 됐고(cmd) → 실제 발행값이 얼마인가(out). `out(a=-21.3)` 처럼
조향 출력이 -20 근처면 거의 직진이라는 뜻이다(트림이 -20 이므로 — 4장).
`owner=MISSION_STOP(stale)` 로 나오면 planner 가 죽었거나 통신이 끊긴 것이다.

## 4. `lib/car_interface.py` + `config/car.yaml` — 논리를 실차 숫자로

### 4.1 왜 별도 층이 필요한가

시뮬레이터에서는 "조향 -30" 이라고 쓰면 정확히 그만큼 꺾였다. 실차는 다르다.

* 서보가 기계적으로 오른쪽으로 치우쳐 장착돼 있어 **명령 -20 이 직진**이다 (car.yaml:12).
* 좌우 꺾이는 양이 다르다. 트림 기준으로 좌는 -34, 우는 +64 에서 기계가 걸린다
  (car.yaml:14-15, 코드는 마진을 둬 -32/+62 사용).
* 속도 명령 4 미만은 모터가 아예 안 구른다 (데드존, car.yaml:18).
* 센서리스 ESC 라서 정지 상태에서 갑자기 큰 속도를 주면 물리지 않는다. 점진 램프 필수
  (car.yaml:17).
  ESC 는 Electronic Speed Controller, 모터를 실제로 돌리는 전자 변속기다. 이 차의 구동 모터는
  세 가닥 전선에 순서대로 전기를 넣어 돌리는 방식이라, 지금 모터 축이 어디쯤 있는지를 알아야
  다음에 어느 가닥을 켤지 정할 수 있다. **센서리스**는 그 위치를 재는 센서가 따로 없어
  모터에서 나오는 전기 신호로 짐작한다는 뜻이다. 멈춰 있으면 그 신호가 안 나오므로 위치를
  모른다 → 정지 상태에서 큰 명령을 때리면 물리지 못하고 덜컥거리거나 헛돈다. 그래서 속도를
  조금씩 올리는 램프가 필수다.

이 지저분한 실차 사정을 **한 파일에 다 모아 놓은 것**이 CarInterface 다. 덕분에
motion_node 는 "논리 조향 -30, 논리 속도 24" 같은 깨끗한 값만 다루면 된다.
`rclpy` 를 import 하지 않는 순수 파이썬 클래스라서 ROS 없이 단위 테스트가 가능하다
(실제로 `test/test_car_interface.py` 가 있다).

### 4.2 변환 파이프라인 (`to_motor()`, car_interface.py:97-133)

```
 조향  angle_cmd (±100 논리)
   │
   ├─ ×0.42 (steer_scale)          -30 → -12.6
   ├─ clamp(-32, +62) 기계 스톱     -12.6 (통과)
   ├─ + (-20) 트림                  → -32.6   ← 실제 발행값
   └─ 이전 발행값 ±8 이내로 제한 (slew)
                                    ※ 참고 서보 환산 (teleop_node.py:30-32):
                                       servo = out×0.0082518 + 0.5004
                                       -32.6 → 0.231

 속도  speed_cmd (명령단위)
   │
   ├─ clamp(0, 100)   ← allow_reverse=false 면 음수는 0
   ├─ 데드존 스냅:  0<|v|<4 이면 → |v|≥2 는 4 로 올림, 아니면 0 으로
   └─ 이전 발행값 ±1.5 이내로 제한 (램프)     24 → 0 은 16틱(0.8초)
```

`reset()`(74-81행)은 이 램프 상태를 초기화한다. 조향은 `None` 으로 두어 다음 첫 틱에
slew 를 적용하지 않고(서보 현재 위치를 모르니까), 속도는 0 으로 두어 처음부터 다시 램프한다.

**★ 확인된 사실 하나**: motion_node 는 `self._car.reset()` 을 **한 번도 호출하지 않는다**
(grep 확인). CarInterface 의 사용 규칙 주석(car_interface.py:16)은 "제어권 재장악/estop
직후에는 reset()" 이라고 적혀 있는데 motion 은 그러지 않는다. 다만 motion 은 20Hz 로
**끊김 없이** 계속 발행하므로 slew 기준값이 항상 유효하고, 오히려 reset 을 하면 다음 틱에
조향이 slew 없이 튈 수 있다. 의도된 것으로 보이지만 주석과 코드가 어긋나 있으니
팀 안에서 한 번 확인하면 좋다.

좌우 비대칭이 눈에 띈다. 좌 32 / 우 62 로 **거의 두 배 차이**가 난다. 이건 서보 혼(horn —
서보 축에 끼우는 팔. 여기에 앞바퀴로 가는 조향 막대가 연결된다)이
치우쳐 조립된 결과이고, 현재 코드는 이 비대칭을 그대로 인정하고 클램프만 건다.
즉 **좌회전 최소 회전반경이 우회전보다 훨씬 크다.** 지름길 좌회전(BLOCK)이 조향 -100 을
쓰는데(motion_node.py:127), 실제로는 rel -32 에서 잘린다는 점을 기억해야 한다.

### 4.4 아커만 조향이란 무엇이고, 이 코드는 그걸 쓰는가

**아커만(Ackermann) 조향**은 자동차가 코너를 돌 때 안쪽 바퀴와 바깥쪽 바퀴가 서로 다른
반지름의 원을 그리므로, 안쪽 바퀴를 더 많이 꺾어 줘야 네 바퀴가 미끄러지지 않고 돈다는
기하 원리다. 링키지(조향 막대와 관절로 이어진 기계 연결부)가 그 각도 차이를 만들어 준다.
Xycar 도 이 구조다(RC카 표준).

그림으로 보면 이렇다. 네 바퀴가 **하나의 공통 중심** 둘레를 돌아야 안 미끄러진다.
그 중심은 뒷축을 옆으로 늘인 선 위에 있다.

```
   위에서 내려다본 그림 — 좌회전 중이다

                        ╱ 왼(안쪽) 앞바퀴 : 크게 꺾인다
                       ╱   ╱ 오른(바깥쪽) 앞바퀴 : 덜 꺾인다
                    [앞축]╱
                    ┌──────────┐
                    │          │
     ● O            │  차 몸통  │      L = 휠베이스 (앞축 ~ 뒷축 거리)
   회전중심          │          │
                    └──────────┘
                    [뒷축]  뒷바퀴는 안 꺾인다
     └───────R───────┘
     뒷축을 옆으로 쭉 늘인 선 위에 회전중심 O 가 있고,
     O 에서 차까지의 거리가 회전반경 R 이다

   · 안쪽 바퀴는 O 에 가깝다   = 작은 원을 그린다 = 더 많이 꺾여야 한다
   · 바깥쪽 바퀴는 O 에서 멀다 = 큰 원을 그린다   = 덜 꺾여야 한다
   · 두 앞바퀴를 똑같은 각도로 꺾으면 한쪽은 반드시 옆으로 끌리며 미끄러진다
   · 그 각도 차이를 만들어 주는 것이 조향 링키지의 기하다 = 아커만
```

즉 아커만은 **기계가 이미 해 주고 있는 일**이고, 소프트웨어가 계산할 일은 아니다.
소프트웨어가 정하는 건 "서보를 몇 도 돌릴까" 하나뿐이다.

제어 코드에서는 보통 이걸 **자전거 모델(bicycle model)** — 좌우 두 바퀴를 가운데 한 바퀴로
합쳐서, 앞바퀴 하나 뒷바퀴 하나인 자전거처럼 놓고 계산하는 단순화 — 로 바꿔서 쓴다.

```
   δ = atan(L / R)          L = 휠베이스(앞뒤 축 거리), R = 회전반경
   또는  δ = atan(2·L·sin(α) / Ld)    (순수추종의 표준 조향식)
```

**★ 그런데 이 저장소의 코드는 이 식을 쓰지 않는다.** `wheelbase`, `wheel_base`,
`ackermann` 같은 단어를 저장소 전체에서 grep 해도 **한 건도 나오지 않는다**(확인함).
즉 휠베이스도, 최대 물리 조향각(도 단위)도 코드 어디에도 없다.

대신 이 코드는 **경험적 매핑**을 쓴다. "경로점을 향하는 각도(도)에 게인을 곱해 논리 조향값을
만들고, 그 논리값에 0.42 를 곱해 서보 명령으로 보낸다." 게인 1.62/2.22 같은 숫자는
시뮬레이터에서 튜닝된 값이고(`# [SIM]` 표시), 0.42/-20/-32/+62 는 실차 실측값이다.

이게 나쁜 설계는 아니다. 실제로 Xycar 급 소형 차량에서는 서보 명령↔실제 조향각 관계가
링키지 비선형(명령을 2배 준다고 실제 각도가 정확히 2배가 되지는 않는 관계) 때문에 이론식과
잘 안 맞고, 위치 피드백(실제로 몇 도 꺾였는지 되돌려 알려 주는 신호)도 없어 검증이 어렵다. 예선에서
검증된 튜닝을 보존하는 편이 안전하다는 판단으로 보인다. **다만 대가가 있다.**

* 물리 단위(회전반경 m)로 계산하는 로직을 쓸 수 없다. 예를 들어 "1.5 m 반경으로 돌아라"를
  직접 명령할 수 없다.
* 시뮬 유래 게인이 실차에서 맞는지는 **실주행으로만** 확인 가능하다.
  `# [SIM]` 표시가 붙은 파라미터가 motion_node 에만 40개가 넘는다(tuning.yaml:139-205).
  이것이 본선 튜닝의 최대 리스크다.

### 4.5 ★ 아직 실측이 안 된 값 — 반드시 채워야 할 것

1. **`tacho_scale: 0.0`** (car.yaml:49). 타코미터(모터가 몇 바퀴 돌았는지 계속 세어 놓는
   누적 카운터. 자동차 계기판의 주행거리계에 해당한다) 카운트 → 미터 환산계수가 0 이라는 건
   **미실측**이라는 뜻이다. 이 값이 0 이면 car_state 는 속도를 시간 적분(매 순간 속도×시간을
   계속 더해 거리로 만드는 것)해 거리를 만드는
   폴백(원래 방법을 못 쓸 때 대신 쓰는 대체 방법)으로 동작한다(car_state_node.py:142-148).
   적분 거리는 오차가 누적되므로,
   "정지선 앞 몇 m" 같은 거리 기반 판단을 쓴다면 위험하다.
   → **실측 방법: 차를 정확히 1 m 밀고 tacho 변화량을 나눈다.**

2. **라이다 → 앞범퍼 거리가 저장소 어디에도 없다.** 좌표계 원점은 라이다 회전중심을 지면에
   내린 점인데, 실제로 부딪히는 건 앞범퍼다. "전방 0.5 m 에 장애물"이 실제로는 범퍼에서
   몇 cm 인지 코드가 모른다. 알려진 기하는 `dev/README.md` 의 "라이다가 카메라보다 10 cm 앞"
   하나뿐이다. → **줄자로 라이다 축 ↔ 범퍼 최전단 거리를 재서 파라미터로 넣을 것.**

3. **휠베이스·트레드·최대 물리 조향각** (4.4 참조). 당장 계산에 안 쓰이지만, 회피 경로가
   물리적으로 가능한지 검증하려면 필요하다.

4. **좌우 조향 비대칭 보정 여부.** 현재는 비대칭을 인정하고 클램프만 한다. 서보 혼을
   한 칸 돌려 대칭으로 만들면 좌회전 반경이 크게 개선되지만, **그러면 트림·스케일·스톱
   4개 값을 전부 재측정**해야 한다. 본선 전에 할지 말지 결정할 사안이다.

5. **VESC 자체 타임아웃.** motion 이 죽었을 때 VESC 가 마지막 명령을 유지하는지 스스로
   멈추는지 미확인. 이 결과에 따라 vesc_relay 데드맨을 켤지 정해야 한다(0.2절).

## 5. `car_state_node.py` — 차가 지금 어떤 상태인가 (181줄)

한 문단 요약: IMU 와 VESC 텔레메트리를 받아 "출발할 때 기준으로 몇 도 돌았는지, 지금 몇 m/s 로
가는지, 얼마나 갔는지, 배터리는 몇 V 인지"를 20Hz 로 `/car_state` 하나에 담아 뿌린다.
예선에는 없던 노드다. 예선에서는 planner 가 `/imu` 를 직접 구독해 절대 방위각만 썼다
(car_state_node.py:10-12).

```
  /imu (35Hz) ──> 쿼터니언 → yaw(deg)  ──┐
                  출발 기준각 빼기         ├──> /car_state (20Hz, 8칸)
  /vesc/state ──> eRPM ÷ 4614 = m/s     ──┤     yaw_rel, yaw_rate, speed_ms,
                  tacho 또는 적분 = 거리   │     dist_m, voltage, fault,
                  전압/폴트              ──┘     vesc_fresh, yaw_ref_set
  /capture_yaw ─> 기준각 재캡처 트리거
```

### 5.1 상대 yaw — 왜 절대각이 아니라 상대각인가

IMU 가 주는 절대 방위각은 "자북 기준 몇 도"에 가까운 값이라 트랙 위에서는 의미가 없다.
필요한 건 "출발했을 때에 비해 몇 도 돌았나"다. 그래서 첫 IMU 수신 때 그 순간의 방위각을
**기준각으로 저장**하고(car_state_node.py:86-90), 이후로는 항상 그 차이를 보낸다(152행).

각도 뺄셈에는 함정이 있다. 359° 와 1° 의 차이는 358° 가 아니라 2° 다. 이걸 처리하는 게
`_wrap_deg()`(26-28행)이고, 결과는 항상 -180~180 범위로 접힌다. 코드 곳곳의
"wrap-safe" 라는 표현이 이 뜻이다.

기준각은 `/capture_yaw` 토픽(빈 메시지)으로 언제든 다시 잡을 수 있다(114-121행).
IMU 가 아직 안 왔으면 "다음에 오면 잡겠다"고 예약해 둔다.

이 상대 yaw 를 실제로 쓰는 곳이 지름길 좌회전이다. planner 가 `yaw_rel_deg` 의 변화량을
보고 "목표한 만큼 돌았으니 BLOCK 종료"를 판정한다(path_planner_node.py:806-812 부근).

### 5.2 속도·거리

* 속도: `speed_ms = erpm / 4614` (car_state_node.py:134). 4614 의 근거로 저장소에 적혀 있는
  것은 "eRPM = 4614 × m/s (실측검증)" 하나다(car.yaml:48, car.yaml:20). 이 값이 컨테이너 안
  벤더 `vesc.yaml` 설정과 일치하는지는 **저장소 안에서 확인할 수 없다** — 벤더 파일이 우리
  저장소에 없기 때문이다(7.4절).
* 거리: `tacho_scale > 0` 이면 타코미터 차분 × 계수, 아니면 **속도 적분 폴백**
  (142-148행). 지금은 후자다(4.5절 1번).
* 적분은 `vesc_fresh` 일 때만 한다(146행). 데이터가 안 오는 동안 헛 적분하지 않는다.

### 5.3 신선도와 저전압 경고

`vesc_fresh` 는 마지막 `/vesc/state` 수신이 0.5초 이내인지다(129-130행, drive_cmd.py:21).
속도값 자체는 스테일이어도 마지막 값을 유지해서 보내고, "믿어도 되는지"는 이 플래그로
알린다 — 소비하는 쪽이 판단하라는 설계다.

배터리 전압이 8.6 V 미만이면 5초에 한 번 경고를 찍는다(109-112행). 0.5 V 미만은 릴레이
초기화 중 쓰레기값으로 보고 무시한다. NiMH 는 전압이 떨어진 채로 고부하가 걸리면
VESC 저전압 컷오프로 **주행 중에 그냥 멈춘다.** 대회 직전 반드시 완충(10~11 V) 확인.

## 6. `teleop_node.py` — 수동 조종 (234줄)

한 문단 요약: 터미널에서 키보드로 차를 직접 몬다. 캘리브레이션, 트림 측정, 차를 트랙
시작점으로 옮기기, 자율주행 중 긴급 개입에 쓴다.

### 6.1 두 가지 모드

```
  기본 (mux 경유)                       --direct (직발행)
  ─────────────────────                 ─────────────────────
  teleop → /teleop_cmd → motion         teleop → /xycar_motor
                          ↓                       (CarInterface 로컬 적용)
                    CarInterface
                          ↓             ※ motion 이 안 떠 있어야 함
                    /xycar_motor           (동시에 뜨면 두 노드가 같은
                                            토픽에 싸운다)
```

기본 모드는 **자율주행이 도는 중에도 개입 가능**하다. `/teleop_cmd` 가 오는 동안 motion 이
자율 출력을 버리고 사람 명령을 쓰기 때문이다(motion_node.py:306-311). 키를 놓고 0.3초가
지나면 자동으로 자율로 복귀한다.

`--direct` 모드는 motion 없이 혼자 도는 모드다. 트림/스톱 측정처럼 motion 을 띄우면 안 되는
작업에 쓴다.

### 6.2 키 매핑 (teleop_node.py:146-182, 도움말은 95-111)

| 키 | 동작 |
|---|---|
| `w` / `s` | 목표속도 +2 / -2 (`speed_step`) |
| `a` / `d` | 조향 좌/우 미세 (논리 5) |
| `A` / `D` | 조향 좌/우 크게 (논리 24) |
| `space` | 즉시 정지 + estop 플래그 |
| `c` | 조향 중립(0) — 속도는 유지 |
| `x` | 전부 0 + estop 해제 |
| `k` 또는 엔터 | 유지(keepalive) — 워치독만 갱신 |
| `1`~`5` | 속도 프리셋 10/20/30/40/50 |
| `q` | 정지 후 종료 |

조향 상태는 `steer_lo`~`steer_hi` 로 제한되는데, 이 값은 기계 스톱을 **논리 단위로 역산**한
것이다(teleop_node.py:75-76): -32/0.42 = -76.2, +62/0.42 = +147.6. 즉 논리값으로
한계까지 탐색할 수 있게 열어 뒀다(트림 측정용).

### 6.3 안전 관련 동작

* **TTY 강제**: stdin 이 터미널이 아니면 즉시 종료한다(120-124행). SSH 스크립트로 잘못
  실행돼 키 입력 없이 돌아가는 사고를 막는다.
* **워치독 3초**: 키가 3초간 없으면 목표속도를 0 으로(184-186행). 화면에 `WD!` 로 표시된다.
  0.3초짜리 토픽 계약 워치독과는 **다른 것**이다. 이건 "사람이 손을 놓았나"를 본다.
* **종료 시 정지 반복 발행**(218-228행): `finally` 블록에서 25회(0.5초) 정지를 보낸다.
  Ctrl+C 로 죽여도 이 블록은 실행된다.
* **터미널 복구**: `termios.tcsetattr` 로 원래 터미널 설정을 되돌린다(227행).
  이게 없으면 종료 후 터미널이 먹통이 된다.

### 6.4 ★ 알아둬야 할 두 가지 함정

1. **mux 모드에서는 후진이 안 된다.** teleop 은 `allow_reverse: true`(car.yaml:34)라
   `s` 키로 음수 속도를 만들 수 있지만, 그 값을 실제로 변환하는 건 motion 쪽
   CarInterface 이고 그쪽은 `allow_reverse: false`(car.yaml:19)다. 음수는 0 으로 클립된다
   (car_interface.py:125). 후진하려면 `--direct` 모드를 써야 한다.
2. **스페이스는 mux 모드에서 즉시 정지가 아니다.** 0.2절 3번 참조. `node.car.reset()`
   (teleop_node.py:167)은 teleop 자기 CarInterface 만 리셋하므로 direct 모드에서만 효과가 있다.

## 7. `ros1_docker/vesc_relay.py` — ROS1 도커라는 헷갈리는 구조

### 7.1 왜 모터가 ROS1 에 있나

Xycar 는 벤더가 만든 차다. 벤더의 모터 제어 스택(VESC 드라이버, `xycar_motor.py`,
`vesc.yaml`)은 **ROS1 noetic** 으로 작성돼 있고, 그게 **도커 컨테이너 안에서** 돈다.
우리 코드는 ROS2 humble 이다. 둘은 서로 말이 안 통한다. 그 사이를 잇는 게
**ros1_bridge** 라는 프로그램이고, 이건 호스트(도커 밖)에서 돈다.

```
 ┌──────────────── 차 PC (호스트) ────────────────────────────────┐
 │                                                                │
 │  [ROS2 humble]                    [ros1_bridge]                │
 │   우리 코드 전부                    dynamic_bridge              │
 │   /xycar_motor  ────────────────>  (토픽 양방향 변환)           │
 │   /vesc/state   <────────────────                              │
 │                                          │                     │
 │  ┌───────────────────────────────────────┼──────────────────┐  │
 │  │ 도커 컨테이너 (osrf/ros:noetic-xycar) │  [ROS1 noetic]   │  │
 │  │                                       v                  │  │
 │  │   vesc_relay.py   /sensors/core <── VESC 드라이버        │  │
 │  │        │                                  │              │  │
 │  │        └──> /vesc/state              xycar_motor.py      │  │
 │  │                                           │              │  │
 │  └───────────────────────────────────────────┼──────────────┘  │
 └──────────────────────────────────────────────┼─────────────────┘
                                                v  서보 + BLDC 모터
```

### 7.2 이 파일이 존재하는 이유 — "std 타입만 건널 수 있다"

VESC 는 `/sensors/core` 에 `vesc_msgs/VescStateStamped` 라는 **벤더 전용 메시지 타입**으로
텔레메트리를 뿌린다. ros1_bridge 는 양쪽에 똑같은 메시지 정의가 있어야 변환할 수 있는데,
우리 ROS2 쪽에는 `vesc_msgs` 가 없다. 그래서 그냥은 못 건넌다.

해결책이 이 릴레이다. **ROS1 안에서** 벤더 메시지를 표준 타입 `Float32MultiArray` 로
풀어 담아 `/vesc/state` 로 다시 발행한다(vesc_relay.py:58-69). 표준 타입은 브리지가
아무 설정 없이 통과시킨다. 파일 머리말에 "ros1_bridge는 std 타입만 통과시키므로 이 변환이
이 파일의 존재 이유"라고 정확히 적혀 있다(vesc_relay.py:5-6).

칸 순서는 `lib/drive_cmd.py` 의 `/vesc/state` 계약과 **반드시 같아야 한다**
(vesc_relay.py:8-10 ↔ drive_cmd.py:185-191). 한쪽만 고치면 전압이 속도로 읽히는 식의
사고가 난다. 이 파일이 저장소 안에 들어 있는 이유도 그것 — 계약을 한 커밋에서 같이 보려고.

### 7.3 데드맨 가드 (88-99행)

"데드맨 스위치"는 기관사가 손을 놓으면 열차가 서는 장치다. 여기서도 같다.
**ROS2 쪽이 통째로 죽어 `/xycar_motor` 가 0.4초 이상 조용해졌는데 마지막 명령 속도가 0이
아니었다면**, ROS1 쪽에서 `[트림(-20), 0]` 을 반복 발행해 차를 세운다.

한 가지 영리한 처리가 있다(80-86행). 데드맨이 발동해 자기가 보낸 정지 명령을 자기가
다시 구독해 받는다. 그걸 "명령이 왔다"고 치면 침묵 판정이 풀려 반복 발행이 한 번 하고
끊긴다. 그래서 **자기 에코(트림 조향 + 속도 0)는 신선도 갱신에서 제외**한다.

* 기본값은 **꺼짐**(`deadman_enable=False`, 34행). 켜려면 `_deadman_enable:=true`.
* `last_cmd_t` 가 None(=외부 명령을 한 번도 못 봄)이면 아무것도 안 한다(90행).
  텔레옵도 자율도 안 띄운 상태에서 멋대로 개입하지 않는다.

### 7.4 ★ 왜 이게 헷갈리고, 왜 건드리면 안 되나

* **토픽 이름이 양쪽에 똑같이 존재한다.** ROS2 의 `/xycar_motor` 와 ROS1 의
  `/xycar_motor` 는 브리지가 이어 준 **서로 다른 시스템의 같은 이름**이다.
  `ros2 topic list` 로 보이는 것과 컨테이너 안에서 `rostopic list` 로 보이는 게 다르다.
* **네임스페이스를 붙이면 안 된다.** 반드시 절대 토픽 `/xycar_motor` 여야 한다
  (motion_node.py:9 "절대토픽"). `/xycar/xycar_motor` 로는 VESC 에 도달하지 않는다.
* **브리지는 잘 죽는다.** 죽으면 조용히 모터 명령만 안 간다 — 에러도 안 난다.
  "차가 안 움직이는데 토픽은 잘 나온다" 는 증상이면 브리지를 먼저 의심할 것.
* **컨테이너 안 벤더 파일(`vesc.yaml`, `xycar_motor.py`)은 우리 저장소에 없다.**
  거기 값을 바꾸면 우리 `car.yaml` 의 실측값이 통째로 무효가 된다(트림·스케일·데드존이
  전부 그쪽 설정 위에서 측정된 값이다). 벤더 파라미터는 노드 시작 시 1회만 읽으므로
  바꾸면 모터 스택 재시작이 필요하고, 재시작 절차를 잘못하면 컨테이너가 내려간다.
  **결론: 대회 전에는 손대지 않는다.**

## 8. 정리 — 이 문서에서 기억할 것

1. `/xycar_motor` 는 20Hz 로 **무조건** 나간다. motion_node 가 떠 있으면 차는 언제든 움직일
   수 있다 (motion_node.py:185, 313-317).
2. 명령은 라치가 아니라 **스냅샷**이다. 놓쳐도 50ms 뒤 완전한 상태가 다시 온다
   (drive_cmd.py 전체).
3. 조향은 **가우시안 가중 다점 순수추종**이다. 앞 4~5 m 를 중심으로 여러 경로점을 가중평균해
   "그쪽으로 꺾는 각 + 그 자리 길 방향" 을 섞는다 (motion_node.py:494-540).
4. 속도는 **기본속도 → 하한 → 고정 → 상한** 순으로 중재되고, **상한이 항상 이긴다**
   (arbitration.py:31-66).
5. 실차의 지저분한 사정(트림 -20, 좌우 비대칭, 데드존 4, 램프 1.5)은 전부
   **CarInterface 한 곳**에 있다 (car_interface.py).
6. 이 코드는 휠베이스 기반 기구학 모델을 **쓰지 않는다**. 경험적 매핑이고,
   게인 대부분이 시뮬 유래(`# [SIM]`)라 실차 튜닝이 남아 있다.
7. 모터 제어부는 **ROS1 도커** 안이고, 우리가 만든 다리는 `vesc_relay.py` 하나다.
   브리지가 죽으면 조용히 명령이 끊긴다.
8. 실측이 남은 것: `tacho_scale`, 라이다→앞범퍼 거리, VESC 자체 타임아웃(→데드맨 활성 여부),
   좌우 비대칭 조정 여부.
