# 01. 전체그림 — 이 차는 어떻게 스스로 달리는가

이 문서는 본선 실차 코드(`본선/track_drive/`)의 지도다. 어떤 프로그램(노드)이 몇 개
뜨는지, 그것들이 무슨 데이터를 주고받는지, 카메라가 사진 한 장을 찍은 순간부터
바퀴가 돌아갈 때까지 어떤 함수들이 순서대로 불리는지를 파일명과 줄번호까지 붙여
설명한다. 읽고 나면 "차선을 보고 따라간다"가 "yolo_node.py:317 이 마스크를 만들고,
bev.py:494 가 그걸 미터 좌표로 바꾸고, lane_planner.py:1205 가 2차식으로 피팅하고,
motion_node.py:494 가 조향각을 계산한다"로 바뀌어야 한다. 세부 알고리즘은 02~08 번
문서로 넘기고, 여기서는 **연결 관계**에 집중한다.

## 0. 이 문서에 나오는 용어

읽다 보면 제어·영상 쪽 전문용어가 튀어나온다. 여기서 한 번에 풀어 둔다. 본문에서도
그 말이 처음 나오는 자리마다 짧게 다시 설명하니, 이 표는 "읽다가 막혔을 때 돌아오는
곳" 정도로 쓰면 된다. **이 문서에 실제로 나오는 말만** 담았다.

### 0.1 구조·통신 쪽

| 용어 | 쉬운 뜻 | 어디서 나오나 |
|---|---|---|
| 노드(node) | 따로 켜지고 따로 죽는 프로그램 하나. 이 시스템은 노드 여러 개가 동시에 돈다 | 1, 2절 |
| 토픽(topic) | 노드끼리 데이터를 주고받는 방송 채널. 보내는 쪽이 발행(publish), 받는 쪽이 구독(subscribe) | 1, 3절 |
| 콜백(callback) | 토픽이 도착하면 자동으로 불리는 함수. "오면 알아서 실행되는 처리기" | 5-5 |
| 틱(tick) | 일정 주기로 반복되는 실행 한 번. 20Hz 틱 = 0.05초마다 한 번 | 1, 5-5 |
| QoS | 토픽을 "어떻게" 주고받을지 정하는 통신 옵션 묶음(큐 크기, 재전송 여부 등) | 5-1 |
| BEST_EFFORT | QoS 중 "한 번 쏘고 잊는다" 방식. 유실돼도 재전송 안 한다 (반대는 RELIABLE) | 5-1 |
| depth=1 (큐 깊이) | 아직 처리 못 한 메시지를 몇 개까지 쌓아 둘지. 1이면 최신 하나만 남기고 버린다 | 5-1 |
| 백로그(backlog) | 처리 못 하고 밀려 쌓인 데이터 더미. 쌓이면 옛날 사진을 보고 운전하게 된다 | 5-1 |
| 스테일(stale) | "데이터가 너무 오래됐다". 마지막 수신 후 정해진 시간이 지나면 없는 셈 친다 | 부록 A |
| 워치독(watchdog) | 정해진 시간 안에 소식이 없으면 자동으로 안전 동작으로 넘기는 감시 타이머 | 6절 |
| 데드맨(deadman) | 사람이 손을 놓으면 서는 장치. 여기서는 모터 명령이 끊기면 정지를 쏘는 가드 | 부록 A |
| fail-safe | 뭔가 잘못됐을 때 자동으로 "안전한 쪽"으로 떨어지게 미리 정해 둔 기본값 | 6절 |
| 래치(latch) | 한 번 켜지면 조건이 사라져도 계속 켜져 있는 걸쇠 | 3.5, 6절 |
| 원샷(one-shot) | 딱 한 번만 실행되고 다시는 안 되는 동작 | 6절 |
| 디바운스(debounce) | 깜빡거리는 판정을 "N번 연속 같아야 인정"으로 걸러 안정시키는 것 | 5절 흐름도 |
| 스냅샷 | 그 순간의 상태를 통째로 한 장 찍어 보내는 것. "켜라/꺼라"를 따로 안 보낸다 | 3.5 |
| demux (역다중화) | 한 채널에 섞여 온 데이터를 종류별로 다시 갈라내는 것 | 3.3 |
| 상태머신 | "지금 어떤 상태인가"를 하나 정해 두고, 조건이 맞을 때만 다른 상태로 넘어가는 구조 | 2절 (내용은 6절) |
| respawn | 프로세스가 죽으면 launch 가 자동으로 다시 띄우는 옵션 | 2절 |

## 1. 큰 그림 — 본다 · 판단한다 · 움직인다

자율주행 소프트웨어는 결국 세 덩어리다. **본다(인지, Perception)** → **판단한다
(계획, Planning)** → **움직인다(제어, Control)**. 사람이 운전할 때 눈으로 차선을 보고,
머릿속으로 "저 커브에서 속도를 줄이고 왼쪽으로 붙자"고 정하고, 손발로 핸들과 페달을
움직이는 것과 똑같다. 우리 코드도 이 세 덩어리가 각각 별개의 프로그램(ROS 노드)으로
분리돼 있고, 사이사이는 **토픽(topic)** 이라는 방송 채널로만 연결된다.

토픽은 라디오 방송에 가깝다. 발행(publish)하는 쪽은 누가 듣는지 신경 쓰지 않고
정해진 채널에 계속 쏘고, 구독(subscribe)하는 쪽은 필요한 채널만 골라 듣는다. 그래서
노드 하나가 죽어도 나머지는 계속 돌고, 노드 하나를 교체해도 채널 규격만 지키면
나머지는 그대로다. 이 구조 덕분에 인지 담당과 제어 담당이 따로 개발할 수 있다.

```
   [ 본다 = 인지 ]        [ 판단한다 = 계획 ]      [ 움직인다 = 제어 ]
 ┌──────────────────┐   ┌───────────────────┐   ┌──────────────────┐
 │ usb_cam          │   │                   │   │                  │
 │  카메라 사진      │   │  path_planner     │   │  motion          │
 │        ↓         │   │                   │   │                  │
 │ yolo             │──▶│  지금 무슨 상황?   │──▶│  그 경로를 따라   │
 │  차선/표지/신호등 │   │  어디로 가야 하나? │   │  핸들 몇 도?      │
 │                  │   │  달려? 서?         │   │  속도 얼마?       │
 │ xycar_lidar      │──▶│                   │   │                  │
 │  주변 장애물      │   │  → /center_path   │   │  → /xycar_motor  │
 │                  │   │  → /drive_cmd     │   │                  │
 │ xycar_imu ─┐     │   │                   │   │                  │
 │ VESC ──────┴▶car_state▶ 내 차 상태(각도/속도) │   │                  │
 └──────────────────┘   └───────────────────┘   └──────────────────┘
        30Hz 카메라           20Hz 주기 틱            20Hz 주기 틱
        ~11.5Hz YOLO      (path_planner_node        (motion_node
                            .py:351 타이머)          .py:185 타이머)
```

그림 아래쪽의 "20Hz 주기 틱"에서 **틱(tick)** 은 일정 주기로 반복되는 실행 한 번을
뜻한다. 20Hz 면 1초에 20번, 즉 0.05초마다 한 번씩 같은 처리를 되풀이한다는 말이다.
카메라만 자기 속도(30Hz)로 사진을 밀어 넣고, 판단과 제어는 사진이 오든 말든 자기
박자로 돈다.

여기서 중요한 설계 결정이 하나 있다. **판단과 제어를 굳이 두 노드로 쪼갠 이유**다.
path_planner 는 "무엇을 할지"만 정하고(어느 선을 따라갈지, 지금 서야 하는지),
motion 은 "그걸 어떻게 실행할지"만 한다(핸들 각도 계산, 트림 보정, 급변 방지).
이렇게 나누면 판단 쪽이 느려지거나 잠깐 멈춰도 motion 은 20Hz 로 계속 모터에 명령을
쏜다. 실차 모터 컨트롤러(VESC)는 명령이 끊기면 위험하게 동작하므로, 이 "20Hz 연속
발행"은 계약 사항이다(motion_node.py:9, `/xycar_motor(... 20Hz 연속)`).

## 2. 노드 지도 — 실제로 뜨는 프로세스들

노드(node)는 ROS 에서 프로그램 하나를 뜻한다. 실행 파일 이름은 `setup.py:29-42` 의
`console_scripts` 에 정의돼 있고, 그중 어떤 게 실제로 뜨는지는 launch 파일이 정한다.
launch 파일은 "이 노드들을 이 설정으로 한꺼번에 켜라"는 실행 스크립트다.

**주행 launch (`launch/drive.launch.py:31-36`) — 규정 실행 명령으로 뜨는 4개**

| 실행이름 | 소스 파일 | 한 줄 역할 |
|---|---|---|
| `yolo` | `track_drive/yolo_node.py` | 사진 1장에 YOLO 3모델 순차 추론 |
| `path_planner` | `track_drive/path_planner_node.py` | 상태머신 + 경로 생성 |
| `motion` | `track_drive/motion_node.py` | 경로 추종 + 모터 명령 변환 |
| `car_state` | `track_drive/car_state_node.py` | IMU·VESC 를 하나로 집계 |

표의 "상태머신"은 **지금이 어떤 구간인가를 딱 하나 정해 두고, 조건이 맞을 때만 다른
구간으로 넘어가게 만든 구조**를 말한다. 사람이 "주차 중 / 주행 중 / 정지 중" 중
하나인 것과 같다. 어떤 구간들이 있는지는 6절에서 다룬다.

**센서 launch (`launch/sensors.launch.py:57-61`) — 차에서 따로 켜는 3개**

| 노드 | 출처 | 한 줄 역할 |
|---|---|---|
| `usb_cam` | 외부 패키지 | USB 카메라 → `/image_raw` |
| `xycar_lidar` | 차에만 설치 | 2D 라이다 → `/scan` |
| `xycar_imu` | 차에만 설치 | 자이로/가속도 → `/imu` |

**따로 켜는 것들**

| 노드 | 실행 | 한 줄 역할 |
|---|---|---|
| `yolo_lane_viewer` | `viewer.launch.py:16` | BEV 디버그 창 (OpenCV). BEV = 위에서 내려다본 그림, 4절 |
| `teleop` | `ros2 run track_drive teleop` | 키보드 수동 조작 |
| `vesc_relay` | 도커 안 ROS1 | VESC 텔레메트리 중계 |

노드 구성에서 눈여겨볼 점 세 가지.

첫째, **뷰어는 주행 launch 에 없다.** 대회 규정상 `drive.launch.py` 에 뷰어를 넣으면
안 되기 때문에 `viewer.launch.py` 로 분리했다(viewer.launch.py:2 주석). 예선에서는
섞여 있었다.

둘째, **센서 launch 는 차에 없는 패키지를 만나도 안 죽는다.** `xycar_lidar` /
`xycar_imu` 는 실차에만 설치돼 있어서, 개발 PC 에서 이 launch 를 돌리면 원래
에러로 죽는다. 그래서 `_include_if_present()` (sensors.launch.py:23-32) 가 패키지
존재 여부를 먼저 확인하고 없으면 경고 로그만 남기고 넘어간다.

셋째, **카메라는 죽으면 자동 재기동한다.** `respawn=True`(sensors.launch.py:41).
`respawn` 은 "이 프로세스가 죽으면 launch 가 알아서 다시 띄운다"는 옵션이다.
이 USB 카메라가 첫 실행에서 자주 실패하는 게 실측으로 확인됐기 때문이다. 그리고
픽셀 포맷이 `mjpeg2rgb` 인 이유도 실측이다 — YUYV 로 1920x1080 을 뽑으면 6fps 밖에
안 나오고, MJPG 여야 30fps 가 나온다(sensors.launch.py:48-49).

### 3.2 토픽 요약표

| 토픽 | 타입 | 무슨 데이터인가 |
|---|---|---|
| `/image_raw` | Image | 카메라 원본 사진 |
| `/detect/lane` | PoseArray | 차선점의 **지면 좌표(미터)** + 클래스 |
| `/detect/lane_quality` | Float32 | 차선 검출이 얼마나 믿을 만한가 (0~1) |
| `/detect/objects` | PoseArray | 표지판/신호/차량 박스의 **픽셀 좌표** + 클래스 |
| `/detect/traffic_light` | String | `GREEN` / `RED` / `NONE` |
| `/scan` | LaserScan | 라이다 500방향 거리 |
| `/imu` | Imu | 자세 쿼터니언 (차가 어느 쪽을 보나) |
| `/vesc/state` | Float32MultiArray | 전압/전류/eRPM/타코미터/폴트 |
| `/car_state` | Float32MultiArray | 위 둘을 합친 "내 차 상태" 스냅샷 |
| `/center_path` | PoseArray | 따라가야 할 목표 경로 (미터) |
| `/target` | PointStamped | 경로 위 목표점 하나 (x=3.0m 지점) |
| `/lane_left`, `/lane_right` | PoseArray | 시각화용 좌/우 차선 경계 |
| `/drive_cmd` | Float32MultiArray | "지금 누가 운전대를 쥐나 + 속도 제한" |
| `/teleop_cmd` | Float32MultiArray | 키보드 수동 명령 |
| `/xycar_motor` | Float32MultiArray | 최종 모터 명령 `[angle, speed]` |
| `/capture_yaw` | Empty | "지금 각도를 기준각으로 저장해" 신호 |
| `/corridor_path` | PoseArray | 외부팀 콘 통로 모듈이 주는 기준선 |
| `/manual_go` | Bool | 사람이 주는 출발/진행 신호 |

표에 처음 나온 낯선 말 네 개를 여기서 풀어 둔다.

- **쿼터니언(quaternion)** — 3차원 회전을 숫자 4개로 표현하는 방식이다. 각도 3개
  (roll/pitch/yaw)로 표현하는 방법도 있지만 특정 자세에서 계산이 깨지는 문제가 있어
  센서는 보통 쿼터니언으로 낸다. 우리는 그중 **yaw**(차가 좌우로 얼마나 돌았나)
  하나만 뽑아 쓴다(car_state_node.py:79).
- **eRPM** — 모터의 "전기적" 회전수다. 바퀴 회전수가 아니라서 그대로는 못 쓰고,
  실측으로 구한 4614 로 나눠 m/s 로 바꾼다(car_state_node.py:38, :134).
- **타코미터(tacho)** — VESC 가 세는 누적 회전량. 자전거 주행거리계와 같은 역할이고,
  이걸로 누적 주행거리를 낸다(car_state_node.py:143-144).
- **폴트(fault) 코드** — 모터 컨트롤러가 스스로 낸 고장 번호다. 0 이면 정상.

### 3.3 ★ `/detect/lane` — PoseArray 에 클래스ID를 욱여넣은 구조

여기가 이 코드에서 가장 헷갈리는 지점이므로 따로 설명한다.

`geometry_msgs/PoseArray` 는 원래 "3차원 위치 + 자세"의 배열이다. 각 `Pose` 안에
`position.x`, `position.y`, `position.z` 세 숫자가 있다. 그런데 우리는 지면 위의
차선점만 다루므로 높이(z)가 늘 0이다. **z 칸이 남는다.** 그래서 거기에 "이 점이 어떤
종류의 선인가"를 나타내는 클래스 번호를 집어넣었다.

```
  PoseArray /detect/lane
  ┌─────────────────────────────────────────────────────┐
  │ header.frame_id = "lidar_frame"   ← 라이다 기준 좌표계 │
  │ header.stamp    = 원본 사진의 촬영 시각               │
  ├─────────────────────────────────────────────────────┤
  │ poses[0].position.x = 2.35   ← 전방 2.35 m           │
  │ poses[0].position.y = 0.71   ← 왼쪽 0.71 m           │
  │ poses[0].position.z = 8.0    ← ★ 좌표 아님! 클래스ID │
  │                                  8 = MID(노란 중앙선) │
  │ poses[1].position.x = 2.53                           │
  │ poses[1].position.y = 0.69                           │
  │ poses[1].position.z = 8.0                            │
  │ ...  (전방 x 를 0.18 m 씩 끊어 bin 하나당 점 1개)      │
  └─────────────────────────────────────────────────────┘
```

**왜 이렇게 했나.** 클래스별로 토픽을 따로 만들면(`/detect/lane_mid`,
`/detect/lane_white`, …) 토픽 수가 늘고, 구독하는 쪽에서 "이 세 토픽이 같은 프레임에서
나온 게 맞나"를 시각으로 맞춰야 한다. 한 메시지에 다 담으면 그 문제가 사라진다.
그리고 이 관습은 예선 코드에서 그대로 물려받은 것이라, 예선에서 검증된
`lane_planner.py` 를 손대지 않고 재사용할 수 있다(yolo_node.py:68 주석
"예선 `/detect/lane` 관습 그대로").

**쓰는 쪽 코드.** `path_planner_node.py:388-411` 의 `_on_lane()` 이 z 값을 보고 세
묶음으로 쪼갠다(demux — 역다중화. 한 채널에 섞어 보낸 것을 받는 쪽에서 종류별로
다시 갈라내는 것을 말한다. 섞어 보내는 반대 동작이 mux 다).

```python
cls = np.fromiter((int(p.position.z) for p in msg.poses), ...)   # :404
ym = np.isin(cls, list(YELLOW_CLS_IDS))       # {8}     노란 중앙선  :406
dm = np.isin(cls, list(YELLOW_DASH_CLS_IDS))  # {16}    노란 점선    :407
wm = np.isin(cls, list(WHITE_CLS_IDS))        # {6, 2}  흰 외곽선    :408
```

클래스 번호의 정의는 `lane_planner.py:41-43` 에 있다. 8=MID(노란 중앙선),
16=어린이보호구역 노란 점선, 6=흰 외곽선, 2=학교영역 마킹.

주의할 점 하나. **지금 yolo_node 는 z=8 만 발행한다.** `yolo_node.py:329` 의
`targets = [(SEG_MID, Z_MID)]` 가 기본이고, z=16 은 `enable_child_dash` 파라미터를
켜야만 추가된다(:330-331, 기본 `False`). z=6/2 를 만드는 코드는 없다. 즉 planner 의
흰선 분기(`_white_xs`)는 현재 항상 빈 배열이고, 실제 주행은 노란 중앙선만으로
이뤄진다. 이건 `lane_planner.plan()` 이 애초에 흰선을 안 쓰기 때문에 문제가 아니다
— `lane_planner.py:1209` 에 "흰선 점은 안 쓴다 (signature 는 호환 위해 유지)"라고
명시돼 있다.

### 3.4 ★ `/detect/objects` — 같은 PoseArray 인데 의미가 완전히 다르다

여기서 진짜로 헷갈린다. `/detect/objects` 도 PoseArray 지만, **x, y 가 미터가 아니라
픽셀이다.**

```
  /detect/lane                      /detect/objects
  ┌───────────────────────┐        ┌───────────────────────────┐
  │ frame_id "lidar_frame"│        │ frame_id "usb_cam_front"  │
  │ x = 전방 거리 [m]      │   vs   │ x = bbox 가로 중심 u [px] │
  │ y = 좌측 거리 [m]      │        │ y = bbox 아래변  v [px]   │
  │ z = 클래스 ID          │        │ z = 클래스 ID              │
  └───────────────────────┘        └───────────────────────────┘
      지면 좌표 (미터)                   이미지 좌표 (픽셀)
```

**★ z 의 번호 체계도 서로 다르다.** 두 칸 다 이름이 "클래스 ID"라 같은 번호표를 쓰는
것처럼 보이지만, 서로 다른 모델이 매긴 서로 다른 번호다.

- `/detect/lane` 의 z = 예선 `/detect/lane` 관습 번호 (8=노란 중앙선, 16=노란 점선,
  6=흰 외곽선, 2=학교영역 마킹 — `lane_planner.py:41-43`).
- `/detect/objects` 의 z = **best.pt 학습 번호 그대로** (0=BLACK_CAR … 6=GREEN,
  8=HUMAN, 14=STOP — `path_planner_node.py:52-53`).

즉 z=6 은 lane 에서는 "흰 외곽선"이지만 objects 에서는 "초록불"이고, z=8 은 lane 에서
"노란 중앙선", objects 에서 "사람"이다. 한 술 더 떠서 lane.pt 모델 **내부** 클래스
번호는 또 다르다 — 어린이보호 점선은 lane.pt 안에서는 2번인데 발행할 때 16으로
바꿔 내보낸다(`yolo_node.py:69-71`, `SEG_CHILD_DASH=2` → `Z_CHILD_DASH=16.0`).
숫자만 보고 옮겨 쓰면 반드시 사고가 난다. 어느 토픽의 번호인지를 먼저 확인할 것.

**★ 번호 체계 세 벌 — 한눈에 보기**

말로 읽으면 헷갈리므로 표로 못박는다. 같은 "클래스 ID"라는 이름을 쓰지만 서로
완전히 다른 세 개의 번호표다.

| 번호 체계 | 정의된 곳 | 번호 → 뜻 |
|---|---|---|
| ① `/detect/lane` 의 z (예선 발행 관습) | `lane_planner.py:41-43` | 8=노란 중앙선(MID), 16=노란 점선(어린이보호), 6=흰 외곽선, 2=학교영역 마킹 |
| ② lane.pt 모델 **내부** 번호 (밖으로 안 나감) | `yolo_node.py:68-71` | 8=중앙선 → z=8 로 그대로 발행 / 2=어린이보호 점선 → z=16 으로 **바꿔서** 발행 |
| ③ `/detect/objects` 의 z (best.pt 학습번호 그대로) | `yolo_node.py:73-77`, `path_planner_node.py:52-53` | 0=BLACK_CAR 1=CHILD_END 2=CHILD_LANE 3=CHILD_START 4=CROSSROAD_OUT 5=GOAL 6=GREEN 7=GREEN_CAR 8=HUMAN 9=LANE 10=LEFT 11=MID 12=POLICE 13=RED 14=STOP 15=YELLOW |

같은 숫자가 체계마다 뭘 뜻하는지 겹쳐 보면 위험이 분명해진다.

| 숫자 | ① `/detect/lane` 의 z 로 읽으면 | ③ `/detect/objects` 의 z 로 읽으면 |
|---|---|---|
| 2 | 학교영역 마킹 (흰선 묶음) | CHILD_LANE — 발행 전 걸러짐 |
| 6 | 흰 외곽선 | GREEN (초록불) |
| 8 | 노란 중앙선 | HUMAN (사람) |
| 14 | (정의 없음) | STOP (정지 표지) |
| 16 | 노란 점선 (어린이보호) | (없음 — best.pt 는 0~15) |

②의 존재가 특히 함정이다. lane.pt 안에서 어린이보호 점선은 **2번**인데, 발행할 때
`Z_CHILD_DASH=16.0` 으로 갈아끼워 내보낸다. 그래서 "lane.pt 에서 2번"과
"`/detect/lane` 의 z=2"는 완전히 다른 것을 가리킨다. 모델 쪽 번호를 그대로 토픽
번호로 믿으면 안 된다.

`/detect/objects` 는 실제로는 표의 16개를 다 안 보낸다. 차선 계열 세 개
(2=CHILD_LANE, 9=LANE, 11=MID)는 lane.pt 가 담당하므로 발행 전에 걸러진다
(`OBJ_IGNORE_CLASS_IDS`, yolo_node.py:78).

네 번째 번호표도 사실 있다 — `light.pt` 의 0=GREEN, 1=LEFT, 2=RED
(yolo_node.py:81-83). 다만 이 번호는 노드 밖으로 나가지 않는다. `/detect/traffic_light` 은
`"GREEN"` / `"RED"` / `"NONE"` **문자열**로 바뀌어 나가므로 번호가 섞일 일이 없다.
그래서 실무에서 조심해야 할 번호표는 위 세 벌이다.

발행하는 코드는 `yolo_node.py:404-408`:

```python
p.position.x = float((x1 + x2) * 0.5)  # u 중심          :405
p.position.y = float(y2)               # v 하단 (클수록 가까움)  :406
p.position.z = float(cls_id)                              :407
```

**왜 미터로 안 바꾸나.** 차선은 지면에 붙어 있으니 호모그래피로 미터로 펼 수 있지만,
표지판과 신호등은 공중에 떠 있어서 "지면 위의 점"이라는 가정이 안 맞는다. 억지로
변환하면 엉뚱한 거리가 나온다. 대신 **박스 아래변의 v 픽셀값을 거리 대용으로 쓴다.**
이미지에서 v(세로 좌표)는 아래로 갈수록 커지고, 지면에 서 있는 물체는 가까울수록
화면 아래쪽에 찍힌다. 그래서 "v 가 크다 = 가깝다"가 성립한다(:406 주석 그대로).

planner 는 이 v 값을 클래스별로 최댓값(=가장 가까운 것)만 뽑아 캐시한다(캐시 =
나중에 쓰려고 최근 값을 그때그때 저장해 두는 것. 콜백은 저장만 하고, 판단은 20Hz
타이머가 저장된 값을 꺼내 쓴다)
(`path_planner_node.py:445-476`). 예를 들어 정지선 표지(cls 14)의 v 가 임계값
312 를 넘으면 "정지선이 코앞"으로 판정한다(`:751`, `stop_v_threshold`).

**★ 해상도 함정과 그 대응.** 이 임계값 312 는 예선 시뮬 480p 화면에서 튜닝한
픽셀값이다. 실차 카메라는 1080p 라 같은 거리의 물체가 v 로 2.25배 크게 들어온다.
그냥 두면 정지선이 훨씬 멀리서 오발동한다. 그래서 기동할 때 한 번
`_resolve_obj_v_scale()`(`:413-443`)이 `camera.yaml` 의 `image_height` 를 읽어
`480/1080 = 0.4444` 배율을 구하고, 들어오는 v 마다 곱해서 "480p 기준값"으로
환산한다(`:453`). `camera.yaml` 을 못 읽으면 배율 1.0 + 경고 로그다(`:433-436`) —
조용히 틀리지 않게 하려는 설계다.

여기서 **래치(latch)** 는 한 번 켜지면 조건이 사라져도 계속 켜져 있는 걸쇠를 말한다.
현관문 잠금쇠가 딸깍 걸리면 손을 떼도 안 풀리는 것과 같다. 상태를 "켜라/꺼라" 두
메시지로 나눠 보내면 어쩔 수 없이 래치가 생긴다 — "꺼라" 한 장이 유실되는 순간
받는 쪽은 영원히 켜진 상태로 남는다. 어린이보호구역을 지났는데도 속도 제한이 안
풀리는 식이다.

본선에서는 이걸 전부 없애고, **매 틱마다 처음부터 다시 계산한 스냅샷 하나**
로 대체했다(스냅샷 = 그 순간의 상태를 통째로 한 장 찍어 보내는 것. "지금 owner 는
LANE, 속도 상한은 22" 전부가 매번 다시 들어 있으므로, 한 장이 유실돼도 0.05초 뒤
다음 장이 알아서 바로잡는다)(path_planner_node.py:13-14, :364 `_fresh_cmd()` "매 틱 재계산 — 라치 금지").
받는 쪽도 0.3초만 안 오면 `MISSION_STOP` 으로 간주한다
(`lib/drive_cmd.py:19`, `motion_node.py:234-236`). 통신이 끊기면 자동으로 선다.

## 4. 좌표계 — 픽셀과 미터, 두 개의 세계

초보가 가장 많이 헷갈리는 부분이다. 이 코드에는 좌표계가 **두 개** 있고, 둘은 축 방향도
부호도 원점도 다르다.

```
 ① 이미지 좌표 (픽셀)                  ② 지면 좌표 (미터, ROS REP-103)
 원점 = 사진 왼쪽 위                     원점 = 라이다 회전중심에서
                                              지면으로 내린 수선의 발
   (0,0)──── u 증가 ────▶ 1919                        ▲ +x (전방)
     │  ┌──────────────────┐                          │
     │  │                  │              +y ◀────────●────────▶ -y
     │  │   하늘·먼 곳       │             (좌측)     원점      (우측)
     │  │ ─────────────────│  ← 소실선                 │
   v  │  │   먼 차선 (작게)  │                          │
  증가 │  │                  │            · 단위: 미터
     │  │   가까운 차선(크게)│            · x 앞이 +, y 왼쪽이 +
     ▼  │                  │            · frame_id = "lidar_frame"
   1079 └──────────────────┘            · 차선점, 라이다점, 경로가 전부 여기
          v 클수록 = 가까움
```

그림에 나온 **REP-103** 은 ROS 진영이 정해 둔 좌표 표준 규약의 문서 번호다. "x 는
앞, y 는 왼쪽, z 는 위, 길이는 미터, 각도는 라디안"을 못박아 둔 것이고, 우리 지면
좌표도 이걸 따른다. 그래서 y 가 **양수면 왼쪽**이다 — 화면 좌표에 익숙하면 반대로
읽기 쉬우니 주의한다. 그림 가운데의 **소실선**은 지면이 무한히 멀어져 하늘과 만나는
가로줄이다. 그 위쪽 화소는 지면이 아니므로 아무리 계산해도 미터로 펼 수 없다.

**왜 두 개가 필요한가.** 카메라는 세상을 비스듬히 본다. 그래서 사진에서는 실제로
평행한 차선 두 줄이 멀리서 한 점으로 모인다(원근). 픽셀 거리 10 이 가까운 곳에서는
3cm 인데 먼 곳에서는 30cm 다. 이 상태로는 "저 차선이 몇 미터 왼쪽에 있나"를 계산할 수
없다. 반대로 라이다와 모터 제어는 처음부터 미터 세계에 산다. 그러니 어딘가에서
**픽셀 → 미터 변환**을 해야 한다.

그 변환이 **호모그래피(Homography)** 다. 비스듬히 찍은 바닥 사진을 "위에서 똑바로
내려다본 것처럼" 펴주는 3x3 행렬이다. 기울여서 찍은 종이 사진을 스캐너로 반듯하게
편다고 생각하면 된다. 단, **지면 위의 점에만 성립한다** — 공중에 뜬 물체는 못 편다.
그래서 3.4 절에서 본 것처럼 차선은 미터로 변환하고 표지판은 픽셀로 남긴다.

**변환이 일어나는 정확한 지점**은 `lib/bev.py:494` 의 `mask_to_bev_points()` 다.

```python
H_pix2bev = M_GRID @ np.asarray(H, dtype=np.float64)        # bev.py:504
bev_mask  = cv2.warpPerspective(mask, H_pix2bev, (BEV_W, BEV_H), ...)  # :505
return _mask_to_centerline_xy(bev_mask)                     # :509
```

여기 행렬이 둘 곱해져 있다. `H` 는 "이미지 픽셀 → 지면 미터"(camera.yaml 의 `H` 필드,
2026-07-31 캘리브 결과), `M_GRID`(bev.py:42-46)는 "지면 미터 → BEV 이미지 픽셀"이다.
왜 다시 픽셀로 돌아가냐면, OpenCV 의 `warpPerspective` 로 마스크 전체를 한 번에
변환하는 게 점 하나하나 변환하는 것보다 훨씬 빠르기 때문이다. BEV 이미지는
5cm/픽셀(`BEV_RES=0.05`), 전방 -2~12m, 좌우 ±5m 의 200x280 격자다(bev.py:35-39).
마지막에 `_lane_mask_to_lidar_xy()`(:413-422)가 격자 인덱스를 다시 미터로 되돌린다.

한 가지 더. 이 변환 직전에 **차체 가림선**을 적용한다(`yolo_node.py:355` →
`bev.apply_car_mask`). 사진 아래쪽 `car_mask_v=951` 픽셀 밑은 지면이 아니라 우리 차의
라이다 원통과 범퍼다. 안 자르면 그 화소들이 호모그래피를 통과해 "전방 0.1~0.2m 에
차선이 있다"는 가짜 점이 된다(bev.py:145-150 주석).

## 5. ★ 한 프레임의 여정 — 사진 한 장이 바퀴를 돌리기까지

이 절이 이 문서의 핵심이다. 카메라 셔터가 열린 순간부터 서보가 돌아갈 때까지를
시간 순서로 따라간다.

```
 t=0     카메라 셔터 → usb_cam → /image_raw 발행
 t≈0     yolo_node._on_image() 수신
             │ 처리 중이면 여기서 버림 (백로그 금지)
         BGR 변환 → 왜곡보정
         lane.pt  추론 → 마스크 → BEV → /detect/lane + /detect/lane_quality
         best.pt  추론 → bbox        → /detect/objects
         light.pt 추론 → 디바운스     → /detect/traffic_light
 t≈87ms  여기까지가 한 프레임. 3모델 순차 ≈11.5Hz 실측이므로 프레임당 총
         예산이 약 87ms 다(yolo_node.py:5). 모델별 내역은 코드에 적힌 값이
         없고, 실행 중 [perf] 로그(yolo_node.py:303-310)로만 확인된다.
    │
    ├─(별도 20Hz 타이머) path_planner._tick() → 경로 + /drive_cmd
    │
    └─(별도 20Hz 타이머) motion._tick() → 조향/속도 → /xycar_motor
                                                          ↓
                                                     VESC → 바퀴
```

흐름도 셋째 줄의 **디바운스(debounce)** 는 판정이 깜빡거리는 걸 막는 장치다. 신호등
판정을 한 프레임만 보고 바로 내보내면 GREEN 과 NONE 이 계속 뒤집혀서 planner 가
출발과 정지를 반복한다. 그래서 **같은 판정이 3프레임 연속 나와야** 그때 발행한다
(`light_debounce_n` 기본 3 — yolo_node.py:97, :441). 전등 스위치를 딸깍거려도 한 번만
켜지게 만드는 회로에서 온 말이다. 6절의 "GREEN 6틱 확인 후 출발"도 같은 발상이다.

### 5-1. 사진이 도착한다 — `yolo_node.py:242`

```python
def _on_image(self, msg: Image):
    if self._busy:
        return          # 처리 중 도착한 프레임 드랍          :243-244
    self._busy = True
```

카메라는 30Hz 로 쏘는데 CPU 로 YOLO 3모델을 돌리면 11.5Hz 밖에 안 나온다
(yolo_node.py:5, 실측). 그냥 두면 처리 못 한 프레임이 큐에 쌓여서, 나중에는 3초 전
사진을 보고 운전하게 된다. 그래서 **처리 중이면 그냥 버린다.** 구독 QoS 도
`depth=1` + `BEST_EFFORT` 로 큐를 아예 1칸만 준다(:145-150). 늦은 정보보다 없는 게
낫다는 원칙이다.

여기 나온 통신 용어를 풀어 둔다. **QoS(Quality of Service)** 는 "이 토픽을 어떻게
주고받을까"를 정하는 통신 옵션 묶음이다. 우리가 건드린 건 두 개다.

- **`depth=1`(큐 깊이 1)** — 아직 읽지 않은 메시지를 몇 개까지 쌓아 둘지다. 1이면
  새 사진이 도착하는 순간 안 읽은 옛 사진은 버려진다. 우체통을 한 칸짜리로 만들어
  새 편지가 오면 헌 편지를 밀어내게 하는 것과 같다.
- **`BEST_EFFORT`** — "한 번 쏘고 잊는다"는 뜻이다. 중간에 유실돼도 다시 안 보낸다.
  반대는 `RELIABLE` 로, 받았다는 확인이 올 때까지 재전송한다. 사진은 어차피 30분의
  1초 뒤에 새것이 오므로 옛것을 재전송해 봐야 쓸모가 없고, 재전송하느라 대역폭과
  시간을 쓰는 게 오히려 손해다.

이렇게 처리 못 하고 밀려 쌓인 데이터 더미를 **백로그(backlog)** 라고 한다. 코드
주석의 "백로그 금지"(yolo_node.py:158)가 바로 이 뜻이다.

### 5-2. 인코딩을 풀고 렌즈 왜곡을 편다 — `yolo_node.py:254`, `:277`

```python
bgr, info = preprocess.image_msg_to_bgr(msg)                   # :254
if bgr is None:
    self.get_logger().warn(f"image 변환 실패: {info}", ...)     # :257-258
...
frame = self._undist.apply(bgr)                                # :277
```

`lib/preprocess.py:42` 는 `rgb8`, `bgr8`, `mono8`, `yuv422` 계열 등 여러 인코딩을
받아 OpenCV 표준인 BGR 로 통일한다. **실패해도 조용히 넘어가지 않고 반드시 사유
문자열을 돌려준다**(preprocess.py:6-7). 예선에서 인코딩이 안 맞으면 무음으로 프레임을
버려서 "차가 왜 안 가지?"를 한참 헤맨 적이 있고, 그걸 "재도입 금지 버그 8"로 못박아
뒀다.

`self._undist.apply()` 는 렌즈 왜곡 보정이다. 광각 렌즈는 직선을 휘게 찍는다. 실제로
직선인 차선이 사진에서 휘어 있으면 호모그래피가 성립하지 않으므로, 먼저 펴야 한다.
왜곡 모델은 `plumb_bob`(브라운-콘라디, 일반 광각용)이다. 벤더 PDF 에는 "170도 어안"
이라고 적혀 있었지만 실측 HFOV 는 87.2도였고, 87도 렌즈에 어안(fisheye) 모델을 쓰면
파라미터가 과해서 오히려 가장자리가 나빠진다(bev.py:15-19).

용어 셋만 풀어 둔다. **왜곡 모델**은 "이 렌즈가 직선을 어느 정도로, 어떤 모양으로
휘게 만드는가"를 숫자 몇 개짜리 공식으로 적어 둔 것이다. `plumb_bob` 은 보통
광각 렌즈에 쓰는 표준 공식이고, **어안(fisheye)** 은 180도 가까이 보는 초광각 렌즈
전용의 다른 공식이다. 공식을 잘못 고르면 안 휜 곳까지 억지로 펴서 더 나빠진다.
**HFOV** 는 Horizontal Field of View, 카메라가 좌우로 몇 도까지 보느냐(수평 화각)다.
숫자가 클수록 넓게 본다.

프레임 크기가 캘리브 기준(1920x1080)과 다르면 리맵 테이블을 다시 만들고 경고를
찍는다(:266-276). **리맵(remap) 테이블**은 왜곡보정을 매 프레임 빠르게 하려고
"원본의 어느 픽셀을 결과 이미지의 어디로 옮길지"를 미리 계산해 둔 표다. 매번
공식을 다시 푸는 대신 표를 보고 옮기기만 하면 되므로 훨씬 빠르다. `new_K` 는
왜곡을 편 뒤의 카메라 내부 파라미터(초점거리·영상중심)를 말한다. 해상도가 바뀌면
`new_K` 가 바뀌고, `new_K` 가 바뀌면 **H 가 통째로
무효**이기 때문이다. 이 대조는 기동 시 `check_new_K_match()`(bev.py:379)로 한 번 더 한다.

### 5-3. 모델 3개를 순서대로 돌린다 — `yolo_node.py:280-291`

```python
if self._model_light is not None: self._run_light(frame)              # :290
```

예선에서는 이게 노드 3개였다. 노드 3개면 같은 사진을 3번 받아서 3번 디코딩하고
3번 왜곡보정한다. 실차 CPU 에서는 그 낭비를 감당할 수 없어서 **한 노드가 한 번
받아서 3번 추론**하는 구조로 합쳤다(yolo_node.py:2, :12).

여기 미묘한 함정이 하나 있다. `MODEL_WANTS_RGB`(:65)라는 테이블이다. ultralytics 는
numpy 입력을 BGR 로 가정하는데, `lane.pt` 와 `best.pt` 는 예선에서 RGB 배열을 스왑
없이 그대로 넣은 채로 학습돼서 **모델이 기대하는 채널 순서가 RGB** 다. `light.pt` 만
표준(BGR)이다. 그래서 앞의 둘만 `frame[:, :, ::-1]` 로 되스왑해서 넣는다(:318, :376).

### 5-4. 차선 마스크 → 지면 좌표 — `yolo_node.py:317-371`

`lane.pt` 는 세그멘테이션(segmentation) 모델이다. 박스가 아니라 "이 픽셀이 차선인가"를
픽셀 단위로 칠해준다. 그렇게 칠해 나온 결과물이 **마스크(mask)** 다 — 차선이면 흰색,
아니면 검정인 흑백 이미지고, 중간 회색 없이 0 아니면 255 두 값만 남기면
**이진 마스크**가 된다. 흐름은 이렇다.

```
 마스크 (모델 해상도)
   ↓ cv2.resize → 원본 크기, 0.5 넘으면 255      yolo_node.py:349-352
 이진 마스크 (1920x1080)
   ↓ apply_car_mask — v>951 아래 차체 영역 삭제  yolo_node.py:355
   ↓ mask_to_bev_points — H 로 BEV warp         yolo_node.py:358
 BEV 마스크 (200x280, 5cm/px)
   ↓ _mask_to_centerline_xy — x 0.18m bin 마다  bev.py:425-457
   ↓   중앙값 1점만 추출
 (xs, ys) 미터 좌표 점 목록
   ↓ Pose 로 포장, z=8                          yolo_node.py:360-364
 /detect/lane 발행                              yolo_node.py:368
```

**왜 bin 마다 1점만 뽑나.** 여기서 **bin** 은 연속된 값을 일정 폭으로 잘라 만든 칸을
말한다 — 전방 거리를 0.18m 씩 끊어 "0~0.18m 칸, 0.18~0.36m 칸 …" 으로 나눈 것이다.
차선은 폭이 있어서 마스크 픽셀을 그대로 넘기면 한 x 위치에
점이 수십 개 생기고, 그 두께와 노이즈가 2차식 피팅에 그대로 들어가 직선 구간에서
좌우로 와리가리(weaving)가 난다. 그래서 전방 0.18m 구간마다 중앙값 하나로 줄인다
(bev.py:428-430 주석).

말 두 개를 더 풀어 둔다. **피팅(fitting)** 은 흩어진 점들을 가장 잘 지나는 식 하나를
찾아 맞추는 것이다(여기서는 2차식 `y = ax² + bx + c`). 점 하나하나를 따라가는 대신
매끄러운 곡선 하나로 대표시키는 셈이다. **위빙(weaving, 와리가리)** 은 직선인데도
핸들이 좌우로 계속 흔들려 차가 뱀처럼 가는 현상을 말한다. 그리고 **중앙값(median)**
은 값들을 크기순으로 줄 세웠을 때 딱 가운데 값이다 — 평균과 달리 엉뚱하게 튄 값
하나가 섞여도 결과가 거의 안 흔들린다. 노이즈 낀 마스크에서 평균 대신 중앙값을 쓰는
이유가 이것이다.

같은 함수 끝에서 품질 점수도 낸다(:370-371). `lane_quality()`(bev.py:514)는
`(점 개수/20) × (x 스팬/3.0m)` 로 0~1 을 만든다. 점이 많고 멀리까지 뻗어 있으면 1에
가깝다. planner 는 이게 0.3 미만이면 속도 상한 7 을 건다
(path_planner_node.py:610-612).

### 5-5. planner 가 20Hz 로 판단한다 — `path_planner_node.py:574`

planner 는 YOLO 결과를 **기다리지 않는다.** 콜백은 값을 캐시에만 넣고, 판단은 별도
20Hz 타이머(`:351`)가 한다. **콜백(callback)** 은 토픽이 도착하면 ROS 가 자동으로
불러 주는 함수를 말한다. 내가 "언제 부를지"를 정하는 게 아니라 데이터가 오면 알아서
불린다. 그래서 콜백 안에서 무거운 계산을 하면 데이터가 몰릴 때 통째로 밀린다 —
받아 적기만 하고 계산은 타이머로 뺀 이유다. 인지가 11.5Hz 로 느려도 판단은 20Hz 로 일정하게 돈다.

```python
def _tick(self):
    self._cmd = self._fresh_cmd()      # 스냅샷 초기화, 라치 금지     :580
    self._update_stop_block(now)                                     :584
    if   self.phase == "IDLE":        ...                            :586
    elif self.phase == "WAIT":        self._tick_wait(...)           :591
    elif self.phase == "CONE":        self._tick_cone(...)           :593
    elif self.phase == "LANE":        self._tick_lane_phase(...)     :595
    elif self.phase == "PEDESTRIAN":  self._tick_pedestrian(...)     :597
    elif self.phase == "SHORTCUT":    self._tick_shortcut(...)       :599
    ...
    self._publish_drive_cmd()                                        :614
```

정상 주행(LANE)일 때 `_tick_lane_phase`(:667) → `_tick_lane_publish`(:1140) 로 가고,
거기서 예선 검증 코드인 `lane_plan()`(= `lane_planner.py:1205` 의 `plan()`)을 부른다
(:1155). 이 함수가 노란 중앙선 점들을 2차식 `y = ax² + bx + c` 로 피팅하고, 그 곡선
자체를 목표 경로로 삼는다(lane_planner.py:1231 `center_coef = yellow_fit.copy()`).
그리고 x=1.0~11.0m 구간 13점을 샘플링해서 돌려준다(:1233-1234, `SAMPLE_*` 상수 :104-106).

그다음 `_publish_lane_result`(:1188)에서 **라이다 회피 오프셋**을 얹는다. 여기서
**횡오프셋(lane offset)** 은 "원래 가야 할 선에서 좌우로 몇 미터 비켜 갈까"를 뜻하고,
**클러스터(cluster)** 는 라이다 점들 중 가까이 뭉쳐 있는 덩어리 하나 — 즉 물체 하나로
간주한 묶음이다(라이다는 "물체"를 보는 게 아니라 점만 찍어 주므로, 가까운 점끼리
묶어서 물체로 만드는 단계가 필요하다). 확정된
장애물 클러스터를 `PathGen.generate()`(lib/path_gen.py:91)에 넘기면, 횡오프셋
후보를 0.3m 간격으로 훑으면서 "장애물 여유 + 차선 복귀 + 직전 오프셋과의 연속성"의
비용이 가장 낮은 횡이동량을 고른다. 후보 격자 자체는 -1.2~+1.2m 지만(path_gen.py:51),
왼쪽(+y)은 좌 조향 스톱 여유가 부족해 `left_offset_max` 로 잘라낸다 —
planner 가 0.9 를 주므로(path_planner_node.py:144) 실제 후보는 **-1.2~+0.9m**
비대칭이다(path_gen.py:53-54). 한 번에 0.06m 이상은 못 움직이게 제한해서(램프) 경로가
툭 튀지 않는다(path_gen.py:67-70). **램프(ramp)** 는 값을 툭 바꾸지 않고 비스듬한
경사로처럼 조금씩 옮기는 것을 말한다. 목표가 1.2m 옆으로 뛰어도 실제로는 한 틱에
0.06m 씩, 20틱(1초)에 걸쳐 옮겨 간다. 결과가 `/center_path` 로 나간다(:1231).

동시에 `/drive_cmd` 도 만들어진다(`_publish_drive_cmd`, :1117-1136). 이번 틱에 쌓인
`caps` 후보 중 **최솟값**이 최종 speed_cap 이다(:1120-1121). 여러 상황이 동시에
"천천히"를 요구하면 가장 보수적인 값이 이긴다.

### 5-6. motion 이 20Hz 로 실행한다 — `motion_node.py:230`

```python
cmd_stale = self._age(self._cmd_stamp, now) > dc.DRIVE_CMD_STALE_SEC  # :235
owner = dc.Owner.MISSION_STOP if cmd_stale else cmd["owner"]          # :236
...
if path_fresh:                                                        # :261
    seg_xs, seg_ys, seg_s = self._reanchored_segment(...)             # :262
    lane_angle, v_base, in_corner = self._shadow_lane(...)            # :265
```

핵심 개념이 **섀도우(shadow) 계산**이다. 그림자처럼 뒤에서 계속 따라 돌지만 밖으로는
안 나가는 계산이라는 뜻이다. 경로가 신선하기만 하면 owner 가 뭐든
(정지 중이든 좌회전 블록 중이든) LANE 조향 계산을 **매 틱 돌려서 내부 상태를 갱신**
한다(:254 주석). 그리고 최종 출력만 owner 로 게이트한다(:284-304). 이렇게 안 하면
정지했다가 다시 출발할 때 내부 상태가 3초 전 값에서 얼어 있어서 핸들이 튄다.

조향각 계산은 `_compute_steering`(:494)이다. 순수 추종(pursuit, "목표점이 어느 쪽에
있나")과 방향 정렬(heading, "경로가 어느 쪽으로 기울었나") 두 각도를 섞고, 경로 위
여러 점에 **가우시안 가중치**를 준다.

세 용어를 풀면 이렇다.

- **순수 추종(pure pursuit)** — 경로 위에 "저기 앞 저 점"을 하나 찍고 그 점을 향하도록
  핸들을 꺾는 고전적인 방식이다. 자전거를 탈 때 발밑이 아니라 앞을 보고 가는 것과
  같다. 코드에서는 목표점의 좌우 위치 y 와 전방 거리 x 로 각도를 낸다(:502).
- **방향 정렬(heading)** — 목표점 위치 대신 **경로가 그 지점에서 어느 쪽으로 기울어
  있는가**(기울기)를 보고 꺾는다(:504-508). 순수 추종만 쓰면 목표점에 도달할 때
  차 방향이 경로와 어긋난 채 붙을 수 있어서, 둘을 섞는다.
- **가우시안 가중치** — 종 모양으로 부드럽게 줄어드는 가중치다. 기준 거리에서
  가까운 점일수록 크게, 멀수록 작게 쳐 준다. 특정 한 점만 딱 보지 않으므로 그 점
  하나가 튀어도 조향이 덜 흔들린다. 종의 폭은 `steer_focus_sigma` = 1.8m 다
  (motion_node.py:57).

```python
weights = np.exp(-((focus - focus_x) / self.STEER_FOCUS_SIGMA) ** 2)  # :538
angle   = float(np.average(sample_angles, weights=weights))            # :539
```

`focus_x` 는 "지금 몇 미터 앞을 보고 운전할까"(lookahead, 전방주시거리)다. 속도에
비례해서 4.2~5.0m 사이로 움직인다(:535-537) — 빠를수록 멀리 봐야 위빙이 없다.
사람도 주차장에서는 코앞을 보고, 고속도로에서는 멀리 보고 운전하는 것과 같다.

계산된 각도는 그대로 나가지 않는다. 코너 탈출 언와인드(:542) → IIR 스무딩 + 스텝
제한 + 데드밴드(:553-563)를 거친다. 급격한 핸들 변화를 물리적으로 막는 장치다.

각각이 뭘 하는지 풀어 둔다(코드상 실제 적용 순서는 언와인드 → 데드밴드 → IIR →
스텝 제한이다 — motion_node.py:402-403, :553-563).

- **언와인드(unwind)** — "감은 것을 푼다"는 말이다. 직전까지 많이 휘던 경로가 갑자기
  펴지면(곡률비 0.45 이상 → 0.22 이하) "코너를 빠져나왔다"로 보고, 5틱 동안 조향
  크기를 0.8배로 줄여 감아 둔 핸들을 의도적으로 빨리 풀어 준다
  (motion_node.py:386-395, :542-551). 아래 스무딩만 있으면 핸들이 천천히 풀려 코너
  출구에서 안쪽으로 붙기 때문이다.
- **데드밴드(deadband)** — "이만큼 미만의 변화는 아예 무시"하는 둔감 구간이다. 새
  각도와 직전 각도의 차이가 0.6도(`angle_deadband`) 미만이면 그냥 직전 값을 그대로
  쓴다(:555-556). 계산값이 미세하게 떨리는 걸 조향에 그대로 흘리지 않는다.
- **IIR 스무딩** — 직전 값을 새 값 쪽으로 **조금씩만** 끌어당기는 필터다.
  `새값 = 이전값 + α × (목표값 − 이전값)` 이고, 여기서 α = 0.55
  (`angle_smooth_alpha`, :558). α 가 작을수록 부드럽지만 반응이 느려지고, 1이면
  스무딩이 없는 것과 같다. IIR 은 Infinite Impulse Response 의 약자로, 과거 값이
  완전히 사라지지 않고 계속 조금씩 남아 영향을 준다는 뜻이다.
- **스텝 제한(max step)** — 그래도 한 틱에 12도(`angle_max_step`) 넘게는 못 움직이게
  최종적으로 잘라낸다(:559-561).

### 5-7. 논리 명령 → 실제 모터값 — `motion_node.py:314`

```python
angle_out, speed_out = self._car.to_motor(angle_cmd, speed_cmd)   # :314
out.data = [float(angle_out), float(speed_out)]                   # :316
self._pub_motor.publish(out)                                      # :317
```

여기까지 계산된 각도는 **논리 단위**(±100)다. 실제 차의 서보는 그 값을 그대로 못
받는다. `lib/car_interface.py:97` 의 `to_motor()` 가 실차 실측값을 전부 흡수한다.

```
 논리 angle (±100)
   ↓ ×0.42 (steer_scale)                       car_interface.py:113
   ↓ 기계 스톱 클램프 -32 ~ +62 (실측 -34/+64에 마진)      :114
   ↓ + 트림 -20 (이 차는 -20 이 직진이다, 실측)             :115
   ↓ 틱당 8 이상 못 움직임 (slew)                          :116-119
 angle_out → /xycar_motor[0]

 논리 speed (명령단위, ×0.08 = m/s)
   ↓ [0, 100] 클립 (자율주행은 후진 금지)                  :122-125
   ↓ 데드존 스냅 — 4 미만은 안 구르니 4로 올리거나 0으로    :126, :135-147
   ↓ 틱당 1.5 이상 못 변함 (센서리스 ESC 기동 램프)         :127-129
 speed_out → /xycar_motor[1]
```

박스 안에 나온 말들을 풀어 둔다.

- **클램프(clamp) / 클립(clip)** — 값을 정해진 최소~최대 밖으로 못 나가게 잘라내는
  것이다. "-32 ~ +62 클램프"는 그보다 더 꺾으라는 명령이 와도 거기서 멈춘다는 뜻이고,
  기계적으로 더 안 꺾이는 스톱에 무리하게 밀어붙이지 않으려는 보호다.
- **트림(trim)** — 서보 중립이 기계적으로 딱 가운데가 아닐 때, 그 어긋난 만큼을
  상수로 더해 주는 보정값이다. 이 차는 -20 을 줘야 실제로 직진한다.
- **slew(슬루) 제한** — 출력이 **한 틱(0.05초)에 변할 수 있는 양의 상한**이다. 조향은
  틱당 8, 속도는 틱당 1.5 로 묶여 있다(car_interface.py:31-32). 목표가 아무리 멀리
  뛰어도 출력은 계단을 밟듯 그만큼씩만 따라간다. 이렇게 서서히 옮기는 걸 **램프(ramp)**
  라고도 한다 — 같은 말이다.
- **데드존(deadzone)** — 명령을 줘도 실제로는 안 움직이는 구간이다. 이 차는 속도 명령
  4 미만이면 모터가 아예 안 돈다.
- **센서리스 ESC** — ESC 는 모터를 돌려 주는 전자 변속기(Electronic Speed Controller)
  다. '센서리스'는 회전자가 지금 어느 위치에 있는지 알려 주는 센서가 달려 있지
  않다는 뜻이고, 대신 모터가 돌면서 만드는 전압(역기전력)으로 위치를 추정한다.
  그런데 멈춰 있으면 그 전압이 안 나오므로 위치를 모른다. 이 상태에서 갑자기 큰
  명령을 주면 제대로 못 물고 헛돌거나 멈춘다. 그래서 정지에서 출발할 때 속도를
  램프로 천천히 올려야 한다.

트림 -20 은 이 차 고유값이다. 서보 중립이 기계적으로 정확히 가운데가 아니라서,
0을 주면 차가 한쪽으로 흐른다. 데드존 4 도 실측 — 4 미만 명령은 모터가 아예 안 돈다.
그래서 명령이 2.5 로 나오면 `_snap_deadzone`(:135)이 4로 올려 실제로 굴러가게 하거나,
1.0 이면 0으로 내려 확실히 세운다. 이 처리가 없으면 "명령은 나가는데 차는 안 가는"
상태가 된다(재도입 금지 버그 7).

**모든 실차 수치가 이 파일 하나(그리고 `config/car.yaml`)에만 있다**는 게 중요하다.
teleop_node 도 같은 클래스를 쓴다(teleop_node.py:73). 수치가 여기저기 흩어져 있으면
한 군데만 고치고 나머지를 잊는 사고가 난다.

## 6. 주행 모드(phase)와 명령 소유권(owner)

이 코드에는 **두 층의 상태**가 있다. 헷갈리기 쉬우니 구분해 두자.

- **phase** = planner 내부 상태. "지금 무슨 구간을 달리는 중인가."
- **owner** = motion 에게 전달되는 명령 소유권. "지금 누가 운전대를 쥐고 있나."

phase 가 여러 개라도 owner 는 4개뿐이다. 예를 들어 SHORTCUT 의 WAITING 서브상태는
owner=MISSION_STOP 을 낸다.

```
        ┌──────┐  센서 붙음
        │ IDLE │──────────────▶┌──────┐
        └──────┘               │ WAIT │  GREEN 또는 /manual_go
                               └──────┘  → 6틱 확인 → 출발
                                   │      + /capture_yaw 발행
                                   ▼
   ┌───────────────────────────────────────────┐
   │                  LANE                     │◀──┐
   │  노란 중앙선 따라 주행 (기본 상태)          │   │
   └───────────────────────────────────────────┘   │
       │            │              │               │
   콘 클러스터    정지선 감지     보행자 감지        │
   3연속 스캔       (v>312)     (기본 비활성)       │
       ▼            ▼              ▼               │
   ┌───────┐   ┌──────────┐   ┌────────────┐      │
   │ CONE  │   │ SHORTCUT │   │ PEDESTRIAN │      │
   │라바콘 │   │ WAITING  │   │ 2.2초 정지 │──────┤
   │ 주행  │   │ TURNING_1│   └────────────┘      │
   │       │   │ FOLLOW   │                       │
   └───────┘   │ TURNING_2│───────────────────────┘
       │       └──────────┘   (원샷 래치 — WAITING 타임아웃 때만 풀린다)
       └──── miss 20스캔 ─────────────────────────┘
```

그림 오른쪽 아래의 **원샷 래치**는 "한 번 하면 끝, 다시는 안 한다"를 강제하는
장치다. 지름길(SHORTCUT)에 한 번 들어가는 순간 `_shortcut_done` 플래그가 서고
(path_planner_node.py:296, :761-769), 그 뒤로는 정지선이 다시 보여도 재진입하지
않는다. 같은 지름길을 두 번 타면 코스를 벗어나기 때문이다. 유일한 예외가 WAITING
단계에서 8초 안에 못 들어간 경우로(`sc_wait_timeout_sec` 8.0, :186), 이때만 플래그를
다시 내려 재시도를 허용한다(:795-801). "원샷"은 딱 한 번만 실행되는 동작,
"래치"는 3.5 절에서 본 걸쇠 — 둘을 합쳐 "한 번 걸리면 안 풀리는 1회 실행"이다.

**phase 목록** (`path_planner_node.py:586-604` 의 분기가 전부다)

| phase | 한 줄 설명 |
|---|---|
| `IDLE` | 기동 직후. 센서가 하나라도 붙으면 WAIT 로 |
| `WAIT` | 정지 상태로 출발 신호 대기 (GREEN 또는 `/manual_go`) |
| `LANE` | 기본 주행. 노란 중앙선 추종 + 라이다 회피 |
| `CONE` | 라바콘 구간. 왼쪽 콘 줄을 피팅해 트랙폭 절반만큼 안쪽을 주행 |
| `SHORTCUT` | 지름길. WAITING→TURNING_1→FOLLOW→TURNING_2 4단계. 원샷 |
| `PEDESTRIAN` | 보행자 정지 (기본 비활성, `enable_pedestrian=false`) |

**phase 가 아닌 "부가 상태"** — 이것들은 LANE 위에 겹쳐서 켜진다.

| 이름 | 효과 | 기본 |
|---|---|---|
| `_red_stopping` | 정지선 + GREEN 아님 → owner=MISSION_STOP | 활성 |
| `_child_zone` | 어린이보호구역 → speed_cap 22 | 비활성 |
| `_s_zone_active` | S자 구간 → steer_profile=S_ZONE | 비활성 |
| corner boost | child 종료 후 speed_floor | 비활성(floor=0) |
| `OvertakeStub` | 추월 — **인터페이스만 있는 빈 껍데기** | 미구현 |

**owner 4종** (`lib/drive_cmd.py:28-33`)

| owner | motion 의 동작 |
|---|---|
| `LANE` (0) | 섀도우 계산 결과를 그대로 출력 |
| `BLOCK` (1) | 하드코딩 좌회전 실행 (조향 -100, 속도 10) |
| `MISSION_STOP` (2) | 속도 0, 조향은 마지막 값 유지 |
| `SAFETY_STOP` (3) | 동일 (owner 칸을 못 읽었을 때의 fail-safe 값) |

표의 `SAFETY_STOP` 설명에 나온 **fail-safe** 는 "뭔가 잘못됐을 때 자동으로 안전한
쪽으로 떨어지도록 미리 정해 둔 기본값"을 뜻한다. 값을 못 읽었으면 아무거나 쓰는 게
아니라 "선다"로 가게 만들어 둔 것이다.

`SAFETY_STOP` 이 나오는 경우를 정확히 해 두자. **미수신(0.3초 침묵)은 SAFETY_STOP 이
아니라 MISSION_STOP** 이다 — motion 의 워치독이 그렇게 덮어쓴다(motion_node.py:235-236).
**워치독(watchdog)** 은 "정해진 시간 안에 소식이 없으면 이상으로 보고 안전 동작으로
넘긴다"는 감시 타이머다. 여기서는 0.3초 동안 `/drive_cmd` 가 안 오면 planner 가
죽었거나 통신이 끊긴 것으로 간주하고 스스로 정지로 간다.
SAFETY_STOP 은 메시지의 **[0] 칸 자체가 없거나 NaN/inf/모르는 값일 때** 나온다
(drive_cmd.py:44-48, :75). 배열이 짧아도 [0] 이 정상이면 그 owner 를 그대로 쓴다
(motion 은 `decode_drive_cmd` 가 주는 `valid` 를 보지 않는다).

`BLOCK` 이 특이하다. motion 은 **실행만** 하고 언제 끝나는지는 판단하지 않는다.
planner 가 IMU 로 "90도 돌았다"를 확인하고 owner 를 LANE 으로 되돌린다
(path_planner_node.py:803-822). 같은 동작이 두 번 실행되는 걸 막으려고 `block_id` 를
쓴다 — 새 블록마다 +1 하고, 같은 id 는 무시한다(:844, arbitration.py:86).

`OVERTAKE` 는 **아직 없다.** `OvertakeStub.update()` 는 항상 `None` 을 돌려준다
(path_planner_node.py:102-104). 자리만 잡아둔 것이고, 본선 전에 채워야 할 TODO 가
:95-97 에 적혀 있다.

자세한 상태 전이 조건과 파라미터는 **03 문서**에서 다룬다.

트리에 나온 말 둘. **폴리핏(polyfit)** 은 점들에 다항식 하나를 맞추는 것으로,
5-4 절에서 본 "피팅"과 같은 말이다. **트래커(tracker)** 는 매 스캔마다 새로 나온
클러스터를 직전 스캔의 클러스터와 짝지어 "아까 그 물체가 지금 여기 있다"로 이어
붙이는 부분이다 — 한 프레임 튀었다고 장애물이 사라졌다 나타났다 하지 않게 해 준다.

### ★ 왜 `lib/` 을 따로 뺐나

`lib/` 안의 파일들은 **`import rclpy` 를 하지 않는다.** 각 파일 맨 위 docstring 에
"rclpy 금지"라고 못박혀 있다(drive_cmd.py:8, arbitration.py:10, car_interface.py:4).

이유는 세 가지다.

1. **테스트가 가능해진다.** `test/test_arbitration.py`, `test_car_interface.py`,
   `test_path_gen.py` 같은 유닛테스트를 차 없이, ROS 없이, 노트북에서 `pytest` 로
   1초 만에 돌릴 수 있다. 로직 버그를 실차에 올리기 전에 잡는다.
2. **rosbag 재생으로 재현할 수 있다.** 노드에 로직이 박혀 있으면 그 로직만 떼서
   기록된 데이터에 다시 돌려보기가 어렵다.
3. **외부팀과 공유할 수 있다.** 콘 통로 모듈을 만드는 외부팀은 `lib/cluster.py`
   하나만 import 한다. 그래서 cluster.py:13-14 에 "외부팀도 이 파일 하나만
   import 한다 — 패키지 내 다른 모듈/rclpy 에 의존하지 말 것"이라고 적혀 있다.

즉 **노드 = 배선 담당, lib = 계산 담당**이다. 노드는 토픽을 받아서 lib 함수에 넘기고
결과를 다시 토픽으로 내보내는 일만 한다. 새 기능을 만들 때 계산 로직은 되도록
lib 에 두는 게 이 프로젝트의 규칙이다.

`lane_planner.py` 만 예외적으로 `lib/` 밖에 있고 rclpy 를 import 한다. 이건 친구(sm)가
쓴 원본을 **한 글자도 고치지 않고** 그대로 가져왔기 때문이다(파일 헤더 :3
"[친구(sm) 원본 — 수정 금지]"). path_planner 는 여기서 `plan()` 함수만 꺼내 쓴다.

## 부록 A. 이 시스템의 안전 장치 목록

코드 곳곳에 "이러이러하면 무조건 선다"는 장치가 흩어져 있다. 한 곳에 모아 둔다.

| 조건 | 결과 | 위치 |
|---|---|---|
| `/drive_cmd` 0.3초 미수신 | owner=MISSION_STOP | motion_node.py:235 |
| `/drive_cmd` [0] 칸 없음/비정상 | owner=SAFETY_STOP | drive_cmd.py:44-48, :75 |
| `/detect/lane` 0.6초 스테일 | `/center_path` 발행 중단 | path_planner_node.py:1146 |
| `/center_path` 0.5초 스테일 | 직전 조향 유지 + 1초 선형 감속 | motion_node.py:441 |
| `/scan` 1.0초 스테일 | 회피 장애물 목록 비움 | path_planner_node.py:1201 |
| 차선 품질 < 0.3 | speed_cap 7 | path_planner_node.py:610 |
| teleop `estop` 키 | angle=0, speed=0 | motion_node.py:309 |
| teleop 3초 무입력 | 목표속도 0 | teleop_node.py:185 |
| `/xycar_motor` 0.4초 침묵 | (도커) 데드맨 — **기본 꺼짐** | vesc_relay.py:34, :88-99 |
| 배터리 8.6V 미만 | 경고 로그 (정지는 아님) | car_state_node.py:109 |

표에 반복해서 나오는 **스테일(stale)** 은 "데이터가 너무 오래됐다"는 뜻이다. 값 자체는
변수에 남아 있지만, 마지막으로 받은 시각에서 정해진 시간이 지나면 **없는 셈 치고**
안전 동작으로 넘어간다. 냉장고에 음식이 남아 있어도 유통기한이 지나면 안 먹는 것과
같다. 이게 없으면 3초 전에 끊긴 차선 정보를 계속 최신인 줄 알고 따라가게 된다.

마지막 줄의 **데드맨(deadman)** 은 기차 기관사가 손잡이에서 손을 떼면 열차가 서게
만든 장치에서 온 말이다. 여기서는 모터 명령이 일정 시간 끊기면 대신 정지 명령을
쏴 주는 가드를 가리킨다.

★ 마지막에서 두 번째 줄은 조건부다. vesc_relay 의 데드맨 가드는 `deadman_enable`
파라미터가 **기본 False** 라 그냥 띄우면 동작하지 않는다(vesc_relay.py:34, :47-51).
켜려면 `python3 /root/vesc_relay.py _deadman_enable:=true` 로 실행해야 한다
(vesc_relay.py:20). 켰을 때만 `/xycar_motor` 가 0.4초 끊기고 마지막 명령 속도가
0이 아니었을 경우 `[트림값, 0]` 을 반복 발행한다.

lane-lost 처리는 특히 눈여겨볼 만하다. 예선에서는 차선을 놓치면 핸들을 ±100 으로
꺾어 "찾으러 가는" 복구 동작을 했는데, 실차에서는 그게 벽으로 돌진하는 동작이다.
본선에서는 **직전 각도를 유지한 채 1초에 걸쳐 속도만 0으로 줄인다**
(motion_node.py:441-452). 헤더에 "±100 복구 금지(버그 1)"로 명시돼 있다.
