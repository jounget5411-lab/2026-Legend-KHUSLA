# 05. 설정 파일 완전 해설 — "숫자를 어디서 바꾸나"

이 문서는 본선 실차 코드(`본선/track_drive/`)의 **설정 파일 전부**를 한 줄씩 해설한다.
다루는 것은 `config/camera.yaml`(카메라 캘리브레이션), `config/tuning.yaml`(노드 튜닝
파라미터 212줄 전부), `config/car.yaml`(차량 실측값), `launch/` 3개, 그리고 패키지
설정(`setup.py` / `package.xml` / `setup.cfg`)이다. 알고리즘이 *어떻게* 동작하는지는
다른 문서가 다루고, 여기서는 **"그 동작을 조절하는 숫자가 어느 파일 몇 줄에 있고,
올리면 무슨 일이 생기는가"** 만 본다. 모든 설명은 실제 파일을 읽고 쓴 것이며 줄번호를
붙였다(예: `bev.py:181`). 줄번호는 2026-07-31 기준이다.

## 0. 이 문서에 나오는 용어

설정값을 읽다 보면 제어·영상 쪽 전문용어가 섞여 나온다. 아래 표는 **이 문서 안에서 실제로
쓰인 용어만** 모은 것이다. 본문에서도 각 용어가 처음 나오는 자리에 한 번씩 풀어 놨으니,
여기서는 "그게 대충 뭐였지"를 되짚는 용도로 쓰면 된다.

| 용어 | 쉬운 뜻 | 이 문서 어디서 나오나 |
|---|---|---|
| 호모그래피(H) | 비스듬히 찍은 바닥 사진을 위에서 내려다본 것처럼 펴주는 3x3 변환표. 평평한 바닥에만 성립한다 | 2.2, 2.6 |
| BEV | 그렇게 편 결과인 "새가 내려다본 그림" | 2.2, 2.6 |
| 왜곡보정(undistort) | 렌즈 때문에 휘어 보이는 직선을 곧게 펴는 처리 | 2.3~2.5 |
| 주점(cx, cy) | 렌즈 광축이 센서에 닿는 픽셀. 보통 화면 한가운데 근처 | 2.3 |
| 어안(fisheye) | 시야각 180° 안팎의 반구형 렌즈를 위한 왜곡 모델. 이 차 카메라는 해당 없음 | 2.4 |
| 리맵 테이블 | "원본 몇 번 픽셀을 편 그림 몇 번 자리로 옮길지"를 미리 계산해 둔 표 | 2.7 |
| 마스크 | 픽셀마다 0/1만 담은 흑백 그림. 1인 자리만 골라 쓰는 도장 같은 것 | 2.6, 2.10 |
| 플래그 | 참/거짓 하나만 담는 스위치 값 | 2.8 |
| 폴백(fallback) | 제대로 된 값이 없을 때 대신 쓰는 예비값 | 2.6, 2.8 |
| 패스스루 | 아무 처리도 하지 않고 입력을 그대로 통과시키는 것 | 2.8 |
| 추론(inference) | 학습이 끝난 YOLO 에 그림 한 장을 넣고 결과를 받는 것 | 3.2 |

| 틱(tick) | 제어 루프가 한 바퀴 도는 것. 이 코드는 20Hz 라 1틱 = 50ms | 3.3, 3.12 |
| 스캔(scan) | 라이다가 한 바퀴 돌아 만든 점 묶음 하나. 틱과는 다른 단위다 | 3.6, 3.11 |
| 클러스터 | 가까이 붙어 있는 라이다 점들을 하나의 물체로 묶은 덩어리 | 3.4 |
| k-of-n | 최근 n번 중 k번 보이면 진짜라고 확정하는 규칙 | 3.4 |
| ROI(관심영역) | 그 안만 보겠다고 미리 잘라 둔 범위 | 3.6, 3.7 |
| 피팅(fitting) | 흩어진 점들을 가장 잘 지나가는 곡선식 하나를 찾아내는 것 | 3.7 |
| IIR 평활(alpha) | 새값 = 이전값 + α×(측정값−이전값). α 가 작을수록 부드럽고 느리다 | 3.7, 3.12 |

| 램프(ramp) | 계단처럼 튀지 않고 비탈처럼 서서히 올리는 것 | 3.12, 4.1 |
| 데드밴드 | 이보다 작은 변화는 아예 없던 것으로 무시하는 폭 | 3.12 |
| 세그먼트 | 경로 전체가 아니라 지금 따라갈 앞쪽 토막 | 3.12 |
| 트림(trim) | 원점 보정값. 이 차는 명령 −20 을 줘야 바퀴가 실제로 직진한다 | 3.1, 4.1 |
| 데드존 | 명령을 줘도 안 움직이는 죽은 구간. 여기서는 speed 4 미만 | 3.1, 4.1 |

| 센서리스 ESC | 회전 센서 없이 모터가 만드는 역기전력만 보고 돌리는 전자변속기 | 4.1 |
| eRPM | 모터의 전기적 회전수. 이 차는 eRPM = 4614 × m/s | 4.1, 4.3 |

## 1. 설정 파일 지도 — 뭘 바꾸려면 어디를 여나

먼저 결론부터. "이걸 바꾸고 싶다" → "이 파일을 연다" 표다.

| 바꾸고 싶은 것 | 열 파일 | 항목 |
|---|---|---|
| 차선 검출을 더 민감하게 | `config/tuning.yaml` | `yolo_node: conf_lane` (낮출수록 민감) |
| YOLO 속도 ↔ 정확도 | `config/tuning.yaml` | `yolo_node: imgsz` (416↓ 빠름 / 640↑ 정확) |
| 신호등 오판 줄이기 | `config/tuning.yaml` | `conf_light`, `light_debounce_n` |
| 기본 주행 속도 | `config/tuning.yaml` | `motion_node: speed_default` |
| 조향 반응 세기 | `config/tuning.yaml` | `curve_pursuit_gain`, `curve_heading_gain` |
| 정지선을 더 일찍/늦게 서기 | `config/tuning.yaml` | `stop_v_threshold` (480p 기준 픽셀) |
| 라바콘 구간 판정 | `config/tuning.yaml` | `cone_enter_*`, `cone_exit_miss_scans` |
| 직진이 한쪽으로 쏠림 | `config/car.yaml` | `steer_trim` (실측 근거 필수) |
| 차가 안 굴러감(정지 상태 유지) | `config/car.yaml` | `speed_deadzone`, `speed_min_drive` |
| 조향이 기계적으로 안 꺾임 | `config/car.yaml` | `steer_limit_left/right`, `steer_scale` |
| 카메라 해상도 | `launch/sensors.launch.py` **+** `config/camera.yaml` | 둘 다 같이 (아래 5장) |
| 카메라 장치 경로(/dev/videoX) | `launch/sensors.launch.py` | `video_device` |
| 지면 좌표(BEV)가 안 맞음 | `config/camera.yaml` | ★ 손편집 금지 — `tools/ground_fit.py` |
| 차체(바퀴·라이다)가 차선으로 잡힘 | `config/camera.yaml` | ★ `tools/bev_view.py` 의 `m`→`s` 키 |
| 노드를 하나 더 추가 | `setup.py` | `console_scripts` |

원칙 하나만 기억하면 된다.

```
 config/camera.yaml  = "물리 세계와 픽셀의 관계"   → 도구로만 수정
 config/car.yaml     = "이 차 한 대의 실측 특성"   → 실측 근거 있을 때만 수정
 config/tuning.yaml  = "주행 성향(취향·코스 대응)" → 자유롭게 튜닝하는 곳
```

### 1.1 설정이 노드까지 도달하는 경로

```
   ros2 launch track_drive drive.launch.py
             │
             │ drive.launch.py:22-25  parameters=[tuning.yaml, car.yaml]
             │   (같은 키가 양쪽에 있으면 뒤에 준 car.yaml 이 이긴다)
             ▼
   ┌──────────────────────────────────────────────────────┐
   │  yolo   path_planner   motion   car_state            │  ← 4개 노드
   └──────────────────────────────────────────────────────┘
        │                     │
        │ declare_parameter(name, 기본값)  ← yaml 에 없으면 이 기본값이 쓰인다
        │                     │
        ├── yolo_node.py:122  camera_yaml 파라미터로 camera.yaml 경로를 받아
        │    bev.load_camera_config() (bev.py:181) → K/D/H/new_K/car_mask_v
        │
        └── path_planner_node.py:413  camera.yaml 의 image_height 만 따로 읽어
             /detect/objects 의 v 좌표를 480p 기준으로 환산
```

여기서 놓치기 쉬운 점: **`camera.yaml` 은 ROS 파라미터 파일이 아니다.** `tuning.yaml`,
`car.yaml` 두 개만 launch 가 파라미터로 넘기고(`drive.launch.py:22-25`), `camera.yaml`
은 노드가 **직접 파일을 열어서** 읽는다(`yolo_node.py:123`, `path_planner_node.py:425`).
그래서 형식도 다르다 — `tuning.yaml`/`car.yaml` 은 `노드명: ros__parameters:` 구조지만
`camera.yaml` 은 평평한 키-값 구조다.

## 2. camera.yaml — 카메라 캘리브레이션 (71줄) ★가장 중요

### 2.1 한 문단 요약

`camera.yaml` 은 "카메라가 찍은 그림 속 한 점이 실제 바닥의 어디인가"를 정의하는 파일이다.
이 파일이 틀리면 차선은 잘 보이는데 **차가 엉뚱한 데로 간다.** 값은 크게 셋이다.
① 렌즈 자체의 성질(`K`, `D`) ② 왜곡을 편 뒤의 좌표계(`new_K`) ③ 편 그림의 픽셀을
바닥 미터로 바꾸는 변환(`H`). 여기에 이 값들이 유효한지 알려주는 플래그(flag, 참/거짓
하나만 담는 스위치 값) 2개와, `H` 를 다시 만들 때 쓰는 물리 파라미터 묶음(`h_phys`)이 붙는다.

### 2.2 전체 구조 그림

```
  카메라 원본 그림 (1920x1080, 렌즈 때문에 휘어 있음)
        │
        │  K, D          ← 렌즈 내부 파라미터 + 왜곡계수
        │  (cv2.initUndistortRectifyMap, bev.py:347)
        ▼
  왜곡 보정된 그림  ─── 이 그림의 좌표계를 정하는 것이 new_K (camera.yaml:62-71)
        │
        │  H            ← 3x3 호모그래피 (camera.yaml:8-17)
        ▼
  지면 좌표 (x 전방 m, y 좌측 m)  원점 = 라이다 회전중심의 지면 투영점
        │
        │  M_GRID (bev.py:42-46)
        ▼
  BEV 이미지 (200x280 px, 5cm/px, 전방 -2~12m, 좌우 ±5m)
```

용어 풀이 두 개만 하고 가자.

- **호모그래피(Homography)** 는 카메라가 비스듬히 본 바닥 사진을 "위에서 내려다본 것처럼"
  펴주는 3x3 변환 행렬이다. 기울여 찍은 종이 사진을 반듯하게 펴는 것과 같다. 단, 진짜로
  평평한 바닥에 대해서만 성립한다 — 그래서 차체나 콘 같은 **높이가 있는 물체**를 이 변환에
  넣으면 엉뚱한 위치로 날아간다(2.9절 `car_mask_v` 가 이 문제를 막는다).
- **BEV(Bird's Eye View)** 는 그 결과로 얻은 "새가 내려다본 그림"이다.

### 2.3 K — 렌즈 내부 파라미터 (camera.yaml:18-27)

```
K = [ 789.0055     0.0    966.7561 ]   fx  0  cx
    [   0.0      874.5620  540.2523 ]    0 fy  cy
    [   0.0        0.0       1.0    ]
```

| 원소 | 값 | 뜻 |
|---|---|---|
| `fx`, `fy` | 789.0, 874.6 | 초점거리를 픽셀로 잰 값. 크면 망원(좁게 보임), 작으면 광각 |
| `cx`, `cy` | 966.8, 540.3 | 주점 — 렌즈 광축이 센서에 닿는 픽셀. 보통 화면 중앙 근처 |

`intrinsics_source`(camera.yaml:59-60)에 출처가 적혀 있다. 640x480 으로 잡은 캘리브 결과를
1920x1080 으로 환산했고, 배율 1.9999 에 잘림 원점 (319.6, 52.8) 을 ORB 특징점 정합으로
실측했다는 기록이다. ORB 특징점 정합이란 두 장의 사진에서 "코너처럼 눈에 띄는 점"을 각각
뽑아 같은 점끼리 짝지어, 두 사진이 서로 얼마나 확대·이동돼 있는지를 자동으로 재는 방법이다
(눈대중 대신 쓴 실측 수단이라는 뜻이다). 이 카메라는 저해상도 모드가 단순 축소가 아니라 **센서를 잘라낸 것**
이라서 폭 비례 환산이 통하지 않는다(`ground_fit.py:117-120` 의 `SCALE` 표가 그 실측치다).

### 2.4 D — 왜곡 계수 (camera.yaml:2-7)

`D = [k1, k2, p1, p2, k3] = [-0.373976, 0.11051, 0.001014, 0.000505, 0.0]` — 5개짜리
`plumb_bob`(브라운-콘라디) 모델이다. `k*` 는 방사 왜곡(중심에서 멀수록 휘는 정도),
`p*` 는 접선 왜곡(렌즈가 센서와 살짝 안 나란할 때 생기는 비틀림)이다.

★ 여기 중요한 실측 사실이 있다. 벤더 PDF 는 이 카메라를 "170도 어안"이라고 적어 놨지만,
실측해 보니 HFOV≈87°/VFOV≈64° 의 **평범한 광각**이었다(`bev.py:15-19`). 어안(fisheye)은
시야각 180° 안팎의 반구형 렌즈를 위한 왜곡 모델이라 휨을 표현하는 항이 훨씬 많다. 87° 짜리
평범한 렌즈에 그 모델을 쓰면 파라미터가 남아돌아(맞출 대상보다 손잡이가 많아서) 계산이
한 답으로 모이지 않는다 — OpenCV 가 그 상태를 걸러내며 내는 오류가 `CHECK_COND` 실패고,
억지로 통과시켜도 화면 가장자리가 더 나빠진다.
그래서 기본 모델을 `plumb_bob` 으로 두고, fisheye 경로는 카메라 교체 대비로 남겨만 뒀다.
어느 쪽을 쓸지는 `model:` 키(camera.yaml:61)가 정한다. 값이 없거나 이상하면 `D` 의 길이로
추론한다 — 5개면 plumb_bob, 4개면 fisheye (`bev.py:81-110`).

### 2.5 new_K — 보정된 그림의 좌표계 (camera.yaml:62-71)

```
new_K = [ 847.5229   0.0    960.0 ]
        [   0.0    939.4247  540.0 ]
        [   0.0      0.0       1.0 ]
```

왜곡을 펴면 픽셀이 이리저리 움직이므로, **편 그림에도 자기만의 카메라 행렬이 필요하다.**
그게 `new_K` 다. 이 값은 `h_phys` 에서 다음 규칙으로 만들어진다(`ground_fit.py:383-386`):

```
new_K.fx = out_fx                    = 847.5229
new_K.fy = out_fx × (fy / fx)        = 847.5229 × (874.562/789.006) = 939.4247
new_K.cx, cy = 이미지 폭/2, 높이/2   = 960.0, 540.0
```

★ **`H` 는 `new_K` 좌표계에 매달려 있다.** `new_K` 가 조금이라도 달라지면 `H` 는 통째로
무효다. 그래서 코드가 기동할 때 캘리브 당시 `new_K` 와 런타임 `new_K` 를 직접 대조한다
(`bev.check_new_K_match`, `bev.py:379-408`, 허용오차 `1e-3` = `bev.py:78`). 일치하면
`"[camera] new_K 일치 — H 좌표계가 런타임 undistort 와 같다"` 로그가 뜨고
(`yolo_node.py:217-218`), 어긋나면 경고가 뜬다. **기동 로그에서 이 줄을 항상 확인해라.**

관련해서 `undistort_alpha` 파라미터(`yolo_node.py:110`)가 있는데, 이건 `new_K` 가 yaml 에
**없을 때만** 쓰인다(`bev.py:339-346`). 여기서 alpha 는 "왜곡을 편 뒤 그림을 얼마나 넓게
남길지"를 정하는 0~1 값이다 — 0 이면 검은 여백이 안 생기게 바짝 잘라내고, 1 이면 원본
화소를 전부 남기는 대신 가장자리에 검은 부분이 생긴다. (뒤에 3.7·3.12 에서 나오는 **IIR
평활의 alpha 와는 이름만 같고 전혀 다른 것**이다. 그쪽은 값을 부드럽게 만드는 계수다.)
지금은 `new_K` 가 기록돼 있으므로 alpha 값은 결과에 영향이 없다. yaml 의 `h_alpha: 0.0`(camera.yaml:32)도 같은 이유로 기록용 흔적이다.

### 2.6 H — 지면 호모그래피 (camera.yaml:8-17)

보정된 그림의 픽셀 `(u, v)` 를 지면 좌표 `(x 전방 m, y 좌측 m)` 으로 바꾸는 3x3 행렬이다.
사용처는 `bev.mask_to_bev_points()`(`bev.py:494-509`) — 차선 마스크를 통째로
`warpPerspective` 로 펴서 BEV 마스크를 만들고, 거기서 차선 중심점을 뽑는다.
여기서 **마스크(mask)** 는 픽셀마다 0 아니면 1 만 담은 흑백 그림이다. "이 픽셀은 차선,
저 픽셀은 아님"만 표시한 도장 같은 것이라고 보면 된다. `warpPerspective` 는 그 그림 전체를
`H` 로 한 번에 펴 주는 OpenCV 함수다.

원소 하나하나에는 사람이 읽을 의미가 없다. 9개가 서로 얽혀 있어서 손으로 못 맞춘다.
그래서 이 프로젝트는 **뜻이 분명한 물리값으로 H 를 만든다**(`ground_fit.py:83-98` 의
`build_H`). H 를 실제로 결정하는 것은 카메라 자세 4개(높이·내림각·좌우틀어짐·기울기)와
축척 2개(fx·fy), 그리고 원점을 라이다로 옮기는 오프셋(`--lidar-offset`)이다.
호출부가 `ground_fit.py:407-409` 이고, 넘기는 인자가 정확히 그것뿐이다.

★ 함정: `h_phys` 의 `grid_x0`/`grid_y0` 는 **H 에 안 들어간다.** 이 둘은 검증용 초록
격자를 화면에서 앞뒤·좌우로 옮기는 값일 뿐이다(`ground_fit.py:443` 에서만 쓴다). 차를
어디에 세웠는지에 맞추는 값이라, 좌표가 틀어졌다고 이것부터 만지면 안 된다.

그 물리값이 `h_phys` 블록에 그대로 보존돼 있어서(camera.yaml:41-54) 다음 번에 이어서
튜닝할 수 있다.

`h_calibrated: false` 이면 코드는 yaml 의 H 를 **버리고** 예선 시뮬 폴백 H
(`bev.py:49-53`)로 돌아간다. **폴백(fallback)** 은 제대로 된 값이 없을 때 대신 쓰는
예비값이다 — 없으면 노드가 죽어버리니 일단 굴러가게는 해 주되, 그 값이 맞다는 보장은 없다. 이때는 지면 좌표가 부정확하니 경고 로그가 뜬다
(`yolo_node.py:219-222`).

### 2.7 image_width / image_height 가 왜 결정적인가 (camera.yaml:56-57)

`image_width: 1920`, `image_height: 1080`. 이 두 줄은 단순 메타데이터가 아니라 **세 곳에서
실제로 쓰이는 계약값**이다.

| 쓰는 곳 | 무슨 일이 일어나나 |
|---|---|
| `bev.py:131-141` `_as_size_or_none` | 왜곡보정 리맵 테이블을 이 크기로 만든다 |
| `yolo_node.py:266-276` | 실제 프레임 크기와 다르면 경고 + 리맵 재생성 |
| `path_planner_node.py:413-443` | `/detect/objects` 의 v 를 480p 기준으로 환산 |

**리맵 테이블(remap)** 이란 "원본 그림의 몇 번 픽셀을, 편 그림의 몇 번 자리로 옮길지"를
픽셀 하나하나에 대해 미리 계산해 둔 대응표다. 매 프레임 삼각함수를 다시 푸는 대신 이 표를
한 번 만들어 놓고 그대로 베껴 오기 때문에 빠르다. 대신 **그림 크기가 달라지면 표가 통째로
쓸모없어져서** 다시 만들어야 한다 — 위 두 번째 줄의 "리맵 재생성"이 그 얘기다.

해상도가 달라지면 `new_K`(=폭/2, 높이/2가 들어감)가 달라지고, 그러면 **H 가 통째로 무효**가
된다. `yolo_node.py:268-271` 이 이 상황에서 남기는 경고가 정확히 그 문장이다:
`"프레임 크기 ... 가 캘리브 기준 ... 와 다르다 — 리맵 재생성. new_K 가 달라져 H 는 무효일
수 있다."` 그래서 `launch/sensors.launch.py` 의 카메라 해상도와 이 두 줄은 **반드시 같아야
한다**(5장 참조).

### 2.8 두 개의 캘리브 플래그 (camera.yaml:33, 58)

```
  intrinsics_calibrated: true   → K/D 가 유효 → 왜곡보정을 실제로 실행
  h_calibrated:          true   → H 가 유효   → 지면 좌표를 믿어도 됨
```

왜 둘로 쪼갰나. 실차에서는 **"K/D 는 잡았는데 지면 H 는 아직"** 이라는 중간 상태가 실제로
자주 생기기 때문이다(`bev.py:11-14`, `185-195`). 예전처럼 `calibrated` 하나로 묶으면 H 가
없다는 이유로 실측 K/D 까지 버려져 왜곡보정이 통째로 죽는다.

| 플래그 조합 | 코드 동작 |
|---|---|
| `intr=true, h=true` | 정상. yaml 의 K/D/H/new_K 전부 사용 |
| `intr=true, h=false` | 왜곡보정은 켜지고 H 는 시뮬 폴백 → **좌표계가 어긋난 상태** (경고) |
| `intr=false, h=true` | 왜곡보정 패스스루. H 가 원본 픽셀 기준인지 확인 필요 (경고) |
| `intr=false, h=false` | 전부 폴백. 지면 좌표 신뢰 금지 |

여기서 **패스스루(pass-through)** 는 아무 처리도 하지 않고 입력을 그대로 통과시킨다는 뜻이다.
K/D 가 없으니 왜곡을 펴지 못하고 원본 그림을 그냥 다음 단계로 넘긴다는 말이고, 그러면 `H` 가
"편 그림 기준"인지 "원본 기준"인지가 어긋날 수 있어서 경고가 뜬다.

구버전 파일의 단일 키 `calibrated`(camera.yaml:28)는 두 플래그의 기본값으로 해석된다
(`bev.resolve_calib_flags`, `bev.py:166-178`).

### 2.9 h_phys — H 를 만드는 물리 파라미터 (camera.yaml:41-54)

★ 이 표가 이 문서에서 제일 실용적인 부분이다. 설명 문구는 `ground_fit.py:101-114` 의
`PARAMS` 표에서 그대로 가져왔다(도구 화면에 뜨는 그 문구다).

| 키 | 현재값 | 조절 손잡이 이름 | 바꾸면 화면에서 무엇이 변하나 |
|---|---|---|---|
| `height` | 0.2 | 높이(m) | 크게 = BEV 가 통째로 커진다 (거리·좌우 전부 확대) |
| `pitch_deg` | 7.24 | 내림각(deg) | 크게 = 먼 곳이 화면 위로 올라간다 (전방거리 축척 변화) |
| `yaw_deg` | -0.2 | 좌우틀어짐(deg) | 격자가 좌우로 회전한다 (차가 정면을 안 볼 때) |
| `roll_deg` | -1.6 | 기울기(deg) | 화면이 갸우뚱한 정도 (수평선이 기울었을 때) |
| `grid_x0` | 0.45 | 격자_앞(m) | **라이다 중심**에서 첫 가로줄까지 거리. 검증용 격자만 이동 |
| `grid_y0` | 0.0 | 격자_옆(m) | 중앙 세로줄의 좌우 위치 (0=정면). 검증용 격자만 이동 |
| `fx` | 789.01 | fx | **가로 축척**. 작게 = 지면 좌우가 넓게 계산됨 |
| `fy` | 874.56 | fy | 세로 축척. 전방거리는 높이/내림각으로 맞추는 게 낫다 |
| `out_fx` | 847.52 | 출력화각 | 보정영상을 얼마나 넓게 담을지. 작게 = 더 넓게. **BEV 좌표엔 영향 없음** |
| `dist_cx` | 966.76 | 왜곡중심X | 좌우 오차가 서로 다를 때 만지는 값 — 왜곡의 대칭 중심 |
| `dist_cy` | 540.25 | 왜곡중심Y | 위아래 오차가 다를 때 |
| `dist_k1` | -0.374 | 왜곡k1 | 보정 세기. 더 음수 = 더 세게 편다 |
| `undistort` | true | — | 이 H 를 왜곡보정된 픽셀 기준으로 잡았는지 여부 |

`fx/fy/dist_cx/dist_cy/dist_k1` 은 그냥 기록이 아니라 **`K`/`D` 그 자체**다. 저장할 때
`K = [[fx,0,dist_cx],[0,fy,dist_cy],[0,0,1]]`, `D[0] = dist_k1` 로 기록된다
(`ground_fit.py:374-380`, `690-695`). camera.yaml 의 K(18-27)·D(2-7)와 숫자가 정확히
일치하는 것을 확인할 수 있다.

주의할 함정 하나(`ground_fit.py:371-373` 주석): 조절되는 `fx/fy` 는 **왜곡모델 K** 에
들어가야 한다. 출력 `new_K` 에만 넣으면 뒤에서 `inv(new_K)` 로 상쇄돼 아무 효과가 없다.
픽셀→각도 변환을 정하는 것이 이 `fx` 이고, 그게 곧 지면 축척이기 때문이다.

### 2.10 car_mask_v — 차체 가림선 (camera.yaml:29-31)

```
car_mask_v: 951.4285714285714     # 1080p 보정영상 기준 픽셀 행(v)
car_mask_note: 이 v 아래는 차체(바퀴·라이다)라 지면이 아니다. ...
```

화면 아래쪽에는 우리 차의 라이다 원통·범퍼·바퀴가 찍힌다. 이건 지면이 아닌데도 `H` 를
통과하면 **x≈0.1~0.2m 지점의 가짜 차선점**으로 둔갑한다(`bev.py:144-151`,
`yolo_node.py:130-131`). 그래서 이 v 아래를 통째로 0 으로 지운다.

| 항목 | 내용 |
|---|---|

| 뷰어 표시 | `yolo_node.py:390` `bev.car_mask_row(...)` |

환산이 왜 필요한가: `car_mask_v=951` 은 1080p 기준값이라, 640x480 프레임에 그대로 쓰면
화면 밖(480 < 951)이라 마스킹이 통째로 무효가 된다(`bev.py:463-465` 주석).

격자 실측 오차는 1~3cm 였다.

## 3. tuning.yaml — 노드 튜닝 파라미터 (212줄)

### 3.1 [SIM] 태그의 의미 ★

파일 머리말(`tuning.yaml:2-7`)에 이렇게 적혀 있다.

> `# [SIM]` = 시뮬(예선) 유래 값 — 본선 실차에서 재튜닝 대상.

즉 **[SIM] 이 붙은 값은 "시뮬레이터에서는 잘 됐던 값"일 뿐 실차에서 맞다는 보장이 없다.**
예선은 시뮬, 본선은 1/10 실차라 관성·타이어 그립·모터 응답·카메라 화각이 전부 다르다.
실차 주행이 이상하면 **[SIM] 표시된 항목부터 의심하는 것**이 정해진 순서다.
반대로 [SIM] 이 없는 값은 실차 계약값이거나 본선에서 새로 정한 값이다.
`[SIM=640]` 처럼 괄호가 붙은 건 "예선 값은 640이었고 실차에서 416으로 낮췄다"는 뜻이다.

차량 고유 실측값(트림/기계스톱/데드존/`cmd_to_ms`)은 이 파일이 아니라 `car.yaml` 로
분리돼 있다 — 성향 튜닝과 하드웨어 실측을 섞지 않기 위해서다. (트림·기계스톱·데드존이
각각 무슨 뜻인지는 4.1 에서 푼다. 짧게만 말하면 트림은 "직진의 영점", 기계스톱은 "핸들이
물리적으로 더 안 꺾이는 한계", 데드존은 "명령을 줘도 바퀴가 안 도는 죽은 구간"이다.)

### 3.2 yolo_node (tuning.yaml:9-23)

### 3.7 CONE 왼쪽 콘 피팅 (tuning.yaml:60-77)

왼쪽 콘 줄을 다항식으로 피팅해 기준선을 만드는 부분이다. 전부 예선 `_tick_cone` 이식.

**피팅(fitting)** 은 흩어진 점들을 가장 잘 지나가는 곡선식 하나를 찾는 것이다. 왼쪽에 놓인
콘들의 좌표가 점으로 들어오면, 그 점들을 관통하는 선 `y = a·x² + b·x + c` 를 구해 "왼쪽
콘 줄은 이렇게 생겼다"는 식 하나로 압축한다. 여기서 `a`(x² 계수)가 **곡률항** — 얼마나
휘었는지를 담는 항이고, `b` 가 **기울기**다. 점이 적거나 앞뒤로 벌어진 폭(**스팬**)이
좁으면 2차식은 아무렇게나 휘어버려서 위험하므로, `cone_fit_deg2_span`(2.0m) 이상 벌어져
있고 점이 3개 이상일 때만 2차식을 쓰고 그 외에는 직선으로 맞춘다. `cone_fit_curve_max`,
`cone_fit_slope_max` 는 그렇게 구한 `a`, `b` 가 말이 안 되게 큰 값이면 잘라내는 안전장치다.

`cone_fit_smooth_alpha` 의 **IIR 평활**은 이 문서에서 여러 번 나오는 방식이라 여기서 한 번
제대로 풀어 둔다. 매번 새로 구한 값을 그대로 쓰면 한 스캔 튄 값에 기준선이 통째로 흔들린다.
그래서 직전 값을 조금씩 새 값 쪽으로만 끌어당긴다.

```
 새값 = 이전값 + α × (이번에 측정한 값 − 이전값)
      = (1−α) × 이전값 + α × 측정값          (path_planner_node.py:941-946)
```

`α`(alpha)가 그 "끌어당기는 비율"이다. α = 0.2 면 이번 측정값을 20%만 반영하고 80%는
과거를 유지한다는 뜻이다. **α 가 작을수록 부드럽지만 반응이 느리고, 클수록 반응이 빠른
대신 떨린다.** α = 1 이면 평활이 없는 것과 같다. IIR 은 "무한 임펄스 응답"의 약자로,
옛날 값이 완전히 사라지지 않고 계속 조금씩 남아 있다는 뜻이다 — 과거 몇 개를 딱 잘라
평균 내는 방식(이동평균)과 달리 기억할 값이 직전 결과 하나뿐이라 가볍다.

`cone_coast_decay` 의 **coast(코스팅)** 는 콘이 잠깐 안 보일 때 직전 피팅 결과를 계속
쓰되, 못 본 스캔이 쌓일수록 곡률항 `a` 를 `1 − (놓친 스캔 수 × 0.2)` 배로 줄여 점점
직선에 가깝게 만드는 것이다(`path_planner_node.py:937-939`). "안 보이면 일단 직전 판단으로
관성 주행하되, 오래되면 과감한 곡선 판단은 버린다"는 뜻이다.

### 3.8 정지선(STOP) / 지름길(SHORTCUT) (tuning.yaml:78-94)

★ 2026-07-31 에 추가된 핵심 항목이 여기 있다.

```
obj_v_ref_height: 480.0    # v 임계값들이 튜닝된 기준 높이 — 바꾸지 말 것
```

**무슨 문제를 푸는가.** `/detect/objects` 는 표지판 박스의 아래쪽 픽셀 행 `v` 를 실어
보내고, planner 는 "v 가 크면 가까이 왔다"로 거리를 대신 판단한다. 그런데 `stop_v_threshold:
312` 같은 숫자는 **480p 화면에서 튜닝된 픽셀값**이다. 실차 카메라는 1080p 라 같은 거리에서
v 가 2.25배 큰 값으로 나온다. 그대로 비교하면 정지선이 아주 멀리 있을 때 이미 트리거된다.

**어떻게 푸는가.** `path_planner_node._resolve_obj_v_scale()`(`path_planner_node.py:413-443`)
가 기동할 때 `camera.yaml` 의 `image_height` 를 읽어 배율을 만든다.

```
scale = obj_v_ref_height / image_height = 480 / 1080 = 0.4444
비교 직전에:  v_bot = 발행된 v × scale          (path_planner_node.py:453)
```

즉 **해상도를 바꿔도 `*_v_threshold` 값들은 그대로 두면 된다.** 그래서
`obj_v_ref_height` 는 "바꾸지 말 것"이다 — 이걸 건드리면 480p 기준으로 튜닝된 임계값
전부(`stop_v_threshold`, `cross_v_threshold`, `child_start_v_thr`, `child_end_v_thr`)가
동시에 어긋난다. `image_height` 를 못 읽으면 배율 1.0 으로 가되 경고를 남긴다
(`:432-437`) — 조용히 틀리지 않게 만든 것이다.

아래 표에 `heading`, `yaw` 가 나오므로 먼저 풀어 둔다. **yaw** 는 차를 위에서 내려다봤을 때
좌우로 얼마나 돌아가 있는지의 각도다(고개를 좌우로 젓는 방향). **heading** 은 "지금 향하고
있는 방향"이라는 뜻으로, yaw 와 사실상 같은 것을 가리키지만 3.12 에서는 차가 아니라
**경로가 향한 방향**을 뜻하는 데도 쓴다. 어느 쪽이든 **조향각(핸들을 얼마나 꺾었나)과는
다른 것**이다 — 조향각은 입력이고 heading 은 결과다.

| 항목 | 기본값 | 뜻 / 올리면 | [SIM] |
|---|---|---|---|
| `obj_v_ref_height` | 480.0 | v 임계값의 기준 해상도. **변경 금지** | |
| `stop_v_threshold` | 312.0 | STOP 박스 하단 v. 올리면 **더 가까이 가서** 반응 | [SIM] |
| `cross_v_threshold` | 278.0 | CROSSROAD_OUT 판정 v | [SIM] |

### 3.12 motion_node (tuning.yaml:136-206)

거의 전부 [SIM] 이다 — 즉 **실차 재튜닝 1순위 구역**이다. 기본값은 `motion_node.py` 의
`_prm(name, 기본값)` 호출(`motion_node.py:190-193`)에 그대로 박혀 있다.

#### 3.12.0 ★ 먼저 "곡률비"부터 — 이 절 전체의 손잡이

3.12 의 값 중 이름에 `ratio` 가 붙은 것(`steer_curve_switch_ratio`, `corner_enter_ratio`,
`corner_exit_ratio`, `corner_exit_unwind_start_ratio`/`_end_ratio`)은 **전부 같은 종류의
숫자 하나를 놓고 그은 금**이다. 그 숫자가 곡률비다. 이걸 모르면 이 절의 숫자들이 전부
정체불명이 되므로 여기서 먼저 푼다.

**곡률비란 "지금 눈앞의 경로가 얼마나 굽었나"를 0~1 한 숫자로 압축한 값이다.**
0 이면 완전한 직선, 1 이면 "이 이상은 더 안 센다" 할 만큼 굽은 상태다. 단위는 없다.
이름이 "비(比)"인 이유는 두 곡률을 나눈 값이라서가 아니라, **직선으로 칠 기준과 최대
커브로 칠 기준 사이의 어디쯤인가를 0~1 로 환산한 비율**이기 때문이다.

먼저 **곡률(curvature, κ)** 자체부터. 곡률은 선이 굽은 정도이고, 값은 **그 지점에서 그리는
원의 반지름의 역수**다(κ = 1/R). 직선은 반지름이 무한대라 κ=0 이고, 작게 도는 커브일수록
κ 가 크다. 이 코드가 쓰는 기준값으로 환산하면 감이 온다.

| 곡률 κ | 회전반지름 | 이 코드에서의 의미 |
|---|---|---|
| 0.018 | 약 55m | 여기부터 "굽었다"고 세기 시작 (`preview_curv_start`) |
| 0.080 | 약 12.5m | 여기면 곡률 쪽 점수는 만점 1.0 (`preview_curv_full`) |

**곡률비를 만드는 계산** (`motion_node.py:565-621`, `623-665`). 경로점 `(x, y)` 를 받아
서로 다른 두 갈래를 각각 0~1 로 만든 뒤 **둘 중 큰 값**을 채택한다. 하나만 크게 나와도
커브로 치겠다는 뜻이다. 아래 표의 첫 줄은 두 종류에 공통이고, 둘째 줄은 조향용에만,
셋째 줄은 속도용에만 쓰인다.

| 갈래 | 무엇을 보나 | 0→1 로 펴는 구간 |
|---|---|---|
| 곡률 갈래 (공통) | 경로 곡률 κ 의 85퍼센타일 | `preview_curv_start`(0.018) → `preview_curv_full`(0.080) |
| 꺾임 갈래 (조향용) | 경로의 heading 이 시작점 대비 얼마나 돌았나(85퍼센타일, deg) | `steer_heading_start_deg`(4°) → `steer_heading_full_deg`(20°) |
| 횡편차 갈래 (속도용) | 경로가 시작점 대비 좌우로 얼마나 벌어지나(최댓값, m) | `preview_lateral_start_m`(0.45m) → `preview_lateral_full_m`(1.35m) |

여기서 **85퍼센타일**은 값들을 크기순으로 줄 세워 85% 지점의 값을 뽑는 것이다. 최대값을
쓰면 튄 점 하나에 통째로 휘둘리고, 평균을 쓰면 앞쪽의 굽은 구간이 직선 구간에 묻혀 사라진다.
그 사이를 택한 것이다.

**곡률비는 두 종류가 있고 쓰임이 다르다.** 이걸 구분해야 표의 숫자들이 읽힌다.

| 이름 | 어디까지 보나 | 무엇을 결정하나 |
|---|---|---|
| `steer_ratio` (조향용) | 가까운 `steer_gain_distance_m`(2.4m) 구간과 먼 `steer_preview_distance_m`(5.5m) 구간을 각각 계산해 **큰 쪽** (`:352-356`) | 얼마나 **세게 꺾을지** — 커브 게인 전환, 직진 부스트 허용, unwind 트리거 |
| `preview_ratio` (속도용) | 전방 `preview_distance_m`(5.0m) 한 구간 (`:351`) | 얼마나 **속도를 줄일지** — 코너 진입/이탈 판정, 예측 감속 |

**곡률비가 실제로 쓰이는 자리 네 곳** — 3.12 의 `ratio` 값들이 전부 여기 걸린다.

| 조건 | 일어나는 일 | 코드 |
|---|---|---|
| `steer_ratio` ≥ `steer_curve_switch_ratio`(0.50) | 커브 게인(1.62/2.22)으로 전환. 미만이면 직진 게인(0.08) | `:509-514` |
| `steer_ratio` ≤ 0.50 (같은 값) | 직진 부스트 허용 게이트가 열림 | `:366`, `:76` |
| `preview_ratio` ≥ `corner_enter_ratio`(0.55) / ≤ `corner_exit_ratio`(0.35) | 코너 상태 진입 카운터 +1 / 0 으로 리셋 | `:359-363` |
| 직전 `steer_ratio` ≥ 0.45 였는데 지금 ≤ 0.22 | corner-exit unwind 발동 (커브가 풀리는 순간을 잡는다) | `:389-393` |

★ **꼭 알아야 할 연동 하나.** `preview_curv_start`/`_full`(3.12 속도 표에 있는 그 값)은
이름 때문에 속도 전용처럼 보이지만, 실제로는 **`steer_ratio` 계산에도 같이 쓰인다**
(`motion_node.py:613-616`). 즉 이 두 값을 만지면 예측 감속만이 아니라 **직진↔커브 게인
전환 시점까지 동시에 움직인다.** 조향만 손보고 싶으면 `steer_curve_switch_ratio` 쪽을,
속도만 손보고 싶으면 `corner_enter_ratio`/`corner_exit_ratio` 쪽을 만지는 것이 안전하다.

**추종 게인 (tuning.yaml:139-156)**

여기서 **추종(pursuit)** 은 "앞쪽에 목표점을 하나 찍고 그 점을 향해 핸들을 꺾는" 방식을
말한다(순수추종, pure pursuit 계열). 이 코드의 조향각은 성격이 다른 두 항을 더해서 만든다
(`motion_node.py:501-527`).

```
 조향각 = pursuit_gain × (그 점을 바라보는 각도 — 내 정면에서 좌우로 몇 도 벌어져 보이나)
        + heading_gain × (그 지점에서 경로가 향한 각도 — 경로가 내 정면 대비 얼마나 틀어졌나)
```

앞 항은 **위치 오차**(옆으로 벗어난 것)를 잡고, 뒤 항은 **방향 오차**(비뚤어진 것)를 잡는다.
차가 차선 한가운데 있어도 비스듬히 서 있으면 앞 항은 0에 가깝고 뒤 항이 일한다.
**게인(gain)** 은 그 오차를 조향각으로 바꿀 때 곱하는 배율이다 — 크면 세게 잡아당기고,
너무 크면 지나쳐서 좌우로 사행(위빙)한다. 아래 표에서 직진용 게인(0.08)과 커브용 게인(1.62/2.22)이
20배 넘게 차이 나는데, 그 둘을 갈아 끼우는 스위치가 위의 `steer_curve_switch_ratio` 다.

| 항목 | 기본값 | 올리면 |
|---|---|---|
| `straight_pursuit_gain` / `straight_heading_gain` | 0.08 / 0.08 | 직진 중 미세 보정이 세짐 (과하면 사행) |
| `straight_boost_pursuit_gain` / `_heading_gain` | 0.40 / 0.40 | 부스트 상태의 보정 세기 |
| `curve_pursuit_gain` / `curve_heading_gain` | 1.62 / 2.22 | 커브에서 확 꺾음 (과하면 안쪽 파고듦) |
| `s_steer_focus_x` | 3.7 | S존 전용 전방주시거리(m) |
| `steer_focus_sigma` | 1.8 | 가우시안 가중 폭(m). 올리면 여러 점을 뭉뚱그려 봄 |
| `steer_focus_base` / `_k` / `_min` / `_max` | 3.8 / 0.055 / 4.2 / 5.0 | 속도비례 전방주시: `clip(base + k×직전속도, min, max)` |
| `steer_gain_distance_m` | 2.4 | 게인 산출 기준 거리(m) |
| `steer_preview_distance_m` | 5.5 | 앞을 내다보는 거리(m) |
| `steer_heading_start_deg` / `_full_deg` | 4.0 / 20.0 | heading 항이 켜지기 시작/최대가 되는 각도 |
| `steer_curve_switch_ratio` | 0.50 | 직진↔커브 게인 전환 곡률비 |

표 가운데 `steer_focus_*` 무리는 **전방주시거리(lookahead)** 를 정하는 값들이다. 사람이 운전할
때 범퍼 바로 앞이 아니라 저 앞을 보는 것과 같다. 이 코드는 경로 위의 여러 점을 다 쓰되,
`focus_x` 라는 기준 지점에 가까운 점일수록 크게 치는 **가우시안 가중**을 준다 —
가중치 = `exp(−((거리−focus_x)/sigma)²)` (`motion_node.py:538`). 종 모양 곡선이라 기준
지점에서 멀어질수록 중요도가 매끄럽게 떨어진다는 뜻이고, `steer_focus_sigma`(1.8m)가 그
종의 폭이다. 넓히면 여러 점을 뭉뚱그려 보게 되어 부드럽지만 둔해진다.
그리고 `focus_x` 자체는 고정이 아니라 **속도에 비례해서** 정해진다
(`clip(base + k×직전속도, min, max)`, `:535-537`) — 빠를수록 멀리 봐야 좌우로 흔들리지
않기 때문이다.

**직진 부스트 (tuning.yaml:157-162)**

이름은 "부스트"지만 **속도가 아니라 조향 게인을 키우는 장치**다. 부스트 레벨이 오르면
평상시 게인(`straight_pursuit_gain` 0.08)이 부스트 게인(`straight_boost_pursuit_gain`
0.40) 쪽으로 섞인다(`motion_node.py:515-522`).

작동은 2단이다.

```
 1단 게이트: 곡률비 steer_ratio ≤ steer_curve_switch_ratio(0.50) 일 때만 켠다
             = "지금 경로가 직선인가"  (motion_node.py:366, 76)
 2단 세기  : 경로의 평균 heading 오차 line_angle_error(deg) 로 정한다
             = "직선인데 얼마나 틀어져 있나" (motion_node.py:607)
```

여기서 쓰는 각도는 **조향각이 아니라 경로의 heading 오차**다. 헷갈리지 마라.

| 항목 | 기본값 | 뜻 |
|---|---|---|
| `straight_boost_off_deg` | 0.0 | 이 각도 이하면 부스트 0 (램프 시작점) |
| `straight_boost_on_deg` | 5.0 | 여기까지 오르면 기본 부스트(레벨 1.0) 도달 |
| `straight_boost_full_deg` | 10.0 | 여기까지 오르면 최대 부스트 도달 |
| `straight_boost_max_level` | 1.8 | 그 최대 부스트 레벨 |
| `straight_boost_blend_alpha` | 0.45 | 부스트 진입/이탈 평활. 올리면 급격 |

표의 "램프"는 **ramp**, 즉 계단처럼 툭 튀지 않고 비탈길처럼 서서히 올라가는 구간을 말한다.
`off_deg`(0°)에서 `on_deg`(5°)까지가 부스트 0→1 로 올라가는 비탈이고, 거기서 `full_deg`(10°)
까지가 1→1.8 로 더 올라가는 두 번째 비탈이다. 문턱 하나로 켜고 끄면 경계에서 덜컥거리므로
비탈로 만든 것이다. `straight_boost_blend_alpha` 는 3.7 에서 푼 **IIR 평활과 같은 방식**으로,
계산된 목표 부스트 값을 현재 레벨이 매 틱 45%씩 따라가게 한다(`motion_node.py:381-384`).

★ **방향에 주의해라. 각도 오차가 커질수록 부스트가 세진다**(`motion_node.py:367-378`).
0°→5° 구간에서 레벨이 0→1 로 오르고(제곱 곡선이라 초반은 완만), 5°→10° 구간에서
1→1.8 로 더 오른다. "직선인데 조금 틀어져 있으면 더 세게 잡아당겨라"가 이 로직의 뜻이다.
"조향각이 작을 때 켜진다"가 아니다 — 직선 여부는 1단 곡률비 게이트가 판단한다.

부스트가 허용되는 최대 곡률비는 별도 항목이 아니라 `steer_curve_switch_ratio` 와 같은
값으로 묶여 있다(`motion_node.py:76`) — 예선과 동일하게 유지한 결정이다.

**unwind(언와인드)** 는 감아 놓은 것을 되푼다는 뜻이다. 커브를 다 돌고 나면 핸들을 원위치로
돌려야 하는데, 조향 스무딩 때문에 되돌아오는 게 늦으면 커브 출구에서 반대쪽으로 밀린다.
그래서 "커브가 끝났다"고 판단되는 순간 조향각을 한 번 더 줄여 준다. 트리거 조건은 **직전
틱의 (가까운 구간) 곡률비가 0.45 이상이었는데 이번 틱에 0.22 이하로 떨어졌을 때**다
(`motion_node.py:389-393`). 두 문턱이 다른 것은 히스테리시스와 같은 이유다 — 하나로 두면
경계에서 계속 발동한다. 발동하면 5프레임 동안 조향 크기를 `unwind_scale`(0.80) 배로
줄인다(`:542-551`). 그래서 이 값은 **작을수록 더 세게 되감는다.**

**조향 스무딩 (tuning.yaml:169-174)**

계산으로 나온 조향각을 그대로 서보에 보내면 매 틱 값이 조금씩 튀어 핸들이 부르르 떤다.
그래서 세 단계를 순서대로 거친다(`motion_node.py:553-563`).

```

 3) 스텝 상한: 그렇게 나온 변화량을 ±12 로 자른다 (한 틱 = 50ms)
```

### 4.1 motion_node 블록 (car.yaml:9-22)

표를 보기 전에 이 블록에만 나오는 용어 넷을 푼다.

- **트림(trim)** — 영점 보정값이다. 이 차는 조향 명령 0 을 줘도 바퀴가 똑바로 안 서고,
  실제로는 **-20** 을 줘야 직진한다. 그 -20 이 `steer_trim` 이다. 코드는 계산한 조향값에
  항상 이 트림을 더해서 내보낸다(`car_interface.py:113-115`). 조립 오차·링키지 유격 때문에
  차마다 다르므로 실측값이고, RC 송신기의 트림 노브와 같은 개념이다.
- **기계 스톱** — 서보가 더 이상 안 꺾이는 물리적 한계다. `steer_limit_left/right` 가 그
  한계이고, 트림(-20)을 기준으로 잰 상대값이다. 실측 -34/+64 에서 2씩 마진을 뺀 -32/+62 을
  쓴다. 한계를 넘겨 명령하면 서보가 벽을 밀며 발열·소음이 나므로 코드가 먼저 자른다.
- **슬루레이트(slew rate, `slew_*_per_tick`)** — "한 틱에 이만큼보다 더 빨리 바뀌지 마라"는
  변화량 제한이다. 목표값이 아무리 멀어도 매 틱 정해진 폭씩만 다가간다
  (`car_interface.py:116-129`).
  속도 쪽에 이게 꼭 필요한 이유가 `slew_speed_per_tick` 옆에 적힌 **센서리스 ESC** 다 —
  ESC(전자변속기)는 모터를 돌리는 컨트롤러인데, 이 차 것은 회전 센서 없이 모터가 만드는
  역기전력만 보고 회전 위치를 추측한다. 그래서 **멈춘 상태에서는 볼 신호가 없어** 정지에서
  고속으로 직행하면 헛돌거나 덜컥거린다. 서서히 올려야 물린다.
- **데드존(deadzone)** — 명령을 줘도 바퀴가 아예 안 도는 죽은 구간이다. 이 차는 speed 명령
  4 미만이면 안 구른다(실측). 코드는 0 과 4 사이 명령이 들어오면 애매하게 흘려보내지 않고
  **4로 올리거나 0으로 내려버린다**(2 이상이면 4, 미만이면 0 — `car_interface.py:135-147`).
  "가라는 명령을 줬는데 안 가는" 상태를 없애기 위한 처리다.

| 항목 | 값 | 뜻 / 어디서 쓰나 |
|---|---|---|
| `steer_trim` | -20.0 | **직진 트림**: 명령 -20 이 실제 직진 (실측). `car_interface.py:52` |
| `steer_scale` | 0.42 | 논리 조향(±100) → 기계 조향 배율. `car_interface.py:53` |
| `steer_limit_left` | -32.0 | 트림 기준 좌 기계 스톱 (실측 -34, 마진 2) |
| `steer_limit_right` | 62.0 | 트림 기준 우 기계 스톱 (실측 +64, 마진 2) |
| `slew_angle_per_tick` | 8.0 | 20Hz 틱당 조향 출력 변화 상한 |
| `slew_speed_per_tick` | 1.5 | 틱당 속도 변화 상한 — **센서리스 ESC 는 정지→고속 직행 불가** |
| `speed_deadzone` | 4.0 | 명령 4 미만은 안 구른다 (실측) |
| `allow_reverse` | false | 자율주행 경로는 후진 금지 |
| `cmd_to_ms` | 0.08 | speed 명령 ×0.08 = m/s (실측검증, eRPM = 4614×m/s) |
| `speed_min_drive` | 5.0 | 주행 최저 명령 — 데드존(4) 초과 보장 |

위 표에서 마지막 `speed_min_drive` 를 뺀 **9개**가 `lib/car_interface.py` 의
`DEFAULT_CFG`(`car_interface.py:26-36`)와 **키가 1:1로 같다.** `motion_node.py:134-135`
가 `DEFAULT_CFG` 의 키 목록을 그대로 돌면서 파라미터를 읽어 `CarInterface` 에 넘긴다.
`speed_min_drive` 는 `CarInterface` 키가 아니라 motion_node 가 따로 읽는 중재 하한이다
(`motion_node.py:131`) — car.yaml 에서도 `# ---- 중재 하한 ----` 로 구분해 놨다.
변환 순서는 `car_interface.py:97-103` 에 요약돼 있다:

```
 조향: rel = clamp(angle_cmd × steer_scale, left, right)
       out = steer_trim + rel  →  slew 제한
 속도: [0,100] 클립 → 데드존 스냅 → slew 램프
```

읽는 법. **clamp/클립**은 "정해진 범위 밖으로 나가면 경계값으로 잘라낸다"는 뜻이고
(120을 주면 100으로), **스냅**은 "애매한 값을 정해진 값으로 붙여 버린다"는 뜻이다(위의
데드존 처리). **램프**는 앞서 나온 대로 한 번에 안 가고 비탈처럼 서서히 간다는 뜻이다.
순서가 중요한데, **트림을 더하는 것이 기계 스톱 클램프보다 뒤**라는 점이 핵심이다 —
좌우 한계가 트림을 기준으로 잰 값이기 때문이다.

표의 `cmd_to_ms` 옆에 나오는 **eRPM(electrical RPM)** 은 바퀴의 분당 회전수가 아니라
**모터 내부의 전기적 회전수**다. 모터 극(자석 쌍) 수만큼 곱해져 나오는 값이라 바퀴 회전수보다
훨씬 큰 숫자가 찍힌다. 이 차는 실측으로 eRPM = 4614 × (m/s) 관계라, 반대로 나눠서 속도를
역산한다(4.3 의 `erpm_per_ms`).

`speed_min_drive: 5.0` 옆의 `# 재도입 금지 버그 7 대응` 주석이 중요하다. 명령 4 미만은
바퀴가 안 도는데 중재 결과가 그 아래로 내려가면 "가라는데 안 가는" 상태가 된다.
그래서 하한을 데드존보다 확실히 위(5.0)로 잡았다.

### 4.2 teleop_node 블록 (car.yaml:24-43)

수동 조종 노드도 같은 실차 변환을 쓴다. 값이 motion 과 대부분 같고 **`allow_reverse` 만
true** 다 — 텔레옵은 후진을 허용한다(`car.yaml:34`).

| 항목 | 값 | 뜻 |
|---|---|---|
| `rate_hz` | 20.0 | 모터는 20Hz 연속 수신이 필요 |
| `speed_step` | 2.0 | `w`/`s` 한 번당 목표속도 변화 |
| `angle_step` | 5.0 | `a`/`d` 논리 조향 스텝 |
| `angle_step_big` | 24.0 | `A`/`D` 큰 스텝 |
| `speed_max` / `speed_min` | 100.0 / -50.0 | 명령 한계 (후진은 allow_reverse 전제) |
| `watchdog_sec` | 3.0 | 무입력 시 감속 시작 |

**워치독(watchdog)** 은 "입력이 끊기면 스스로 안전한 쪽으로 넘어가는 감시 타이머"다.
개가 집을 지키다 이상하면 짖는다는 비유에서 온 이름으로, 정해진 시간 안에 새 입력이
안 들어오면 "보내는 쪽이 죽었다"고 보고 미리 정해둔 동작(여기서는 감속·정지)을 한다.
사람이 키보드에서 손을 뗀 채 차가 계속 달리는 상황을 막는 장치다.

`watchdog_sec: 3.0` 은 **토픽 계약 워치독 0.3초와는 다른 것**이다. 후자는 파라미터가
아니라 상수다(`lib/drive_cmd.py` 의 `DRIVE_CMD_STALE_SEC=0.3`, `TELEOP_STALE_SEC=0.3` —
`car.yaml:5-6` 주석).

### 4.3 car_state_node 블록 (car.yaml:45-50)

| 항목 | 값 | 뜻 |
|---|---|---|
| `erpm_per_ms` | 4614.0 | eRPM = 4614 × m/s (실측검증). 속도 환산의 기준 |
| `tacho_scale` | 0.0 | tacho→m 환산계수. **0 = 미실측** → eRPM 적분 폴백 사용 |
| `low_voltage_warn` | 8.6 | NiMH 완충 10~11V, 8.6V 미만이면 경고 |

`tacho_scale: 0.0` 은 "아직 안 쟀다"는 뜻이고 코드가 그 경우 다른 방법으로 우회한다.
0을 "쓰지 말라는 뜻"으로 쓴 관습이니 실측하면 채워 넣으면 된다.

## 5. launch 파일 3개

```
  ros2 launch track_drive sensors.launch.py   ← 센서 먼저 (카메라/라이다/IMU)
  ros2 launch track_drive drive.launch.py     ← 주행 4노드 (규정 실행 명령)
  ros2 launch track_drive viewer.launch.py    ← 디버그 뷰어 (규정상 주행과 분리)
```

| 파일 | 띄우는 것 | 언제 쓰나 |
|---|---|---|
| `sensors.launch.py` | usb_cam + xycar_lidar + xycar_imu | 실차에서 항상 먼저 |
| `drive.launch.py` | yolo, path_planner, motion, car_state | 본선 주행 (규정 명령) |
| `viewer.launch.py` | yolo_lane_viewer 1개 | 디버깅할 때만 |

### 5.1 drive.launch.py — 주행 4노드

핵심은 파라미터 두 개를 순서대로 넘기는 부분이다(`drive.launch.py:21-25`).

```python
params = [ .../config/tuning.yaml,
           .../config/car.yaml ]     # 뒤가 이긴다
```

예선 대비 변경점이 파일 머리말에 적혀 있다(`drive.launch.py:7-8`): 6노드+뷰어 → 4노드.
YOLO 3노드와 integration 노드가 `yolo` 하나로 합쳐지고 `car_state` 가 신설됐다.
**뷰어는 규정상 주행 launch 에 넣지 않는다.**

### 5.2 sensors.launch.py — 센서 브링업 (실차 신규)

카메라 파라미터가 여기 박혀 있다(`sensors.launch.py:43-54`).

| 파라미터 | 값 | 이유 |
|---|---|---|
| `video_device` | `/dev/video0` | 실차에서 다르면 여기만 수정 |
| `pixel_format` | `mjpeg2rgb` | ★ **YUYV 1080p 는 6fps 밖에 안 나온다** (실측) |
| `image_width/height` | 1920 / 1080 | ★ `camera.yaml` 과 반드시 일치 |
| `framerate` | 30.0 | MJPG 1920x1080 이 지원하는 유일한 값 |

★ **MJPG 강제 이유** (`sensors.launch.py:48-49`): `v4l2-ctl --list-formats-ext` 로 실측한
결과 이 카메라는 YUYV(무압축) 1920x1080 에서 6fps 밖에 안 나온다. USB 2.0 대역폭이
모자라기 때문이다. MJPG(카메라 내부 JPEG 압축)여야 30fps 가 나온다. 그래서
`mjpeg2rgb` 로 받아서 `/image_raw` 를 `rgb8` 로 낸다.

★ **해상도 일치가 왜 계약인가** (`sensors.launch.py:45-47` 주석): 여기 해상도를 바꾸면
`new_K` 의 `cx, cy`(=폭/2, 높이/2)가 달라지고 → `H` 가 통째로 무효 → BEV 좌표가 전부
틀어진다. 바꿔야 한다면 **camera.yaml 을 다시 캘리브해야 한다.** 한쪽만 고치면 안 된다.

`respawn=True, respawn_delay=2.0`(`:41-42`)도 실측 대응이다. usb_cam 은 첫 실행이 flaky
해서(간헐적으로 죽는다) 죽으면 2초 뒤 자동 재기동하게 해 뒀다.

**`_include_if_present` 기법** (`sensors.launch.py:23-32`)

```python
def _include_if_present(pkg):
    try:
        share = get_package_share_directory(pkg)
    except PackageNotFoundError:
        return LogInfo(msg="... 패키지 없음 — 실차에서만 기동됨 (스킵)")
    candidates = sorted(glob(.../launch/*.launch.py))
    if not candidates:
        return LogInfo(msg="... launch 파일 없음 (스킵)")
    return IncludeLaunchDescription(PythonLaunchDescriptionSource(candidates[0]))
```

`xycar_lidar` / `xycar_imu` 는 **실차에만 설치돼 있는 패키지**다. 그냥 include 하면 개발
PC 에서 launch 전체가 죽는다. 그래서 없으면 예외를 잡아 **경고 로그만 남기고 넘어간다.**
덕분에 같은 launch 파일 하나로 개발 PC(카메라만)와 실차(전부)를 모두 돌릴 수 있다.
"환경마다 다른 launch 를 만들지 않는다"는 것이 이 기법의 요점이다.

### 5.3 viewer.launch.py — 디버그 뷰어

`yolo_lane_viewer` 하나만 띄운다(`viewer.launch.py:15-17`). OpenCV 창이 뜨므로 모니터나
X 포워딩이 필요하다. 예선에는 `drive.launch.py` 안에 섞여 있던 것을 규정 때문에 분리했다
(`viewer.launch.py:2`, `7`).

## 6. setup.py / package.xml / setup.cfg

### 6.1 console_scripts — 파일명과 실행이름이 다르다 ★함정

`setup.py:29-42` 의 `entry_points` 가 "실행 이름 = 모듈:함수" 매핑을 만든다.
**`console_scripts`** 란 "이 이름으로 명령을 치면 저 파이썬 파일의 저 함수를 실행하라"는
등록표다. 빌드할 때 그 이름의 작은 실행 스크립트가 자동으로 생성되기 때문에, `ros2 run`
에 쓰는 이름은 **파일명이 아니라 여기 등록한 이름**이 된다.

| 실행 이름 (`ros2 run` 에 쓰는 것) | 실제 파일 |
|---|---|
| `yolo` | `track_drive/yolo_node.py` 의 `main()` |
| `path_planner` | `track_drive/path_planner_node.py` |
| `motion` | `track_drive/motion_node.py` |
| `car_state` | `track_drive/car_state_node.py` |
| `teleop` | `track_drive/teleop_node.py` |
| `yolo_lane_viewer` | `track_drive/yolo_lane_viewer_node.py` |

★ 그래서 이렇게 써야 한다.

```
  ros2 run track_drive yolo          ← 맞다
  ros2 run track_drive yolo_node     ← 틀리다 (그런 실행파일 없음)
```

launch 파일도 이 실행 이름을 쓴다(`drive.launch.py:32-35` 의 `node("yolo")` 등).
설치 결과를 보면 `install/track_drive/lib/track_drive/` 아래에 `yolo`, `motion`,
`path_planner`, `car_state`, `teleop`, `yolo_lane_viewer` 여섯 개의 실행 스크립트가 생겨
있는 것을 확인할 수 있다. 그 위치는 `setup.cfg` 가 정한다:

```
[install]
install_scripts=$base/lib/track_drive     ← ROS2 규약 위치
```

`packages=[package_name, package_name + '.lib']`(`setup.py:11`)에서 `.lib` 를 명시한 이유도
적혀 있다 — `lib/` 는 rclpy 없는 순수 파이썬 모듈이라 유닛테스트/rosbag 재생에 쓰인다.

### 6.2 data_files — config/launch 가 share 로 간다

`setup.py:12-21`:

| 원본 | 설치 위치 |
|---|---|
| `launch/*.py` | `share/track_drive/launch/` |
| `config/*.yaml` + `config/*.pt` | `share/track_drive/config/` |
| `package.xml` | `share/track_drive/` |

`drive.launch.py:20` 의 `get_package_share_directory("track_drive")` 가 가리키는 곳이
바로 이 `share/track_drive/` 다. YOLO 가중치(`*.pt`, 총 20MB)까지 같이 설치된다.

### 6.3 수정하면 재빌드해야 하나? — 이 워크스페이스 실측

일반적으로 `colcon build` 는 파일을 **복사**하므로 소스만 고치면 반영이 안 된다. 그런데 이
워크스페이스는 `--symlink-install` 로 빌드돼 있어서 실제로는 심링크 사슬이다.
**심링크(symlink, 심볼릭 링크)** 는 파일 자체가 아니라 "진짜는 저기 있다"를 적어 둔
바로가기다. 복사본이 아니므로 원본을 고치면 그쪽도 같이 바뀐 것으로 보인다 — 재빌드가
필요 없는 이유가 이것이다.

```
 install/track_drive/share/track_drive/config/camera.yaml
     └─→ build/track_drive/config/camera.yaml
             └─→ 본선/track_drive/config/camera.yaml   (소스 원본)
```

`launch/*.py` 도 같고, 파이썬 코드는 `.egg-link`(파이썬 패키지판 바로가기 — 설치 폴더에
코드를 복사하는 대신 원본 폴더 경로를 적어 두는 방식)로 `build/track_drive` 를 가리키며
`build/track_drive/track_drive` 가 소스 디렉터리를 심링크한다. 결론:

| 바꾼 것 | 재빌드 필요? | 해야 할 일 |
|---|---|---|
| `tuning.yaml` / `car.yaml` 값 | 불필요 | 노드 **재시작**만 (파라미터는 기동 시 1회 로드) |
| `camera.yaml` 값 | 불필요 | 노드 재시작 (`yolo_node.py:123` 이 기동 때 읽음) |
| `launch/*.py` 내용 | 불필요 | 다시 launch |
| `*.py` 노드 코드 | 불필요 | 노드 재시작 |
| **파일을 새로 추가** (새 yaml/새 노드) | **필요** | `setup.py` 의 `glob` 재평가 + `console_scripts` 등록 |
| `setup.py` 자체 수정 | **필요** | `colcon build --symlink-install` |

★ 단, 이건 이 워크스페이스가 심링크 설치라서 그렇다. **차 PC에서 일반 `colcon build`
(심링크 없이)로 빌드했다면 config 는 복사본이므로 반드시 재빌드해야 한다.** 어느 쪽인지는
`ls -la install/track_drive/share/track_drive/config/` 로 확인하면 즉시 알 수 있다 —
`->` 화살표가 보이면 심링크다.

### 6.4 package.xml

`build_type` 이 `ament_python`(`package.xml:16`)이라는 것과 테스트 의존성 4개만 들어 있다.
런타임 의존성(rclpy, ultralytics, opencv 등)이 선언돼 있지 않은데, 이건 `rosdep` 으로
의존성을 설치하지 않고 실차 환경에 이미 깔려 있는 것을 쓰는 방식이기 때문이다.
(**의존성 선언**은 "이 패키지를 돌리려면 저것들이 먼저 필요하다"는 목록이고, `rosdep` 은
그 목록을 읽어 자동으로 설치해 주는 도구다. 여기서는 실차에 이미 다 깔려 있어 안 쓴다.)
`description` / `maintainer` 는 아직 템플릿 기본값(`TODO`, `root`)이다.

## 7. 자주 하는 작업 체크리스트

**(1) 코스에서 차가 차선을 잘 못 따라간다**
1. 먼저 `yolo` 기동 로그의 `[camera]` 줄을 본다 — `h_calibrated=true`, `new_K 일치`,
   `size=1920x1080`, `car_mask_v=951` 이 다 나오는지.
2. 하나라도 어긋나면 `tuning.yaml` 은 건드리지 말고 캘리브부터 고친다.
3. 전부 정상이면 `motion_node` 의 [SIM] 게인부터 만진다.

**(2) 해상도를 바꿔야 한다**
1. `launch/sensors.launch.py:51-53` 수정
2. `tools/ground_fit.py` 로 **재캘리브** → `camera.yaml` 자동 갱신
3. `tools/bev_view.py` 로 `car_mask_v` 재설정
4. `tuning.yaml` 의 `*_v_threshold` 는 **손대지 않는다** (자동 환산됨)

**(3) 정지선에서 너무 일찍/늦게 선다**
`stop_v_threshold`(기본 312, 480p 기준)만 조정한다. 올리면 더 가까이 가서 반응한다.
`obj_v_ref_height` 는 절대 건드리지 않는다.

**(4) 직진이 한쪽으로 쏠린다**
`car.yaml` 의 `steer_trim`(-20.0). 단, 평평한 바닥에서 실제로 재고 바꿔야 한다.
캘리브의 `yaw_deg` 와 혼동하지 마라 — 전자는 바퀴, 후자는 카메라다.
